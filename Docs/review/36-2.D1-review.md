# R-2.D1: security review of the own-device link (ticket 2.D1)

Opus security review of commit 3b77107 on `p2/device-link`. It checks the code against
Docs/protocol/device.md (D13, OD-P2-8, OD-P2-9), approval.md, ticket 2.D1
(23-phase2-tickets.md), review 24 M8/M9 and review 26 N1–N5. Fixes were made in place,
with tests.

**Verdict: pass after fixes.** Critical 0, High 0, Medium 1 (fixed), Low 8 (3 fixed,
5 noted).

## Medium

### M1: a local agent could send the other device's half of a link through `mail_submit` (fixed)

- **Location:** `internal/daemon/outbox.go` (`mail_submit`); `deviceLinkKind` in
  `internal/daemon/device.go`.
- **Problem:** `device.link` has no signature of its own. The mail signature is the only
  proof that the sender's human confirmed. But `mail_submit` is an ordinary IPC method, not
  gated by debug, and it signs and sends **any** kind. Any local IPC client could use it,
  including a prompt-injected agent. Say the helper's human runs `device link @laptop --as
  helper` and confirms. An agent on the laptop can then send
  `{"role":"controller","controller":<laptop>,"helper":<desktop>,"nonce":<any>}` itself.
  The desktop activates, so the laptop becomes its controller without any confirmation by
  the laptop's human, and without the laptop's human checking the desktop's fingerprint.
  This breaks D13 ("confirmed on BOTH devices") and the threat-model control "links are
  created only by `device_link` on both devices with a local human approval each". It was
  reproduced: without the fix, the new test sees the helper go `active`.
- **Fix:** `mail_submit` refuses every `device.*` kind with `bad_request`. Only the
  `device_link`/`device_unlink` handlers send them, through `Outbox.SubmitTx`. The spec was
  updated: ipc.md `mail_submit` error codes, and device.md §Kinds. Tests:
  `TestDeviceLinkOfferCannotBeForgedThroughMailSubmit` (e2e: forged offer and unlink
  refused, nothing queued, helper stays `waiting`). `TestDeviceUnlinkFromThirdPeerChangesNothing`
  now sends C's real `device_unlink` and checks that `mail_submit device.link` is refused.
  The "third peer names the link id" case moved to
  `TestDeviceUnlinkNamingAnotherPeersLink`, which calls the Kind directly, because that
  mail can no longer be forged over IPC.

## Low

### L1: the approval's Precondition did not lapse stale intents (fixed)
- **Location:** `device_link` Precondition, `internal/daemon/device.go`.
- **Problem:** Intents lapse lazily (`ExpireTx`). `CreateIntent` and the receive path call
  `ExpireTx`, but the Precondition did not. So an intent with another peer that was valid
  at creation and lapsed before the code was typed still counted toward the hierarchy
  (a spurious `device_cycle` or limit error). Also, a row of its own that was past 10 min,
  but not yet swept, could still be approved (the two TTLs are equal, so the window is only
  milliseconds wide).
- **Fix:** The Precondition calls `ds.ExpireTx` first, in the same tx. There is no
  dedicated test, because the observable case needs 8 controller attempts that lapse in
  between. The existing e2e tests exercise the path.

### L2: the decoy-digit filter missed split and non-ASCII digits (fixed)
- **Location:** `stripLongDigits`, `internal/daemon/device.go`.
- **Problem:** Only runs of 6 or more ASCII digits were removed. A peer name such as
  `Code 482 913`, `48-29-13` or fullwidth `４８２９１３` still shows a code-like decoy in front
  of the real code (review 26 N4). The effect is wrong-code attempts, which can lead to
  `approval_locked`.
- **Fix:** A run now counts any Unicode digit and may be split by single spaces,
  punctuation or symbols. `TestStripLongDigits` was extended, and its old
  `"12 345 678"` expectation now becomes `…`.

### L3: `device unlink` left an unconfirmed link attempt's approval on screen (fixed)
- **Location:** `device_unlink`, `internal/daemon/device.go`.
- **Problem:** Unlink revoked the `pending_approval` row but did not reject its approval.
  The window kept asking for a code that its Precondition would refuse.
- **Fix:** After commit, the approvals of the revoked `pending_approval` rows are rejected
  (via `unlinked`). This is the local side only; for a remote unlink or `peers remove`,
  the Precondition still refuses. Test: `TestDeviceUnlinkRejectsPendingApproval`.

### L4: a late or delayed offer can activate one side only (noted, spec)
- **Location:** `TryActivateTx` (`internal/device/device.go`); device.md §Link flow step 3.
- **Problem:** The spec activates when the kept offer is younger than 10 min *by receipt*
  and `at ≥ intent.created − 10 min`. A relay that delays a `device.link` by up to ~10 min
  therefore stretches the window past the sender's own intent expiry. The result is one
  side `active` while the other side's intent has lapsed (the M9 asymmetry, made on
  purpose). If the relay also reorders a delayed offer after a later `device.unlink` from
  the same peer, the offer is kept after the unlink. It then activates only if this
  device's human starts a new link within 10 min. Both humans did confirm at some point,
  and unlink from either side still works, so this is Low.
- **Suggestion (owner/spec):** Also require `now < offer.at + 10 min`, so that the
  sender's intent is still alive by its own clock. Also ignore an offer whose `at` is older
  than the last `device.unlink` received from that peer.

### L5: no desktop notification on activation (noted, spec deviation)
- **Location:** `deviceLinkKind`, `device_link` Perform.
- **Problem:** device.md §Link flow step 3 says "audit `device.link_active`, notify". The
  code audits but does not notify, and the worker's design notes say this was on purpose.
  A notification is the only signal that tells the human the link went active on this
  device from the other side's confirmation.
- **Suggestion:** Either notify after commit (a Kind `After` hook that checks the audit or
  `activated_at`), or amend the spec. This is the owner's call.

### L6: the two sides can hold different link ids after an asymmetric retry (noted)
- **Problem:** Suppose A is active with `(nonce_c, nonce_h1)` and B's intent lapsed. B then
  links again: its new intent `nonce_h2` meets A's kept offer, so B is active with a
  different id, while A keeps the old one (A has no waiting intent, and B's new offer is
  only kept). This does not affect authority, because `device.unlink` ignores `link` and
  revokes by `msg.from` (review 24 M8). But `device list` shows different ids on the two
  devices, and 2.D2 must never key cross-device behaviour on the link id.

### L7: `mail_submit` still sends other daemon-owned kinds (noted, outside 2.D1)
- **Problem:** The same generic send also accepts `grant`, `grant.revoke`, `ws.*`,
  `request`, `team.*` and similar kinds. This review did not check whether each of those
  has its own proof (for example, grants carry a capability signature).
- **Suggestion:** In a follow-up, turn `mail_submit` into an allowlist of kinds that have
  no handler (debug/test kinds), and send every daemon-owned kind only from its own handler.

### L8: a rejected (not superseded) attempt blocks the hierarchy for up to 10 min (noted)
- **Problem:** `approval.Action` has no reject hook, so a `pending_approval` row whose code
  the human rejected stays until it lapses. It still counts: a rejected `--as helper`
  attempt with P1 makes `device link @P2 --as helper` fail with the limit error for up to
  10 min. A retry with the same peer replaces it at once. This is UX only.
- **Suggestion:** Add an `OnReject` hook to `approval.Action` (2.D2 needs the same thing
  for `device_scope`).

## Checked and found sound

- **Where device trust comes from.** Only `internal/device` writes `device_links`. The
  writers are `CreateIntent` (IPC, local), `ApproveTx` (inside the approval), and
  `TryActivateTx` (only with an existing `waiting` intent of the complementary role).
  Pairing, team/roster/`team.join` and `peers verify` never touch it
  (`TestDeviceTrustOnlyFromLinkFlow`). An offer alone is inert, at most one per peer.
  `SetTrustTx` only raises trust (the CASE keeps the higher rank).
- **Third-peer and forged offers.** `parseOffer` binds `controller`/`helper` to
  `msg.from`/self by role and rejects extra members, and `TryActivateTx` selects the intent
  by `peer = msg.from`. A replayed mail is caught by mail dedupe. An old offer delivered
  late fails `at ≥ created − 10 min`, because `created` is reset at confirm. A `relay`-trust
  peer (D5) gains nothing: the local intent needs an approval that first raises the trust
  to `fingerprint`, and D5 is re-checked in the Precondition.
- **Fingerprint.** Compared in constant time against the stored key's fingerprint before
  any row exists. The row, the approval and the offer are all keyed on the public key, not
  the name. Each side checks the other's fingerprint, and `link_id` hashes both keys and
  both nonces (the vector matches).
- **i- → l- key change.** The approval closure holds the `i-` id. After activation (or
  supersede, unlink or expiry) `GetTx` fails and the Precondition refuses, so there is no
  dangling approval. The partial unique index on `peer` allows one live row per peer. The
  daemon's single SQLite connection (`SetMaxOpenConns(1)`) serialises CreateIntent,
  approval, receive and unlink, so the 8-helper and one-controller limits cannot race.
- **Hierarchy.** It is checked at creation, in the Precondition and at activation. Intents
  count. Supersede revokes only the same peer's `pending_approval` row in the same tx, so
  it cannot open a reverse link or a chain.
- **Unlink.** It is applied to `msg.from` only (review 24 M8), and is sent even with no
  active link (M9). Scopes are deleted in the same tx. `peers remove` and team GC revoke
  through the chained `OnRemovedTx`, inside the removal tx
  (`TestDevicePeersRemoveRevokesLink`).
- **Audit.** The `device.*` rows hold only ids, enums and keys, with no nonces or scope
  content. The `peer.verify` rows reuse the existing detail of `peers verify`.
- **Migration 17.** It matches device.md §Tables, `main` has no 17, and both rewind tests
  drop the three tables.
