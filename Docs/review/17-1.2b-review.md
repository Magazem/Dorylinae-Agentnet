## Medium (fixed)

| # | Finding | Fix |
|---|---|---|
| M1 | **Online edge ignored the effective state.** `Store.Accept` set `edge` only when the stored `state` was not `online`. A peer that crashed or lost its link without a goodbye keeps `state = online` in its row. When it came back (new boot) there was no edge, so `Outbox.OnPeerOnline` (step 6) would never fire, and queued mail would wait for normal backoff. Spec step 6 says "not *effectively* online", which includes the `2.5 × interval` timeout | `Accept` reads the previous `interval` and `last_rx` and uses the new `EffectivelyOnline(state, lastRx, interval, now)` (the `daemon_online` formula, receiver clock). `TestReceiverOnlineEdgeAfterSilence` covers it: no edge at exactly 75 s, an edge after 151 s of silence and a restart |
| M2 | **Unbounded memory in the reject-log limiter.** `Receiver.drop` kept `lastDrop[env.From]` forever. Step 1 rejects any unpaired key, so rejected senders are chosen by the attacker. A Sybil flood (review 15 L2: many keys, 600/min each, forwarded by the relay) grew the map without limit | Capped at `maxDropPeers = 1024`. When the map is full, entries older than a minute are swept at most once a minute (O(1) per frame during a flood). While it is full of fresh entries, new peers are not logged. `TestReceiverDropLimiterBounded` runs 3072 Sybil keys and then checks that logging resumes after the entries age out |
| M3 | **Presence rows outlived their peer.** presence.md §Tables: "Rows of peers that are removed are deleted with the peer." Neither `peers.Store.Remove` nor `GCIntroduced` touched `presence_peers`. The `last_seen` and flags of a removed or GC'd introduced peer stayed on disk, and a re-introduced peer would be compared against a stale row | `peers.removeTx` (shared by `Remove` and `GCIntroduced`) also deletes the `presence_peers` row in the same transaction. `TestRemoveDeletesPresenceRow` covers both paths |

## Low (not fixed)

- **L1 Padding hides the flags, not every field.** Agent and human are single digits, so
  they never change the size (now tested on the real sealed output,
  `TestSealedPaddingAllCombinations`: 0–32 epochs, epoch values and `seq` of 1 to 16 digits,
  plaintext always a multiple of 256, same payload size across agent/human). But `offline`
  is one byte longer than `online`, and `seq`, epoch values and the number of epochs vary in
  length. So about 1 message in 256 crosses a 256-byte boundary, and a goodbye can then be
  told apart by size. The number of teams is visible as a size bucket (0–32 epochs span about
  256 to 2304 bytes). The spec only promises "multiple of 256". A fix would be a fixed width
  (for example padding to a constant 2560 bytes). That is a spec change, so it is left to the owner.
- **L2 No presence-specific size cap before crypto.** `OpenPresence` accepts payloads up to
  the mail `MaxPayload` (about 700 KiB). The relay drops presence over 8 KiB
  (`EphemeralMaxBytes`), but a hostile relay can deliver bigger ones. Such a payload still
  needs a paired `from` (step 1), and AEAD fails on it, so the cost is one ChaCha20-Poly1305
  pass. That is no worse than a bogus mail. A cap of about 4 KiB in `OpenPresence` after step 1 would be cheap.
- **L3 Step 1 is a SQLite query, not a map lookup.** The daemon's `peerDirectory.IsPaired`
  runs `SELECT 1 FROM peers` per frame. It still runs before any crypto (verified: step 1
  is first in `openCore`, and `TestPresenceUnpairedBeforeCrypto` passes). Review 15 L2
  expected "one map lookup", so 1.2c could cache paired keys if a flood shows up in profiles.
- **L4 No team scoping on receive.** Any paired peer can publish presence and gets a row,
  including a directly paired peer that shares no team. The spec does not require scoping,
  and `status --team` lists only members, so nothing leaks. An introduced member that was
  removed is GC'd from `peers` and dropped at step 1 (verified). Its row is now deleted too (M3).
- **L5 Same-second cross-boot replay.** The cross-boot rule accepts `created ≥ row.created`
  at 1 s granularity. If a daemon restarts within the same second, the relay can replay the
  old boot's last message (for example its goodbye) once. The row flips back to the old
  boot, and the next genuine heartbeat restores it (≤ 1 interval). This is self-healing and
  bounded by the 10 min window.
- **L6 The sender does not validate the body.** `presence.Seal`/`Build` do not run the
  `Parse` rules. A 1.2c bug (for example `agent = 1` with `offline`, or `interval = 0`)
  would seal bodies every receiver drops silently. Suggest `Seal` round-trip the body
  through `Parse`, or cover it in 1.2c tests.
- **L7 Read-then-write in a deferred transaction.** `Store.Accept` starts with `SELECT` and
  then writes. Two concurrent `Handle` calls could hit `SQLITE_BUSY`. Today there is one
  relay reader goroutine. Note for 1.2c if it parallelises.
- **L8 Test precision.** `TestPresenceUnpairedBeforeCrypto` asserts step 1 but not that
  `Keys` was never consulted. The ordering is clear in code, and a trap `Keys` would make it explicit.

## Verified, no finding

- **Domain separation.** Mail and presence share the signature tag, the HPKE `info` and
  `aad = id` by design (presence.md §Envelope). The `m-` and `p-` id formats are disjoint
  and covered by the signature and the aad. A presence relabelled `mail` fails mail step 9,
  and a mail relabelled `presence` fails `OpenPresence` step 9 (`TestPresenceRelabelling`).
  So even before the kind check, neither can be replayed as the other. `mail.Seal` cannot
  produce a `p-` id, and `SealPresence` cannot produce an `m-` id or another kind. A mail
  of kind `presence` sent over the mail path is ordinary unknown-kind mail from a paired
  peer: no escalation.
- **Refactor keeps mail byte-identical and in the same order.** `openCore` is the old steps
  1–10 verbatim, with only the step 9 predicate parameterised. Steps 11–12 run after it
  unchanged, so the reject step and reason are the same for every input. `mail.Seal` now
  checks the id before the key and kind. That only changes which error text a doubly invalid
  input gets, never the sealed bytes. The mail vectors reproduce, and all mail tests pass.
- **No audit, no oracle.** `OpenPresence` never calls `Audit` (`TestPresenceNeverAudits`).
  `Receiver.Handle` only logs at debug level, rate-limited and without a peer id. Nothing is
  sent back to the sender, and presence is never acked, so there is no decryption or
  verification oracle. `key_miss` starts no recovery.
- **Replay, reorder, clock.** Same boot needs a strictly higher `seq`. Another boot needs
  `created ≥` the stored one. The ±10 min window and `last_rx` use the receiver clock
  (`Now`). Acceptance tests cover: replay dropped, lower seq dropped, old boot with older
  created dropped, new boot accepted, 11 min old or 11 min ahead dropped, 10 min old accepted,
  `interval` 0/301 dropped and 1 accepted, bad kind or body dropped.
- **Strict body.** Exactly 8 members, `seq ≥ 1`, and team-id keys with at most 32 entries.
  Values beyond the canonical integer range fail at step 5/7.
- **Migration 10 is atomic.** `store.apply` runs the DDL and the `migrations` row in one
  transaction. The schema matches presence.md §Tables verbatim.
