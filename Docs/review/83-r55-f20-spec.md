# 83 — R55-F20 spec: request-id collisions

Ticket R55-F20 (review 55 [99-report.md](55-code-review/99-report.md) §4): R55-063, R55-128,
plus R55-163 (review 55 D14, an owner choice), which sits in the same code. Spec only. Base:
main `eb283bf`, after F12, F13 (migrations 24/25), F18 (migration 22) and F23.

## 1. Summary

A request id is chosen by its sender and is unique only per sender: the table key is
`(direction, peer, id)`. A paired peer can send us a request whose id it has seen, either one
of our own requests to it or one printed in a Decision file someone shared. Several paths then
resolve that id alone to the wrong row or to the first row found (R55-063):

- `request_show` returns our `out` row and ignores `from` (`internal/request/query.go:12-30`).
- `GetByRequestID` uses `LIMIT 1` with no role or peer (`internal/worksession/store.go:279-289`).
  It drives `session`/`wait`/every `ws_*` given an `r-` id, and the one-step consult answer
  (`internal/daemon/consult.go:61-66`).
- `debate <id> --cancel` on the **respondent** in `invited` calls `request_cancel`, which
  cancels the user's own unrelated outgoing request with that id (`cmd/agentnet/debate.go:582-584`).
- `log --session r-X` merges every session and request with that id (`internal/audit/query.go:230-262`).
- The debate notification title reads `out` first (`internal/daemon/notify.go:124-131`).

R55-128: `decision_show` with an unknown `s-` or an ambiguous `r-` id, and the request-layer
errors of `debate_submit`'s one-step accept, come out as `internal`
(`internal/daemon/decision.go:61-66`, `debate.go:227-249`).

The fix, in four rules:

1. **Refuse a colliding id (prevent).** A new incoming request whose id any other
   `requests` row already has (our `out` row to any peer, or an `in` row from another peer)
   is an [invalid body](../protocol/request.md#invalid-bodies). A resend of the sender's own
   id still dedupes as before. `Submit` draws a fresh id again if any row already has it.
2. **Detect old collisions (resolve).** Rows from before F20 can still collide. No
   migration renames them. Every reference by id alone looks at every row it could mean,
   and more than one match is `ambiguous_request`. `from` on `request_show` selects the `in`
   row only.
3. **Map the errors (R55-128).** `decision_show`: unknown `s-`/`r-` gives `unknown_decision`
   and ambiguous gives `ambiguous_request`. `debate_submit` maps request-layer errors as
   `request_accept` does.
4. **R55-163 (OD-F20-4).** A request that consumes an early-cancel tombstone is still stored
   `cancelled` (the sender has already received that `seq = 1`). If D5 or the team checks
   would have declined it, it keeps no content (`body = {}`).

**Wire change:** none. **Migration:** none (OD-F20-7). **New error codes:** none
(`ambiguous_request` and `unknown_decision` exist).

## 3. Design notes

- **Why every other row, not only "our `out` ids to that peer"** (the report's wording,
  OD-F20-1). Ids leak beyond the pair: a Decision file carries the request id and is meant
  to be shared, so any peer can learn our `out` ids to someone else. Another peer's `in` id
  produces the same ambiguity in `ws_*`, `log` and `debate_*`. Each sender draws ids from
  128 random bits, so the wider rule never refuses an honest request. A sender cannot use
  it against a third peer's request: that peer's row is already stored, and its own resend
  dedupes on `(from, id)` before the new check runs.
- **Order inside step 2.** The `(from, id)` lookup (duplicate/conflict) comes first, so
  existing rows and resends behave exactly as before, including old colliding rows. The
  collision bullet follows the 30-day and Decision bullets, which are also invalid-body
  outcomes, and comes before the daily caps. A refused mail therefore counts towards no
  cap and does not consume a tombstone. (The code currently runs the 30-day check after the
  tombstone, review 55 T6a-19. That is not changed here; see §7.)
- **Why `bad_body` (OD-F20-2).** The request cannot be stored under its id, and a row with
  an auto-decline would itself be the collision. The invalid-body path already gives the
  right outcome: `mail_seen` only, `mail.reject {bad_body}` (rate-limited), ack `rejected`,
  and the sender's row `failed`. An honest sender never sees it.
- **Tombstone with a colliding request.** It stays until the 31-day prune. Tombstones are
  never shown, and `request.cancel` itself is not checked for collisions (its effect is
  only that tombstone).
- **Legacy rows.** A database may already hold a collision. No migration is needed (OD-F20-5)
  because each reference detects it. `request_cancel` and `request_resend` look only at
  `out` rows, which never collide with each other (locally drawn ids, now re-drawn on any
  hit).
- **`request_show` without `from` on an old out/in collision (OD-F20-3).** Returns
  `ambiguous_request`, whose message says to pass `from` for the incoming request. The
  outgoing one stays in `request list`, and its session can be reached by its `s-` id. No
  `to` parameter is added for a case that only old rows can reach.
- **R55-163.** Running step 3 before the tombstone would store `declined` with a `seq = 1`
  `request.decline`. The tombstone has already sent `request.cancelled` with `seq = 1`, so
  the sender's mirror would receive two different `seq = 1` replies. Keeping the
  `cancelled` row and dropping its content gives the same safety (no peer text from a peer
  that D5 or team rules refuse) without a second reply. `inbox_full` is left out because it
  counts open rows, and a cancelled row is not open.

## 4. Plan (files and functions)

1. `internal/request/receive.go` `apply`: after the debate-Decision check (`:187-196`) and
   before `checkDailyCaps`, run `SELECT 1 FROM requests WHERE id = ? AND NOT (direction = 'in'
   AND peer = ?) LIMIT 1`. A hit gives `badBody("request id is already used here")`.
2. `internal/request/receive.go` `consumeTombstone`: before the insert, call
   `s.policyDeclineCode(ctx, tx, req)`. `policyDeclineCode` (`:346-377`) covers exactly
   `unverified_peer`, `unknown_team` and `not_team_member`, never `inbox_full`. If it returns
   a code, store `emptyBody` instead of `canon` (`body_hash` unchanged). Callers already
   handle `{}` (`view.go:148-155`).
3. `internal/request/submit.go` (`:95`): generate the id through a `Store` hook (`s.newID`,
   default `NewID`, overridable in tests). Inside the transaction, loop while `SELECT 1 FROM
   requests WHERE id = ?` hits, at most 8 tries, then return an error.
4. `internal/request/query.go` `Show`: with `from != ""`, return `findInRow(id, from)` only.
   Without it, collect the `out` row and the `in` rows with that id. Exactly one match
   returns it. More than one returns `ErrAmbiguousRequest`. None returns `ErrUnknownRequest`.
   `lifecycleError` already maps these. Update its message to "pass from, or use the s- id".
5. `internal/worksession/store.go` `GetByRequestID`: select every row with that
   `request_id` (no `LIMIT`). Two or more return a new `worksession.ErrAmbiguousRequest`
   (or `request.ErrAmbiguousRequest`, if the import direction allows it; it does not today,
   so add the sentinel). Map it in `internal/daemon/session.go` `sessionError` to
   `CodeAmbiguousRequest`, with the message "use the s- id". Fix the doc comment ("only ever
   holds one role" is wrong).
6. `internal/daemon/consult.go` `findAnswerable`, `r-` path: resolve the `in` row through
   `rs.Show(ctx, id, "")` restricted to `in`. Add `request.Store.FindIn(ctx, id, from)` that
   exposes `findInRow`. Two or more `in` rows give `ErrAmbiguousRequest`, which `answerError`
   already maps. Then check for a session with the exact key, using `ws.Get(ctx,
   worksession.DeriveID(row.peer, self, id))`, instead of `GetByRequestID`.
7. `internal/audit/query.go` `sessionClause`, `r-` path: collect the distinct `(role, peer)`
   of the matching sessions. More than one returns a new `audit.ErrAmbiguous`. With no
   session, read `SELECT direction, peer FROM requests WHERE id = ?`:
   - one row: `reqPeer{id, peer}`;
   - more than one: `ErrAmbiguous`;
   - none (pruned): `reqPeer{id, ""}`, as today.
   Map `ErrAmbiguous` to `ambiguous_request` in the daemon's `audit_list` handler. The CLI
   `log` then exits 1 with the message.
8. `cmd/agentnet/debate.go` `runDebateCancel`: in `invited`, if `shown.Debate.Role` is not
   the initiator, print `bad_state`: "you were invited to <s-id>: decline it with agentnet
   decline <r-id>" and exit 1, without calling `request_cancel`.
9. `internal/daemon/notify.go` `debateNotifyAdapter`: choose the direction from the
   debate's role. Either extend `debate.Store.OnEvent` with `role` (every caller has its
   `row`), or look the row up by `sid`. Read only that one `ShowKey`.
10. `internal/daemon/decision.go` `decisionError`: map `debate.ErrUnknownDebate` to
    `unknown_decision` and `request.ErrAmbiguousRequest` to `ambiguous_request`.
11. `internal/daemon/debate.go` `debateError`: before `default`, return `lifecycleError(err)`
    for `request.BadStateError`, `ErrUnknownRequest` and `ErrAmbiguousRequest`. Map
    `mail.ErrUnpaired` to `bad_request` "peer is no longer paired", as
    `internal/daemon/request.go:359` does. Keep the existing `debate.BadStateError` case
    first.

## 5. Acceptance tests

1. **Out collision, same peer.** A sent `r-X` to B. B's new request `r-X` produces no row,
   a `mail_seen` row, `mail.reject {bad_body}` and an ack of `rejected`. A's `out` row is
   unchanged.
2. **Out collision, other peer.** A sent `r-X` to C. B's request `r-X` is refused as in 1.
3. **In collision.** C's `in` row `r-X` exists. B's `r-X` is refused. C's resend of `r-X`
   (same hash) is still a `duplicate` and its echo still runs.
4. **No cap, tombstone kept.** B sends `request.cancel` for `r-X` (A's `out` id), then the
   request `r-X`. The request is refused, the tombstone row is still present, and B's daily
   count is unchanged.
5. **Submit re-draws.** With the id hook returning an id that an `in` row already holds,
   and then a fresh id, the stored `out` row has the fresh id.
6. **`request_show`, old rows** (inserted directly): with `out r-X` and `in (B, r-X)`, no
   `from` gives `ambiguous_request`, and `from: B` gives the `in` row. With only `out`, the
   call returns `out`. With only `in`, it returns `in`.
7. **`ws_show r-X`** with a requester and a worker session for `r-X` gives
   `ambiguous_request`, and the `s-` ids work. `wait r-X` gives the same error. With one
   session, behaviour is unchanged.
8. **One-step answer.** With `in (B, r-X)` a pending question and an `out` row `r-X`,
   `ws_result r-X` answers B's question (not `not_worker`). With two `in` question rows
   `r-X` from B and C, it gives `ambiguous_request`.
9. **`audit_list {session: r-X}`.** Two sessions with different peers give
   `ambiguous_request`. With no session and `in` rows from B and C, it gives
   `ambiguous_request`. With one request row from B, C's audit rows naming `r-X` are not
   shown. With no row at all, rows with `detail.request = r-X` are shown.
10. **`decision_show`.** An unknown `s-` gives `unknown_decision`, and an ambiguous `r-`
    gives `ambiguous_request`. `debate_submit` one-step accept on a request that is no longer
    pending gives `bad_state`, not `internal`.
11. **`debate --cancel`, respondent, `invited`:** exits 1 with `bad_state`, and the user's
    own `out r-X` is still `pending` with no `cancel`. On the initiator, behaviour is
    unchanged.
12. **Debate title.** On the respondent, with an `out r-X` titled "mine" and the debate's
    `in r-X` titled "theirs", the `debate.agreed` webhook title is "theirs".
13. **R55-163.** A `trust = relay` peer on a non-loopback relay sends a cancel, then the
    request. The row is `cancelled` with `body = {}`, no title in `inbox --all`, `state_seq =
    1`, and `last_reply` is the tombstone's `seq = 1`. The same sequence from a verified team
    member keeps the body. A non-member of the named team gets `{}`.
14. Existing tests stay green, mainly the receive, cancel and consult suites and
    `internal/debate` resolve.

## 6. Owner decisions

| OD | Question | Options | Recommended |
|---|---|---|---|
| OD-F20-1 | Which existing ids an incoming request may not reuse | (a) Any other `requests` row: an `out` row to any peer, or an `in` row from another peer. (b) The report's wording: our `out` ids to that same peer only. Ids learned from a shared Decision file and `in`/`in` collisions stay, and only rule 2 handles them. (c) Our `out` ids to any peer | **(a)** |
| OD-F20-2 | How a colliding request is refused | (a) The invalid-body path: `mail.reject {bad_body}`, ack `rejected`. (b) A new reason `id_collision` (a new `mail` sentinel and audit reason; clearer diagnosis, more plumbing). (c) Auto-decline: impossible, since the row itself would collide | **(a)** |
| OD-F20-3 | `request_show <id>` without `from` when an old `out` and `in` row share the id | (a) `ambiguous_request`; `from` gives the `in` row, and the `out` row stays in `request list` and under its `s-` id. (b) Keep "`out` first" and let only `from` reach the `in` row. The R55-063 confusion stays for old rows. (c) (a) plus a new `to` parameter | **(a)** |
| OD-F20-4 | R55-163: tombstone path before D5 and the team checks | (a) Leave as designed and document it; a refused peer's title can appear as a cancelled row, bounded by the daily cap. (b) Keep `cancelled` and the `seq = 1` reply, but store `body = {}` when `unverified_peer`, `unknown_team` or `not_team_member` applies. (c) Run step 3 first and store `declined`: the sender gets a second, contradictory `seq = 1` reply | **(b)** |
| OD-F20-5 | Collisions already stored | (a) No migration; references detect them (rule 2). (b) A migration that finds and reports them, or renames them: ids are signed wire data, so they cannot be renamed | **(a)** |
| OD-F20-6 | `debate --cancel` on the respondent in `invited` | (a) `bad_state` with a pointer to `agentnet decline`. (b) The CLI declines for the user, which needs a reason and is surprising | **(a)** |
| OD-F20-7 | Index for `WHERE id = ?` with no direction or peer | (a) None. The check runs only for a new id, after the `(from, id)` primary-key miss, at most 200 per peer a day. `findInRow` already scans this way. (b) Migration 26: `CREATE INDEX requests_id ON requests (id)` | **(a)**; take (b) if a benchmark at 100k rows shows > 10 ms |
