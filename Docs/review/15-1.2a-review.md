# Review 15: 1.2a relay ephemeral envelopes

Reviewer: R-1.2a (Opus). Worktree `AgentNet-wt/t1-2a`, branch `p1/t1-2a` at `0984bca`.
Scope: `internal/envelope/frames.go`, `internal/relay/{relay,conn,ephemeral}.go`,
`internal/relayclient/relayclient.go`, and their tests. Checked against ticket 1.2a
(`Docs/review/11-phase1-tickets.md`), `Docs/protocol/presence.md` §Relay,
`envelope.md` §ready and review 12 (M6, M8, L15). The implementer read "at most half full"
as occupancy before the send ≤ half, so the buffer can reach half + 1. That reading is
accepted.

**Verdict: ready to merge after the fixes below** (applied in the worktree, uncommitted).
Critical 0, High 0, Medium 2 (both fixed), Low 7.

## Medium (fixed)

### M1: Concurrent senders could fill the buffer past half, so mail went to the queue

`conn.directEphemeral` read `len(c.out)` and then sent, with no lock between the two steps.
Each sender connection routes on its own goroutine, so many senders could all pass the
check at once. A probe with 64 goroutines against a 64-frame buffer reached **40** frames
(the limit is 33). Given enough concurrent senders the buffer fills, `direct` returns
`directBusy`, and the recipient's mail goes into the queue path. Review 12 M6 exists to
prevent exactly this.

Fix: added `conn.ephMu`, which makes the check and the send one step (`internal/relay/conn.go`).
It serialises only ephemeral sends, so mail, control and drain sends never wait on it.
Invariant: ephemeral frames in the buffer ≤ half + 1, so mail always has at least
`cap − half − 1` slots.

Tests: `TestDirectEphemeralConcurrentStaysAtHalf` (fails at 34 without the fix) and
`TestPresenceFloodDoesNotPushMailToQueue`. The second test runs 32 Sybil keys × 200
presence frames through the real `Server.route` while a peer sends 30 mail frames
concurrently. The recipient's writer is stalled, so the buffer only fills. It asserts
that all 30 mails are forwarded directly, nothing is queued, no sender gets any frame, and
at most 33 presence frames are in the buffer.

### M2: Limiter state grew without bound, pruning was O(n) per new key, and drops were lost

`ephemeralLimiter.allow` pruned only when a **new** key arrived while the map held more than
1024 entries, and it never pruned entries that had drops. So:

- a Sybil key that sent 601 frames and then disconnected stayed in the map forever;
- above 1024 live keys, every new key scanned the whole map under the lock;
- the `ephemeral_limited` count of a key that never sent again was never logged, contrary
  to presence.md ("counted in the log, once a minute").

Fix (`internal/relay/ephemeral.go`): at most once per window, `allow` deletes every ended
window and returns a `limitReport` for each one that dropped envelopes. `routeEphemeral`
logs one line per reported key. The map now holds only keys that sent in about the last
two minutes, and the scan cost is amortised to one per minute.

Tests: `TestEphemeralLimiterEvictsIdleKeys` (5000 keys → 1 after a window; a limited key that
leaves is still reported) and the updated `TestEphemeralLimiterWindow`.

## Low (not fixed)

- **L1 Boundary burst.** With a fixed window, one key can send 600 at 0:59 and 600 at
  1:00. The spec says "per minute", and the half-buffer rule bounds what the recipient
  receives, so this is acceptable. A sliding window would be the stricter choice.
- **L2 No relay-side pairing bound (Sybil).** Any keypair that passes auth can send presence
  to any online key. The per-key limit does not bound many keys. The relay bounds each
  recipient only by the half buffer, meaning at most its write throughput. This is no worse
  than today: any key can already send, or even queue, mail to any key. **1.2b must reject
  an unknown or unpaired `from` before HPKE open and signature verification**, so a flood
  costs the receiver one map lookup per frame (compare review 12 L15).
- **L3 Size check after decode.** The `EphemeralMaxBytes` check runs after the frame has been
  read (≤ 1 MiB `MaxFrameBytes`) and JSON-decoded twice (`Classify`, `ParseHeader`). This is
  the same cost as any envelope, and the type is unknown until then. Oversize frames count
  against the sender's rate limit, which is fine.
- **L4 Old recipient daemons.** A pre-1.2a daemon puts presence in its seen-set and acks it,
  so the relay does a no-op `DELETE` for each one (`queue.ack`). This is harmless and bounded
  by the rate limit. The ack goes to the relay, not to the sender, so it creates no oracle.
  Senders cannot see the recipient's version. Old daemon handlers ignore the type
  (`peers.Manager.HandleEnvelope`, `session.Manager.HandleEnvelope`), and the daemon routes
  only `type == "mail"` to the mail layer (`internal/daemon/daemon.go`), so presence is never
  treated as mail.
- **L5 Lazy drop report.** Limit reports are logged on the next ephemeral frame from any key.
  If ephemeral traffic stops entirely, the last window's drops are logged only when it
  resumes. Hooking the existing `sweepLoop` would fix this if needed.
- **L6 Presence to self** is forwarded back to the sender. This is harmless, and 1.2b drops it
  as a non-peer.
- **L7 No race detector.** `go test -race` needs cgo, which this toolchain does not have. The
  concurrency was checked with the deterministic stress tests above.

## Verified, no finding

- **No online oracle.** Forwarded, offline, over-limit, oversize and busy-buffer presence all
  produce nothing for the sender: no `queued`, no `error`, no queue row, no queue accounting
  (`routeEphemeral`). Errors happen only for `bad_envelope` and `bad_sender`, before the
  recipient lookup, so they do not depend on the recipient.
- **Backlog bypass.** `directEphemeral` ignores `draining`, and presence never enters the
  queue. `TestEphemeralForwardedToConnectedPeerWithBacklog` covers this.
- **No payload in logs.** Per-frame ephemeral lines are at debug level and log only header
  fields (`TestEphemeralLogsNoPayload`).
- **relayclient.** Presence is parsed and validated (`envelope.Parse`) like every envelope,
  handed up without the seen-set, and never acked (`TestPresenceBypassesSeenSetAndIsNotAcked`:
  10 000 presence frames, `session.*` duplicate still suppressed, no presence ack). Signature
  and seal checks belong to 1.2b's opener, which is out of scope here. `features` is set before
  `OnReady` and cleared on disconnect.
- **Features in both directions.** `TestReadyFeaturesCompat` (new): a relay without `features`
  gives `Features() == nil` and `HasFeature(ephemeral) == false`, and a ready frame with
  unknown features and an unknown member still connects. An old client decodes `ready` with
  `encoding/json`, which ignores unknown members.
- **Malformed frames.** They go through the existing `Classify`/`ParseHeader` error paths
  (`bad_envelope`) before any ephemeral code runs. Nothing on the ephemeral path indexes or
  asserts, so there is no panic path.
