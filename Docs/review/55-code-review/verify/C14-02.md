# Verify C14-02
Verifier: V-C14-02 · model claude-opus-5-5 · elapsed 2 min · commit 6cc26a7
**Outcome:** confirmed (High)

**Claim restated:** `device_scope_set` accepts a scope whose summary is up to 16384 bytes, but every approval window cuts the summary to 4096 code points. So a scope can be approved even though the human never saw its last commands. Precondition: the helper has an active device link with the controller, and a local agent, possibly prompt-injected, can call IPC `device_scope_set` (or `agentnet device scope`).

**Path traced (from the entry point):**
1. The IPC `device_scope_set` handler, `internal/daemon/device_scope.go:191`, decodes the scope strictly (`:105-116`) and resolves the helper link (`:200`, `:167-186`).
2. `device.ValidateScope` (`:204`) enforces per-field limits only (`internal/device/scope.go:21-31`): up to 32 commands, 64 argv strings each, and 4096 bytes per argv string. A single 4000-byte argument is allowed.
3. `scopeSummary` (`device_scope.go:149-162`) lists every command in order and ends with "Confirm only if you set this scope yourself."
4. The only length gate is `len(summary) > maxScopeSummary` (16384 **bytes**) at `device_scope.go:210`. Nothing checks the summary against `notify.MaxWindowSummary`.
5. `apprStore.Create` (`internal/approval/store.go:50`) passes the summary unchanged to `window.Start` (`:107`).
6. `ApprovalWindow.Start` (`internal/notify/window.go:18-19`) calls `windowText` → `Clean(summary, 4096)` (`window.go:39`). `truncate` (`internal/notify/notify.go:47-65`) keeps 4095 runes and adds "…". The cut happens before any OS-specific `startDialog` (darwin, linux and windows), so every platform is affected.
7. `approve --open` goes through the same `window.Start` (`store.go:781-785`).

**Checks that could block it:**
- **ValidateScope limits:** they do not block it. They are per field, and a single 4 KiB argv string already pushes later commands past the cut. A scope of 32 commands × 64 args can hide far more than that.
- **Spec:** it supports the finding. `Docs/protocol/device.md:95-97` says the 16384-byte limit exists "because the approval window must show all of it". The code breaks that promise.
- **Owner decision or open finding:** O-167 ("Needs its own ticket") records only the size mismatch. No D-decision accepts truncation. The finding adds the local-agent exploit and a test, so "escalates O-167" is justified rather than being a duplicate.
- **Other places the human could see the full scope:**
  - The CLI prints the whole scope (`cmd/agentnet/device_scope.go:181-191,288`), but to the caller's stdout. That is the agent's shell in this scenario, not something the human must read.
  - The code notification body carries the summary (`store.go:201-205`), but OS toasts cut much earlier.
  - The approval window is the surface the spec relies on, and it is cut.
- **The precedent was fixed only for debates:** `debate_constrain.go:91-97` refuses a summary longer than `MaxWindowSummary` runes (R46 H2). Device scope has no equivalent check.
- **Visual cue:** the window ends in "aaa…" with no closing sentence. That is a hint at best, not a control. The hidden command is still approved.

**Severity reasoning:** the rubric (§1) says a local agent must never "widen a scope … without the human" or "make the daemon exec anything other than the configured argv". Under §2, High covers "A core security property breaks, but the attacker needs a narrower position (a local agent via IPC …)", and the listed example is "A local agent completes a device scope change without the window". The same class was rated High in R46 H2 (debate constraints). This is not Critical, because it needs a local agent plus a human who types the code. Terminal approval mode is off by default and I did not check it. **High confirmed.**
