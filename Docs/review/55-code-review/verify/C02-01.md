# Verify C02-01
Verifier: CR-V1 · model claude-opus-5-5 · elapsed 10 min · commit 6cc26a7
**Outcome:** confirmed

**Claim restated:** `relay restore --replay-journal` takes the backup time from the `--from` file's mtime. A restore from a backup that was downloaded and decrypted (so the file is new) therefore replays no journal entry, and says nothing about it. Unbind, account_delete and suspend changes made after the backup are silently rolled back. Precondition: accounts are on (`--accounts`, off by default); a backup taken at T0; security changes journaled at T1 > T0; the restore input written at T2 > T1. Under the spec's own flow (encrypt → upload off-host → download → `age -d`), T2 > T1 always holds.

**Path traced:**
- `cmd/relay/main.go` `runRestore`: `relay.Restore(*from, *dbPath, *force)` (`internal/relay/backup.go:52-88`) copies the bytes (`copyFile`, `backup.go:90-105`). Nothing in it reads a backup timestamp.
- `cmd/relay/main.go` (`--replay-journal` branch): `os.Stat(*from)` → `info.ModTime()` → `relay.ReplayJournal(dbPath, journal, info.ModTime())`.
- `internal/relay/journal.go:111-114`: `if e.Time.Before(since) { continue }`. Entries dropped here are not counted anywhere. `skipped` only counts entries that have no handler (`journal.go:115-118`).
- Handlers exist and work. `internal/relay/accounts_store.go:565-586` registers `unbind`, `account_delete`, `suspend`/`unsuspend` in `init()`. The unbind entry carries `short(key)` (8 chars, `accounts_store.go:419`, `relay.go:972`), and the handler matches it by prefix. So the entries are lost only because of the mtime cutoff.
- Minor citation fix: the finding cites `journal.go:216-219`. The file has 126 lines; the real lines are 111-114.

**Checks that could block it:**
- *The spec defines the backup time as the file's mtime*: no. relay-hosted.md §3 Restore says "re-applies every journal entry newer than the backup". It does not say how the backup time is found. §3 Backup requires encrypt + upload off-host, so the restore input is always a new file. The code comment on the flag ("after --from's backup time") is not an owner decision.
- *HANDOFF §3 decisions (D1–D42)*: nothing there chooses mtime or accepts the risk. D40 (early relay: no accounts, no backups yet) and the 4.1b deferral only mean the backup job is not deployed yet. They do not change what the code does once it is.
- *Download tools that keep mtime (rclone, `cp -p`)*: `age -d` always writes a new file, and the spec requires encryption. So this does not help.
- *Handler idempotence / DB content*: `Restore` stores no backup time in the DB (no `relay_meta` row). Nothing else could be used for the cutoff.
- *Operator sees the loss*: no. The output reads `replayed 0 journal entries (0 skipped, no handler yet)`, which looks normal. The "no handler yet" wording is also out of date now that 4.2a registers handlers.
- *Separate small issue, same root cause*: even the original file's mtime marks the end of `VACUUM INTO`, not its snapshot start. An entry journaled while the VACUUM runs is skipped even without a download.

**Severity reasoning:** High. Rubric §2 High: "a core security property breaks, but the attacker needs a narrower position … or the impact is bounded", and "silent loss/corruption of durable state". The mechanism that is supposed to prevent review 50 M6 (restored security state going back in time) fails silently on the documented path. Consequences: a stolen device's key is bound again, an erasure is undone, a suspended abuser is reinstated. The actor is a holder of a key revoked after the backup (thief or abuser). They need no special action, only an operator restore, which is rare (DB loss). That rarity is what keeps it below Critical. Accounts are off by default (`--accounts`), and the 4.1b backup job is not deployed yet, so per rubric §2 the consolidator may lower it by one level.
