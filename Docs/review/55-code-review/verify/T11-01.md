**Outcome:** confirmed (Medium)

**Claim restated:** on Linux with zenity, the daemon puts the approval summary into
`zenity --entry --text=…` after escaping only `& < >`. zenity runs that value through GLib's
`g_strcompress`, so a backslash escape in peer-chosen text (a paired peer's card name) becomes
a NUL that cuts the window text, or becomes newlines, bidi or invalid-UTF-8 bytes, all after `notify.Clean`.
Precondition: a Linux desktop where zenity is found at a root-owned path (the spec's first choice), a
paired peer with a card name that contains `\`, and an approval whose summary includes that name.

**Path traced (from the entry point):**
1. Peer card name: `agentcard.checkText` (`internal/agentcard/agentcard.go:109-122`) refuses only
   `unicode.IsControl` and `RuneError`. `\` and digits pass, so `Bob\0` (5 runes) is valid. It is
   stored as the peer name at `internal/peers/pairing.go:713` (`Name: sc.Card.Name`).
2. Summary: `peerDisplayName` → `stripLongDigits(notify.Clean(p.Name, 40))`
   (`internal/daemon/debate_constrain.go:70`). `Clean` (`internal/notify/notify.go:25-40`)
   replaces only C0/C1/DEL/bidi/U+2028-9, so `\` survives. `stripLongDigits`
   (`internal/daemon/device.go:103`) removes only runs of 6 or more digits. `constraintSummary`
   (`debate_constrain.go:58-60`) inserts the name raw, before the `DisplayQuote`d text.
3. Window: `ApprovalWindow.Start` → `windowText` (`internal/notify/window.go:36-43`, `Clean`
   again, `\` kept, then the fixed "The code is in…" sentence is appended) → `startDialog`
   (`internal/notify/window_linux.go:180,188`) → `escapeArg` (`:128-130`) = `escapeMarkup` only
   (`desktop_linux.go:68-73`, `& < >`). There is no backslash doubling, unlike `notifySendBody` (`desktop_linux.go:39-41`).
4. zenity: upstream `src/entry.c` in **zenity 3.42.1** (Ubuntu 22.04), lines 113-115, and in
   **4.0.1** (Ubuntu 24.04), lines 94-96, both do
   `gtk_label_set_text_with_mnemonic(GTK_LABEL(text), g_strcompress(entry_data->dialog_text))`
   (fetched read-only from gitlab.gnome.org). GLib `g_strcompress` (`glib/gstrfuncs.c`, 2.80.0)
   decodes `\0`–`\377` octal, `\b \f \n \r \t \v`, and drops the backslash of any other escape.
   Its C-string result ends at the first NUL.
   Result: the window reads `debate_constraint: add a human constraint to the debate s-… with Bob`.
   The constraint text, the "signed into the Decision as a human decision" warning and the
   "code is in the notification" sentence all disappear.

**Checks that could block it:**
- `checkText` / `Clean` / `stripLongDigits`: none of them touches `\` (see above). They do not block it.
- `escapeMarkup`: handles `& < >` only. It does not block it.
- The spec (`Docs/protocol/approval.md:177`, Linux row) requires only markup escaping. It does not
  mention `g_strcompress`, so no decision makes this intended. Review 21 M1 fixed the same GLib
  behaviour for notify-send only.
- Toast: `deliveryText` (`internal/approval/store.go:201-206`) puts the full summary in the code
  notification's body over in-process D-Bus (`internal/notify/approval_linux.go:101`, no
  `g_strcompress`), so the full constraint is visible there. This is only a partial mitigation:
  review 46 H2's rule is that the window must show the full text, and desktop shells collapse long toast bodies.
- kdialog (Qt `--inputbox`): not checked. It probably does not unescape. The finding holds for zenity only.
- `DisplayQuote`d constraint text is safe from the NUL cut: JSON escaping turns `\` into `\\`,
  which compresses back to `\`.

**Severity reasoning:** the actor is a paired peer (semi-trusted) plus a prompt-injected local
agent. The human still has to type the code, so the approval gate is not bypassed. The defect
hides what the human approves, or adds fake lines to it (a grant window with
`Mallory\n\nApproved by IT`, a device-scope summary cut after the controller's name). That breaks
the spec's rule that the window shows the full text (review 46 H2) and approval.md's
local-agent boundary through deception, not directly. It is Linux/zenity only, but zenity is the default helper there.
Rubric Medium: "a spec deviation with security or data impact but no direct exploit". It is not
High because the human still sees an approval of a kind they did not request, and the toast body shows the full text.

**Side observation (not part of this finding):** zenity `--entry` sets the label with
`gtk_label_set_text_with_mnemonic`, **not markup**. So `escapeMarkup` shows `&amp;`/`&lt;`
literally, and `_` is consumed as a mnemonic. approval.md:177's premise ("markup-escaped for both
tools") is wrong for zenity `--entry`. This is display fidelity only, likely Low. It is a lead for T11.
