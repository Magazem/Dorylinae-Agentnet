**Outcome:** confirmed (High)

**Claim restated:** On Windows, `validateResource` compares spellings, not files. A resource written as `\\?\<dir>`, `\\?\UNC\…` or `\\host\C$\…` gets past the grant.md §Issuance step 3 refusal of the config dir (and of the home dir). The stored path is then served. Precondition: a local agent (possibly prompt-injected) with IPC access, an open work session where it is the requester with a paired peer, and a human who approves the grant window.

**Checks that could block it:**
- The human approval does not block it. The spec refusal exists on top of the approval. The window shows only the label, so the human cannot spot the prefix.
- `recheckResource` does not block it: it is the same function, with the same flaw.
- `capability` serving does not block it: `openRoot` and `walk` only confine access to within the stored root. They have no config-dir denylist.
- `ValidScopePath` does not block it. It applies to `scope` only, not to the resource.
- `paths.Default` (`internal/paths/paths.go:28-38`) confirms the default config dir is `%AppData%\dorylinae`, which is the one the test targets.

The test is sound: it calls the real `validateResource` and the real `FSBackend.Read`. The only thing not covered end to end is a live daemon that holds `dorylinae.db` open. SQLite on Windows opens with read and write sharing, and Go's `os.Open` asks for read sharing, so a concurrent read should succeed. I reasoned this and did not run it.

**Severity reasoning:** The rubric's High criterion fits: "A core security property breaks, but the attacker needs a narrower position (a local agent via IPC …)". The spec-required refusal (grant.md §Issuance step 3, "Refused: the config dir … or any path inside it") can be bypassed. The result is that a peer gets the DB, which holds all mail, requests, approvals and audit, plus key files if the file keystore is in use. It is not Critical because it needs a local agent, a paired peer on an open requester session, and a human approval. The window shows only a label that looks harmless, and that keeps it above Medium.

On home: the home half adds little. The spec only refuses the home dir itself, so subdirectories such as `.ssh` can already be granted with approval. The config-dir half carries the severity.

`\\localhost\C$` forms need the admin shares, but `\\?\` works for any user.

**Leads (not investigated further):**
- `internal/daemon/device_scope.go:136`: `scopeResolver` uses the same `validateResource`, so the device scope `repo` paths have the same bypass. Device scopes are approval-gated.
- `grant.go:420` / `:885`: `EvalSymlinks` on `\\attacker-host\share\x` runs before any approval. A local agent could make the daemon open an outbound SMB connection, which may leak an NTLM hash, with no human involved. This is the same class as O-151, but it is reached through `grant_create`/`grant_policy_add`, and I did not check it further.
