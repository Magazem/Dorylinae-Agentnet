# Verify C01-01
Verifier: CR-V2 · model claude-opus-5-5 · elapsed ~15 min · commit 6cc26a7
**Outcome:** confirmed

**Claim restated:** Presence (ephemeral) frames are charged to the relay-wide outbound budget (`--max-inflight`) with `add`, which never refuses. So a stranger's own non-reading recipient keys can fill the budget with presence alone. After that, every direct mail send on the relay fails `tryAdd` and takes the queue path, and every queue drain waits in `reserve`. Mail between honest online peers stops for as long as the attacker keeps the budget full.
Precondition: the attacker can hold roughly `max-inflight / (33 × 8 KiB)` recipient connections, each with a full half-buffer, and keep every one alive (each 10 s write has to complete).

**Path traced:**
1. `serve` → `readFrame` → `route` (`internal/relay/relay.go:624,734`).
2. `from` is checked (`relay.go:760`). Then `envelope.IsEphemeral` sends the frame to `routeEphemeral` (`relay.go:764`) **before** `sendAllowed`, so the per-key 120/min, per-key 32 MiB/min, per-prefix 600/min and per-prefix 64 MiB/min limits never apply to it.
3. `routeEphemeral` (`internal/relay/ephemeral.go:81-98`) checks only the per-sender-key 600/min window and the 8 KiB size, then calls `directEphemeral`.
4. `directEphemeral` (`internal/relay/conn.go:97`) checks only `len(out) <= cap/2`, so a recipient takes up to 33 frames. It then calls `send` → `charge` → `inflight.add` (`conn.go:109-138`). There is no `maxBytes` check and no `tryAdd`.
5. Effect on mail: `route` → `dst.direct` → `sendCappedLocked` → `inflight.tryAdd` fails (`conn.go:211`) → `directBusy` → `enqueue` (`relay.go:786-796`). Draining that mail needs `drainStep` → `reserve` → `tryAdd`, which waits in a loop while the budget is spent (`conn.go:148-170`, `relay.go:885`).
6. The bytes are released only in `written` (`conn.go:220`) or `release` (`relay.go:510`). While the recipient keeps each write under the 10 s `writeTimeout`, they stay charged.

**Checks that could block it:**
- **Per-key ephemeral 600/min** (`ephemeral.go:50`): does not block it. At 600/min × 8 KiB, one sender key moves 4.8 MiB/min. Filling 48 MiB takes about 10 key-minutes, so a handful of sender keys is enough. My test with the default limit still spends the budget.
- **Per-prefix limits for ephemeral:** there are none. relay-hosted.md §2 lines 155/162/163 apply the prefix/key envelope and byte limits to *non-ephemeral* frames only, and the code matches (`relay.go:764` returns before `sendAllowed`). O-072 (no per-pair ephemeral limit) is related but would not block this either: it uses many recipients.
- **4 MiB per-connection cap (`maxBytes`):** does not apply. It is checked only in `sendCappedLocked` and `reserve`, not in `send`. It would not matter anyway, because 33 × 8 KiB = 264 KiB is far below 4 MiB.
- **Half-buffer rule:** limits each connection to about 264 KiB, but not the relay-wide total. presence.md §Relay promises "a presence flood from many senders cannot push a recipient's mail into the queue path". That holds per connection (frame slots) but is broken relay-wide through the shared byte budget.
- **MaxKeysPerPrefix / MaxConnsPerPrefix 64** (`limits.go:21,26`): these only force more prefixes. 48 MiB / 264 KiB ≈ 186 recipient connections plus about 5–10 senders ≈ 200 connections, which needs **4 prefixes** (IPv4 /24 or IPv6 /48; `clientPrefix` at `relay.go:562`). At the 256 MiB default it needs about 1000 connections, or 16 prefixes.
- **--max-conns 2000:** not reached (about 200 connections are needed).
- **Reconnect 20/min, control 60/min:** not involved.
- **writeTimeout 10 s** (`relay.go:34`, `conn.go:310`): this is the only real cost. Each recipient must read a little, about 1 frame per <10 s, so no write stalls for 10 s. Otherwise the connection dies and `release` refunds its bytes.
  - Sustaining the attack means refilling about 186 frames per 8–10 s ≈ 1,100–1,400 frames/min, which is 2–3 sender keys at 600/min. That is roughly 150–200 KiB/s in and the same out.
  - The TCP, loopback and proxy socket buffers absorb a few hundred KiB per connection once at the start. This is not charged to the budget and only adds a one-off ~50 MiB of upload.
- **R-4.0 H1 / review 50 M2:** they added `reserve`/`sendReserved` and the separate `reading` budget, but not a bound on ephemeral pushes. The `send` comment "bytes are counted but never refused" (`conn.go:106-108`) shows this was a deliberate choice that assumed presence is small and bounded per connection. That assumption misses the relay-wide sum. No owner decision (HANDOFF D-list) accepts it.
- **Accounts:** off on the early relay (no `--accounts`). `accountRoutes` is a no-op there, so nothing blocks unbound keys.
- **Mail loss?** No. Mail is queued (subject to queue caps) and delivered after the attack stops. This is delay, not loss.

**Early private relay (4.1p, `deploy/early/agentnet-relay.service`):** the finding applies as configured, and it is at its cheapest there, because of `--max-inflight 48MiB` and no accounts. Rough attacker cost:
- 4 network prefixes;
- about 190 free keys (about 186 slow-reading recipients plus 3–10 senders);
- a 1–2 minute ramp-up (about 50–100 MiB upload in total);
- then about 200 KiB/s each way to hold it.

After that, all honest mail on the relay is queued and not delivered until the attack stops. Separately, at `--max-conns 2000` the same frames would pin roughly 2000 × 264 KiB ≈ 0.5 GiB of frame bytes, more with the slice backing counted in C01-03. That is above `GOMEMLIMIT=400MiB` on the 512 MB VM, an OOM path the budget does not catch. It needs about 32 prefixes; it belongs to C01-03 and I did not re-verify it here.

**Severity reasoning:** High. Rubric §2 High: "a cheap unauthenticated attacker can take the hosted relay down (OOM, disk, fd, lock) for everyone".
- Actor: an internet stranger with free keys and no accounts.
- Reachability: normal protocol use (presence frames within all rate limits), a few prefixes, low bandwidth.
- Impact: relay-wide denial of mail delivery for every user, for as long as the attack lasts. Presence and auth keep working and no mail is lost, so it is not a full outage and not data loss. That keeps it below Critical, which needs code execution, disclosure or forgery. It is also above Medium: Medium's "bounded DoS that needs a paired peer or many resources" does not fit, because this needs no pairing and few resources, and it hits everyone.

The early relay's 48 MiB flag makes it cheaper, not less severe.
