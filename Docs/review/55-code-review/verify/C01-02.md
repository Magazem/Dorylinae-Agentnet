# Verify C01-02
Verifier: CR-V-C01-02 · model claude-opus-5-5 · elapsed 25 min · commit 6cc26a7
**Outcome:** confirmed (High)

**Claim restated:** once authenticated, a connection can start a text message, send part of it and stop. Nothing ever times the frame out, and its buffer stays charged to the relay-wide read budget (`--max-inflight`). When a few dozen such connections hold the whole budget, every other connection's next frame fails its first 4 KiB `tryAdd`, and the relay closes *that* connection with 1013. The holders are never evicted. Precondition: the attacker can authenticate (keys are free; accounts are off on 4.1p) from one network prefix, and can open about 50 connections.

**Path traced:** `ServeHTTP` (`internal/relay/relay.go:445`) → `admitUpgrade` (`limits.go:221`: auth-fail lockout, upgrades 30/min with a burst of 60, 64 conns per prefix, 256 unauthenticated) → `authenticate` (`relay.go:583`, bounded by the challenge TTL, which only applies before auth) → `reconnect` (`relay.go:492`, per key, attacker keys are fresh) → `admit` (`relay.go:524`: max-conns 2000, 64 keys per prefix) → `SetReadLimit(MaxFrameBytes)` (`relay.go:508`) → `serve` → `readFrame(ctx, c)` (`relay.go:664`; `ctx` is the connection context, which has no deadline) → `c.ws.Reader(ctx)` returns on the first frame header → growth loop, `s.lim.reading.tryAdd(delta)` (`relay.go:713`) → `r.Read` blocks with no deadline (`relay.go:720`). For any other connection, the first growth (4 KiB) runs `tryAdd` (`limits.go:426`: `cur+n > max && cur > 0` → false) → `errReadBudget` → `ws.Close(1013)` (`relay.go:665-668`).

**Checks that could block it:**
- *ReadHeaderTimeout / IdleTimeout* (`cmd/relay/transport.go:33-40`): header phase only. With `ReadTimeout` 0, net/http clears the read deadline once the headers are read, and the file itself says it "does not cover a hijacked WebSocket". Does not block.
- *Challenge TTL* (`relay.go:589`): applies to the auth read only. Does not block.
- *Read/idle deadline after auth*: none exists. A grep for Deadline/Ping/keepalive in `internal/relay` and `cmd/relay` finds none on the read side. `writeTimeout` (`relay.go:34`) covers writes to the attacker only, and nothing is written to an idle attacker key. The attacker's client still answers WebSocket pings, since control frames may interleave with fragments. Does not block.
- *Caddy in front of 4.1p* (`deploy/early/Caddyfile`): plain `reverse_proxy`. There is no stream timeout for upgraded connections, and it sets the real client IP, so the attacker gets one prefix per /24. Does not block (this is the prefix accounting the finding assumes).
- *Per-key/per-prefix envelope and byte rates* (`limits.go:285`, called at `relay.go:768`): charged in `route`, only after a frame has been read completely, so an unfinished frame is never charged. Does not block.
- *1 MiB frame cap* (`SetReadLimit`, growth capped at `MaxFrameBytes+1`, `relay.go:711`): this caps each holder at about 1 MiB, so the budget divided by 1 MiB gives the connection count (≈ 48–51). It sets the cost; it does not block.
- *Per-prefix caps* (64 conns, 64 keys, burst 60): 51 connections fit in one /24. My test runs with every default on and hits none of them. Does not block. IPv6: one /48 is the unit, and those are cheap.
- *Separate outbound budget / drain reserve* (R52 H1): separate from the read budget. The relay still *delivers* to victims, but it cannot read their acks, mail or presence. Does not block.
- *Deliberate trade-off?* R52 H1 (`Docs/review/52-4.0-r40-review.md:93-94`) chose "close the reader" over waiting, because waiting could deadlock. It did not consider that closing the new reader leaves the budget with the first holders indefinitely. No D-decision or spec text accepts this (`relay-hosted.md` §2 does not list the read budget; its "Memory bound" paragraph is about memory, not fairness). `envelope.md` §Forwarding says errors on one envelope never close the connection. So the finding reopens R52 H1's choice; it is not intended behaviour.

- Mine, full size, one prefix: `internal/relay/zz_review55_C01-02v_test.go` `TestReview55C01_02VerifyOnePrefixFullSize`. It uses `MaxInflight 48 MiB`, all other limits at their defaults, and every attacker in 10.1.0.0/24. Result: "one /24: 51 connections, 45363 KiB uploaded, hold 50331648 of 50331648 read-budget bytes (1.755s)", then "still held after 2s … honest 200-byte mail closed 1013" → PASS (the attack works). Each nearly full frame charged ≈ 1 MiB. A frame of 512 KiB + 1 byte already charges 880 KiB, so the attacker can trade connections for upload: ~57 connections with ~29 MiB, or ~50 connections with ~44 MiB.

**Severity reasoning:** rubric §2 High says "a cheap unauthenticated attacker can take the hosted relay down (OOM, disk, fd, lock) for everyone". The actor is an internet stranger with free keys. It is cheap: one /24 (or one IPv6 /48), ~50 connections, a one-time upload of 29–45 MiB in under 2 s on loopback, and then nothing but idle TCP connections, held indefinitely. The effect reaches everyone. Every honest daemon is closed 1013 on its next mail, ack or presence frame. It reconnects, is closed again, and after 20 reconnects a minute it is refused with `rate_limited`. Mail is still delivered to it but never acked, so it is redelivered. The relay is effectively down, although memory stays bounded (the H1 fix works as a memory bound). This is not Critical: there is no content, key or code-execution impact. It is not Medium: it needs neither a paired peer nor many resources. **High, unchanged.**

**Applies to the early private relay (4.1p): yes**, as configured in `deploy/early/agentnet-relay.service` (`--max-inflight 48MiB`, `--max-conns 2000`, no `--accounts`). Caddy passes WebSockets through with no stream timeout. Attacker cost: one /24 or /48 prefix, ~50–57 connections (under the 64/prefix and burst-60 caps), 29–45 MiB uploaded once, then no further bandwidth. I did not check whether `--accounts` (unbound-per-prefix eviction) would change this; it is off on 4.1p.
