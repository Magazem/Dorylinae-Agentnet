# Verify C03-01
Verifier: CR-V1 · model claude-opus-5-5 · elapsed 15 min · commit 6cc26a7
**Outcome:** confirmed
**Claim restated:** On a relay with `--accounts` on, an unauthenticated stranger can repeat `bind_start` from unbound keys; each call leaves a durable `bind_requests` row (~425 B) that lives at least 24 h 10 min, with no bind-specific rate limit and no disk or size cap. Enough prefixes fill the hosted relay's volume, and every insert is an fsync'd write on the single SQLite connection. Precondition: accounts mode `github`, `email` or `both`.

**Path traced:**
- WebSocket frame → `route` (`internal/relay/relay.go:734`) → `lim.controlAllowed` (`relay.go:742`, `limits.go:310-346`: 60 non-ack control frames per key per minute; a key closes only after 3 minutes in a row *over* the limit, so exactly 60/min runs forever).
- → `handleControl` (`internal/relay/pairing.go:141`) → `accountAllows` passes `bind_start` for any key (`internal/relay/accounts.go:260-262`) → `handleAccountOp` (`accounts.go:306-309`) → `bindStart` (`accounts.go:324-344`). Its only gates are already-bound and a valid device/os.
- → `createBind` (`internal/relay/accounts_store.go:234-268`): `UPDATE … SET state='cancelled'` on the previous row, then `INSERT` a new row, in one tx. Nothing is deleted.
- → `notePoll` (`accounts.go:399-410`) adds a `lastPoll` entry. It is swept only past 1024 entries, and only entries older than `bindTTL`.
- Deletion happens only in `prune` (`accounts_store.go:458-463`), via `Sweep` (`relay.go:377-383`): rows with `expires < now-24h`. With `bindTTL` 10 min and `bindKeep` 24 h (`accounts_store.go:87-91`), each row lives 24 h 10 min.

**Checks that could block it:**
- **Accounts off (the default; the early private relay 4.1p runs without `--accounts`): not reachable.** `s.acct` is nil unless `Accounts` is set and not `off` (`relay.go:343`). `handleControl` then returns false for `bind_start`/`bind_poll`/`bind_cancel`/`unbind` (`pairing.go:146-149`), and the connection closes on the first such frame. No row is written. This finding does not block the 4.1p deploy.
- **Per-key control rate (60/min):** does not block it. It bounds each key, but keys are free. The reviewer's test runs at exactly this rate.
- **`maxUnboundPerPrefix` = 16 (`accounts.go:27`, `listUnbound` `:225-234`):** caps *live* unbound connections; the 17th evicts the oldest (`relay.go:641-644`). It is not a rate limit. Rows of evicted keys stay. Churning fresh keys at the upgrade rate (30/min, burst 60, `limits.go:19-20`) gives each new key a fresh 60-frame window. That is about 30 rows/s per prefix, so the reviewer's 16/s is conservative.
- **`maxKeysPerPrefix` = 64 and `maxConnsPerPrefix` = 64 (`relay.go:532`, `limits.go:231`):** concurrent caps, higher than 16. They do not bind.
- **Queue caps and free-disk check:** they do not count bind rows. The queue totals count only the `queue` table (`queue.go:150-167`), and `storageLow` (`queue.go:190-202`) is consulted only on enqueue, never in `createBind`. Bind inserts continue below the 1 GiB free-disk floor (`relay-hosted.md` §2 line 185) until the volume is full. Before that, the floor already makes the queue refuse all new mail ("relay storage low") for everyone.
- **Spec:** accounts.md §Frames (lines 95-96) says "at most one pending bind per key" and nothing about how long finished rows are kept or any bind_start rate. relay-hosted.md §2 lists no bind_start limit; its threat model (line 28) says a stranger must not "exhaust memory, disk". No decision in HANDOFF §3 accepts this.
- **Duplicates:** O-187 is the must-check list for accounts; 02 says C03 findings are new. O-015 (queue flood without accounts) and O-027 (free-disk fail-open) are different defects. Not a duplicate.

**Test:** `internal/relay/zz_review55_C03-01_test.go`, `go test ./internal/relay -run 'TestReview55C03_01' -count=1 -v` → PASS, `rows=20000 after-sweep=20000 db+wal bytes=8507392 (425 B/row); one prefix … = 592 MB`. The test passes when the defect is present: it asserts that every row survives `Sweep`. So it shows the stated mechanism, not an unrelated effect. It calls `handleControl` directly, which skips `controlAllowed`. It advances the clock 1 s per round across 16 keys, i.e. exactly 60/min per key, which is within the limit I traced above.

**Severity reasoning:** Rubric High: "a cheap unauthenticated attacker can take the hosted relay down (OOM, disk, fd, lock) for everyone". The actor is an internet stranger with no account. The queue stops accepting mail once free disk drops below 1 GiB. On the 2-3 GB volume that takes about 1-2 GB of rows, i.e. 2-4 /24s or IPv6 /48s over roughly 24 h (fewer with key churn). The fsync'd writes also compete for the single DB connection. It is not Critical: there is no code execution, content read or forgery. Per rubric §2, accounts is off by default, so the consolidator may lower it by one level. It is not reachable with accounts off.
