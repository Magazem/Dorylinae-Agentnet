# Verify C15-01
Verifier: V-C15-01 · model claude-opus-5-5 · elapsed 6 min · commit 6cc26a7

**Outcome:** confirmed (High)

**Claim restated:** the owner's signing step signs whatever `SHA256SUMS` is attached to the
draft release when they download it, and nothing binds that file to the one CI built and
tested. So anyone who can replace draft assets before signing gets their archives signed.
**Precondition:** the attacker holds a credential with `contents: write` on the repository
(a leaked PAT or token, or a taken-over owner account), and acts between `draft` creating
the release and the owner running step 2.

**Path traced** (from the entry point, the tag push). `git diff --stat 6cc26a7 HEAD` is empty
for `tools/`, `scripts/`, `.github/`, `Docs/ops/`, `packaging/` and spec 49, so the worktree
HEAD (57760ba) matches the freeze for every file cited.
1. A `v*` tag push → `release.yml:30-32`. `meta` (`:54-92`) validates the version.
   `build` (`:106-194`) builds and uploads `dist-*` artifacts.
2. `sums` (`:196-225`) writes `SHA256SUMS`, prints it to the log (`:217`), checks its
   format (`:218`) and uploads the `release-files` artifact. These two are the only copies
   CI keeps.
3. `install-sh` (`:229-244`) and `homebrew` (`:248-275`) test those exact files.
4. `draft` (`:277-325`, `environment: release`, `contents: write`) runs
   `gh release create --draft … dist/agentnet_* dist/SHA256SUMS` (`:321-322`). The notes
   (`:310-318`) tell the owner to `gh release download $TAG -p SHA256SUMS`, i.e. to fetch
   the **mutable draft asset**, not the run artifact or the logged digest.
5. After this the draft's assets can be deleted and re-uploaded by any `contents: write`
   holder (GitHub drafts are editable; even "immutable releases" only lock assets once a
   release is published). Nothing in the repo checks for this.
6. Owner runbook `Docs/ops/release-signing.md` §Every release step 2: download → `sign`
   → `verify -install-sh` → upload.
   - `cmdSign` (`tools/releasesign/main.go:329-363`) runs only `checkSums`
     (`:234-266`), which checks format only: six targets, one version, the right extension.
     It then signs the bytes.
   - `cmdVerify` checks the new signature against the key in `install.sh`. That passes by
     construction.
7. Step 4 renders Homebrew from "the SHA256SUMS you just signed" (`render.sh` trusts it,
   `packaging/homebrew/render.sh:5-6`). `install.sh` then accepts the swapped archives,
   because their hashes match the now-signed sums (`scripts/install.sh:8-16`).

**Checks that could block it:**
- `checkSums` / `cmdCheck`: format only. The attacker writes a well-formed file. Does not block.
- `environment: release` on `draft` (`release.yml:280`): it gates when the job starts, not
  later edits to the draft's assets. Does not block.
- Runbook "Before signing, look at the draft: the commit it was built from and the version":
  "Built from $SHA" is in the notes and `target_commitish`, and both can be edited with the
  same permission. Even when accurate, neither names a digest. Does not block.
- `verify -install-sh`: checks the key and the signature, not where the file came from.
  Does not block.
- No `pull_request_target` or other PR-reachable `contents: write` in any workflow
  (`grep` of `.github/workflows/*.yml`), so the actor stays a credential holder, not a
  stranger. This narrows the actor but is not a block.
- Owner decisions: D36 / OD-P4-19 (ii) chose the offline key and a draft in order to defeat
  a GitHub account takeover or a leaked token (49 OD-P4-19 rationale; 49 §install "a swap
  of the release artefacts on GitHub (a leaked token, …)"). The pre-sign window defeats
  exactly that goal, so this is a flaw D36 did not consider, not intended behaviour.
- Not a duplicate:
  - O-180 / R53 L5 is a build that was already bad in CI.
  - O-181 / R53 L9 serves an *older signed* release.
  - R53 M1 ("nothing binds a signature to a reviewed commit") was scoped to dry-run
    versions and fixed with `0.0.Z`.
  None covers swapping the assets of the current release before it is signed.

**Test:** `tools/releasesign/zz_review55_C15-01_test.go`,
`TestReview55C1501SignAcceptsSwappedSums`. It writes a well-formed `SHA256SUMS` with
arbitrary hashes unrelated to any build and asserts that `sign` refuses it.
Command: `go test ./tools/releasesign -run TestReview55C1501 -count=1` → FAIL as expected:
`sign signed a SHA256SUMS with no binding to the CI run (rc=0): Signed agentnet 1.2.3: wrote …SHA256SUMS.sig and …SHA256SUMS.minisig`.
The test only shows the tool side. The draft-mutability step is GitHub behaviour and was
not exercised (no web, no repo writes).

**Severity reasoning:**
- Not Critical. The actor is not the relay, a stranger or a paired peer: they need a
  leaked `contents: write` credential or the owner's account, plus acting in the draft
  window. That is the rubric's "narrower position".
- High: "a core security property breaks, but the attacker needs a narrower position". The
  property that breaks is the one the release signature exists for: resisting a swap of the
  GitHub assets. The impact would otherwise be Critical-class, since every `curl | sh` and
  Homebrew install would run the attacker's binaries with a valid release signature. The
  window is realistic: drafts wait for the owner, and the attacker can poll.
- Mitigation not in the code: GitHub branch/tag protection might let the same credential do
  other damage too. That does not remove this path, which leaves no commit trace.
- Rating: High, unchanged.
