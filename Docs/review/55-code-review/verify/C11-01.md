**Outcome:** confirmed (High)

**Claim restated:** The human approval text for `grant_create` and `grant_policy_add` omits fields that decide what is being approved: for a grant, the resolved path (only a random label is shown), branch, scope, sensitive/public and the peer fingerprint. For a policy, branch, scope, public, `until` and the fingerprint. So a prompt-injected local agent can get a broader or quarantine-free grant or policy approved under a summary that looks like the benign request.
Precondition: a local agent with IPC access. For `grant_create` it also needs an open work session where we are the requester with that peer, which is normal use when the agent works with bob.

**Path traced:**

  - Steps 1–2 (session, D5): `:386-421`.
  - Resource resolve: `:423-439`. Scope is only checked for syntax, `capability.ValidScopePath` at `:434`.
  - `sensitive := p.Action != git.read || !p.Public`: `:443`. The public flag comes straight from IPC params and has no other gate.

**Checks that could block it:**
- The Precondition re-checks at `:561-583` and `:931-948` cover state (session open, peer paired, D5, debate, resource still valid). None of them compares the approved text with the request, so they do not block this.
- The spec requires the fields. `Docs/protocol/approval.md:119`: "The dialog shows … the summary (action, resource, peer name and fingerprint, expiry)". The code shows a label, not the resource, and no fingerprint. `grant.md` §Sensitive grants: "the default is sensitive and the human opts out", but the human never sees the opt-out. So this is a spec deviation, not intended behaviour.
- Owner decisions and prior reviews: R28 (`Docs/review/28-2.2c-review.md:33`) mentions "the approval summary carries the label or path". That is about content leakage, not completeness, and records no decision to omit scope, public or fingerprint. The sibling approvals were deliberately made complete: `device_scope.go:149` (full argv, "Confirm only if you set this scope yourself") and `debate_constrain.go:58` (full text, R43 H3, R46 H2). The grant summaries are the outliers.
- The CLI `agentnet grant` prints the view with path and scope. However, the agent runs the CLI, not the human, so this does not reach the human.
- `agentnet grants` could show it, but only if the human checks by hand before typing the code. Nothing prompts them to.
- Not in 02-open-findings. O-067 (name collisions/fingerprint in the CLI) and O-129 (decoy digits) are related but narrower.
- Side note: the grant and policy summaries use raw `peer.Name`, without the `stripLongDigits(notify.Clean(...))` used by `device.go:487`, `device_scope.go:208` and `debate_constrain.go:70`. The window's `Clean` removes control characters but not decoy digits. That falls under O-129 and is not a new finding.

**Severity reasoning:** Rubric §2 High: "A core security property breaks, but the attacker needs a narrower position (a local agent via IPC …)". The actor is a prompt-injected local agent, which approval.md treats as a boundary that must never "widen a scope or grant". The human approval is the only control for grants and policies. With these summaries the human cannot tell a scoped, sensitive grant from a whole-repo, non-quarantined one, or a 30 d policy from a 90 d public one. That silently removes the result quarantine (OD-P2-13), which is the stated mitigation for data exfiltration (`grant.md:488`).
- Not Critical: it needs a local agent plus the human's (misinformed) approval, and a live requester session with the target peer.
- Not Medium: it defeats an approval gate's purpose, the same class as the rubric's High example "A local agent completes a device scope change without the window".
