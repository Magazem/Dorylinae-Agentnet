# T13: Cross-platform parity (Windows, macOS, Linux)

Reviewer: TH-T13 · model claude-opus-5-5 · elapsed ~9 min (shell clock) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 1 | 0 | 2 | 3 |

Verdict: every OS split that ships (windows, darwin, linux) has a real implementation. The
`_other` fallbacks all **fail closed**: an error, a not-ready window, or `ErrUnsupported`, and
none of them is built for a shipped target. The one exception is `perm_acl_other.go`, which
returns nil on macOS; that is O-160 as recorded. `GOOS=linux|darwin|windows go vet ./...` is
clean, and freebsd builds.

The parity problems are in code that has no OS split but assumes one filesystem model:
- **Path identity is compared by spelling.** The chunk reviews found this on Windows (C11-04
  `\\?\`/UNC, C11-02 junctions, C14-01, C16-05). The same flaw exists on macOS: the firmlinked
  spelling `/System/Volumes/Data/Users/…` gets past grant.md §Issuance step 3 for the config
  dir, the home dir and in effect the whole data volume (**T13-01, High**).
- **Unix-only enforcement.** The config dir's owner-only guarantee is enforced (chmod, fail
  closed) only on Unix. On Windows a foreign-created home is used silently, and `doctor`
  calls a directory "owner-only" after checking writers only (**T13-02**).
- **Keychain accounts.** They are hashed from the unnormalised directory spelling, so a
  second spelling on a case-insensitive filesystem tells the user to delete their card
  (**T13-03**).
- **CI coverage.** Lint (gosec, errcheck) never sees the Windows- or macOS-only files. The
  release workflow tests only on Linux. The macOS approval window has no test (**T13-05**).

### Q2. `_other` or unsupported fallbacks that silently succeed

Only one fallback returns success. `internal/device/perm_acl_other.go:7` returns nil on
macOS/BSD, which is O-160 as documented. Every other fallback fails closed:
- `idle_other.go:12` and `desktop_other.go:13` return an error;
- `approval_other.go:12` returns an error;
- `window_other.go:14` returns a not-ready handle, which makes the approval unavailable;
- `current_other.go:6` returns `ErrUnsupported`;
- `diskfree_other.go:9` returns an error, and the relay then skips the check (O-027 records
  that fail-open, but this file is only for non-Unix, non-Windows relays).

`runner_unix_other.go:9` (no death signal on macOS) is O-159. None of the `_other` files is
built for a shipped target: release and CI build only darwin, linux and windows
(`.github/workflows/release.yml:112`, `ci.yml:203`).

## Findings

### T13-01 · High · confirmed-read
- **Where:** `internal/daemon/grant.go:133-162` (`validateResource`), `grant.go:170-186`
  (`caseInsensitiveFS`, `foldPath`, `pathEqualOrContains`), `grant.go:209-216`
  (`isFilesystemRoot`); serving `internal/capability/fs.go:231` (`os.OpenRoot` of the stored path).
- **What goes wrong:** Since macOS 10.15, `/Users` on the system volume is a **firmlink** to
  `/System/Volumes/Data/Users`. A firmlink is not a symlink, so `filepath.EvalSymlinks`
  returns `/System/Volumes/Data/Users/me/…` unchanged. The step-3 checks compare folded
  strings. So these all pass:
  - the config dir under its Data-volume spelling;
  - the home dir itself;
  - `/System/Volumes/Data`, which is the data volume's root but is not `/`.
- **Scenario:** a local agent (prompt-injected, IPC only) with an open requester session
  calls `grant_create` with `action=fs.read` and one of these resources:
  - `resource=/System/Volumes/Data/Users/me/Library/Application Support/dorylinae`, which
    serves the DB (mail, requests, approvals, audit) and, with the file keystore, the key
    files;
  - `/System/Volumes/Data/Users/me`, which serves `~/.ssh`;
  - `/System/Volumes/Data`, which serves every file the user can read.

  The window shows the label only: "approve grant fs.read on dorylinae-xxxx / me-xxxx /
  Data-xxxx to bob …" (C11-01). Once the human types the code, the peer reads the files.
  `recheckResource` uses the same function, so fetches keep working. This is the macOS twin
  of C11-04 (Windows `\\?\`/UNC). The same trick works for `grant_policy_add` and for device
  scope repos, which also call `validateResource`. I did not run it (no macOS here). The Go
  side is traced: `EvalSymlinks` resolves only `ModeSymlink` components, and a firmlinked
  path has none. The Apple side is documented firmlink behaviour. A verifier on a macOS
  runner can check it with `stat -f %i /Users/$USER /System/Volumes/Data/Users/$USER` (same
  inode) and a `validateResource` call.
- **Spec:** `Docs/protocol/grant.md` §Issuance step 3, "Refused: the config dir … or any
  path inside it or containing it, the user's home directory itself, and a filesystem root".
- **Fix direction:** compare by file identity (`os.SameFile` of the resource and each of its
  ancestors against the config dir and home), not by spelling. This covers C11-04, C11-02
  and T13-01 together. Also treat any mount point as a root (compare `st_dev` with the parent).
- **Related:** C11-04, C11-02, C11-01, O-135 (APFS NFC/NFD, same check), D24

### T13-02 · Low · confirmed-read
- **Where:** `internal/paths/paths.go:56-66` (`Ensure`: chmod/fail-closed only when
  `GOOS != windows`), `internal/keystore/perm_windows.go:35-38` (no check on load),
  `cmd/agentnet/doctor.go:246-270` (`checkConfig` uses `device.CheckProgramOwner`, a
  **writers-only** check, then prints "exists and is owner-only")
- **What goes wrong:** the owner-only config dir is a guarantee on Unix only:
  - On Unix, `Ensure` chmods the directory to 0700 at every start. It fails closed when
    another user owns the directory, and `perm_unix.go` refuses a key file that others can
    read.
  - On Windows nothing checks either the directory or the key file, so a directory created
    by someone else is used as is.
  - `doctor` reports "owner-only" for any directory that others can read but not write,
    because `CheckProgramOwner` only looks at write, delete and ACL rights.
- **Scenario:** another OS user on the same PC. The owner picks a custom home on a shared
  location, for example `DORYLINAE_HOME=C:\agentnet` (drive-root subfolders can be created
  by any user). The other user created `C:\agentnet` first, with `Everyone:F`, and planted:
  - `identity.key`, holding a seed the other user knows;
  - `agent-card.json`, a matching self-signed card.

  The owner's daemon starts without complaint: the file backend `Stat`s the key and loads
  it. From then on the other user knows the owner's identity key and can impersonate the
  owner to every peer the owner pairs with. On Unix the same setup fails closed: the chmod
  gets EPERM, or the key is refused as group- or world-readable. A readable-only variant
  (Users:RX inherited) exposes the DB while `doctor` prints "owner-only". This needs the
  owner's own choice of a shared path, so it is at most Low (rubric §2).
- **Spec:** `Docs/protocol/agent-card.md:110-111` (0600, refused on load; Windows: protected
  DACL); `Docs/protocol/ipc.md:12` ("Config dir is `0700`", Unix row only);
  `Docs/cli/doctor.md` `config` row, "exists and is owner-only".
- **Fix direction:** on Windows, set a protected owner-only DACL on the directory in
  `Ensure`, refuse a directory whose owner is not the user, and run `OwnerOnly` on key load.
  In `doctor`, also check read access (or print "not writable by others").
- **Related:** O-030 (key re-check on load; this adds the planted-key path and the parity
  contrast), C16-08 (no DACL on the directory, Info), D24

### T13-03 · Low · confirmed-read
- **Where:** `internal/keystore/keychain.go:28-31` (`AccountFor` hashes the directory string);
  callers `internal/identity/identity.go:62`, `internal/mailbox/mailbox.go:88,123`,
  `internal/daemon/daemon.go:712`; `internal/paths/paths.go:42-43` (only `filepath.Abs`); the
  error `identity.go:131-133`
- **What goes wrong:** the identity, mailbox and webhook keychain accounts are keyed on the
  config directory's exact spelling. On NTFS and default APFS, `C:\Users\Me\ag` and
  `c:\users\me\ag` (or `~/AgentNet` and `~/agentnet`) are the same directory, with the same
  `agent-card.json`, but different keychain accounts. With the second spelling the daemon
  finds the card but no key, and fails with `ErrKeyLost`: "restore it or delete
  agent-card.json to start a new identity". On Windows the second spelling also gets its own
  pipe, so two daemons can run on one directory (C16-05).
- **Scenario:** no attacker. The owner installed with `--home C:\Users\Me\AgentNet` (the task
  keeps that spelling) and later exports `DORYLINAE_HOME=c:\users\me\agentnet` for a script,
  or a tool lower-cases the path. `agentnetd run` under the new spelling reports the key as
  lost. If the owner follows the printed advice, the identity and every pairing are gone.
  The key sits in the file backend only when the keychain was unavailable at first run; in
  that case the file is found and the only symptom is C16-05. Unix with a case-sensitive
  filesystem is affected only through symlinked spellings (for example `/home` →
  `/var/home` on Fedora Atomic).
- **Spec:** `Docs/protocol/agent-card.md` §Key storage (the account is `<id>` of the config
  dir). It does not say how the directory is normalised.
- **Fix direction:** canonicalise the directory once in `paths.In` (`EvalSymlinks`; on
  Windows also `GetFinalPathNameByHandle`; case-fold where the filesystem is
  case-insensitive), and use that form for the pipe name and every `AccountFor`.
- **Related:** C16-05, C05-02, O-197

### T13-04 · Info · suspected
- **Where:** `internal/capability/fs.go:161-175` (`componentErr` refuses any
  `ModeIrregular`), per `$GOROOT/src/os/types_windows.go:206-228` (Go 1.27: every reparse tag
  other than symlink, AF_UNIX and DEDUP → `ModeIrregular`)
- **What goes wrong:** on Windows the fs grant refuses every non-link reparse point as
  `symlink`, not only junctions. OneDrive Files-On-Demand files and folders carry
  `IO_REPARSE_TAG_CLOUD_*`. Windows 11 often redirects Documents, Desktop and Pictures into
  OneDrive. So a grant on those folders would fail file by file (`symlink`), while the same
  folder synced by Dropbox or iCloud on macOS is served.
- **Scenario:** no attacker. The owner grants `fs.read` on `C:\Users\me\OneDrive\Documents\proj`.
  The peer's reads fail with a confusing `symlink`. Not confirmed: this PC's OneDrive files
  carry no reparse attribute (the client is not syncing), so I could not show the tag.
- **Spec:** `Docs/protocol/grant.md:275-279` chose "other reparse points" → `symlink` on
  purpose. This is a design note for the owner, not a spec violation.
- **Fix direction:** allow the cloud-file tags as regular (as Go does for DEDUP), or
  document the limitation in grant.md and in the `fetch` error hint.
- **Related:** C11-02, C14-01, O-162

### T13-06 · Info · suspected
- **Where:** `internal/notify/window_darwin.go:25-33,57-62`, `internal/notify/approval_darwin.go:13-26`
- **What goes wrong:** macOS passes the window and notification text as raw UTF-8

  confirmed: I have no macOS machine, and no test covers it (T13-05).

  does not mention encoding.
- **Fix direction:** pass base64 in the environment and decode it in the script (as on
  Windows), or read with `do shell script "printenv …"`, which is UTF-8-safe. Add a
  non-ASCII test on the macOS runner.
- **Related:** O-166 (window display fidelity), C12

## Assumptions and contracts

- Grant step 3 assumes that `filepath.EvalSymlinks` yields one canonical spelling per
  directory (`internal/daemon/grant.go:140,147,152`). **Checked: false** on Windows (C11-04,
  C11-02) and macOS (T13-01).
- `paths.Ensure` makes the config dir private on every OS (`internal/daemon/daemon.go:269`
  relies on it before `ipc.Listen` and key creation). **Checked**: true on Unix only (T13-02).
- `keystore.File.Get` relies on `checkOwnerOnly` to refuse a foreign key file
  (`internal/keystore/file.go:27`). **Checked**: this is a no-op on Windows (O-030, T13-02).
- The pipe name and keychain accounts assume `paths.In` returns a canonical directory
  (`paths.go:43`, `keychain.go:28`). **Checked: false** (C16-05, T13-03).
- `componentErr` assumes that `ModeIrregular` on Windows means "a link-like reparse point"
  (`internal/capability/fs.go:167`). **Checked**: Go sets it for every non-surrogate tag
  except DEDUP (T13-04).
- `device.CheckProgramOwner` is reused by `doctor` as a privacy check
  (`cmd/agentnet/doctor.go:247`). **Checked**: it tests writers only (T13-02).
- The approval `WindowRunner` relies on each OS killing its window when the daemon dies.
  **Checked**: Windows (job) and Linux (`Pdeathsig`) do; macOS relies on `giving up after`
  (`window_darwin.go:33`).
- go-keyring never puts the secret in argv (another-user threat, approval.md:31 by analogy).
  **Checked**: v0.2.8 darwin `Set` writes to `security -i` over stdin (`keyring_darwin.go:76-99`).
