# T3: Cryptography and key handling, end to end

Reviewer: TH-T3 · model claude-opus-5-5 · elapsed ~240 min wall clock (includes a usage-limit pause; about 70 min of active work) · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 2 · Info 1.

The cryptographic design holds end to end, and I found no new exploitable defect. Every Ed25519
signature the identity key makes carries its own domain tag. Each tag ends in `\n`, and no tag
is a prefix of another. Every verifier re-canonicalises the generically parsed object that the
signer covered, and checks the binding the signer made (recipient, origin, role, peer). Every
MAC or tag comparison of a secret is constant time. Every secret and every id that must be
unguessable comes from `crypto/rand`. `math/rand` appears only in four jitter calculations.
Noise nonces cannot repeat. The release chain (embedded key, `SHA256SUMS` format, both install
verifiers) is consistent, with the residuals C15 already reported.

The two new findings are both in the keystore's multi-backend logic, the same area as C05-01:
- **T3-01:** a secret saved while the keychain is unavailable goes to the file, but the older
  keychain copy stays in front of it. After a webhook secret rotation during a keychain outage,
  the daemon later goes back to signing with the pre-rotation secret.
- **T3-02:** on a machine without a keychain service, `Keychain.Delete` returns an unwrapped
  error. `Store.Delete` then fails every time, although it did remove the file copy. The
  results: `--webhook off` reports an error halfway through, and deleted mailbox keys are
  never marked deleted.

The Info (T3-03) is about the daemon's identity-key loaders, which do not check the loaded key
against the card.

Confusion analysis:
- **Identity-key signatures:** 8 distinct tags. All end in `\n` and none is a prefix of another,
  so no two signed messages can collide. The relay chooses only 32 nonce bytes (v1) or nonce plus
  origin (v2), always behind a relay-auth tag.
- **Mail and presence share `dorylinae-mail-v1\n`.** They are told apart by the id format (`m-`
  versus `p-`, enforced at step 9 in both directions, `open.go:213`), by `kind` (presence checks
  `Kind == "presence"`, `internal/presence/receive.go:69`), and by `mail_submit` refusing the
  `presence` prefix (C07 Q4). A presence message cannot be replayed as mail, or the reverse.
- **Recipient binding:** mail binds `to` inside the signature (step 8), so a peer cannot forward
  a mail it received to a third party. Grants bind `aud`. Decisions bind both participants.
  Noise binds both identities in the prologue.
- **Verifier checks less than the signer binds:** none found. `verifycard` is laxer than the
  daemon (C05-05), and `decision verify` fails a non-strict signature at step 3 rather than
  step 1 (C25-02). Both are already reported.

### 3. Constant time, randomness, nonces, encodings

- **Secret comparisons:**
  - `hmac.Equal` for pairing tags (`pairing.go:945`) and approval MACs (`approval/store.go:280`);
  - `subtle.ConstantTimeCompare` for webhook `Verify` (`notify/sign.go:42`);
  - fingerprints, which are public, also use it (`daemon/trust.go:64`, `daemon/device.go:375`).

  A grep for `bytes.Equal` and `==` next to sig/mac/tag/hash/token/secret finds only public
  values: stored-token equality (`capability/fetch.go:582,605`, `grant_kinds.go:85`), the
  Decision hash (`decision/verify.go:115`), the minisign key id (`releasesign/main.go:296`) and
  the debate canonical form (`debate/decode.go:62`).
- **`math/rand`:** used only for jitter (`mail/outbox.go:490`, `presence/sender.go:453`,
  `notify/queue.go:244`, `relayclient/relayclient.go:496`). All 27 id, nonce, code and key
  sources use `crypto/rand` (grep in Commands).
- **Nonces:**
  - Noise: counter only, monotonic, advancing only after successful authentication.
  - HPKE: a fresh ephemeral key per seal, and `Reseal` also re-encapsulates (`mail.go:208-243`).
  - Relay: a fresh 32-byte nonce per connection, with its length checked on decode (`frames.go:240-246`).
- **Strict encodings:**
  - `RawURLEncoding.Strict()` for keys and signatures in cards, mail, envelope, pairing and
    grants (`sigPattern`).
  - Exact lengths are checked everywhere. Ed25519 `Verify` rejects non-canonical `S`.
  - Small-order identity keys are not rejected (cofactorless verify, C25). This is acceptable,
    because keys are self-chosen and bound by pairing or fingerprint.
  - `verifycard` is laxer (C05-05). The lone-surrogate aliasing is C05-04.

### 4. Release chain

- **Keys:** the embedded PEM and minisign keys are the same key, and the key id matches
  (C15 Q1, re-read: `scripts/install.sh:48-51`).
- **Sums format:** `releasesign checkSums` requires all 6 targets, one version and no
  duplicates (`tools/releasesign/main.go:220-265`). `install.sh` re-checks every line with an
  anchored regex, one version, `--version` and the minimum (`install.sh:276-291`).
- **Verification:** either `openssl pkeyutl -verify -rawin` or `minisign -V`. Both are chosen
  before any download, with no unsigned fallback (`install.sh:169-194,259-272`).
- **Legacy minisign:** `minisig`/`verifyMinisig` implement the `Ed` layout with the global
  signature over sig ‖ trusted comment (`releasesign/main.go:270-308`). A global signature cannot
  pass for a signature over a sums file, because the release key signs only strict-format
  `SHA256SUMS` and the global message starts with 64 signature bytes.
- **Residuals:** C15-01 (the owner signs a mutable draft), C15-02 (cache and unpinned actions),
  O-181 and O-182.

## Findings

### T3-01 · Low · confirmed-test
- **Where:** `internal/keystore/keystore.go:57-67` (`Save` falls through to the next backend and
  leaves the more-preferred copy), `:36-55` (`Load` returns the first backend that answers); hit by
  `internal/notify/webhook.go:73-82` (`RotateSecret`) through `internal/daemon/daemon.go:707-714`
- **What goes wrong:** when the keychain is unavailable (locked, Secret Service not started,
  5 s timeout), `Save` writes the new secret to the file and returns success, but the old secret
  stays in the keychain. As soon as the keychain answers again, `Load` returns the old secret,
  and the file's new one is never read.
- **Scenario:** no attacker; a local fault that breaks a security action.
  1. The webhook secret S1 lives in the keychain.
  2. The user suspects S1 leaked and runs `agentnet notify --rotate-secret` while the keychain is
     locked (for example, a macOS service session or a Linux login before unlock).
  3. S2 is saved to `webhook.key` and printed, and the user configures the receiver with S2.
  4. After the keychain unlocks, every delivery is signed with S1 again. The receiver rejects all
     of them, and the leaked S1 is still the secret the daemon uses.

  The same shadowing hits an identity re-created during an outage. There, start fails with
  "stored private key does not match" (`identity.go:121-123`), which fails closed but confuses
  the user. Mailbox keys are not affected, because every key has its own account.
  Test: `internal/keystore/zz_review55_T3-01_test.go` `TestReview55T3_01StaleKeychainWins` →
  `after rotation Load returns "S1-old-secret" from keychain`.
- **Spec:** notify.md §Secret (rotation replaces the secret); agent-card.md §Key storage
  (keychain, then file fallback).
- **Fix direction:** after a fallback `Save`, delete (or mark stale) the copy in every
  more-preferred backend, or fail the rotation while a more-preferred backend is unavailable.
- **Related:** C05-01 (same unavailable-versus-absent folding), O-116

### T3-02 · Low · confirmed-test
- **Where:** `internal/keystore/keychain.go:61-67` (`Delete` does not wrap backend errors in
  `ErrUnavailable`, unlike `Get` at `:40-47`), `internal/keystore/keystore.go:92-106`; consumers
  `internal/mailbox/mailbox.go:426-439` (`deleteKey`), `:401-422` (`sweepLocked`),
  `internal/daemon/notify.go:225-234` (`--webhook off`)
- **What goes wrong:** on a host with no keychain service (headless Linux without Secret
  Service, SSH sessions, WSL, and platforms where go-keyring returns `ErrUnsupportedPlatform`),
  `keyring.Delete` returns a D-Bus or platform error. `Store.Delete` does not treat it as
  "unavailable", so it removes the file copy and still returns an error, every time.
- **Scenario:** default `auto` mode on a headless Linux daemon.
  1. **Mailbox keys.** Every hourly `Rotate` tries to delete keys past `not_after + 7 d`. The
     file is removed, but the row is never marked `deleted`. It is retried and logged every
     hour forever, stays in the "live" list, and blocks the "more than 3 live" early-deletion
     loop, which breaks at its first failure.
  2. **Webhook.** `notify --webhook off` clears the setting, deletes `webhook.key`, then returns
     the keystore error. `FailAllPending` and the `notify.config` audit never run, and the user
     is told the command failed although the webhook is gone.

  There is no secret-retention impact, because the file copy is deleted.
  Test: `TestReview55T3_02DeleteFailsWithoutKeychain` →
  `Delete err=keystore: delete from keychain: dbus: no session bus; file after delete: keystore: secret not found`.
- **Spec:** mail.md §Lifecycle (keys deleted and marked at `not_after + 7 d`); notify.md
  §Configuration (`--webhook off` removes the secret, pending deliveries fail `removed`).
- **Fix direction:** have `Keychain.Delete` wrap non-`ErrNotFound` failures in `ErrUnavailable`,
  the same way `Get` does. Or have `Store.Delete` succeed when every available backend no longer
  holds the secret.
- **Related:** C05-01 ("`Store.Delete` does not swallow keychain delete errors" is correct
  where a keychain exists, but it is the cause of this finding where none exists), O-113

### T3-03 · Info · confirmed-read
- **Where:** `internal/daemon/mail.go:113-124` (`newMailReceiver`'s `priv`), `:215-226`
  (`identityPriv`), used for the outbox, receiver acks, keys push, presence and grants
  (`daemon.go:361,536,601`, `mail.go:208`)
- **What goes wrong:** these loaders return whatever seed the keystore holds without checking it
  against the card, unlike `keystoreSigner` (`relayclient/signer.go:52-54`) and
  `debate.Store.sign` (`debate/decision.go:108-111`). `Seal` derives `from` from that key
  (`mail/mail.go:143`), so a mismatched seed produces mail that every peer rejects at step 6
  (`sender_mismatch`), and nothing in our own logs says why.
- **Scenario:** it is only reachable if the keystore's answer changes while the daemon runs,
  because the start check (`identity.go:121-123`) covers boot. The one path I found is T3-01's
  shadowing: an identity re-created in an outage, then the keychain comes back. The relay
  connection would fail too, since `keystoreSigner` refuses, which makes the state visible.
- **Spec:** none.
- **Fix direction:** reuse `keystoreSigner`'s match check in `identityPriv`.
- **Related:** T3-01, review 47 L3
