# T9: Persistence, transactions, migrations and durability

Reviewer: TH-T9 · model claude-opus-5-5 · elapsed 11 min (shell clock, `date +%s` at start and end) · commit 6cc26a7

(Worktree HEAD `ef03d14`; `git diff --stat 6cc26a7..HEAD -- . ':!Docs'` is empty, so the code is the freeze.)

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 4 | 1 |

**Verdict.** The daemon's durability core holds. Mail dedupe, Apply, the inbox copy and every
outgoing reply commit in one transaction, and the ack goes out only after the commit. Every
outbox transition is conditional on a non-final state. Daemon migrations run one at a time
under `BEGIN IMMEDIATE`, re-read the version, and are safe with two openers. Every approval
`Precondition`/`Perform` and every mail `Apply` I read writes only through its `tx` (no pool
access, so no single-connection deadlock). All `pending*` maps are keyed by the `*mail.Opened`
pointer, so a stale entry can never be *used* later; it can only leak.

That leak is the one Medium (T9-01, confirmed by test). `mail_seen` is pruned at 35 days but
`mail_inbox` is never pruned. A paired peer that reuses the id of one of its own old mails
therefore passes dedupe, runs `Apply` in full, and then fails on the `mail_inbox` primary key.
It can do this on every delivery. Each attempt is rolled back and never acked, and it leaves
its `*Opened` (up to ~320 KiB of plaintext for a request) in a process-global `pending*` map.
The heap grows at the relay's per-key byte rate. This escalates O-077 from "small leak" to a
peer-driven one.

The Lows:
- The relay migration runner has no transaction and no guard against two openers, and its
  10 s timeout covers the whole run (T9-02).
- The relay security journal is not fsynced, and one truncated line aborts the whole replay
  (T9-03).
- Every non-rejection receive failure is discarded silently, so poison mails and DB failures
  are invisible (T9-04).
- The Phase 1 fallback trigger is lost if the daemon stops between the ack and its goroutine
  (T9-05).

The Info is that `-wal` keeps deleted content past a checkpoint, which work-session.md
understates (T9-06, confirmed by test).

## Questions (the theme's Method, items 1–4)

1. **Effects in the transaction, after the commit, and on a crash between them.** See the
   inventory tables *Mail kinds* and *IPC writes* below.
   - Receiver: `mail_seen`, Apply and `mail_inbox` share one tx (`internal/mail/receiver.go:188-236`).
     A crash before the commit stores nothing and acks nothing, so the sender resends. A crash
     after the commit but before the ack gives a duplicate on resend, which is re-acked
     (`:200-201`, `:173-175`). No mail is acked with uncommitted effects.
   - Every reply mail a kind needs is `Outbox.SubmitTx` inside the Apply tx, for example auto-decline
     (`request/receive.go:340-362`), the tombstone reply (`request/cancel.go:312-316`),
     `transitionTx` (C18 Q5) and the helper auto-accept (`request/lifecycle.go:235-254`).
   - `After` is at-most-once (C07-04). Across every kind, `After` holds only audit rows,
     notifications, `Outbox.Wake`, runner kicks, the team roster broadcast (O-081), the
     `keys` re-seal and push, and the `device.unlink` approval reject. Each one self-heals:
     `Wake` has the 1 s ticker, `ExpireStale` runs at start (`approval/approval.go:317`),
     the runner sweep re-checks `CheckRunTx`, and presence resync repairs rosters. The
     exceptions are lost audit rows (the known pattern of O-095 and C22-05) and the Phase 1
     fallback, which has no rescan (T9-05).
   - Deterministic Apply failures are treated as transient, which makes them poison mails.
     C22-01, C24-01 and T9-01 are three peer-triggerable instances, and T9-04 makes all three
     silent.
2. **Migrations.**
   - Daemon (1–21): atomic, ordered, and safe with two openers (`internal/store/store.go:589-624`,
     C26 Q2).
   - The rewind tests are complete. `TestMigration8PreservesPeers` (rewinds to v7) and
     `TestMigrationAddsPeerTrust` (rewinds to v2) drop every table of migrations 9–21 and 4–21,
     `experience_records` included, and recreate migration 1's `audit_events`
     (`internal/store/store_test.go:80-110`, `:171-205`). `migration19_test.go` rewinds to v18.
   - No table declares a `REFERENCES`, so the `DROP`/`RENAME` rebuilds (8, 19) are safe with
     `foreign_keys(1)`.
   - Every migration is a pure schema step on top of the previous version, so a jump from any
     earlier version runs the same statements as the tests.
   - Residuals, already recorded: C26-03 (newer-schema race), C28-03 (a losing second daemon
     migrates first), O-173.
   - Relay (R1–R2): idempotent but not atomic, see T9-02.
3. **Retention.** See the table *Retention* below.
   - Content is kept indefinitely in `mail_inbox` (O-058), `requests` and `work_sessions`
     (spec'd: request.md:691, work-session.md:432), `debates`/`debate_entries`/`decisions`/
     `experience_records` (O-171) and held `grants` (C09-03).
   - `secure_delete(1)` is set on both daemon and relay DSNs (`store.go:540`, `relay/queue.go:210`).
   - Deletion is not complete on disk: freed pages are zeroed, but the `-wal` file keeps the
     deleted bytes until they are overwritten or the last connection closes (T9-06). Neither
     side sets `journal_size_limit` or runs `wal_checkpoint(TRUNCATE)`.
4. **The `pending*` pattern (O-077).**
   - Inventory: 14 process-global `sync.Map`s, all keyed by `*mail.Opened`. See the table
     below. The approval store's `s.pending` is keyed by approval id and is not the O-077
     pattern.
   - A stale entry is never *used*: `Receiver.Handle` builds a fresh `*Opened` per delivery
     (`receiver.go:122`), and a `sync.Map` key keeps its pointer alive, so an address is
     never reused.
   - Most kinds store only after every fallible step: `worksession/mirror.go:235`, and
     `debate` uses `defer … if err == nil` (`apply.go:346-350`, `:541-545`,
     `constraint.go:175-179`, `decision.go:347-351`). The C22-01 and C24-01 poison errors
     therefore do not leak.
   - The leak that is not small is the post-Apply `mail_inbox` insert, which a peer can make
     fail on every delivery (T9-01).

## Findings

### T9-01 · Medium · confirmed-test
- **Where:** `internal/mail/receiver.go:195-201` (dedupe on `mail_seen` only), `:221-225` (`mail_inbox` INSERT after Apply), `:152-155` (After never runs on error), `:320-327` (`Prune` deletes `mail_seen` at 35 d; nothing prunes `mail_inbox`); leak sites e.g. `internal/request/receive.go:176-182` (`pendingApply.Store` on the duplicate path, no DB write)
- **What goes wrong:** Dedupe keys on `mail_seen`, which is pruned after 35 days. `mail_inbox`
  has the same `(from_key, id)` primary key and is never pruned. A mail whose id was pruned
  from `mail_seen` passes dedupe and runs Apply in full. It then fails on the `mail_inbox`
  insert: `UNIQUE constraint failed`. The failure is not `ErrBadBody`, so the tx rolls back,
  nothing reaches `mail_seen`, nothing is acked, and `After` never runs. Every Apply that
  stored a `pending*` entry leaves it in the global map, and that entry pins the whole
  `*Opened` (`Signed` plaintext plus the decoded body).
- **Scenario:** A paired peer (paired > 35 days) takes the id of any Inbox-kind mail it sent
  us more than 35 days ago. It seals a new mail with that id and a fresh `created`, for example
  its own old `request` again (a question with context, ≤ 320 KiB canonical). It sends this
  over and over to our online daemon: direct forwarding has no relay dedupe.
  - Each delivery opens and runs `request` Apply, which takes the duplicate branch and stores
    `pendingApply`. The inbox insert then fails and everything rolls back.
  - At the relay's default 32 MiB per key per minute, the retained heap grows by roughly
    30–60 MiB a minute, plus a full Open and Apply per frame, until the daemon (mail,
    grants, sessions) runs out of memory.
  - Nothing is logged (T9-04).
  - The same `mail_inbox` collision also turns a reused id of an honest-looking mail into a
    mail that is never acked.
  - Test `internal/mail/zz_review55_T9-01_test.go` (the stand-in kind follows the real kinds'
    pattern): `re-used id delivery error: mail: store inbox: … UNIQUE constraint failed:
    mail_inbox.from_key, mail_inbox.id`, then
    `applies=6 afters=1 leaked pending entries=5 acks sent for re-used id=0 mail_seen rows=0`.
- **Spec:** `Docs/protocol/mail.md` §Dedupe and inbox: "Pruning can never re-admit a replay".
  That argument covers a relay replay (old `created`, stopped at step 11), not a peer that
  re-signs an old id. Rubric §1: a paired peer must not "make us store unbounded data".
- **Fix direction:** Dedupe on `mail_seen` *or* `mail_inbox` (or `INSERT OR IGNORE` the inbox
  row and treat a hit as a duplicate), prune `mail_inbox` with `mail_seen`, and delete a
  kind's `pending*` entry when the transaction fails (for example by passing outcomes through
  `op` rather than a global map).
- **Related:** escalates O-077 (new actor, a paired peer; new impact, unbounded memory; new
  path, the post-Apply inbox insert), O-058, O-059, C22-01, C24-01, T9-04

### T9-02 · Low · confirmed-read
- **Where:** `internal/relay/queue.go:227-253` (`migrateDB`), `:207-221` (`openRelayDB`, used by the relay at `relay.go:326`, `relay admin` at `admin.go:25` and `Restore` at `backup.go:73`)
- **What goes wrong:** Relay migrations do not keep invariant 5 ("migrations atomic").
  - Each migration's multi-statement SQL runs in autocommit, and so does the
    `relay_migrations` insert that follows it. No `BEGIN IMMEDIATE` is taken and the version
    is not re-read.
  - One 10 s `queueOpTimeout` context covers the whole run.
  - Only R1/R2 being entirely `IF NOT EXISTS` makes this safe today.
  - Unlike the daemon (R43 M9), two openers race.
- **Scenario:**
  - (a) An operator runs `relay admin …` while the relay starts on a DB with a pending
    migration (the deploy flow of relay-hosted.md). Both read version N, both apply, and the
    second `INSERT INTO relay_migrations` fails its primary key, so `relay admin` or the relay
    start exits with an error.
  - (b) A future R3 with a non-idempotent statement (`ALTER TABLE … ADD COLUMN`) is interrupted
    by a crash, or by the 10 s cap on a large `queue.db` (index builds). It stays half-applied:
    the column exists, the version row does not. Every restart then fails with "duplicate
    column", and the hosted relay stays down until someone repairs the file by hand.
  - Needs a future migration, or an operator race.
- **Spec:** `Docs/protocol/relay-hosted.md` §3 "Relay migrations … forward-only"; rubric §1 invariant 5.
- **Fix direction:** Mirror `internal/store.apply`: one `BEGIN IMMEDIATE` per migration on a
  dedicated connection, re-read the version inside it, and use no fixed whole-run timeout.
- **Related:** C02 Q2, C03 assumption (OpenAdmin migrates a live DB), C28-03, R43 M9

### T9-03 · Low · confirmed-read
- **Where:** `internal/relay/journal.go:38-48` (`Append`: a `Write`, with no `Sync`), `:51-62` (`ReadJournal`: the first decode error aborts), `:94-97` (`ReplayJournal` returns it)
- **What goes wrong:** The security journal is the only record that survives a DB loss, but:
  - its lines are not fsynced, while the change they record commits with `synchronous=FULL`;
  - a partial last line (a short write on a full disk, a crash mid-write, or a copy that was
    cut short) makes `ReadJournal` fail. `relay restore --replay-journal` then applies
    **nothing** and reports only a decode error.
- **Scenario:** C03-01 fills the disk. `unbind` commits and its journal append writes half a
  line and fails (C03-04 path). Weeks later the DB is lost. The operator's restore with
  `--replay-journal` stops at that line, so every later suspension, deletion and unbind in the
  journal is not replayed until someone repairs the file by hand. Accounts are off by default.
- **Spec:** `relay-hosted.md` §3 Restore ("re-applies every journal entry newer than the backup").
- **Fix direction:** `Sync` after each append (the file is small and the events are rare), and
  have `ReadJournal` skip a truncated final line (report it) instead of failing the whole replay.
- **Related:** C02-01, C03-04, C03-06, O-187

### T9-04 · Low · confirmed-read
- **Where:** `internal/daemon/mail.go:184` (`_ = rcv.Handle(mctx, e) // rejections are audited by the receiver`); non-rejection errors from `internal/mail/receiver.go:152-155` (`store`: begin, Apply, inbox and commit errors), `:189-191`, `:209`, `:233`
- **What goes wrong:** Only Opener rejections are audited. Every other `Handle` error is
  dropped without a log line. That includes a DB error, a non-bad-body Apply error, the
  `mail_inbox` collision (T9-01) and a commit failure. A mail that fails the same way on every
  delivery is invisible to the user and the operator: the sender retries for 7 days and each
  delivery costs a full Open and Apply.
- **Scenario:** A paired peer triggers C22-01 (the experience primary key), C24-01
  (`TooLargeError`) or T9-01. The victim's session or debate stays stuck. `agentnet` shows
  nothing, and `agentnetd.log` has no line to diagnose the cause. The same holds for a real
  disk or DB failure on the receive path.
- **Spec:** mail.md §Dedupe and inbox (errors are retried); rubric §2 ("wrong state the user
  sees and must repair by hand").
- **Fix direction:** Log non-rejection `Handle` errors (kind, peer and id only, no content)
  with a per-(from, id) limiter. After N identical failures, treat the mail as bad-body (mark
  it in `mail_seen` and ack it `unsupported`).
- **Related:** C22-01, C24-01, T9-01, O-057, O-059

### T9-05 · Low · confirmed-read
- **Where:** `internal/mail/outbox.go:394-411` (`finish` commits, then `OnFinal`), `internal/daemon/daemon.go:473-481` (`go wsStore.CheckPhase1FallbackForPeer(context.WithoutCancel(ctx), peer)`, not awaited), `internal/worksession/phase1.go:117-137` (the only caller; no start-up rescan)
- **What goes wrong:** The Phase 1 fallback runs only from the live `OnFinal` hook, in an
  unawaited goroutine, after the outbox row is already final (`failed/unsupported_kind`).
  - If the daemon stops or crashes in that window, the trigger is gone for good. This
    includes a normal `agentnet stop` while the goroutine runs: after `st.Close` it gets
    "database is closed", per C28's note.
  - `peerIsUnsupported` would still find the row, but nothing calls it again.
- **Scenario:** B works for a Phase 1 requester A. B's `ws.result` is acked `unsupported`
  just as B's daemon restarts, for example after an upgrade. B's worker session stays open,
  its request stays `accepted`, and A never receives `request.complete` or the result. It
  heals only if B sends another `ws.result`/`ws.cancel` to A. Needs a restart in a small window.
- **Spec:** work-session.md §Kinds, "Phase 1 requester" (B closes and completes when such a mail fails).
- **Fix direction:** Run `CheckPhase1FallbackForPeer` for every peer with open worker sessions
  at start (cheap: `peerIsUnsupported` is one indexed query), or record the trigger durably.
- **Related:** C21-04, C22-02 (same trigger), C07 lead L2

### T9-06 · Info · confirmed-test
- **Where:** `internal/store/store.go:540` (WAL, `secure_delete(1)`, no `journal_size_limit`); `Docs/protocol/work-session.md:328-340`
- **What goes wrong:** The doc says an old copy of deleted content can remain in `-wal`
  "until the next checkpoint runs". In fact it stays after a full checkpoint *and* after the
  WAL restarts. A checkpoint neither zeroes nor truncates the file, and the old frames stay
  until new frames overwrite them or the last connection closes. The daemon keeps its only
  connection open for its whole life.
- **Scenario:** A discarded or quarantined result is deleted. With the daemon still running, a
  same-user raw read of `dorylinae.db-wal` finds it after a checkpoint (test:
  `checkpoint busy=0 log=157 checkpointed=157; marker in main db: false; marker in -wal (646872 bytes): true`).
  This is the same boundary the doc names (a local, same-user read), so it is not a remote
  exposure.
- **Spec:** work-session.md §Deleted bytes (OD-P3-13).
- **Fix direction:** Correct the doc, or set `journal_size_limit=0` and run
  `wal_checkpoint(TRUNCATE)` after deletions of withheld content.
- **Related:** D30, O-171

### `pending*` maps (O-077)

`request`: `pendingApply`, `pendingMirror`, `pendingCancel`; `worksession`: `pendingResult`,
`pendingState`, `pendingCancel`; `team`: `pendingRoster`, `pendingJoin`, `pendingLeave`;
`debate`: `pending`; `daemon`: `pendingGrant`, `pendingGrantRevoke`, `activatedRoles`
(C13-03). All are keyed by `*mail.Opened`, so none is ever used stale. Two storage patterns:
- Stored only on Apply success: `worksession/mirror.go`, `debate/*`.
- Stored on early-return branches, which still precede the inbox insert: `request/*`,
  `worksession/receive.go`, `worksession/cancel.go`, `grant_kinds.go`.

Both patterns leak on the post-Apply failure of T9-01.

### Also checked and fine
- The ack is sent only after the commit, or after the rollback of a duplicate
  (`receiver.go:170-175`), and `storeBad` re-checks in its own transaction (`:255-282`).
- Every outbox `UPDATE` is guarded by a non-final state, and the `RowsAffected` gate stops a
  final row from being re-sealed (`outbox.go:396-397`, `:461-462`, `:571-579`).
- The approval `Confirm` failure paths roll back before anything else happens, and the
  `approved` mark is part of the Perform transaction (`approval/store.go:332-373`).
- Daemon DSN: `busy_timeout(5000)`, WAL, `foreign_keys(1)`, `secure_delete(1)`. The default
  `synchronous=FULL` makes commits durable in WAL. Relay DSN: `synchronous(FULL)`, set
  explicitly (`relay/queue.go:210`).
- The two `upsert` families (`ON CONFLICT … DO UPDATE`, `INSERT OR IGNORE/REPLACE`) are
  intended: `OpenSession` is idempotent by design (`worksession/hooks.go:36-41`), the
  tombstone `INSERT OR REPLACE` is bounded by `maxTombstones`, and `pair_used_codes` uses
  `RowsAffected`.
