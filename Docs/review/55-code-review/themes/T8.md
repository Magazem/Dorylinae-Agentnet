# T8: Local IPC authority (the prompt-injected local agent)

Reviewer: TH-T8 · model claude-opus-5-5 · elapsed 13 min (shell clock) · commit 6cc26a7
(worktree HEAD `ef03d14`; `git diff --stat 6cc26a7 HEAD -- cmd internal tools scripts` is empty)

## Summary

Critical 0 · High 1 · Medium 2 · Low 1 · Info 2

The code approval itself holds against a local agent. No IPC method or CLI form takes a code.
`Confirm` is reachable only from the window watcher and the terminal reader. Each of the seven
approval kinds runs Precondition and Perform in one transaction under `Store.mu`, and each is
bound to its object (grant id and pre-signed token, policy row, link intent, resolved scope,
constraint text, session `seq`). The daemon never reads or writes a file at a path an IPC caller
names without an approval: the CLI does the fetch, export and context-file I/O itself. No
security-relevant environment variable can be changed by an agent that can only run `agentnet`.

The weak point is what the human is shown. The window and notification are the only channel the
agent cannot reach, and for most kinds they do not identify the peer's key:
- **T8-01 (High).** The device-link fingerprint is compared against a value the IPC caller
  supplies and can read from `peers`. The window shows only the peer's self-chosen name. A
  prompt-injected agent can link this device to a twin-named peer.
- **T8-02 (Medium).** `release` and `accept_result` approvals name only a session id. No
  approval kind shows the fingerprint, although approval.md requires it.
- **T8-03 (Medium).** On a helper, the local agent can submit its own `ws.result` for an
  auto-accepted run session and beat the runner: a forged `pass` / `tests_passed` reaches the
  controller.
- **T8-04 (Low).** Team invites need no human, so an injected agent on a team owner can enrol a
  stranger whom every teammate's daemon then trusts as `team`.

The rest of the local-agent surface is already on record:
- C12-01: `approval_list` vs `grant_create` deadlock.
- C11-01 / C12-02: grant and policy summaries.
- C14-02: scope summary cut at 4096.
- C06-04: `peers_verify` without a human.
- C11-04: config-dir check bypass on Windows.
- O-136: `approval_open` nuisance.
- O-118: webhook SSRF gaps.
- O-070: webhook URL returned by `notify_get`.

## Questions (04-themes.md §T8)

1. **Method table.** See the inventory below: 70 methods, the same list as `00-index.md` §3.a
   (`grep -c 'srv.Handle("' internal/daemon/*.go` = 70 outside tests). Seven are
   approval-gated, matching approval.md §Object `kind` exactly:
   - `grant_create` (unless a policy matches)
   - `grant_policy_add`
   - `ws_release`
   - `ws_accept_result` with `human: true`
   - `device_link`
   - `device_scope_set`
   - `debate_constrain`

   Every other mutating method either narrows access or is Phase 1 behaviour with no gate in any
   spec: reject, revoke, unlink, clear, discard, request-changes, cancel, pairing, teams,
   requests, presence, notify.
2. **Chains of ungated methods that reach a gated effect.**
   - **Policy auto-issue.** `capability.Match` (`internal/capability/store.go:614-661`) needs an
     exact resolved path, the same branch, a scope within the policy's scope, the same
     sensitivity, `expires ≤ max`, and `now < until`. The issue path re-checks session, peer and
     D5 inside the tx (`grant.go:504`). No widening found; C11-08 (match outside the tx) is
     already recorded. `grant_policy_add` checks no D5 (`grant.go:866-958`), which is harmless
     because the match path re-checks it.
   - **`mail_submit` of daemon kinds.** Refused through `ownedKinds` (built from the
     receiver's own kind map) plus `reservedKindPrefixes` (`internal/daemon/outbox.go:25-55`).
     Every registered kind (`mail.go:242-290`, `device.go:317`) is covered. O-157 is the
     residual; C07-03 covers float rounding.
   - **`notify_set` to an attacker URL.** The spec expects an agent to be able to set it
     (notify.md:101-105). It exposes only what the agent can already read through
     `inbox_list`, and it persists after the agent's session ends. Remaining risks are
     O-118 (SSRF ranges) and O-070 (URL returned). `desktop:false` does not make approvals
     fail open: the approval notifier ignores the flag (T8-06).
   - **`team_invite` + `peers`.** Gives D5-passing `team` trust to a stranger on every
     teammate's daemon, with no human anywhere: **T8-04**. Pairing (`pair_new`/`pair_redeem`)
     is equally ungated, so peer trust is not a local-agent boundary. C06-04 (agent raises any
     peer to `fingerprint`) therefore stays Low. It does, however, make an introduced peer's
     rosters count (`team/kinds.go:79`) and clears `introduced_by` (`peers/store.go:307`).
   - **`device_link` intents.** The fingerprint the flow relies on comes from the caller:
     **T8-01**. A new `device_link` or `device_scope_set` rejects the older pending approval
     (`device.go:386-390`, `device_scope.go:213-215`). That only narrows (C14-04 is the race).
   - **`approval_open` spam.** O-136. Each `approval_open` is audited `approval.open`
     (`store.go:721-723`), and there is at most one window per approval (`store.go:742-746`).
     An agent can use up the 5-pending / 20-per-hour budget and so deny the human approvals
     for up to an hour. This is the spec's limit working as designed (no finding).
   - **Quarantined result through a side method.**
     - `ws_show`/`ws_list` get `Result == nil` for a quarantined requester row
       (`worksession/store.go:232-236`) and show only sizes (`daemon/session.go:185-203`).
     - An early `request.complete` drops `result`/`note` (`request/mirror.go:225`,
       `session_hooks.go:29`).
     - `mail_inbox.signed` is stored blank (work-session.md D18; C21 checked the receiver).
     - `ws_discard` and `ws_request_changes` delete the result (spec OD-P2-6 (c)).

     No other IPC method reads `work_sessions.result`. The one gap is which session gets
     released: **T8-02**.
   - **Forging the result of an own-device run from the helper side:** **T8-03**.
3. **Environment variables that change security behaviour.** The daemon reads the following at
   start only; no IPC method or settings row sets them:
   - `DORYLINAE_APPROVAL`, `DORYLINAE_DEBUG` (`daemon.go:265`, `mail.go:144`)
   - `DORYLINAE_KEYSTORE` (`identity.go:71`)
   - `DORYLINAE_HOME` (`paths.go:29`)
   - `DORYLINAE_AGENT_NAME` / `DORYLINAE_HARNESS` (card creation)
   - `DORYLINAE_RELAY_URL` / `DORYLINAE_ALLOW_INSECURE_RELAY` (`cmd/agentnetd`)

   The service definitions carry none of them except home and relay URL (`install.go:62-66`,
   `service/env.go:14-28`). Terminal mode needs a TTY on both stderr and stdin (`approval.go:44`),
   so a service manager cannot start it. An agent limited to `agentnet` can only:
   - call `shutdown`, after which the service restarts the daemon with the same environment;
   - set `DORYLINAE_HOME` or `DORYLINAE_DEBUG` for its own CLI process, which only redirects
     its own calls or shows `agentnet mail`.

   It cannot start `agentnetd` with a new environment. That route needs a raw shell, which
   approval.md "Boundary" puts out of scope. `agentnet doctor` loads the identity seed into
   the CLI process (`doctor.go:297-315`) but prints only the backend name.
4. **Can an agent learn or submit a code?** No. This confirms C12 Q1:
   - `approval.View` holds no code;
   - `approval_list/open/reject` take `{id}` only (`daemon/approval.go:117-151`);
   - `Confirm` is called only from `approval_terminal.go:83` and the window watcher
     (`store.go:821`);
   - the toast process inherits the daemon's environment plus the code
     (`notify/desktop.go:33-40`), not the caller's.

   C12-03 (toast `powershell.exe` found through `PATH`) is the only transport weakness.

## Findings

### T8-01 · High · confirmed-read
- **Where:**
  - `internal/daemon/device.go:367-376`: the fingerprint comes from IPC params and is compared
    there.
  - `internal/daemon/device.go:487-488`: the summary is the name only.
  - `internal/daemon/pairing.go:72-78` and `internal/peers/store.go:257-263`: `peers` returns
    every fingerprint.
  - `internal/notify/window.go:179-184`: the window shows tag, kind and summary, with no
    fingerprint.
- **What goes wrong:** device.md's binding control is "each human types the **other** device's
  fingerprint". But the fingerprint reaches the daemon as a `device_link` IPC parameter, which a
  local agent supplies after reading it from `peers`. The approval window and the notification,
  the only channel the agent cannot reach, show just the peer's self-chosen card name and the
  role. The human confirms a link without any way to tell which key it binds to. A peer whose
  name equals the user's other device (O-067; any trust level is allowed, device.md §Link flow)
  can therefore become this device's controller, or its helper.
- **Scenario:**
  1. A paired peer X names its card "desktop", the same name as the user's real desktop.
     X can be a team-introduced member (`trust=team`), or a key the agent itself paired
     through `pair_redeem`. `resolvePeer` then reports `ambiguous_peer` for the name
     (`ping.go:121-128`), so the agent uses X's key.
  2. The user asks the laptop agent to link the two devices. The agent has been
     prompt-injected, for example by X's own request brief. It calls
     `device_link {peer: <X key>, as: "helper", fingerprint: <fp(X) from peers>}`.
  3. The window reads "link this device as the helper of desktop? Confirm only if you started
     this on both devices." The human did start it, so they confirm.
  4. X sends its complementary `device.link` offer. The link activates, and the
     `device.linked` notification says "desktop is now linked as your controller".
  5. The next approval is `device_scope_set`. Its summary is again name-only
     ("let desktop run commands …", `device_scope.go:151`). Once it is confirmed, X runs the
     configured commands on the laptop and receives their output (≤ 32 KiB each).

  The helper's single controller slot is now X's, so the real desktop's link fails. That is
  the only hint.
- **Spec:**
  - `Docs/protocol/approval.md` §The approval window: "The dialog shows … the summary
    (action, resource, peer name and fingerprint, expiry)".
  - §Threat model: "The notification names the local action and the peer's name and
    fingerprint".
  - `Docs/protocol/device.md` §Link flow: "each human types the other device's fingerprint,
    which binds the link to the right keys".
  - §Threat model: "confirmed by fingerprint on both sides".
- **Fix direction:** Put `fp(peer)` (grouped 4-4-4-4-4) in every device-link and device-scope
  summary. For the link, consider asking the human to type the other device's fingerprint in
  the window itself rather than taking it from IPC.
- **Related:** C06-04 (same "IPC caller proves the fingerprint" flaw, for `peers_verify`),
  C11-01 and C12-02 (grant summaries: name only; C12-02 assumed the device kinds show a
  fingerprint, they do not), C14-02, O-067, D13. The consolidator may merge T8-01, T8-02,
  C11-01 and C12-02 into one root cause: approval summaries do not identify the peer's key.

### T8-02 · Medium · confirmed-read
- **Where:**
  - `internal/daemon/session.go:533` (release summary)
  - `internal/daemon/session.go:396` (accept_result summary)
  - also `internal/daemon/debate_constrain.go:60` and `device_scope.go:151` (name without
    fingerprint)
- **What goes wrong:** The `release` summary is "Release the quarantined result of session
  s-<32 hex>?" and the `accept_result` summary is "Accept the result for session s-…?". Neither
  names the peer or the request. No approval kind shows the fingerprint, which the spec lists as
  part of every summary. The human cannot tell which quarantined result they are releasing to
  the agent.
- **Scenario:**
  1. A has two quarantined sessions: S1 with a trusted colleague, whose result the human
     means to release, and S2 with a peer that read A's repo through a sensitive grant.
  2. The human asks the agent to release S1. The injected agent calls `ws_release {id: S2}`.
  3. The window shows only S2's opaque id. The human confirms, and S2's result, including
     any prompt-injection payload the quarantine exists to hold back
     (work-session.md §Quarantine), goes to the agent.

  The binding to `seq` (`session.go:551-557`) stops a swap of round, not of session.
- **Spec:** `Docs/protocol/approval.md` §The approval window (summary = action, resource,
  peer name and fingerprint, expiry); §Threat model row "A human approving without reading".
- **Fix direction:** Build both summaries with the cleaned peer name, fingerprint, request
  title (cleaned) and round, as the device kinds do for the name.
- **Related:** T8-01, C11-01, C12-02, O-129, O-147.

### T8-03 · Medium · confirmed-read
- **Where:**
  - `internal/daemon/session.go:286-361` (`ws_result`: worker role is the only check)
  - `internal/request/lifecycle.go:315-329` (`request_complete` → `CompleteShorthand`)
  - `internal/worksession/submit.go:45-60` (no guard for run sessions)
  - the runner uses the same entry point: `internal/daemon/device_run.go:442`, `:535`
- **What goes wrong:** An in-scope run request is auto-accepted on the helper and opens a
  normal worker session. The runner submits its outcome through the public
  `ws.SubmitResult`. Nothing marks the session as runner-owned, so the helper's local agent
  can do any of the following on it:
  - `agentnet result <session> --status pass --verification tests_passed`
  - `agentnet complete`
  - `ws_cancel`

  A applies the first result it receives (C21-01), so a result submitted while the run is
  queued or executing replaces the real one.
- **Scenario:**
  1. The controller's agent sends `request <helper> task --run test`.
  2. On the helper, a prompt-injected agent sees the new worker session in `ws_list`. That
     agent may have been injected by the repository it works in, and device.md says "No agent
     on the desktop is needed", not that none exists.
  3. The agent calls `ws_result` with `status: pass`, `summary: "test: exit 0 in 1.2s"` and
     `verification: tests_passed`.
  4. The controller's `wait` returns that result, and its agent or human accepts a green
     test run that never happened. device.md promises that the runner sets `status` from the
     exit code and `verification = none`.
- **Spec:** `Docs/protocol/device.md` §Running: "The runner … submits `ws.result` with
  `status = pass` if the exit code is 0 … and `verification = none`"; line 15 "No agent on the
  desktop is needed".
- **Fix direction:** Mark run sessions (for example from `device.runs`, or a session flag set
  by `RouteTx`). Refuse `ws_result`, `request_complete` and worker `ws_cancel` on them over
  IPC.
- **Related:** C21-01 (B's later result overwrites), C14-03.

### T8-04 · Low · confirmed-read
- **Where:**
  - `internal/daemon/team.go:133-186` (`team_invite`/`team_join`, no approval)
  - `internal/team/kinds.go:65-100` (roster from a `code`/`fingerprint` owner is honoured by
    each member)
  - `internal/daemon/request.go:166-172,192` (D5 passes `team`)
- **What goes wrong:** Inviting into an owned team is completed entirely through IPC, and the
  invite code is returned to the caller. Every other member's daemon then introduces the new
  key with `trust=team`, gives it their presence and the roster (cards, mailbox keys), and
  accepts its requests past D5 and the team check. No human on any of those machines is
  involved. The spec gives team membership no gate and does not discuss an agent-driven
  invite. The effect lands on third parties who trust the owner's **daemon**, not the owner's
  agent.
- **Scenario:**
  1. The owner's agent is prompt-injected.
  2. It calls `team_invite {team: T}` and passes the code out in its next request or answer.
  3. Stranger X redeems the code.
  4. X is now a member on every teammate's machine. It receives their presence heartbeats,
     can send them requests and debates, and appears as a team peer.

  `team.invite` is audited only at `pair.complete` (O-090).
- **Spec:** none (team.md §Invite has no threat model row for a local agent; approval.md
  lists no team kind).
- **Fix direction:** Owner decision. Either document that team membership is agent-grantable,
  or make `team_invite` (owner side) an approval kind.
- **Related:** O-065, O-066, O-090, C06-04, D5.

### T8-05 · Info · suspected
- **Where:** `internal/ipc/ipc.go:138-189` (`serveConn`/`dispatch`, no `recover`);
  `git grep "recover()" -- cmd internal` finds none outside tests
- **What goes wrong:** Any handler panic reachable from params ends the whole daemon. After a
  restart every pending approval is expired (`approval.md` §Object). No reachable panic was
  found in the sampled paths:
  - no unchecked type assertion on IPC input in `internal/daemon`;
  - `argv[0]` is guarded at `device/scope.go:256`;
  - index uses in `grant.go:310`, `request.go:323` and `team.go:454` are guarded.
- **Scenario:** Not constructed; this is defence in depth against a local agent that can call
  any method in a loop.
- **Spec:** none.
- **Fix direction:** Add `recover` in `dispatch` that returns `internal error` and logs the
  method only.
- **Related:** C16 lead (`ipc.go:176`), C12-01 (the other way an agent hangs the daemon).

### T8-06 · Info · confirmed-read
- **Where:**
  - `internal/daemon/notify.go:155-158` (`desktop:false` stored)
  - `internal/notify/trigger.go:147` (the only reader of the flag)
  - `internal/approval/store.go:143`
  - `internal/daemon/outbox.go:76` and `cmd/agentnet/main.go:119,132`
- **What goes wrong:** Two cases of doc drift, neither exploitable:
  1. approval.md §Headless says that with the desktop notifier **disabled**, approvals are
     `approval_unavailable`. In fact the approval notification ignores the flag, so an agent
     that runs `notify --desktop off` does not change approvals. This is the safe direction.
  2. `mail_submit` is always registered and not audited, while the CLI hides `agentnet mail`
     unless the caller sets `DORYLINAE_DEBUG=1` in its own environment. The CLI gate is
     cosmetic, and the daemon's kind allow-list is the real control.
- **Scenario:** none.
- **Spec:** `Docs/protocol/approval.md` §Headless machines, first paragraph.
- **Fix direction:** Align the spec text, or state that approvals ignore `notify.desktop`.
- **Related:** O-107.
