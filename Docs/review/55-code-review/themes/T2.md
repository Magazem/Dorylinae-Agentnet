# T2: Concurrency, goroutine lifecycle, shutdown, locking

Reviewer: TH-T2 · model claude-opus-5-5 · elapsed ~65 min (working time; the run was paused once by a usage limit) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 0 | 3 | 1 |

Verdict: the concurrency design is disciplined. Every package that shares the daemon's single
SQLite connection knows it. `SubmitTx` reads peers through the tx (`TxOutboxPeers`), audits
run after commit or through `AppendTx`, and hooks that may run inside a tx (`kick`) are
asynchronous by design. Lock orders are documented and respected (session `sendMu → mu`, relay
`s.mu → a.mu`, relay `c.mu → q.mu`). Every subsystem goroutine with a done channel is awaited in
`daemon.Run`.

**The only lock-versus-connection cycle in the repository is C12-01** (`approval.Store.List`).
I checked exhaustively: every `rows.Next()` loop and every `Append` call that could run while a
tx is open. I found no second instance.

New defects are all at the shutdown edges and in a fatal-error path:
- **T2-01:** at graceful shutdown the mail worker's context is cancelled before the relay stops,
  so a mail committed in that window loses its `After` effects for good.
- **T2-02:** the relay's `Close` closes the queue DB without waiting for the connection read
  loops, contrary to relay-hosted.md §3.
- **T2-03:** the IPC `Serve` loop treats any `Accept` error as fatal, so running out of file
  descriptors stops the whole daemon.
- **T2-04 (Info):** unawaited background goroutines. The concrete consequences are small.

No `-race` run was needed: no data race was suspected strongly enough to ask for one. See the
Notes for the one candidate I cleared by reading.

   No other cycle exists. Callbacks under a lock: `approval` Precondition/Perform run under

2. **Goroutine inventory.** See the table below. Everything started by `daemon.Run` with a done
   channel is awaited in its defers. The unawaited ones are listed in T2-04. The relay's
   `sweepLoop` and `watchAccounts` are awaited by `Close`. Connection read loops are not
   (T2-02).
3. **Shutdown order of `daemon.Run`.** The defers run LIFO (`internal/daemon/daemon.go:276-583`):
   1. stop the rotation job (no-relay path, not awaited);
   2. presence goodbye (≤ 1 s, relay still up);
   3. presence stop, awaited;
   4. outbox stop, awaited;
   5. `stopRelay` (the relay client is cancelled and awaited, then `stopMail`);
   6. fetch client, then fetch server (O-144 bound);
   7. debate sweep, helper, terminal reader, approvals, webhook (each awaited);
   8. `sessions.Close`, then `pairs.Close`;
   9. the `daemon.stop` audit on a fresh 5 s context;
   10. `st.Close`.

   Before any defer runs, `ipc.Serve` returns only after every IPC connection goroutine has
   finished (`internal/ipc/ipc.go:118-121`). Nothing awaited uses the DB after `st.Close`. The
   gap is that `ctx` (the parent of the mail worker, every IPC handler and the helper) is
   cancelled **first**, while the relay deliberately stays up for the goodbye. That makes
   T2-01. There is no deadlock with a slow relay: every relay write is capped at 10 s
   (`internal/relayclient/relayclient.go:195-207`).

   Relay: `Close` stops the sweep and watcher, waits ≤ 10 s for drains, starts background close
   handshakes and closes the DB at once (T2-02).
4. **DB calls with a tx open on the single connection; tx across network I/O.**
   - Every `Kind.Apply`, `…Tx` helper and approval action reads and writes through `tx`.
     `Outbox.SubmitTx` resolves the peer and its mailbox key through the tx
     (`internal/mail/outbox.go:182-200`, `internal/daemon/mail.go:37-60`). Its only non-DB work
     is the keystore load and sealing.
   - Every `audit.Log.Append` (which takes `db.Conn`) in a function that holds or receives a tx
     runs after `Commit`/`Rollback` or is returned as an `after` closure. I checked:
     `worksession/submit.go:86-96`, `request/session_hooks.go:142-146`, `daemon/grant.go:515-547`,

     `worksession/cancel.go:75`, `request/cancel.go:104,171`, `mailbox.go:377` (after `Commit`)
     and `approval/store.go:386`. This closes C26's non-exhaustive lead.
   - Every `rows.Next()` loop closes its cursor before any further DB call or lock, except

## Findings

### T2-01 · Low · confirmed-read
- **Where:** `internal/daemon/mail.go:168-187` (`mctx` is derived from the daemon `ctx`),
  `internal/daemon/daemon.go:572-576,794-805` (the relay deliberately outlives `ctx`);
  effect at `internal/mail/receiver.go:153-164` (`Append`, `After`, `ack` with the cancelled `ctx`)
- **What goes wrong:** Graceful shutdown cancels `ctx` first. That also cancels the mail
  worker's `mctx`, while the relay connection is kept up for the goodbye, presence, outbox and
  relay stop.
  - A `Handle` that has just committed its dedupe tx then runs `mail.in`'s `Append`, the kind's
    `After` and the ack with a cancelled context, and all of them fail.
  - The sender never gets the ack, so it resends. The resend is a duplicate, so `After` never
    runs again for that mail.
  - Envelopes the relay hands up during the teardown are put in the worker's queue and
    discarded unprocessed. They were already acked to the relay (as in O-057), and the
    sender's outbox resends them later.
- **Scenario:**
  1. A paired peer's `request` arrives while the user runs `agentnet stop`, or a service stop
     or logoff. This is normal use and needs no attacker.
  2. The row is stored `pending`, but `request.in`, the "received" notification
     (`internal/request/receive.go:421-437`), the `mail.in` audit and the auto-accept/helper
     `After` closures are lost.
  3. After the restart the resend is acked as a duplicate. The user was never notified, and
     the audit trail has no `request.in` for a stored request.

  The same applies to every kind's `After` (team, worksession, debate, grant audits and
  notifications). Durable state is intact, because every state change is in `Apply`. This
  turns C07-04's "crash between commit and After" into a routine trigger. It is Low because
  the window is one envelope wide and only audit rows and notifications are lost.
- **Spec:** `Docs/protocol/request.md` §Receiving, final paragraph (audit "once, after a
  successful commit"); `audit.md` (every received request is audited).
- **Fix direction:** Give the mail worker its own context that is cancelled in `stopMail`,
  after the relay client stops, and run `After` and the ack with a context detached from
  shutdown (`WithoutCancel` plus a short timeout).
- **Related:** C07-04, O-057, O-077, C28 (Notes on shutdown order).

### T2-02 · Low · confirmed-read
- **Where:** `internal/relay/relay.go:410-441` (`Close`: drains ≤ 10 s, then background
  `drainClose` and at once `s.q.close()`), `relay.go:643-680` (read loops keep running), effects
  at `relay.go:798-812` (`enqueue` → `internal`), `pairing.go:157-160` (`ack` error only logged),
  `accounts.go` (`touchAccountKey`, `unbind`)
- **What goes wrong:** relay-hosted.md §3 says `Close` "waits for connection goroutines …
  before closing the database". The code waits only for queue drains. Every connection's read
  loop keeps routing frames after `q.close()` until its close handshake ends (up to ~10 s per
  connection). During that window:
  - every `add` for an offline recipient fails ("database is closed") and the sender gets
    `internal`;
  - every `ack` fails silently, so the rows are redelivered after the restart;
  - account ops (`unbind`, bind) and `touchAccountKey` fail with `internal`.
- **Scenario:** The operator runs `systemctl restart agentnet-relay` under load.
  - Daemons that send mail to offline peers in the last seconds get `internal`. They requeue
    (`internal/mail/outbox.go:513-523`) and resend on reconnect, so there is no loss.
  - Recipients that acked frames just before get them again, and dedupe absorbs them.
  - A user whose `agentnet logout` (`unbind`) lands in the window is told "could not unbind"
    and must repeat it.

  No durable promise breaks, which is why it is Low. The spec's stated ordering is not what
  the code does, and the `ack` loss is invisible.
- **Spec:** `Docs/protocol/relay-hosted.md` §3 "Restart without loss": "`Close` waits for
  connection goroutines (review 05 L6) before closing the database".
- **Fix direction:** Track read loops in a WaitGroup (Add under `s.mu` while not `closing`, as
  `startDrain` does), stop reading new frames once `closing`, and wait with a bound before
  `q.close()`.
- **Related:** C02 (unchecked assumption and lead `relay.go:439`), O-001, R05 L6 (listed as
  closed in 02 §D, but only the drain half was built).

### T2-03 · Low · confirmed-read
- **Where:** `internal/ipc/ipc.go:115-123` (`Serve` returns on any `Accept` error other than
  `net.ErrClosed`), `internal/daemon/daemon.go:672` (`return srv.Serve(ctx, ln)`, then every
  defer and `st.Close`)
- **What goes wrong:** `Serve` does not retry a temporary `Accept` failure. `EMFILE`/`ENFILE`
  (and `ECONNABORTED` on some Unix kernels) end `Serve`, `RunWithOptions` returns, and the whole
  daemon shuts down. `net/http` backs off and retries in the same situation.
- **Scenario:**
  - The daemon's file descriptors run out. C27-01 is a peer-driven source: each webhook
    delivery leaves an idle TLS connection open, and a paired peer's request stream grows them
    against a receiver that keeps connections alive.
  - A local agent opening IPC connections without limit (each one is a goroutine and an fd;
    C16 Q1 noted there is no cap) is another source.
  - The next CLI or agent connection's `Accept` fails, the daemon exits, and mail, sessions,
    grants and approvals are all down until the service manager restarts it.

  It is Low because Go raises `RLIMIT_NOFILE` to the hard limit at start on Unix, which makes
  exhaustion slow, and because on Windows the pipe listener has no fd limit. This finding
  changes the impact of an fd leak from degradation to daemon exit.
- **Spec:** none directly. `Docs/protocol/ipc.md` §Endpoint (the daemon serves until
  shutdown).
- **Fix direction:** Retry temporary `Accept` errors with backoff, as `net/http.Server.Serve`
  does, and optionally cap concurrent IPC connections.
- **Related:** C27-01, C16 (C16-leads-R5 item 3, "Accept errors (EMFILE) end Serve").

### T2-04 · Info · confirmed-read
- **Where:** `internal/daemon/device_run.go:171-173` (`kick` → `go r.sweep(context.Background())`),
  `device_run.go:352-357` → `:372-381` (`take` commits the drop, then `cancel` submits `ws.cancel`);
  `internal/daemon/mail.go:171-175` (`RunPrune`, `rot.Run`, `go pusher.PushAll(mctx, …)`,
  not awaited by `stopMail`); `internal/daemon/daemon.go:377,480,582,768`
- **What goes wrong:** several background goroutines are neither tied to a stop function nor
  awaited, so they can run after `st.Close` or with a cancelled context. C28 already lists
  them, as a note. Two of them have a lasting effect:
  - **(a)** A kick-started sweep that has committed "queued run dropped" and then fails
    `SubmitCancel` (DB closed at shutdown, or any submit error) never sends the `ws.cancel`.
    `recoverAfterRestart` sees neither the job nor the session, so the controller's session
    stays open until someone cancels it by hand.
  - **(b)** In the relay path, a rotation that commits a new key during shutdown runs its
    `OnRotate` push with the cancelled `mctx`. No `keys` mail is ever submitted for that key,
    and peers learn it only through key-miss recovery (one miss per peer).
- **Scenario:** each needs shutdown to coincide with a sweep dropping a run, or with the hourly
  rotation. That is a very small window, and there is no attacker.
- **Spec:** `Docs/protocol/device.md` §Limits (a dropped run gets `ws.cancel`); `mail.md`
  §Lifecycle (a new key is pushed).
- **Fix direction:** give these goroutines a daemon-scoped WaitGroup (or run `kick` sweeps on
  the helper loop), and make the rotation push durable (`Submit` inside the hook before
  returning, or re-push on start when the current key is newer than the last push).
- **Related:** C28 Notes, C14-03, C05 (rotation ordering).

## Checked and fine

- `SubmitTx` never touches the pool (`TxOutboxPeers`, `outbox.go:182-200`); `Submit` is never
  called inside a tx in the kinds I read (team `afterRoster` submits after commit, `kinds.go:222-259`).
- `Announcement()`/`MailboxKey()` (DB under `k.mu`) are never called while a tx is open.
  `team.rosterSnapshot` calls it before its tx on purpose (`team/store.go:544-551`).
- The relay's `startDrain` does `drainWG.Add` under `s.mu` and refuses once `closing`
  (`relay.go:859-870`), so `Add` never races `Wait`.
- The relay has no DB call under `s.mu` (`Stats` releases it first, `relay.go:258-262`), and
  every queue op is bounded by `queueOpTimeout`.
- Concurrent `take` from the helper loop and a kick sweep are serialised by the single
