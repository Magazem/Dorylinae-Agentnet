# T7: Error handling: fail-open versus fail-closed

Reviewer: TH-T7 · model claude-opus-5-5 · elapsed ~240 min wall clock (includes a usage-limit pause; about 90 min of active work) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 0 | 1 | 2 |

Verdict: the authorization core fails closed. I traced every allow/deny decision point listed
below: paired checks, D5, quarantine, the sensitive-grant/debate rule, capability Verify and
the fetch recheck, the approval gate (lock, attempts, expiry, Precondition), device link,
scope and run checks, relay accounts, and relay-client loopback/auth-version. Each one refuses,
or returns a retryable error, on a DB read error, a parse error or a nil callback. Every nil
security hook is either wired before the relay starts (`internal/daemon/daemon.go:529-535` vs
`:558`) or refuses when it is nil (`capability/fetch.go:554`, `daemon/session.go:390,523`).
Mail kinds consistently treat only `sql.ErrNoRows` as "orphan" and return any other error, so
the mail is retried and not acked.

The chunk reviews already found the fail-open cases that remain. I cross-checked them and did
not re-report them:
- C17-02: D5 on receive reads a missing peer row as "not relay". It is the **only** D5 site
  that does this: the three other D5 sites refuse a missing row.
- C09-02: the holder's grant apply maps any `GetTx` error to "orphan". It is the only mail
  Apply that folds a DB error into "not found".
- C03-02 / C03-03: the relay accounts cache stays stale after a failed reload.
- C05-01: the keystore reports "unavailable" as "not found".
- C12-05: the daily wrong-code cap is skipped when its write fails.
- C10-03: the fetch audit error is ignored.
- C08-02: an error flips the presence mode to `invisible`, which fails closed.
- O-027: the free-disk check fails open when `Statfs` fails.

One new Low: the helper runner's revocation sweep only logs a failed sweep. A command whose
link or scope was revoked therefore keeps running while the DB errors persist, up to its
`timeout_s` (T7-01). The two Info findings are the inconsistent handling of post-commit audit
errors (T7-02) and one path where the approval expiry timer hits a DB error (T7-03).

2. **Swallowed errors that break a documented guarantee.**
   - I counted 64 `_ = …Append(…)` audit calls in production code (26 files). All of them run
     after a commit (the R27 C1 rule), so none can undo an action. No spec requires an
     action to fail when its audit append fails. Only `AppendTx` inside a transaction does
     that (audit.md:64). Handling is inconsistent (T7-02).
   - `request_submit` is the exception: it fails after the commit (O-095).
   - Journal before or after the commit on the relay: C03-04.
   - Outbox submit after telling the user "done": `team_leave` (C20-03) and `JoinTag`
     (O-088) are known. `Broadcast` (`team/store.go:513-532`) joins per-recipient submit
     errors and relies on resync (O-081). `peers_remove` (`daemon/trust.go:90-118`) is ordered
     so that a retry is safe.
3. **`switch` defaults over peer-controlled enums.** I used an AST walk to list every `switch`
   with a `default:` in `internal/` (110 of them; the tool is described in Commands run).
   - Every switch over a peer-controlled value (op, state, verification, reason, kind, action,
     resource kind, role, result status, urgency, member names) defaults to `badBody`,
     `malformed`, `unknown_grant`, `dismiss` or `unknown`. Examples: `capability/fetch.go:409,589`,
     `verify.go:131`, `token.go:200,215`, `worksession/mirror.go:82,117`, `request/mirror.go:137`,
     `grant_kinds.go:158`, `debate/decode.go:34`, `relay/pairing.go:161`, `relay/auth.go:73`.
   - The permissive defaults are over local or already-validated values:
     - `presence/sender.go:258` treats mode `""` as visible, and a stored mode is written
       only locally;
     - `relay/accounts.go:139,297` return `bound` or `true` only after the suspended and
       unbound cases;
     - `device/device.go:290` counts every non-helper role as a controller, which only makes
       the hierarchy stricter;
     - `device/perm_windows.go:56,132` give the unknown role the strictest mask, and an
       unknown ACE type is ignored because it cannot grant access (C13).
   - I found no R25-L2-style "unknown role treated as holder".
4. **Partial failure.** Every multi-step operation that the approval gate or IPC commits (grant
   issue, device link and scope, release, constraint, device unlink, grant revoke) writes
   its state, mail and audit in one transaction. The known exceptions are C20-03, O-088,
   O-111, O-116, C03-04 and C08-03. The new partial-failure case is on the runner side
   (T7-01).

## Findings

### T7-01 · Low · confirmed-read
- **Where:** `internal/daemon/device_run.go:176-183` (`sweep` only logs a `take` error), `:304-316` (`take` returns before `stopRunning` on any `loadRunState`/`valid` error), `:563-586` (`watch` retries every `runWatchEvery` = 1 min, `:37`)
- **What goes wrong:** A revocation stops the running command only through
  `kick → sweep → take → stopRunning`, and `take` decides to stop only after it has read the run
  state and re-run `CheckRunTx` in a new transaction. If any of those steps errors, the sweep
  logs a Warn and the process keeps running. `watch` retries once a minute. While the error
  persists (for example a corrupt `device.runs` settings row that `loadRunState` cannot
  decode, a full disk that makes `BeginTx` fail, or a busy DB), a command whose link was
  unlinked or whose scope was cleared keeps running until its own `timeout_s` (up to 3600 s).
- **Scenario:** The helper's human runs `agentnet device unlink` (or `device scope --clear`)
  because the controller is compromised. The unlink transaction commits and calls
  `runner.kick()`. The sweep's `take` then fails, for instance with `SQLITE_BUSY` or
  `SQLITE_FULL` while the disk is full, or because of an undecodable run-state row. The
  running command, which the controller chose from the old scope, keeps executing with the
  helper user's rights and its output is still submitted. device.md §Running says it "is
  **killed at once**". No attacker can cause the DB error, so the impact is bounded by
  `timeout_s`. Rated Low (rubric: fail-open on a rare error; it touches revocation timing but
  not what may run).
- **Spec:** `Docs/protocol/device.md` §Running: "A run already executing when the link is revoked is killed at once with its whole process tree"; §Scope: "a running one is killed".
- **Fix direction:** Stop the current run whenever its session's link or scope can no longer
  be confirmed. That means stopping on a `take`/`valid` error too, not only on a clean "no
  longer allowed". Alternatively, have the unlink/clear path call `stopRunning` for that
  peer's run directly after its commit.
- **Related:** C14-03 (a `finish` failure wedges the queue), O-159 (kill gaps), rubric invariant 3.

### T7-02 · Info · confirmed-read
- **Where:** 64 post-commit `_ = …Append(…)` sites. Examples: `approval/store.go:374`,
  `daemon/grant.go:448,537-541`, `daemon/fetch.go:48`, `worksession/transitions.go` (8 sites),
  `request/receive.go` (4 sites). Contrast `daemon/request.go` `request_submit` (O-095) and
  `presence/sender.go:374-378` (C08-03), which return the audit error after committing.
- **What goes wrong:** No spec says whether an action must fail when its after-commit audit
  row cannot be written. Most handlers ignore the error. A few return it after the action
  has already committed. The first choice leaves actions with no audit trace, including
  approvals (`approval.approve`), grant issue (`grant.create`, `grant.auto`) and fetch
  serving (C10-03). The second tells the caller the action failed when it did not, which
  produces the duplicate-on-retry (O-095) and the misleading CLI error (C08-03).
- **Scenario:** A DB that is busy or full at the moment of the append. With the ignoring
  handlers, the grantor's audit (the stated exfiltration mitigation) misses the auto-issued
  grant. With the returning handlers, the user retries an action that already happened.
- **Spec:** `Docs/protocol/audit.md:64` covers only `AppendTx`. The owner should decide.
- **Fix direction:** Pick one rule and document it in audit.md. Suggestion: after a commit,
  log the failure and still report success; inside a transaction, use `AppendTx` for the
  security-relevant actions (approve, grant issue, fetch).
- **Related:** O-095, C10-03, C08-03, C22-05, invariant 5.

### T7-03 · Info · confirmed-read
- **Where:** `internal/approval/store.go:524-557` (`expireNow`)
- **What goes wrong:** The per-approval timer deletes the entry from `s.pending` before its
  DB `UPDATE … state='expired'`. If that update fails, it returns without running
  `OnReject`, without the audit and without removing the notification. The approval can no
  longer be confirmed, because the in-memory code is gone, so this fails closed. But its row
  stays `pending` until `ExpireStale` runs at the next start. The subject also stays
  `pending_approval`: a grant row, a device link intent, or a pending scope in the
  `scopeApprovals` map. That is the O-132 end state, reached through a different path.
- **Scenario:** A DB write error at the 5-minute mark of an approval. `approve --list` keeps
  showing it as pending, and a stale Windows toast stays.
- **Spec:** approval.md §Object (expiry rejects the approval and runs the kind's reject path).
- **Fix direction:** Run `OnReject` (and the notification removal) even when the row update
  fails, or keep the entry and retry the update.
- **Related:** O-132, O-141.

## Assumptions and contracts

- The mail receiver does not ack a mail that `Open` rejected, so a transient `IsPaired` error
  leads to redelivery, not loss (`mail/receiver.go:120-127`). **Checked** (no ack on the
  reject path). The relay-level delivery ack is O-057's domain; the sender's outbox resends
  until the app ack in any case.
- Every `mail.Kind.Apply` returns `ErrBadBody` only for incurable input, and returns a plain
  error on a DB failure, so the mail is retried (O-059). **Checked** for work-session result,
  state and cancel (`worksession/store.go:144-154`, orphan only on `ErrNoRows`), request
  mirror (`request/mirror.go:289-296`), debate slot 1 (`debate/apply.go:159-166`) and device
  link/unlink (`daemon/device.go:219-300`). The exception is holder `grant` (C09-02).
- `ws.Quarantine` and `debate.PeerQuarantine` are non-nil in production. A nil value means
  "no quarantine". **Checked:** `daemon.go:529` (`wireQuarantine`) and `:535`, both before
  `startRelay` at `:558`.
- `approval.Store` runs Precondition and Perform in one transaction under `s.mu`, and a
  Precondition error never runs Perform. **Checked** (`approval/store.go:320-360`).
- The device runner's `kick()` is called after every revocation commit (unlink, clear, peer
  removal, remote unlink). **Checked** at `daemon/device.go:558-568`, `:329-339`,
  `device_scope.go:305-307` and `daemon.go:504-509`. Whether the kick succeeds is T7-01.
- The relay accounts cache is the only source of the relay's routing decisions. **Checked**;
  its staleness is C03-02/03.

## Checked and fine

- D5 at every send site and in the grant/device Preconditions treats a missing peer row as
  "not paired" and refuses (`grant.go:740-771`, `device.go:411-420`). C17-02 is the only
  exception.
- Session frames: a peer-lookup error drops the frame silently (`session/session.go:534-537`).
- The fetch server refuses on a nil `SessionOpen`, a store error, a wrong direction, peer or
  token, or any state other than `active` (`capability/fetch.go:551-592`). `recheck` fails
  closed before every fragment.
- The policy auto-issue path re-checks steps 1-2 and the debate rule inside its transaction.
  A `Match` error aborts, and an unparsable `until` never matches (`grant.go:488-525`,
  `capability/store.go:614-665`).
- Approval `Create` fails on a `Locked` read error, on a sweep error and on a count error.
  `confirm` fails on expiry and attempt read errors before any action runs.
- The Windows/Linux window answer parsing defaults to dismiss (`notify/window_parse.go:21`,
  `window_linux.go:147`).
- The webhook dialer refuses on a resolve error and when no allowed candidate exists
  (`notify/dial.go:161-183`).
- Pairing single-use checks fail the pairing on any DB error (`peers/store.go:203-226`).
- Nothing in production calls `recover()`, so no panic is swallowed into a permissive
  state. The panic surface of peer input is the C16 lead. I sampled type assertions on
  peer bodies: all use the comma-ok form.
- `peers_remove` is ordered so a partial failure can be retried (`daemon/trust.go:90-118`).
- O-027, O-076 and O-081 are still as recorded. C03-02/03, C05-01, C08-02, C09-02, C10-03,
  C12-05 and C17-02 were re-traced and hold as their chunks describe them. This theme adds
  no escalation.

## Leads for other chunks

- `internal/approval/settings.go:43-45`: `wrongCodes` silently skips unparsable timestamps, so
  a tampered row lowers the lock count. Only a same-user DB edit can cause this (out of
  scope), noted for consistency with C12-05.
- `internal/relay/pairing.go:224-226`: `pairNew` re-reads the account binding after
  `accountAllows`. A binding removed between the two leaves `account = ""` and skips the
  per-account limiter for that one frame (tiny window; C02/C03).
- `internal/daemon/device.go:389`, `device_scope.go:215`: a failed `Reject` of the superseded
  approval is ignored. The old approval's Precondition still refuses, so it fails closed, but
  its window stays open (UX; C13/C14).

## Notes

  one-line fix (`ErrNoRows` → unverified or retryable) would make all D5 sites agree.
- C09-02 differs from every other Apply in folding a DB error into "not found". The same
  one-line pattern fixes it.
