# T11: Untrusted text reaching a human (terminal, notifications, windows, Markdown, webhooks)

Reviewer: TH-T11 · model claude-opus-5-5 · elapsed ~12 min by the shell clock (10:26 → 10:38) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 4 | 0 |

The OS-facing sinks are careful. Toasts, webhooks, the Windows and macOS windows and the
Decision Markdown have no injection into script source, argv, XML or Markdown. Every chunk
finding in this area also holds (list below). The theme pass found one new gap between two
layers. On Linux, zenity runs the approval-window `--text` through `g_strcompress` *after* our
`Clean` and `escapeMarkup`. The daemon never escapes backslashes on that path, although it does
for the same GLib behaviour in notify-send (review 21 M1). A peer card name such as `Bob\0`
therefore cuts the window text short. The debate-constraint window then hides the constraint the
human is approving (Medium, suspected: I could not run zenity here). The other findings concern
sanitiser strength. The digit-run guard against decoy codes is bypassed by invisible characters.
`--json` leaves C1 and bidi characters raw. `termSafe`, which O-100 and most chunk findings name
as the fix, is weaker than `decision.Visible`. And one root cause (card names allow `Cf`, the
CLI never escapes them) reaches more sites than any single chunk reported.

## Questions

The T11 section asks for a sink table, sinks weaker than their siblings, fields that bypass the
sanitiser, and places where sanitising changes the meaning. Answers:

1. **Sink table:** see "Inventory" below (in place of "Checked and fine", per 04 §4).
2. **Weaker than siblings:** there are four sanitisers with four different character sets:
   - `notify.Clean` (C0, C1, 11 listed bidi controls, U+2028/9; `internal/notify/notify.go:13-40`);
   - `termSafe` (`!unicode.IsPrint` → `QuoteToGraphic`; `cmd/agentnet/fetch.go:267`);
   - `device.DisplayQuote` (non-graphic and `Cf`; `internal/device/scope.go:360`);
   - `decision.Visible` (C0, C1, `Cf`, non-graphic, VS, default-ignorable, Zs, U+2800;
     `internal/decision/visible.go:20`).

   `Clean` is the weakest, and it is the one used for approval text (T11-02). `termSafe` misses the
   R46 H1 set (T11-04). The Linux zenity path decodes escapes after sanitising, so there it is
   weaker than no sanitiser at all (T11-01).
3. **Fields that bypass sanitising:**
   - the peer card name in grant summaries (C12-02);
   - card names in every CLI table (C05-03 root cause; T11-05 lists the sites no chunk
     reported);
   - relay `last_error` (C04-01/C28-01) and the relay pairing error (C06-02);
   - the `decision verify` reason (C25-01);
   - C1, bidi and `Cf` in request and session text (O-100, C22-04);
   - every `--json` output (T11-03).
4. **Sanitising that changes meaning:**
   - `stripLongDigits` merges a run of digits into "…". So two peers "laptop 2024-05-30" and
     "laptop 2024-06-01" both show as "laptop …" in a device-link summary, which carries no
     fingerprint. This adds nothing beyond O-067 (a peer can already copy a name), so it is a note.
   - The zenity path turns `\0`, `\n`, `\NNN` in *sanitised* text into NUL, a newline or any
     byte (T11-01).
   - On the same path, `DisplayQuote`'s `‮` escape shows as `u202e`, and `_` becomes a
     mnemonic, so the window and the toast show different constraint text (fidelity only, noted
     in T11-01).
   - Decoy codes: T11-02.

## Findings

### T11-01 · Medium · suspected
- **Where:** `internal/notify/window_linux.go:128-130` (`escapeArg`: `escapeMarkup` only), `:186-190` (zenity `--text`); text built at `internal/daemon/debate_constrain.go:57-60,70` and `internal/daemon/device_scope.go:149-151`, `grant.go:616,960`, `device.go:488`; `internal/notify/window.go:36-42` (`Clean` keeps `\`)
- **What goes wrong:** zenity passes `--text` through GLib's `g_strcompress`, which decodes `\0`–`\377`, `\n`, `\r`, `\b` and others. The daemon escapes `& < >` but never doubles backslashes on this path. It does double them for notify-send (`desktop_linux.go:34-41`, review 21 M1). A peer-chosen card name can therefore add a NUL, which ends the C string, as well as newlines, bidi bytes or invalid UTF-8 to the approval window. All of this happens after `Clean`.
- **Scenario:** Linux desktop, zenity installed (the spec's first choice).
  1. A hostile paired peer names its card `Bob\0` (5 characters). `checkText` refuses only `IsControl` (`agentcard.go:117`), and `stripLongDigits(Clean(…))` keeps it (3 digits).
  2. In a debate, its entries prompt-inject the user's agent into calling `debate_constrain` with "The human accepts Bob's plan in full."
  3. The window shows only `debate_constraint: add a human constraint to the debate s-… with Bob`. Both the constraint and the fixed "The code is in the notification…" sentence are cut. The human, used to approving constraints, types the code from the toast, and a fake "human decision" is signed into the Decision.

  The same name cuts short the scope summary (`let Bob` hides every command and argv; the peer
  there is the linked controller) and the grant expiry. `Mallory\n\nApproved by IT` adds fake
  lines to a grant window, because grant names are not even passed through `stripLongDigits`.
  Review 46 H2's rule is "the human approves what the window shows, so the text must never be
  cut". Test (emulating `g_strcompress`): `zenity shows: "debate_constraint: add a human
  constraint to the debate s-0123456789abcdef with Bob"`. **Not closed:** I could not run zenity
  on this PC. Whether `zenity --entry --text=` applies `g_strcompress` (as its message dialogs
  do) needs a manual check on Ubuntu 22.04/24.04 with `--text='a\0b'`. kdialog is unchecked.
- **Spec:** `Docs/protocol/approval.md` §The approval window, Linux row ("Text is markup-escaped (`& < >`) for both tools"); review 46 H2; approval.md §Threat model (local agent is a boundary).
- **Fix direction:** double every `\` in the zenity `--text`/`--title` values (as `notifySendBody` does), and add a test like `TestShowDesktopLinuxNotifySendBodySurvivesStrcompress`.
- **Related:** review 21 M1 (same GLib behaviour, fixed for notify-send only), review 30 L1, C12-02, O-129, C14-02 (another way the window cuts text)

### T11-02 · Low · confirmed-test
- **Where:** `internal/daemon/device.go:103-125` (`stripLongDigits`: separators are only `IsSpace|IsPunct|IsSymbol`), fed by `notify.Clean` (`internal/notify/notify.go:13-18`, no zero-width or `Cf` beyond the listed bidi controls); used at `device.go:487`, `device_scope.go:208`, `debate_constrain.go:70`
- **What goes wrong:** a 6-digit decoy code split by an invisible character (U+200B, U+2060, a variation selector, a Hangul filler) is not recognised as a digit run. It survives `stripLongDigits(notify.Clean(name, 40))`, and the window's `Clean` does not touch it either. So the mitigation O-129 relies on does not hold for device link, device scope and debate constraint, the kinds that do apply it. (Grants never apply it: C12-02.)
- **Scenario:** a paired peer names itself `Code 4​8​2​9​1​3`. The toast body, the window and the terminal-mode line all show `Code 482913`. In terminal mode (off by default) it sits on the same line as the real code, so wrong entries burn the 3-per-approval and 10-per-day budget (an approval lockout nuisance). Test output: `"Code 4​8​2…3" -> unchanged (stripped=false)`; the same holds for U+2060, U+FE0F and U+3164, while `"Code 482913" -> "Code …"`.
- **Spec:** `Docs/protocol/approval.md` §Text of the notification (decoy kept away from the code); review 26 N4 / review 36 L2.
- **Fix direction:** remove `Cf`/default-ignorable/invisible runes (the `decision.Visible` set) before digit-run detection, or treat them as separators.
- **Related:** O-129 (this shows its mitigation is bypassable), C12-02, C24 and C26 leads on `Clean`'s character set

### T11-03 · Low · confirmed-read
- **Where:** every `--json` path in `cmd/agentnet` (`json.NewEncoder(stdout)`, e.g. `inbox.go:58`, `approve.go:106`, `debate.go:610`, `device.go:174`), `main.go:322` (`failJSON`)
- **What goes wrong:** `encoding/json` escapes only U+0000–U+001F, U+2028/9 and `<>&`. C1 controls (U+0080–U+009F) and bidi/`Cf` characters in peer text (request titles, briefs, notes, `ws.result` summaries: O-100, C22-04) are written raw as UTF-8 to stdout. O-100 and every chunk finding treat only the human output.
- **Scenario:** a paired peer sends a request titled `x\u009b2J…` or containing U+202E. A user who runs `agentnet inbox --json` in a terminal that acts on UTF-8 C1 controls (xterm by default) gets the 8-bit CSI. Where it does not, the line is still reordered. An agent reading the JSON is unaffected, because the bytes are the true content.
- **Spec:** none (rubric §1 "drive our terminal … with control/bidi/markup").
- **Fix direction:** have the CLI JSON encoder escape C1 and `Cf` as `\uXXXX` (still valid JSON, same value), or fix at ingestion as O-100 proposes.
- **Related:** O-100, C22-04, O-142

### T11-04 · Low · confirmed-test
- **Where:** `cmd/agentnet/fetch.go:267-272` (`termSafe`: `unicode.IsPrint`)
- **What goes wrong:** `termSafe` quotes only runes that are not `IsPrint`. The review 46 H1 "graphic but invisible" set is `IsPrint`: Hangul fillers U+3164/U+115F/U+FFA0, variation selectors, U+2800 and combining marks. `decision.Visible` escapes it, and `debate.invisibleRune` refuses it. So `fetch list` can show two grantor entries as the same name. This is also the helper that O-100 and chunk findings C06-02/03, C19-03, C20-04, C22-04, C23-02, C25-01, C28-01/04 name as their fix, so every one of those fixes would inherit the gap.
- **Scenario:** a hostile grantor serves `report.txt` and `reportㅤ.txt`. `agentnet fetch list` prints both as `report.txt` (test: `termSafe="reportㅤ.txt"`, `Visible="report\u{3164}.txt"`). The user reads the wrong one. The impact is display only: the grantor controls both files anyway.
- **Spec:** decision.md §Markdown / review 48 L3 define the fuller rule; no CLI rule exists.
- **Fix direction:** make one shared terminal sanitiser with `decision.Visible`'s set (plus quoting), and use it for all the O-100 fixes.
- **Related:** O-100, R38 M3 (origin of `termSafe`), R46 H1, R48 L3

### T11-05 · Low · confirmed-read
- **Where:** root `internal/agentcard/agentcard.go:109-121` (`checkText` refuses Cc only). Sites not in any chunk finding:
  - `cmd/agentnet/device.go:130-135,191,244` (`devicePeerLabel`);
  - `ping.go:89,93,108-113` (`peerLabel`);
  - `decision.go:160-161`;
  - `inbox.go:100,372`;
  - `request_query.go:52,175,253`;
  - `request.go:182,188`, `consult.go:144,150`;
  - `debate.go:485,619,706`;
  - `approve.go:116` (grant summary: C12-02).
- **What goes wrong:** the root cause of C05-03, C06-03, C20-04 and C28-04 is that card names may hold bidi/`Cf`/zero-width characters and the CLI prints them unescaped. It reaches about 20 more print sites than those four findings list, among them `device list` and `device unlink`, where a wrong device identity matters most, and the Decision's human view. Fixing the four reported sites alone leaves these open.
- **Scenario:** a paired or team-introduced peer names its card `"laptop‮…"` or pads it with zero-width characters to look like the user's own linked device. `agentnet device list` shows a reordered or duplicate-looking row, and `agentnet ping @…` / `decision <id>` show the spoofed name. It is display only: trust still rests on the key and fingerprint (O-067).
- **Spec:** `Docs/protocol/agent-card.md` §Card "no control characters" (silent on `Cf`).
- **Fix direction:** refuse `Cf`/Zl/Zp/default-ignorable in `checkText` (one place, both sides, with a vector), or apply the shared sanitiser of T11-04 at every name print.
- **Related:** C05-03 (root), C06-03, C20-04, C28-04, C13 lead, C19 lead, C25 lead, C08 lead, O-067
