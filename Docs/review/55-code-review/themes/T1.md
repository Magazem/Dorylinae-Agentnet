**Verdict.** Parsing of peer input is strict almost everywhere. The one strict parser, `agentcard.ParseStrict`, feeds every signed object: mail plaintext, grant tokens, announcements, cards, Decisions, debate entries and pairing confirms. The code then reads members by exact name from the generic map, checks member counts, keeps numbers as `json.Number` in the ±2^53 range, and verifies signatures over the generic parse. Size bounds come before decoding on every path I traced.

The review found one real parser differential, **T1-01 (Medium, confirmed by test)**. `agentcard.Verify` checks the signature over the exact-name generic card. It then decodes the canonical bytes into the `Card` struct with `encoding/json`. That decoder matches member names without regard to case and uses Unicode simple folding, so U+212A KELVIN SIGN counts as `k` and U+017F LONG S counts as `s`. It keeps the last duplicate, and a folded name sorts after the ASCII one. A card that K1 signs can therefore come back as the card of **K2**, with any name, harness or skills. As a result, a team owner can introduce any key with a card the key's holder never signed.

The rest is small:
- **T1-02 (Low):** the relay's `error` text becomes a ping failure, unbounded and printed raw by `agentnet ping`. This is a third path, beyond C04-01/C28-01 and C06-02.
- **T1-03 (Low):** v1 pairing stores the relay-supplied card bytes, not the canonical card.
- **T1-04 (Info):** device mail `at` accepts offsets and fractions.

## Questions (method of 04-themes.md T1)

1. **Parser differentials (for example `encoding/json` vs `ParseStrict`).**
   - The relay and the daemon both decode envelopes with the same `encoding/json` structs: `ParseHeader` vs `Parse` (`internal/envelope/envelope.go:106-124`) and `Classify` (`frames.go:188-203`). Case-insensitive and last-duplicate-wins matching is the same on both sides, so they cannot disagree about `from`/`to`/`id`. Signed content never depends on those fields: mail step 6 and step 8 compare the envelope with the signed `msg` (`internal/mail/open.go:186-205`).
   - The one differential that matters is **T1-01**: a struct decode after a strict, exact-name signature check.
   - I checked every other place where a signed object is decoded again:
     - grant tokens: exact map reads plus member counts (`internal/capability/verify.go:202-326`); the `sig` re-read at `fetch.go:568` is safe because the member count is exactly 2;
     - announcements: exactly 6 plus 2 members with exact names (`internal/mail/body.go:80-136`);
     - mail `msg`: exactly 7 members (`open.go:259`);
     - `mergeMailboxKeys`: runs only on canonical, count-checked announcements (`internal/peers/store.go:162-195`);
     - device offers: exact names, exact count (`internal/daemon/device.go:153-190`).
   - None of these can hold a folded duplicate.
2. **base64 without `Strict()` on anything compared or signed.** Keys, nonces, card and grant signatures, mail `sig`, announcement `pub`, pairing confirms and Decision keys all use `RawURLEncoding.Strict()` (`envelope.go:31`, `agentcard.go:27`, `peers/pairv2.go:177-202`, `decision/verify.go:282-288`). Non-strict decodes remain in four places:
   - `internal/noise/noise.go:30` (the binding `sig`, inside an authenticated handshake; the signature bytes are what count);
   - fetch fragment data (`daemon/fetch_client.go:374`, content only);
   - the envelope `payload` (`[]byte`, std base64, O-053);
   - `daemon/mail.go:72` (reads our own stored canonical announcement).
   None of them is compared as a string or hashed, so there is no finding.
3. **Integers truncated to `int`.** Every peer integer passes through `json.Number` and `Int64`, and most are range-checked before the conversion: grant `v` checks for wrap (`verify.go:247`); presence and debate check ranges (`presence/body.go:179-209`, `debate/apply.go:784-794`); the team epoch is limited to `[1, 2^53)` (`team/kinds.go:292`). Three sites convert without a range check and matter only on 32-bit builds: `mail/open.go:270` (O-052), `request/decode.go:154` (C17 lead) and `worksession/wire.go:93`. No 32-bit target ships (C15 Q4), so I raise no new finding.
4. **Size bound after allocation.** Every size check I traced runs before the decode:
   - relay: the WebSocket read limit is 1 MiB, and 4 KiB before auth (`relay.go:474`; O-010 records the ephemeral re-decode);
   - relay client: 1 MiB (`relayclient.go:249`);
   - mail: `MaxPayload` before HPKE (`open.go:166`); presence reuses it (O-083);
   - Noise: 64 KiB;
   - tokens: 2048 bytes before `ParseStrict` (C09 Q2);
   - relay pairing card and mbox: 16 KiB and 4 KiB (`envelope/pairing.go:97-124`);
   - `decision verify`: reads at most 8 MiB (C25);
   - IPC: 1 MiB (C16).
   Nesting depth is bounded by `encoding/json` (C05, C25).
   One exception: the card that the daemon receives in `pair_peer` is bounded only by the 1 MiB frame. The relay enforces 16 KiB only on its own intake, so a hostile relay can send a 1 MiB card. The cost is a single parse, which I consider fine.
5. **Peer values used as a map key, file name, SQL, argv, log field or Markdown.**
   - SQL: parameterised everywhere I looked (C19, C26).
   - argv and paths: git is safe (C10), and the fs grammar holds (C09). Peer names never become local paths (C10 Q3).
   - Map keys: `pending*` maps keyed by `*mail.Opened` or by ids (O-077), and relay-chosen `ref`s in `session.refs` / `pairs.sessions`, which are lookups only.
   - Log fields: relay text reaches `lastErr` (C04-01/C28-01). `readControl` also embeds a relay-chosen `op` with `%q` (`relayclient/wire.go:32`): it is escaped but unbounded, which is the size half of C28-01.
   - Markdown: C25.
   - Terminal: relay text reaches `agentnet ping` raw (**T1-02**).

## Findings

### T1-01 · Medium · confirmed-test
- **Where:** `internal/agentcard/agentcard.go:205-213` (`Verify`: struct decode of `canon` after the signature check over the exact-name generic card, `:189-203`); root cause `internal/agentcard/canonical.go:69-72` (duplicates refused only when byte-identical). Consumers: `internal/team/kinds.go:353-359`, `internal/peers/pairing.go:642-648`, `:690-692`.
- **What goes wrong:** `Verify` takes the verification key from `card["public_key"]`, an exact-name read, and checks the signature over the whole generic card. It then decodes the canonical bytes into `Card` with `encoding/json`. That decoder folds member names: ASCII case, plus U+212A→`k` and U+017F→`s`. When several names fold to the same field, the last one wins. A folded variant made from those two runes sorts after the ASCII name in canonical order. So a card holding `"public_key":K1` and `"public_Key":K2` verifies under K1 and returns `Card.PublicKey = K2`. `"harneſſ"` likewise replaces `harness`. `DisallowUnknownFields` does not refuse these names, because each one matches a known field. The self-signature no longer binds the card's key or its fields.
- **Scenario:** Actor: a paired peer who owns a team, or who is recorded as the owner of one (trust `code`/`fingerprint`).
  1. The owner sends `team.roster` with a member entry `{key: K2, card: <card signed by the owner's key K1 with the extra folded public_key = K2 and name "Alice">, mailbox: null, added}`. K2 can be any key: a real person the recipient knows only as an introduced peer, or a stranger.
  2. `parseRosterMember` accepts it, since `sc.Card.PublicKey == key`.
  3. `Introduce` inserts or updates K2 with the owner-chosen name, harness and skills (`peers/store.go:390-409`). An existing introduced row from another team is overwritten as well.
  4. Mail and requests from the real K2 now show under a name the owner chose, for example that of a trusted peer (O-067).
  O-043 recorded only the replay of an *older self-signed* card. Here the card is arbitrary, and K2 never signed it.
  In pairing v2, a code holder that colludes with the relay (which sets `pair_peer.public_key = K2`) can make the issuer store K2 with trust `code`. That requires a valid K2 announcement, which rosters carry, and the harm is limited because the attacker holds no K2 secret.
  Any independent verifier that follows agent-card.md, such as `tools/verifycard`, sees a different card than the daemon.
- **Test:** `internal/agentcard/zz_review55_T1-01_test.go`, `go test ./internal/agentcard -run TestReview55T1_01 -count=1 -v` → `signed under key 0EmzMkdq…; Verify returned Card.PublicKey UsRTNH0a…, Harness "spoofed-harness"` → FAIL (the defect is confirmed).
- **Spec:** `Docs/protocol/agent-card.md` §Verification ("unknown fields are rejected"; the card is self-signed by its `public_key`); `Docs/protocol/team.md` (roster cards are the members' own signed cards). Rubric invariant 4.
- **Fix direction:** Build `Card` from the generic map by exact member name, with an exact member count, as `capability.decodeGrant` does. Alternatively, have `ParseStrict` refuse keys that fold to the same value. At the least, compare the struct's `PublicKey` with the exact `card["public_key"]` used for verification.
- **Related:** O-043, O-067, C05 (Assumptions: "Callers must compare card.public_key"), C20 (roster), C06 Q1; C29-03 (verifycard schema).

### T1-02 · Low · confirmed-read
- **Where:** `internal/session/session.go:319-331` (`HandleError` → `failPeerLocked(r.peer, ef.Code, ef.Message)`), `:800-806`; printed at `cmd/agentnet/ping.go:99-101`.
- **What goes wrong:** When the relay answers a session envelope with an `error` frame whose `ref` is that envelope's id, the relay's `code` and `message` become the ping `Failure`. Neither is bounded (up to about 1 MiB) or filtered by character. `agentnet ping` then prints both raw to stderr, and `ping_status` returns them over IPC.
- **Scenario:** Actor: the relay. The user runs `agentnet ping @bob`. The relay answers the `session.init` with `{"op":"error","code":"peer_offline","message":"\u001b[2K\r… \u001b]8;;https://evil/\u0007…","ref":"<id>"}`. The terminal then receives escape sequences the relay chose, such as an erased line or an OSC 8 link. A message of about 1 MiB of `<` characters also pushes `ping_status` past the 1 MiB IPC line, because of the 6× HTML escaping. This is a third path next to C04-01/C28-01 (`status`/`doctor`) and C06-02 (pairing, where the text is length-capped). It is display harm only, like C06-02.
- **Spec:** envelope.md error table ("human-readable"); rubric invariant 4 and relay row §1.
- **Fix direction:** Fix all relay `error` consumers in one place: in `relayclient`, keep only a known `code` from a fixed set and clip or strip `message` before calling `OnError`. Use `termSafe` in `ping`.
- **Related:** C04-01, C28-01, C06-02, C04 lead (`session.go:331,805`).

### T1-03 · Low · confirmed-read
- **Where:** `internal/peers/pairing.go:689-700` (`onPeerV1` → `store(sc, ctl.Card, …)`), vs v2 `:657-664`
- **What goes wrong:** The v1 pairing path stores `ctl.Card`, the bytes the relay sent, as the peer's `card`. It does not store the canonical card. `Verify` ignores extra top-level members, so the relay can add up to 16 KiB (1 MiB for a hostile relay) of members of its own choosing to the stored card. The v2 path deliberately stores the canonical form, and its comment names this exact risk.
- **Scenario:** Actor: the relay, on a loopback or self-hosted relay with v1 enabled (off by default; v1 peers are only `trust=relay`). The relay pads the `pair_peer` card with `{"card":…,"signature":…,"x":"<junk>"}`. The junk is stored in `peers.card` and later sent onward in rosters that include this peer, where recipients ignore it. The impact is stored and propagated relay-chosen bytes; no signature is bypassed.
- **Spec:** pairing.md §v1; rubric invariant 4 ("parsed strictly and bounded before it is … stored").
- **Fix direction:** Store `canonicalPart(ctl.Card, "card")` in v1, as v2 does.
- **Related:** O-004 (v1 `mbox` not validated), C06.

### T1-04 · Info · confirmed-read
- **Where:** `internal/daemon/device.go:143-149` (`offerBody.offer`), `:278-281` (`device.unlink` `at`); watermark `internal/device/device.go:520-535`
- **What goes wrong:** Both kinds parse `at` with `time.Parse(time.RFC3339, …)`, which accepts numeric offsets and fractional seconds. The wire format is whole-second UTC with `Z`, and other kinds enforce it with a round-trip check (`team/kinds.go:382-388`, `debate/apply.go:768-772`). The kept offer stores the raw text, and the unlink watermark drops the fraction. Every comparison is on parsed times, so the order stays correct.
- **Scenario:** A peer can only mis-date its own offers or unlinks, which it can do anyway. This is a strictness deviation with no effect.
- **Spec:** device.md §Kinds (wire times).
- **Fix direction:** Use the shared round-trip `parseWireTime`.
- **Related:** C13 lead, O-158.

## Checked and fine

- Mail signature verification uses the generic parse and exact member count (`open.go:240-290`). Canonicalisation refuses non-integers and values ≥2^53.
- Grant token decode reads the generic map by exact name, with exact counts per resource kind (`capability/verify.go:202-326`).
- Mailbox announcements must have exactly 2+6 members, with `key_id` recomputed from `pub` (`mail/body.go:80-136`).
- Relay pairing input: lookup and code go through a byte-level normaliser that rejects non-ASCII (`envelope/pairing.go:68-93`); card and mbox are size- and shape-checked (`:97-124`).
- The `fetch.resp` client reads exact keys and checks fragment count, index, size and encoded length before decoding base64 (`daemon/fetch_client.go:353-378`).
- `Classify` cannot turn `{"op":null}` into a control frame (C04).
- Relay auth: strict b64 and exact lengths for key, signature and nonce (`frames.go:240-246`, `authv2.go`).
- Envelope `ts` is RFC 3339 checked; `from`/`to` must be strict 32-byte keys (`envelope.go:56-76`).
- Open findings touched, still as recorded: O-004, O-010, O-043 (escalated in effect by T1-01), O-049, O-050, O-052, O-053, O-083, O-100.
