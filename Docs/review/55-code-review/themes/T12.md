# T12: Time, clocks and replay windows

Reviewer: TH-T12 · model claude-opus-5-5 · elapsed 7 min (shell clock) · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 2 · Info 1.

Every window in the theme matches its spec value and uses the clock the spec names. Where the
code compares stored timestamps as text, both sides use one fixed-width format. Every
peer- or relay-facing replay window is closed by a dedupe store that outlives it: `mail_seen`
35 d > 30 d + 10 min, the fetch `req` store 11 min > 10.5 min, the webhook id 24 h > the
~9.5 h retry span, and pairing and approval timers are monotonic. In-memory timers use Go's
monotonic clock.

The weak spot is the **receiver's own wall clock stepping forward and back**. The specs never
discuss this case. Durable "older than X" jobs run on the wall clock and cannot be undone
when the clock is corrected. Two such jobs matter:
- **T12-01:** mailbox-key rotation deletes every key that peers still use. It then leaves a
  current key whose announcement peers refuse, so inbound mail fails for as long as the step
  lasted. Confirmed by a test.
- **T12-02:** `mail_seen` pruning drops rows early, so the relay can replay non-inbox kinds
  (`team.leave`, `team.join`, `team.roster`). Confirmed by a test.

Both need a clock step of at least 21 days, so they are Low. **T12-03** (Info) lists the
daemon handlers that still read `time.Now()` next to an injected store clock (the O-106 /
R05 L3 pattern).

## Questions

The theme section has no numbered questions. Its method asks for a window table (below),
replay just outside windows, sender/receiver disagreement, and wall-clock timers that should be
monotonic.

1. **Replay just outside a window.** Mail: step 11 is 30 d + 10 min (`internal/mail/open.go:121-123`). Dedupe
   lasts 35 d (`receiver.go:21`, `Prune` `:320-327`). App mail is also capped at 14 d
   (`receiver.go:144`). Mail kinds with an inbox row are also blocked by the
   `mail_inbox (from_key,id)` primary key, which is never pruned (O-058). The margin holds
   only while the receiver clock does not step: see T12-02. Fetch: `ts` must be in
   [now−30 s, now+10 min]. The `req` store remembers 11 min, measured monotonically from
   first sight (`internal/capability/fetch.go:35-37,418,526-548`), and a Noise session sits
   underneath, so no replay is possible. Presence: same boot needs `seq >` the stored one;
   a new boot needs `created ≥` the stored one (`internal/presence/store.go:57-58`). The
   remaining same-second hole is O-064. Webhooks: a retry re-signs with a fresh timestamp
   (`internal/notify/webhook.go:190-200`), per notify.md:192-193. Device offers: the D22 two-clock rule and the
   watermark (`internal/device/device.go:495,528-547`); the residuals are O-158 and C13-02.
2. **Windows that disagree between sender and receiver.** Outbox 7 d (`outbox.go:32`),
   relay TTL 7 d (`internal/relay/queue.go:19`) and ReceiveMaxAge 14 d agree with D10 /
   mail.md:252-261. Key lifecycle: announcement 14 d (`announce.go:15`), rotation 7 d, delete
   at not_after + 7 d (`internal/mailbox/mailbox.go:40,43,405`), which matches mail.md:51-59.
   Mail more than 14 d old by the receiver clock is acked `unsupported` (`receiver.go:144-150`).
   The sender cannot tell this from "unknown kind" (O-188), which feeds C21-04's Phase 1
   fallback. The same happens for a sender whose clock is 14–30 d behind (O-036's neighbour).
   This is noted, not re-reported.
3. **Wall-clock timers that should be monotonic.** Approval expiry uses both an
   `AfterFunc(TTL)` (monotonic) and the stored `expires` checked at confirm
   (`internal/approval/store.go:184,256-276,400-420`). Either one expires the approval, so a
   step in either direction fails closed. Pairing code TTL and confirm wait are
   `AfterFunc` durations (`internal/peers/pairing.go:540,626,757,857`). Relay auth uses
   `time.Since(issued)` (`relay.go:588,609`). Fetch limiters use `now.Sub` on `time.Now()`
   values that carry the monotonic reading. The wall-clock ones are the SQL-stored windows
   (outbox expiry, `mail_seen` prune, key rotation, debate `turn_deadline`, presence
   `last_rx`, device intents). They are wall-clock by nature; T12-01 and T12-02 are the two
   whose effect is permanent.
4. **Text versus time comparison.** See the "Format" column of the table. All stored/compared
   pairs match. One comment is wrong but the code is harmless (Notes).
5. **Injected clock used consistently.** Not everywhere: see T12-03.

## Findings

### T12-01 · Low · confirmed-test
- **Where:** `internal/mailbox/mailbox.go:304` (`Rotate`: `need`), `:333` (`createLocked` signs with
  the stepped `now`), `:401-420` (`sweepLocked`), `:224-226` (`usable`); peer side
  `internal/mail/body.go:134`
- **What goes wrong:** Rotation and deletion are decided on the wall clock and cannot be
  undone. If one hourly `Rotate` run sees a clock at least 21 days ahead, three things happen:
  - it creates a key whose `created` is in the future;
  - it retires the current key;
  - it deletes the private key of every key whose `not_after + 7 d` has "passed", which
    includes the key peers are sealing to.

  After the clock is corrected, `usable` keeps the future key as current, because its
  `not_after` is far ahead. `Rotate` does not replace it for another ~7 d past the step.
  Every peer refuses its announcement with `ErrAnnouncementExpired` (`created > now + 10 min`).
- **Scenario:** No attacker is involved. The owner's machine resumes from a VM snapshot, dual-boots,
  or has its date set wrong, and runs one hour or one daemon start 30 days ahead. NTP then
  corrects the clock. Every inbound mail is now sealed to a deleted key, so it is a key miss.
  Each key-miss reply pushes the future-dated announcement, which peers refuse. The user
  receives no mail from anyone until real time reaches the step's date (30 days here).
  Nothing is logged except per-mail rejects, and the fix is hand-editing
  `mailbox_keys_own` and the keystore. Test: `internal/mailbox/zz_review55_T12-01_test.go`, run with
  `go test ./internal/mailbox -run TestReview55T12_01 -count=1 -v`. Output: `key 7fec965ce77610bb that peers seal to was deleted during the step`,
  `current announcement refused by a peer at true time: mail: mailbox announcement validity window is out of range`,
  `still refused 20 days later`.
- **Spec:** `Docs/protocol/mail.md` §Lifecycle (lines 51-59) and §Announcement check 5 (line 101). Neither
  covers a local clock step.
- **Fix direction:** Treat a current key whose `created` is after `now + MaxSkew` as unusable
  (rotate again at the true time). Do not delete a key that is still in its own
  `not_after + 7 d` window at the last *successful* announcement time, or bound deletions per run.
- **Related:** O-047, O-056, O-197; same clock-step class as T12-02

### T12-02 · Low · confirmed-test
- **Where:** `internal/mail/receiver.go:319-327` (`Prune` by `received_at < now − 35 d` on the
  clock at prune time), `:330-338` (`RunPrune` at start and daily); spec rationale mail.md:281-282
- **What goes wrong:** `mail.md` says pruning is safe because "a replay of a pruned id carries a
  `created` older than `now − 30 d + 10 min`". That holds only if the prune-time clock is
  the clock of the later check. One prune during a forward step of more than 21 days deletes
  rows whose mail is still inside both the 30 d step-11 window and the 14 d ReceiveMaxAge
  once the clock is corrected. A relay replay of such a mail is then accepted and applied a
  second time. Kinds with an inbox row are protected by the never-pruned `mail_inbox` primary
  key (the insert fails and the tx rolls back). The kinds without one are:
  - `team.roster`, `team.join` and `team.leave` (`internal/team/kinds.go:62,425,534`);
  - `keys` (`internal/daemon/mail.go:137`).
- **Scenario:**
  1. Member M's `team.leave` reaches owner O.
  2. M is re-invited and re-joins.
  3. O's machine starts or runs its daily prune while its clock is 31+ days ahead (see
     T12-01 for how that happens), and NTP then corrects the clock.
  4. The relay, which stored M's frames, replays the old `team.leave` from within the last
     14 days.

  `applyLeave` removes M again and broadcasts a new roster (`kinds.go:537-566`). A replayed
  `team.join` is harmless (the invite is `used`). A replayed `team.roster` is refused by its
  epoch check. The actor is the relay, but it needs a victim-side clock step it cannot cause.
  Test: `internal/mail/zz_review55_T12-02_test.go`, run with
  `go test ./internal/mail -run TestReview55T12_02 -count=1 -v`. Output:
  `relay replay of a 5-day-old mail applied again after one prune during a forward step (applied=2)`.
- **Spec:** `Docs/protocol/mail.md` §Dedupe (lines 281-282), whose safety argument assumes a
  monotonic receiver clock.
- **Fix direction:** Prune by the stored `msg.created` (sender time, already checked by step 11)
  instead of `received_at`. Alternatively, skip a prune whose `now` is later than the newest
  `received_at` plus a day.
- **Related:** O-058 (the `mail_inbox` PK that accidentally protects inbox kinds), O-036, T12-01

### T12-03 · Info · confirmed-read
- **Where:** `internal/daemon/grant.go:455,576,582,683,798,921`, `grant_kinds.go:55,171`,
  `session.go:418,422,558`, `team.go:181,280,306,332,360`, `trust.go:98,103`, `request.go:199,274`,
  `notify.go:97,135,154,324`, `status.go:87`, `request_lifecycle.go:360`
- **What goes wrong:** These daemon handlers read `time.Now()`. The stores they call
  (`capability.Store`, `worksession.Store`, `team.Store`, `approval.Store`, `request.Store`)
  run on an injected `Now`. In production both are the wall clock, so behaviour is the same.
  Tests that fake the store clock, however, cannot drive these paths consistently. Two
  examples:
  - `grant.go:576` checks `gr.Exp` against the real clock while the approval store uses its
    own clock;
  - `session.go:418` passes the real clock to `AcceptResultInTx`.

  This extends O-106 and the C21 lead to the whole daemon package.
- **Scenario:** No runtime impact. A test of "the grant expired while its approval waited"
  with a fake clock cannot exercise `grant.go:576`.
- **Spec:** none
- **Fix direction:** Pass one daemon clock (`Options.Now`) to the handlers.
- **Related:** O-002, O-106, C21 lead (`session.go:418`)

## Assumptions and contracts

- `Receiver.Handle` relies on `Opener.Open` having run step 11 with the same clock
  (`receiver.go:120,144`); the daemon leaves both `Now` nil, so both use `time.Now` (`internal/daemon/mail.go:126-138`). **checked**.
- Dedupe safety of inbox kinds relies on `mail_inbox` never being pruned (O-058). If a future
  change prunes it, T12-02 extends to every kind. **checked** (no `DELETE FROM mail_inbox` in non-test code).
- Fetch `req` dedupe relies on the Noise layer for replay across sessions (`capability/fetch.go:526`, grant.md:490). **unchecked** (T-session).
- Approval expiry relies on the per-approval `AfterFunc` firing even while the machine is
  asleep. On resume, the wall-clock check at `Confirm` covers it (`approval/store.go:257`). **checked**.

## Notes

- The phase-1 comparison mixes `…05Z` (outbox) with `…05.000Z` (since). At the same second
  `'Z' > '.'`, so the `>=` still includes the row. Only the comment is wrong.
- `device.go:517-523` stores the unlink watermark with `time.RFC3339`, which drops fractions.
  Honest daemons send whole seconds, so this has no effect.
