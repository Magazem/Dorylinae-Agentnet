# C02: Relay persistence, pairing, backup, journal, binary

Reviewer: CR-R2 · model claude-opus-5-5 · elapsed 6 min (system clock) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 1 | 1 | 4 | 1 |

The queue caps, the pairing limits, the safe-by-default flag rules and the migration runner
hold up. The one serious defect is in 4.1a's restore path, which had no security review
before. `relay restore --replay-journal` takes the backup's time from the `--from` file's
**mtime**. In the specified flow (encrypt, upload off-host, download and decrypt at restore
time), the file is new, so every journal entry is older than its mtime and is silently
skipped. The restore then brings back exactly the security state the journal exists to
prevent (review 50 M6): unbound keys, deleted accounts and lifted suspensions. A test
confirms this (C02-01). The other findings: an unbounded single-statement sweep that can
stall the DB and grow the WAL (suspected), a restore that destroys the old database before it
verifies the new one, a backup that silently creates and copies an empty DB on a wrong
`--db`, and a `/metrics` error status that is never sent.

## Questions

1. **Queue caps and bookkeeping.** A sender cannot exceed the caps. The per-pair and
   per-recipient caps come from indexed queries in the same tx as the insert
   (`internal/relay/queue.go:296-309`). The per-sender and relay-wide caps come from
   in-memory totals under `q.mu` (`:287-293`). Bookkeeping is adjusted only after `Commit`
   succeeds (`:314-317`). `ack` and `sweep` adjust from the `RETURNING` rows of the delete
   itself (`:365-376`, `:386-399`), so an ack of an unknown id changes nothing. Totals are
   rebuilt from the table at open (`:147-169`), so a restart cannot drift them. Many fresh
   keys can fill a victim or the relay-wide cap: this is O-015 (accepted, OD-P4-21). Disk:
   `storageLow` refuses adds below `--queue-min-free-disk` (`:190-202`); it fails open on a
   `Statfs` error (O-027). What it does not cover is the **sweep** transaction itself, which
   is unbounded (C02-02).
2. **Migrations and restore.** R1 and R2 are entirely `CREATE … IF NOT EXISTS`
   (`queue.go:114-127`, `accounts_store.go:23-60`), so each is idempotent on an old
   `queue.db`. Each migration is not run in one transaction with its `relay_migrations` row
   (`queue.go:243-251`), but rerunning is harmless because the statements are idempotent. A
   DB newer than the binary is refused (`:240`). `restore` refuses a non-empty target without
   `--force` (`backup.go:53-56`). However, it deletes the target and its WAL/SHM, copies
   without fsync, and runs migrations (`openQueue`) **before** `integrity_check`
   (`backup.go:65-86`). It has no check that a relay still has the file open (C02-03). No
   path traversal applies: every path is an operator CLI argument. `Remove` then create
   replaces a symlinked `--db` rather than writing through it. DSNs are built as
   `"file:"+path+"?…"` without escaping (`queue.go:210`, `backup.go:30`, `journal.go:98`),
   so a path containing `?` or `#` misparses (Notes).
3. **Pairing.** This holds after 4.0c/4.1a. The per-key and per-prefix `pair_new` limits
   apply to v2 (`pairing.go:238-253`). Failed redemptions are limited per key and per prefix
   (`:361-380`). The relay-wide `maxCodes` backstop is checked before insert (`:290`). The
   redemption count stops at 3 (`:426-433`), matching pairing.md §v2 ("reaches 3"), and
   `peer_offline`/`peer_busy` do not count (`:415-425`, pairing.md:231). D9's "max 3" is the
   issuer-side count (daemon, not in scope). v1 is off on public relays
   (`cmd/relay/main.go:107-112`; `public` from `transport.go:94-99`). v1 `pair_new` skips
   `newLim`/`newLimPrefix` (`pairing.go:238`) but stays bounded by the 5-per-key and
   50-per-prefix outstanding caps. `pair_cancel` is not an oracle (`:443-460`). Filling the
   10 000 relay-wide codes needs roughly 250–500 distinct /24 or /48 prefixes (20 new per 10
   min each). The spec accepts this ("botnet"). Known residuals: O-004 to O-008, O-037.
4. **Journal.** Every event journaled today (unbind, suspend/unsuspend, account_delete:
   `accounts_store.go:419-446`) is written **after** its DB change. When the append fails,
   the operation returns an error but the change stays: this is already O-187.
   `invite_redeem`/`invite_revoke`/`team_remove` are not journaled, because 4.3a is not built
   (no handler, nothing to journal). Journal fields hold account ids, group ids and
   `short(key)` (8 chars, `relay.go:972`) only. There are no emails, payloads or full keys.
   The replay side is broken, though (**C02-01**).
5. **`cmd/relay` defaults.** Non-loopback needs TLS or `--behind-proxy`
   (`transport.go:88-90`; `main.go:94-98`). `/metrics` is served only by its own server on
   `--metrics-listen` (`main.go:163-224`) and never on the public mux (test
   `TestMetricsNotServedOnPublicListener`). Nothing forces that address to be loopback;
   passing an address is the "told otherwise" case the spec allows. The public server has
   ReadHeader, Idle and MaxHeaderBytes limits (`transport.go:33-41`). The metrics server has
   only `ReadHeaderTimeout` (loopback, Notes). The SIGTERM drain is bounded: 5 s
   `Shutdown` plus `drainWaitTimeout` 10 s (`relay.go:38,423-428`). That fits within the
   unit's `TimeoutStopSec=20`, although the unit's comment says 5 s. The flags in
   `deploy/early/agentnet-relay.service` all parse (they validate per `limits.go:246-277`:
   header plus trusted proxy together with `--behind-proxy`) and match the runbook table.
   Both `--metrics-listen 127.0.0.1:9787` and `--db` under the 0700 `StateDirectory`
   match. The metrics endpoint misreports on error (C02-06) and lacks most of the
   spec's metrics (C02-07).

## Findings

### C02-01 · High · confirmed-test
- **Where:** `cmd/relay/main.go:307-312` (`runRestore`), `internal/relay/journal.go:216-219`
- **What goes wrong:** Replay uses the `--from` file's mtime as the backup time. The spec
  says a backup is encrypted, uploaded off-host and then downloaded and decrypted at restore
  time, and that step writes a new file whose mtime is later than every journal entry. The
  restore therefore replays nothing. Skipped-by-time entries are not counted either, so the
  output ("replayed 0 journal entries (0 skipped, no handler yet)") looks normal.
- **Scenario:** A user's laptop is stolen, and the operator runs `relay admin` unbind on
  the key (journaled at T1). Later the DB is lost, and the operator follows relay-hosted.md
  §3: download backup B (taken at T0 < T1), `age -d` it to `b.db` (mtime T2 > T1), then
  `relay restore --from b.db --db … --replay-journal j.jsonl`. The unbind is skipped. The
  thief's key is bound again and can use the relay under the victim's account. The same
  happens to an `account_delete` (an erasure request undone) and a `suspend` (an abuser
  reinstated). This is exactly the harm review 50 M6 describes. Accounts are off by default
  (`--accounts`); the rating assumes they are on.
  Test: `cmd/relay/zz_review55_C02-01_test.go`, `go test ./cmd/relay -run TestReview55C02_01 -count=1`
  → `restore stdout: "…replayed 0 journal entries (0 skipped, no handler yet)"` and
  `C02-01: key unbound after the backup is bound again after restore --replay-journal (rows=1)`.
- **Spec:** `Docs/protocol/relay-hosted.md` §3 Restore, "`relay restore --replay-journal FILE`
  re-applies every journal entry newer than the backup"; §3 Backup (encrypted, uploaded off-host).
- **Fix direction:** Take the backup time from inside the backup (for example a
  `relay_meta.backup_started` row written before `VACUUM INTO`, or the newest
  `relay_migrations`/queue timestamp), or require an explicit `--since`. Replay a margin
  before it (handlers are idempotent), and count entries skipped by time in the summary.
- **Related:** O-187 (journal append after DB change), review 50 M6

### C02-02 · Medium · suspected
- **Where:** `internal/relay/queue.go:381-401` (`sweep`), `:208-210` (DSN: `secure_delete(1)`, no `journal_size_limit`), `:25` (`queueOpTimeout`)
- **What goes wrong:** `sweep` deletes every expired row in one statement, under `q.mu`, on
  the single connection, within 10 s. With `secure_delete=ON`, every freed page is
  overwritten, so the transaction writes about as many WAL bytes as it frees. A large batch
  can therefore (a) exceed the 10 s timeout, which rolls it back and repeats every minute
  with an ever larger batch, stalling `add`/`ack` (they wait on `q.mu`) for 10 s per
  minute, and (b) grow the WAL to the batch size, which the free-disk check (adds only)
  does not account for.
- **Scenario:** Hosted early relay without accounts (O-015): about 16 client prefixes, each
  at 64 MiB/min (`--prefix-bytes-per-min`), send 1 GiB of queued frames to arbitrary offline
  keys within one minute, up to `--queue-max-total 1GiB`. Seven days later (TTL), one sweep
  must delete about 1 GiB in one transaction. On the 2–3 GB volume, DB (1 GiB) plus WAL
  (about 1 GiB) plus the rest approach the disk size (SQLITE_FULL), or the write exceeds 10 s
  and never completes. The expired rows then stay counted in the totals and hold the
  relay-wide cap, so `queue_full` goes to everyone. The same large batch also happens without
  an attacker on the first sweep after a long relay outage. Not confirmed: I did not time a
  1 GiB delete on the Hetzner volume, and I did not confirm that a rolled-back interrupt
  leaves the WAL at its high-water size.
- **Spec:** relay-hosted.md §2 Offline queue (free-disk row: "acks and deletes still work"); §3 (WAL, `secure_delete=ON`)
- **Fix direction:** Sweep in bounded batches (`DELETE … WHERE seq IN (SELECT seq … LIMIT n)`)
  in a loop, and set `journal_size_limit` (or run `wal_checkpoint(TRUNCATE)` after a large
  sweep).
- **Related:** O-015, O-027, O-024

### C02-03 · Low · confirmed-read
- **Where:** `internal/relay/backup.go:52-87` (`Restore`), `:90-105` (`copyFile`)
- **What goes wrong:** `Restore` checks too late and too little. It removes the target
  DB/WAL/SHM, copies the backup without `fsync`, and runs the migrations (a write) on the
  copy. Only then does it run `integrity_check` (within 30 s). A corrupt or truncated backup
  is found only after the old database is gone, and it stays at `--db`. Nothing detects a
  relay that still has the target open. On Linux the relay keeps writing to the unlinked
  inode, and those writes vanish at its next restart.
- **Scenario:** An operator restores with `--force` from a backup whose download was cut
  short. The restore fails `integrity_check` (or its 30 s timeout on a large DB), but the
  previous database has already been deleted, and a crash just after "restored" can leave
  a partly written file. Needs an operator error or a bad file (at most Low, rubric §2).
- **Spec:** relay-hosted.md §3 Restore ("checks `PRAGMA integrity_check` and the migration table")
- **Fix direction:** Copy to `dbPath+".restore-tmp"`, fsync, run `integrity_check` on it
  read-only, migrate, and only then rename it over the target. Refuse when the target's
  `-wal`/`-shm` show a live writer, or take an exclusive lock first.
- **Related:** none

### C02-04 · Low · confirmed-read
- **Where:** `internal/relay/backup.go:20-45` (`Backup`)
- **What goes wrong:** `Backup` opens `dbPath` in the default `rwc` mode, so a wrong
  `--db` creates an empty relay database there. `VACUUM INTO` then copies it, and the command
  prints "backup written" with exit 0. The function also silently deletes an existing
  `--out`, although the flag help (`main.go:264`) and the doc comment say it "must not
  already exist".
- **Scenario:** A daily backup job has a typo or stale `--db` path (for example the old
  `relay-queue.db` name after a `--db` rename). Every nightly backup is then an empty,
  valid-looking file, and a "backup older than 26 h" alert never fires. The first restore
  brings back nothing. Needs an operator mistake (Low).
- **Spec:** relay-hosted.md §3 Backup
- **Fix direction:** Open with `mode=ro` (or `Stat` it first and refuse a missing or empty
  file), and refuse an existing `--out` as documented.
- **Related:** none

### C02-05 · Low · confirmed-read
- **Where:** `internal/relay/pairing.go:223-236` (`pairNew`, account limiter)
- **What goes wrong:** With accounts, `newLimAccount.fail` is charged before the
  per-key/prefix rate checks, the outstanding caps and `lookup_taken`. A refused `pair_new`
  still spends one of the account's 30 per day.
- **Scenario:** A bound account's daemon that retries `pair_new` while at the 5-per-key
  outstanding cap (or behind a busy prefix) burns its daily quota on refusals. It is then
  refused ("try again tomorrow") for a legitimate code. Off by default (`--accounts`). Only
  the account itself is affected.
- **Spec:** relay-hosted.md §2 Pairing L5 ("30 `pair_new` per account per day")
- **Fix direction:** Charge the account after the other checks pass (at issue time).
- **Related:** O-008 (allow/fail split)

### C02-06 · Low · confirmed-read
- **Where:** `cmd/relay/main.go:246-255` (`metricsHandler`)
- **What goes wrong:** On a `Stats` error, the handler has already written the body, so
  `WriteHeader(500)` is a superfluous no-op. A DB failure shows as `200` with
  `relay_queue_rows 0`/`relay_queue_bytes 0`.
- **Scenario:** The single DB connection is stuck or the file is unreadable. Prometheus
  scrapes a healthy-looking 200 with an empty queue, so "queue at 80 %" can never fire and
  the outage is not visible in metrics.
- **Spec:** relay-hosted.md §5 Operator metrics
- **Fix direction:** Call `Stats` first and return 500 before writing any body.
- **Related:** none

### C02-07 · Info · confirmed-read
- **Where:** `cmd/relay/main.go:244-257`
- **What goes wrong:** `/metrics` exports only connections, queue rows and queue bytes. The
  spec lists envelopes routed/queued/expired/refused by limit, DB size, free disk and backup
  age, and three of the §5 alerts (backup age, free disk, auth-failure spike) need them.
- **Scenario:** None as an exploit. The operator cannot build the alerts §5 requires from
  this endpoint (possibly deferred to 4.1b).
- **Spec:** relay-hosted.md §5 "Prometheus text of connections, envelopes routed / queued / expired / refused by limit, queue rows and bytes, DB size, free disk, backup age"
- **Fix direction:** Add the missing gauges and counters, or record the deferral in the 4.1b ticket.
- **Related:** none

## Assumptions and contracts

- `handleControl`'s `OpAck` passes `c.key` (the authenticated key) as `to`, so a key can only
  delete its own queued rows (`pairing.go:158`; auth in `relay.go` `authenticate`). **checked**
  (the call site uses `c.key`).
- `q.add` assumes `h.From == sender.key` was enforced before queuing, or the per-sender
  caps are meaningless (`queue.go:290`). This is enforced at `relay.go:760` (`if h.From != sender.key`). **checked**
  (seen, not traced further).
- `pairNew`/`pairRedeem` assume `c.prefix` is the client's /24 or /48 prefix, taken from
  the trusted header only for trusted proxies (`relay.go:562-575`, `limits.go` `clientAddr`).
  **unchecked** for `clientAddr` (O-029).
- `accountAllows` has let only a bound key in a quota group through before `pairNew` reads
  `acct.state` and ignores the error (`pairing.go:225`). **unchecked** (C03).
- `envelope.CheckCard`/`CheckMbox`/`NormalizePairLookup`/`NormalizePairCode` bound and
  validate peer pairing input (`pairing.go:174-206`). **unchecked** (envelope chunk).
- `issuer.send` never blocks (returns false when the buffer is full), because it is called
  under `p.mu` (`pairing.go:421`). **unchecked** (`conn.go`).
- `Server.Close` waits for drains (`relay.go:418-428`) but not for connection read loops
  before `q.close()` (`relay.go:439`). An in-flight `q.add` after close fails "database is
  closed". The spec (§3 "Restart without loss") says `Close` waits for connection
  goroutines. **unchecked**, a lead for the relay-core chunk.
- The journal replay handlers are idempotent (DELETE, set state), so replaying from an
  earlier `since` is safe (`accounts_store.go:565-585`). **checked**.
- `ReplayJournal` runs against a DB already migrated by `Restore` (it opens without
  migrating, `journal.go:203`). **checked** (`runRestore` order, `main.go:301-312`).

## Checked and fine

- In-memory totals are adjusted only after a successful `Commit`. Ack and sweep use
  `DELETE … RETURNING`, so the counts come from the rows actually deleted (`queue.go:314-317,365-399`).
- Cap queries use indexes. `LENGTH(frame)` does not read the blob, and each is bounded by
  the per-recipient/per-pair caps (`queue.go:323-330`, query-plan test exists).
- Relay migrations R1 and R2 are fully idempotent `IF NOT EXISTS`. A newer schema is refused
  (`queue.go:240`).
- `restore` without `--force` refuses a non-empty target (`backup.go:53-56`, test `TestBackupAndRestoreSubcommands`).
- The backup file gets 0600 after `VACUUM INTO`. In the runbook flow it sits in the 0700
  `StateDirectory` (service `UMask=0077`), so creation-time perms do not leak.
- Pairing codes are stored only as hashes (`pairing.go:120-126`). Lookup/code hashes are
  domain-separated.
- `pair_cancel` does not reply and treats foreign and unknown entries alike (`pairing.go:441-460`).
- `pair_peer` goes to the issuer before the entry is consumed. Offline or busy is not
  counted (`pairing.go:410-433`, pairing.md:231).
- v1 defaults to off whenever the relay is public, including loopback plus
  `--behind-proxy` or a non-loopback `--public-origin` (`main.go:107-112`, `transport.go:94-99`).
- A non-loopback listen without a TLS mode exits 2 (`transport.go:88-90`). `--public-origin`
  is required with every TLS mode (`:91-93`).
- TLS: minimum 1.2, HTTP/1.1 only (HTTP/2 disabled via `TLSNextProto`). The ACME host is
  whitelisted and the cache dir is 0700 (`transport.go:105-131`).
- `/metrics` is on a separate `http.Server` and listener (`main.go:217-224`). It has no
  per-key labels.
- `--behind-proxy` requires `--client-ip-header` plus `--trusted-proxy` (`limits.go:267-276`).
  `byteSize.Set` rejects negatives and overflow (`:324-326`).
- Journal entries hold only ids and 8-char key prefixes. The file is opened
  `O_APPEND|O_CREATE`, 0600 (`main.go:176`). Appends are serialized (`journal.go:44-52`).
- Every `deploy/early/agentnet-relay.service` flag parses and validates, and the unit
  matches the runbook table (`Docs/ops/early-relay-deploy.md:136-137`).
- The SIGTERM path is bounded: 5 s HTTP shutdown plus a 10 s drain wait. The close
  handshake runs in the background (`main.go:231-237`, `relay.go:410-441`).
- O-003, O-004, O-005, O-006, O-007, O-008, O-015, O-020, O-022, O-024, O-027, O-029 are
  still present as recorded. None of them is worse than recorded.

## Leads for other chunks

- `internal/relay/relay.go:439`: `Close` closes the DB without waiting for connection read
  loops, although spec §3 says it waits for them. Check the in-flight `add`/`ack` outcome.
- `internal/relay/relay.go:370`: `sweepLoop` ignores the error of `Sweep` except for a log,
  and a sweep that keeps failing has no metric or alert (ties to C02-02).
- `internal/relay/accounts_store.go:565-574`: the unbind replay matches an 8-char key
  prefix within an account, so it could remove a different key of the same account bound
  after the backup with the same prefix (a 48-bit collision, negligible).
- `deploy/early/agentnet-relay.service:34`: the comment says the drain is 5 s; the actual
  bound is about 15 s (still under `TimeoutStopSec=20`).

## Notes

- DSNs concatenate raw paths (`"file:"+path+"?…"`). An operator path containing `?`/`#`/`%`
  is misparsed. Escape it with `url.PathEscape` or use the `file:` URI rules.
- `run` returns 1 on a `Serve` error without calling `rs.Close()` (`main.go:226-228`).
- The metrics server lacks `IdleTimeout`/`WriteTimeout` (loopback only).
- A static `--tls-cert` is loaded once, so renewal needs a restart.
