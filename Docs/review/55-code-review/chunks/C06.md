# C06: Pairing v2 (daemon side), peers store, trust

Reviewer: CR-R6 · model claude-opus-5-5 · elapsed ~35 min · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 3 | 0 |

The cryptographic core holds. I found no path where the relay can make either side store a key
without a verified tag, or store a key other than the one the tag covers. The R09 M1 fix
(`completing` plus `end(..., completer=true)`) closes every race I traced between confirm,
timers, relay errors and store failure. The Medium is a resource bound that does not hold.
Argon2id derivations (64 MiB each) keep running after their session ends, so the "16 pending"
cap does not bound memory. A local IPC caller can push the daemon to about 2 GiB of heap in under
a second (confirmed by a test). The Lows cover display and audit hygiene of relay-chosen and
peer-chosen text, and `peers_verify`, which carries no human proof.

## Questions

1. **Relay makes a side store an unverified key, a different key, or report "failed" after
   storing?** No. There are three store call sites. (a) `onPeerV1` (`internal/peers/pairing.go:698`)
   runs only when `s.v1` is set, and only `beginRedeemerV1` sets it (`:507`). (b) and (c) are both
   in `checkConfirm` (`:962`). They run after `hmac.Equal` against a tag computed from this attempt's
   own `T` (`:938-945`) and after claiming `completing` under `m.mu` (`:955-961`). The stored key is
   `att.sc.Card.PublicKey`. It equals the frame key (`verifyPeer` `:646`), and `T` covers it through
   the canonical card (`:754`, `:817`). The stored mbox is the canonical announcement verified with
   `identity == key` (`:659`). Once `completing` is set, `end` refuses every non-completer caller
   (`:993`): timers, `HandleError`, `attemptFailed` (`:772`). A store failure ends the pairing as
   `failed` and commits nothing (`store.go:97` rollback). So "failed" never appears with a stored
   peer.
2. **Races between confirm, timeout, relay error and cancel?** None breaks "nothing stored on
   the detecting side". There is one benign window at the 60 s edge. An attempt timer reads
   `accepted=false` (`:758-762`), then `HandleEnvelope` accepts the tag (`:910`), then
   `attemptFailed` marks the attempt `over` (`:776`). `checkConfirm` then sees `over` and returns
   (`:931`). The result is a clean `confirm_timeout` with nothing stored and no `tag_I` sent. The
   code TTL or a relay error during the K wait or the `checkMu` wait ends the pairing before the
   claim, so nothing is stored. `checkMu` serialises the tag checks (`:927`).
3. **Code, lookup, secret, K or tags in logs, audit, IPC errors or status?** None found. The
   only places are the pending issuer's `Status.Code` (`:623`, cleared in `end` `:1000`) and
   `CompletionInfo.Lookup`, which goes to the in-process team Completer (lead below). Log calls
   carry only events, reasons and store errors (`:708`, `:734`, `:885`, `:975`). Audit details
   carry id, role, version, peer, trust, code and reason. The `[]byte` secret is wiped on every
   `end` (`:1012`) and on `reissue` (`:591`). The KDF copy is wiped in the goroutine (`:385`).
   K is wiped in `end` (`:1015`) and `reissue` (`:595`), or never kept if the session already
   ended (`:387-390`). String copies remain (O-040). Relay-chosen text does reach the audit log and
   the terminal: see C06-02.
4. **Trust and `introduced_by`, owner-removal cascade, `peers_verify`.**
   - Trust never lowers: `AddTrusted` uses a CASE rank (`store.go:114-116`), and so does
     `setTrust` (`:304-308`).
   - A direct pairing clears `introduced_by` (`:113`). `SetTrust` clears it for code and
     fingerprint (`:307`). `Introduce` follows team.md's three cases (`:383-412`).
   - `peers_remove` cascades in this order: owned-team membership (`trust.go:198`), then
     `OwnerRemoved` (teams to `left` plus GC in one tx, `internal/team/store.go:463-499`),
     then `Remove`.
   - `removeTx` fails outbox rows, deletes presence and runs `OnRemovedTx` in the same tx as
     the DELETE (`store.go:337-359`).
   - `peers_verify` can only be driven over local IPC, never by a peer. But it proves nothing a
     local agent does not already know: see C06-04.
5. **v1 only with `--v1` and a 10-character code; no downgrade?** Yes. `NormalizeCode` tries
   the 15-character form first (`pairv2.go:72`). A 10-character code without `allowV1` gives
   `ErrNeedV1` (`pairing.go:307`). The issuer is never v1. A v2 issuer that receives a
   `pair_code` carrying `code` fails with `relay_v1` (`:617-621`). A v2 redeemer never takes
   `onPeerV1` (`:678`), and a v1-style `pair_peer` without `mbox` fails with `bad_mbox`.

## Findings

### C06-01 · Medium · confirmed-test
- **Where:** `internal/peers/pairing.go:379-395` (`startKDFLocked`), `:492-498` and `:455-456` (KDF started before the send), `:523` (`failSend`), `:417-428` (`maxPending` counts only pending sessions)
- **What goes wrong:** Each v2 pairing starts a 64 MiB Argon2id goroutine that cannot be cancelled. The `maxPending=16` cap counts sessions, not derivations. A session that ends at once (the send fails, or the relay answers `pair_invalid` or `pair_rate_limited`) frees its slot while its derivation keeps running. The number of concurrent derivations, and the memory they use, therefore has no bound.
- **Scenario:** A local agent (possibly prompt-injected) calls `pair_redeem` over IPC in a loop with fresh random 15-character codes. With no relay connection each call fails in milliseconds. With a relay connection, each call ends on the relay's quick `pair_invalid` or `pair_rate_limited`. Every call leaves a 64 MiB derivation running. The test below made 40 calls in 0.76 s: about 64 extra goroutines were still running and HeapSys was 2060 MiB. A tighter loop, or `pair_new` with no relay connection, drives the daemon to OOM, taking mail, grants and sessions down with it.
- **Spec:** `Docs/protocol/pairing.md` §Local timers, "At most 16 pairings may be pending at once"; §KDF parameters, "one derivation per side per pairing, 64 MiB of RAM"
- **Fix direction:** Bound derivations rather than sessions: a semaphore of at most N concurrent derivations (a waiting session fails or queues). Start the KDF only after the relay accepted the frame (`pair_code` or `pair_peer`).
- **Related:** escalates O-034 (R07 L9 / R09 L8, recorded as "bounded, each needs a user `pair --new`"). New evidence: the bound does not hold at all. Sessions that fail at once leave their derivations running, and a local IPC caller needs no relay cooperation.

### C06-02 · Low · confirmed-read
- **Where:** `internal/peers/pairing.go:571-575` (`HandleError`), `:1042-1043` (audit), `cmd/agentnet/pair.go:121-125`; the frames are not filtered at `internal/envelope/frames.go:198-202` / `internal/relayclient/relayclient.go:449`
- **What goes wrong:** The relay's `error.code` (up to 64 bytes) and `error.message` (up to 200 bytes) are cut to length but not filtered by character. Control characters, ESC, newlines and bidi characters from the relay go (a) into the `pair.fail` audit `code` and `reason`, (b) into `Status.error`, which local agents read over `pair_status`, and (c) unescaped to the terminal: `fmt.Fprintln(stderr, "agentnet: pairing failed: "+msg)`. `verifyPeer` messages also embed `%q`-quoted, attacker-chosen JSON key names in `reason` (`agentcard/canonical.go:71`). That path is quoted, so it only carries attacker text into the audit log.
- **Scenario:** A hostile relay answers a `pair_redeem` with `{"op":"error","code":"x","message":"\u001b[2K\r...Paired with alice (trust: code)...","ref":"pair-…"}`. The user's terminal erases the failure line and shows a fake success. The same 200 bytes of relay-chosen text are stored in the append-only audit log, and a local agent polling `pair_status` sees them as instructions.
- **Spec:** `Docs/protocol/pairing.md` §Logging ("never logged or audited" covers secrets only). The rubric's §1 invariant 4 requires peer input to be bounded and parsed strictly before it is displayed.
- **Fix direction:** Map unknown relay codes to a fixed set, or to `[a-z_]` of 64 bytes at most. Pass `message` through `termSafe` or `strconv.QuoteToGraphic` before storing or printing it.
- **Related:** R09 L4 (length bound applied; charset was not considered), O-100 (same class, other commands)

### C06-03 · Low · confirmed-read
- **Where:** `cmd/agentnet/pair.go:135-136`, `cmd/agentnet/peers.go:90`, `:141`, `:183`; `internal/agentcard/agentcard.go:117` (rejects `IsControl` only)
- **What goes wrong:** A peer's self-signed `name`, `harness` and skills may hold bidi and other `Cf` characters (U+202E, U+2066–2069, zero-width). `agentnet pair`, `agentnet peers`, `peers verify` and `peers remove` print them raw. In the `peers` table they can reorder the TRUST, FINGERPRINT and KEY columns of their own row.
- **Scenario:** A paired or team-introduced peer names itself `"bob‮..."` so that its `peers` row visually shows another fingerprint grouping or trust word. A user comparing fingerprints by eye in `agentnet peers` can be misled, although `peers verify` itself compares the real key.
- **Spec:** none specific (display)
- **Fix direction:** Pass the peer's name, harness and skills through `termSafe` in these commands, or reject `Cf` characters in `checkText`.
- **Related:** O-100, O-067, O-142

### C06-04 · Low · confirmed-read
- **Where:** `internal/daemon/trust.go:150-180` (`peers_verify`)
- **What goes wrong:** `peers_verify` needs the peer and `fp(peer key)`. The fingerprint is public and returned by the `peers` IPC method (`store.go:257-263`), so the call proves nothing that a local IPC caller does not already know. Any local agent can raise any peer to `fingerprint` without a human.
- **Scenario:** A prompt-injected local agent calls `peers` and then `peers_verify {peer, fingerprint}` for (a) a `trust=relay` peer, which lifts the D5 `unverified_peer` refusal on a non-loopback relay, or (b) a team-introduced peer. In case (b), `introduced_by` is cleared (`store.go:307`), so the peer survives team GC and removal of its owner forever. `device_link`, which also sets trust to `fingerprint`, needs a human approval (device.md §Link flow step 2). `peers verify` does not.
- **Spec:** `Docs/protocol/pairing.md` §Storage and trust states, "`fingerprint`: A human compared the fingerprint out of band"; approval.md "Threat model" (local agent is a boundary)
- **Fix direction:** Owner call: make `peers_verify` approval-gated (like `device_link`), or document that `fingerprint` trust is only as strong as local agent confinement.
- **Related:** D5, O-044

## Assumptions and contracts

- `HandleControl`, `HandleError` and `HandleEnvelope` are called serially from one read loop, so `HandleError`→`reissue` cannot interleave with `onCode` (`internal/relayclient/relayclient.go:439-482`). **checked** as far as `dispatch` goes. `reissue` does not re-check `st.Code == ""` (`pairing.go:586`) and relies on this.
- `end` sends `pair_cancel` and runs audit and `Completed` synchronously on the relay read loop (up to 3×5 s). `SendControl` writes directly (`relayclient.go:195-207`), so there is no deadlock. **checked**.
- `mail.ParseAnnouncement(raw, key, now)` checks the signature, `identity == key` and the time window, and returns the canonical `{"announcement","signature"}` (`pairing.go:659`). **unchecked** (C07 scope).

- `Store.OnRemovedTx` (grants and devices, `daemon.go:510`) touches only `tx`. **unchecked**.
- `team.Store.OwnerRemoved` sends the presence goodbyes team.md §Removing the owner asks for (via `s.changed()`, `internal/team/store.go:505`). **unchecked**.

- `resolvePeer` prefers an exact key match over a name match (`internal/daemon/ping.go:110-117`). **checked**.
- The IPC server does not log params (R09 claim). **unchecked** at this commit.

## Checked and fine

- The only v2 store call is after `hmac.Equal` and the claim (`pairing.go:945-962`). v1 is reachable only from `beginRedeemerV1`.
- The issuer sends no tag before a verified `tag_R`. `tag_I` is sent only after store and `Completed` (`:967-978`). Bad or timed-out attempts send nothing.
- Attempts are capped at 3 under `m.mu` when `pair_peer` arrives (`:732`). Each failure is counted once through `att.over`, and the third calls `finish(bad_confirm)` plus `pair_cancel` (`:780-791`, `:1029-1033`).
- The redeemer is single use: `CodeUsed` runs before anything is sent (`:471`), and an atomic `INSERT OR IGNORE` runs right before `tag_R` (`:842`, `store.go:220-225`). It persists and is pruned after 24 h.
- `parseConfirm` is strict: 3 members, `v` is JSON `2`, strict base64url, 32 bytes (`pairv2.go:177-202`). Code generation takes `b&31` from `crypto/rand` (`:54-56`).
- Transcript order: the issuer uses (own, peer) at `:754` and the redeemer uses (peer, own) at `:817`. Both use canonical parts. Role strings are domain-separated.
- `pair.attempt_fail` audits the peer only if the key is well formed (`:784-787`). The relay's code and message are length-bounded (R09 L3/L4 fixes present).
- O-033 is fixed for v2: `verifyPeer` rejects our own key (`:648`). The v1 path still does not check it (not exploitable, as recorded).
- A lookup-taken retry allows 4 `pair_new` in total (`:563-564`) and does not reset `issuedAt`, which keeps the TTL strict.
- The code TTL is issuer-local (`:624-626`). The redeemer's KDF wait is bounded by `RelayWait` (`:820`).
- `Store.List` skips non-canonical keys (R09 L6 fixed, `store.go:257-262`).
- `AddTrusted` keeps `paired_at`, merges mailbox keys, never lowers trust, and clears `introduced_by`, all in one tx.
- `GCIntroduced` refuses a half-migrated teams schema (`store.go:441-443`) and runs `removeTx` per row.
- `peers_remove` cascade order matches R16 M3 (`trust.go:190-214`). The outbox fail runs in the same tx as the delete.

## Notes

- `HandleEnvelope` picks the **last** waiting attempt that matches `(lookup, from)` (`pairing.go:899-903`, no `break`). The relay can replay R's card with an older valid mbox, creating a sibling attempt that consumes R's single `tag_R`. That is only relay DoS, which is out of scope.
- `Close()` leaves pending sessions without timers forever (`armLocked` returns if `closed`). It matters only at shutdown.
