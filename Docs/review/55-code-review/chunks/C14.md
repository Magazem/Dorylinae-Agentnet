# C14: Helper runner and scope execution

Reviewer: CR-R8 · model claude-opus-5-5 · elapsed 9 min · commit 6cc26a7 (worktree HEAD 1da650b; `git diff 6cc26a7 HEAD -- internal cmd` is empty)

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 1 | 0 | 3 | 1 |

The runner is careful. The child's argv, env, directory and stdin come only from the
human's scope. The request carries only a command name. The Windows job is attached before
the first instruction runs. Output is bounded in memory and sanitised to match the D14
rules. Kill on revoke, clear, expiry and replace is wired through `kick` and `watch`.

The one serious gap is the approval display, which is O-167 with new evidence. A scope
whose summary is between 4096 code points and 16384 bytes is accepted for approval, but the
approval window cuts the summary at 4096 code points. A local agent can therefore put a
command last where the human never sees it (C14-02). There are also three Lows:
- the run-time repo re-check does not catch a junction on Windows, although the spec says it does (C14-01, test confirms);
- a failed `finish` wedges the queue and later sends a second, "interrupted" result (C14-03);
- concurrent `device_scope_set` calls do not supersede each other (C14-04).

## Questions

1. **Child inputs.** Nothing comes from the request. `RouteTx` takes only `req.Run.Command`, `req.Type` and `req.Created` (`internal/daemon/device_run.go:236-266`). `execute` builds `RunSpec` only from `plan` (the scope), `internal/daemon/device_run.go:500-504`. Stdin is nil, which means the null device (`internal/device/runner.go:116`). The env is `MinimalEnv(BaseEnv + scope env names)` and drops `DORYLINAE_*` twice: at validation (`internal/device/scope.go` `ValidateScope` env loop) and at build (`internal/device/runner.go:49`). A nil env becomes `[]string{}`, so nothing is inherited (`runner.go:117`). The daemon reads no secret env other than `DORYLINAE_*` (a grep of `Getenv`/`LookupEnv` in `internal`, `cmd`). R24 L1 holds on every OS.
2. **Kill.**
   - **Windows:** the job is created and `KILL_ON_JOB_CLOSE` is set before the child is started `CREATE_SUSPENDED`. The child is assigned to the job, then resumed (`runner_windows.go:30-71`). `BREAKAWAY_OK` is not set, so no child can leave. A daemon crash closes the handle and kills the tree.
   - **Unix:** `Setpgid` and group `SIGKILL` (`runner_unix.go:20-37`). On Linux the leader also gets `Pdeathsig`. The known gaps are O-156 and O-159.
   - **Revoke, clear, replace, expiry:** `kick` → `sweep` → `take` → `stopRunning`/`stillRunning` (`device_run.go:171-213,304-369`). `watch` sweeps at once, which closes the gap before `cur` is set (`:563-586`).
   - **Race with a run that just ended:** revocation wins, and the run is reported as cancelled. That is acceptable.
   - **Restart:** `recoverAfterRestart` does R41 L1 (`:406-450`). Gap: see C14-03.
3. **TOCTOU.** `CheckTarget` runs, then `Run` starts the program by its absolute path. Only the user or an admin can swap the program or a directory above it (`CheckProgramOwner`), so the window between the two is not reachable by another OS user. The repo directory is not ownership-checked; the spec does not ask for that. A swap in that window needs write access to the repo's parent, which means the user themselves or the owner's own ACL mistake (≤ Low). Separately, the directory re-check itself misses junctions: C14-01.
4. **Output.**
   - **Memory:** `tailBuffer` holds at most `rawTail` (128 KiB, `runner.go:23,87-100`). stdout and stderr share one writer.
   - **Sanitising:** CSI sequences, C0 and C1 control characters, invalid UTF-8 and U+FFFD are all replaced (`runner.go:211-249`). This matches `request.ValidateComplete` output rules (`internal/request/result.go:74-80`), so a sanitised output can never fail validation. Only size can fail, and the `trimFront` loop handles that.
   - **Audit:** the audit records only `output_bytes` (`device_run.go:549-552`).
   - **Not stripped:** bidi and zero-width characters. The spec does not require it (see Leads).
5. **Scope summary.**
   - **Shown in full?** No. The window cuts at 4096 code points while the daemon allows 16384 bytes: C14-02 (escalates O-167).
   - **Stored equals approved?** Yes. The same `resolved` value is summarised and stored by `Perform` (`device_scope.go:204-246`). `Precondition` re-checks the link id and the expiry.
6. **`runnerhelper`.** It lives under `testdata/`, which `./...` skips. The release builds only `./cmd/agentnet ./cmd/agentnetd ./cmd/relay` (`.github/workflows/release.yml:143-144`), and the Makefile builds only `./cmd/*`. It is never shipped.

## Findings

### C14-02 · High · confirmed-test
- **Where:** `internal/daemon/device_scope.go:31,209-212` (`maxScopeSummary` = 16384 bytes), `internal/notify/window.go:27,39` (`Clean(summary, 4096)`)
- **What goes wrong:** `device_scope_set` accepts any summary up to 16384 bytes, but the approval window shows only the first 4096 code points followed by "…". Commands listed after the cut, and the closing "Confirm only if you set this scope yourself.", are never shown to the human who types the code.
- **Scenario:** A local agent, possibly prompt-injected, calls IPC `device_scope_set` on the helper.
  1. The first command is a plausible `go test` with one argv of about 4000 characters (for example a long `-run` regex).
  2. The last command is `zz` = `powershell.exe -c <payload>`.
  3. The summary is 4347 bytes, so the daemon accepts it. The window ends in `aaaa…` and the `zz` command is invisible.
  4. The human, who expects a test scope, types the code.
  5. The controller's agent then sends `request … --run zz`, and the helper runs the hidden command.

  This completes an approval-gated scope widening that the human never saw, which is the same class as R46 H2 (debate constraints, rated High). **New versus O-167:** O-167 records only the length mismatch. This finding adds the local-agent actor, the concrete hide-a-command exploit, and a test. Terminal approval mode (off by default) is not affected.
- **Spec:** `Docs/protocol/device.md` §Scope, "a scope whose summary would exceed 16384 bytes is refused … because the approval window must show all of it"
- **Fix direction:** Refuse any summary longer than `notify.MaxWindowSummary` code points, as `debate_constrain.go:95` does, or make the window show 16384 bytes in full.
- **Related:** escalates O-167; R46 H2; O-129
- **Test:** `internal/daemon/zz_review55_C14-02_test.go`: `summary 4347 bytes accepted (limit 16384); window shows 4098 bytes, ends "aaaa…"`, then FAIL "the last command's argv is accepted for approval but not shown in the approval window".

### C14-01 · Low · confirmed-test
- **Where:** `internal/device/runner.go:180-190` (`CheckTarget`)
- **What goes wrong:** On Windows, a repo directory that was replaced by a junction still passes the run-time re-check. Since Go 1.23, `filepath.EvalSymlinks` does not follow mount points, so `resolved == dir`. The command then runs in the junction's target.
- **Scenario:** A writer of the repo's parent swaps `C:\src\repo` for a junction to another directory. That writer is the user, or another OS user only if the owner made the parent writable. The next run passes `CheckTarget` and runs the approved program in the other directory. Impact is small, because that writer could usually edit the repo itself. The finding is that a promise the spec makes is not kept.
- **Spec:** `Docs/protocol/device.md` §Running, "the repo path must still resolve to itself (a directory replaced since by a symlink or junction is refused)". The same spec, §Program ownership, already notes that `EvalSymlinks` does not follow mount points.
- **Fix direction:** Walk the directory with `Lstat` and refuse any reparse point (the `perm.go` link walk already detects junctions), or compare the final path of an opened handle.
- **Related:** R40 L5; O-162 (the same Go behaviour, program side). Also: `TestCheckTarget` has no junction case, and its symlink case skips on this machine, so the promise is untested on Windows.
- **Test:** `internal/device/zz_review55_C14-01_test.go`: `EvalSymlinks(…\repo) = …\repo`, then FAIL "a repo swapped for a junction to another directory passed the directory re-check".

### C14-03 · Low · confirmed-read
- **Where:** `internal/daemon/device_run.go:546-548` (`finish` error only logged), `:338` (`take` starts a job only when `st.Running == nil`), `:421-445` (`recoverAfterRestart`); also `:483` (`_ = r.finish(ctx)`)
- **What goes wrong:** If `finish` fails after the result was submitted, `device.runs` keeps the job as `running`. Two things follow:
  - `take(true)` never starts another queued run, so the helper is wedged until a restart.
  - On restart, the still-valid job is reported again as `"<name>: interrupted"`. `submitResultTx` overwrites the stored result (`internal/worksession/submit.go:78`) and sends a second `ws.result` for the same round.
- **Scenario:** A DB error hits `finish`. Or, more realistically, the daemon stops (service restart, reboot) between the `SubmitResult` commit and `finish`. `finish(ctx)` uses the daemon's context, which is already cancelled. After the restart, the controller receives `fail: interrupted` after the real `pass`. What the controller shows depends on its receive side (unchecked).
- **Spec:** `Docs/protocol/device.md` §Limits: "a run that was executing is reported as fail … interrupted". This run was not executing any more.
- **Fix direction:** Clear `Running` in the same transaction as `SubmitResult`, or run `finish` under `context.WithoutCancel` with a retry. Make `recoverAfterRestart` skip a session that already holds a result for the round.
- **Related:** R41 L1

### C14-04 · Low · confirmed-read
- **Where:** `internal/daemon/device_scope.go:214-216,268-275` (`pending.take` … `apprStore.Create` … `pending.put`)
- **What goes wrong:** The "a newer scope supersedes the older" step is not atomic. When two `device_scope_set` calls run concurrently, both see no pending approval, both create one, and the second `put` overwrites the first entry. The first approval stays pending, and a later clear or unlink no longer rejects it through `pending`. Its own `Precondition` still guards the link.
- **Scenario:** A local agent fires two scope sets at once, and the human sees two windows. Each window shows its own scope, so nothing is hidden. The human may still approve the older scope after the newer one, contrary to the spec's "newer rejects older".
- **Spec:** `Docs/protocol/device.md` §Scope, "A newer `device_scope_set` rejects an older one still waiting for its code."
- **Fix direction:** Serialise `device_scope_set` per controller key, holding a lock across take, Create and put.
- **Related:** O-147

### C14-05 · Info · confirmed-read
- **Where:** `internal/device/runner.go:211-249`
- **What goes wrong:** `SanitizeOutput` leaves bidi controls (U+202E and similar) and zero-width characters in the output that goes to the controller. The spec does not ask for them to be removed. Whether this matters depends on how the controller renders `ws.result` output (`agentnet wait`). That is outside C14; see Leads.
- **Scenario:** A helper program prints `U+202E` in its test output, and the controller's terminal may reorder that line. The helper is the user's own device.
- **Spec:** device.md §Running (lists only CSI and control characters)
- **Fix direction:** None needed here if the controller-side display escapes these characters.
- **Related:** O-126, O-142

## Assumptions and contracts

- `request.Store` calls `Helper.RouteTx` only after D5, team and strict request validation, and it auto-accepts and opens the session in the same transaction when RouteTx returns true (`device_run.go:226`). **Unchecked.**
- `req.Run.Command` is grammar-checked (`[a-z0-9._-]{1,64}`) by request validation. Only an exact map lookup in `Scope.Command` uses it (`internal/device/scope.go` `CheckRunTx`). **Checked:** a bad name can only fail with `CheckCommand`.
- The DB has `SetMaxOpenConns(1)`, so a `kick()` issued inside a caller's transaction sweeps only after that transaction commits (`device.go:336`; `internal/store/store.go:546`). **Checked.**
- `worksession.Store.SubmitResult` and `SubmitCancel` send to the peer through the outbox and do not re-check the device link (`device_run.go:378,535`). **Checked** in `internal/worksession/submit.go:19-90`.
- `CheckProgramOwner` walks every directory and link hop above the program, including junctions on Windows (`runner.go:198`; `internal/device/perm.go`). **Unchecked** (C13 territory).
- `validateResource` resolves the repo path and applies the grant rule at set time (`device_scope.go:134-141`). **Unchecked.**
- `notify.Clean` and the window truncate at `MaxWindowSummary` (`internal/notify/window.go:39`). **Checked** (C14-02).
- `approval.Store` calls `Precondition` and `Perform` in one transaction, and `OnReject` on every reject path (`device_scope.go:225-266`). **Unchecked.**

## Checked and fine

- The request cannot influence argv, env, dir or stdin (`device_run.go:500-504`, `runner.go:116-119`).
- `DORYLINAE_*` is filtered case-insensitively in `ValidateScope` and in `MinimalEnv`. Env names are grammar-checked and folded per OS (`scope.go` `validEnvName`, `envKey`).
- On Windows, `.bat` and `.cmd` programs are refused, including forms with trailing dots or spaces (`scope.go` `resolveProgram`). `argv[0]` is stored absolute, and a relative path with a directory part is refused.
- The Windows job is assigned while the child is suspended, with `KILL_ON_JOB_CLOSE`, no breakaway and handle cleanup on every failure path (`runner_windows.go:30-71`).
- Output memory is bounded (128 KiB raw). A sanitised output always satisfies `result.output` validation. The `trimFront` loop terminates, because output that trims to empty ends it (`device_run.go:534-545,620-629`).
- Nothing in the audit or the logs carries content: `device.run`, `device.out_of_scope`, `device.scope_set` and `device.scope_clear` hold only ids, counts and booleans (`device_run.go:261,527-552`; `device_scope.go:250-253,296`). Log warnings carry the scope's own local paths, never peer text.
- The limits are enforced at route time: 8 queued and 60 per 24 h per controller (`device_run.go:249-256`). `Recent` is pruned and holds only the one controller.
- A running command is stopped when a replaced scope changes its argv, env or dir. A change to `timeout_s` alone does not stop it, as the spec says (`device_run.go:201-213`).
- The approved scope is identical to the stored one, and `Precondition` re-checks the link id and expiry (`device_scope.go:225-246`).
- `device_scope_clear` commits the clear and its audit together, then rejects any pending approval and kicks the runner (`device_scope.go:288-307`).
- The CLI (`cmd/agentnet/device_scope.go`) shows the full resolved scope with `DisplayQuote`/`DisplayArgv`. Types, names and env names are raw, but all are grammar-validated.
- `runnerhelper` is test-only and never built by release or the Makefile.
- O-156, O-159, O-147 and O-167 are still present as recorded; O-167 is escalated in C14-02.

## Notes

- `tailBuffer.Write` moves the whole 128 KiB buffer on every write once it is full. A program that writes one byte at a time costs CPU until its timeout. It is not reachable by a peer.
- In `parseExpires`, `Nd` with a huge N overflows `time.Duration`. The daemon still validates the result, and the window shows the real `expires`.
- `TestCheckTarget` fails on this PC because of the `C:\` ACL (HANDOFF §0), not because of the code.
