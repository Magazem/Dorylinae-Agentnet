# C12: Human approval: store, window, terminal mode

Reviewer: CR-R6 · model claude-opus-5-5 · elapsed 6 min (shell clock) · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 2 · Low 2 · Info 1

The core of the approval gate holds. The code comes from `crypto/rand` and only its HMAC stays
in memory. It reaches only the notifier or the daemon's own stderr. No IPC method or CLI form
accepts a code. The MAC binds each code to its approval id. Rate limits and the lockout are
serialised under `Store.mu`, and a restart expires every pending approval. The Windows, macOS
and Linux dialogs use fixed programs and fixed scripts, get their text through the environment
or `--opt=value` arguments, and are killed on decide, expiry, lockout and daemon stop.

Two Medium defects:
- **C12-01 (confirmed by test):** a lock-order deadlock between `Store.List` and every other
  Store path on the single SQLite connection. It hangs the whole daemon permanently, and a
  normal `approve --list` or `grant_create` running while a human answers can trigger it.
- **C12-02:** grant and grant-policy summaries carry the peer's card name raw. It is not run
  through `notify.Clean` or `stripLongDigits`, and no fingerprint is shown.

## Questions

1. **Can a local agent submit or learn a code?** No path found. Trace:
   - `newCode` (`internal/approval/approval.go:362`) → `codeMAC` (`:380`, in-memory
     `live.mac`) → `deliveryText` (`internal/approval/store.go:201`) → `notifier.Show`
     (`store.go:143`), then the code is dropped.
   - The code is never passed to `WindowRunner.Start` (`store.go:107`, which runs before the
     code exists). It is never in a `View` (`approval.go:207`), SQLite (`store.go:170`), the
     audit (`store.go:187,386,448`) or an error: a Show error becomes a plain `ErrUnavailable`
     (`store.go:148`).
   - Transports: Windows uses env base64 (`internal/notify/approval_windows.go:77`), macOS env
     (`approval_darwin.go:117`), Linux in-process D-Bus (`approval_linux.go:378`), terminal
     mode stderr (`internal/daemon/approval.go:73`).
   - Submit paths: the IPC side has only `approval_list/open/reject`, all `{id}` only
     (`internal/daemon/approval.go:117-151`). The CLI refuses positional arguments
     (`cmd/agentnet/approve.go:76`). `Store.Confirm` is called only by the terminal reader
     (`internal/daemon/approval_terminal.go:83`), which starts only outside desktop mode
     (`internal/daemon/daemon.go:434-453`).
   - One weakness: the Windows toast process that carries the code is resolved through `PATH`
     (C12-03).
2. **Window process.**
   - Programs:
     - Windows: `GetSystemDirectory()\WindowsPowerShell\v1.0\powershell.exe`
       (`window_windows.go:93`).
     - macOS: `/usr/bin/osascript` (`window_darwin.go:63`).
     - Linux: a fixed list of root-owned, non-writable paths (`window_linux.go:39-63`).
   - Scripts are constant. Text arrives through the environment (Windows/macOS) or one
     `--opt=value` argument per value (Linux, `window_linux.go:128,186-194`).
   - `windowText` runs `Clean` on tag, kind and summary and caps the length
     (`window.go:179`).
   - Kill paths:
     - Windows: Job `KILL_ON_JOB_CLOSE`, assigned after `Start`; a failed assignment kills
       the process (`window_windows.go:189-196`; O-139).
     - Linux: `Pdeathsig` (`window_linux.go:205`); no `LockOSThread` anywhere in the repo.
     - macOS: `giving up after`.
   - Output parsing:
     - Windows/macOS: `parseAnswerLine` caps at 256 bytes and anything unknown is dismiss
       (`window_parse.go:278`).
     - Linux: `decodeExit` (`window_linux.go:160`).
     - `isSixDigits` gates confirm (`store.go:841`).
   - Exception: the approval **toast** and its history removal still use `PATH` (C12-03).
3. **Stale or early answers.** Each watcher is bound to `(id, handle)` (`store.go:801-817`).
   The MAC includes the id, so a code typed into another approval's window is a wrong code for
   that approval. At most one window per approval exists: the `opening` flag and the
   `handle != nil` check (`store.go:744`). A window for a decided approval gets
   `unknownOrExpired`. The early answer buffered before Show remains O-137.
4. **Rate limits under concurrency.**
   - MaxPending counts reserved slots (`store.go:73,101`); hourly does not (O-140).
   - Attempts and the daily cap are read-modify-written under `s.mu` (`store.go:283,296`).
   - The 10th wrong code drops every entry before unlocking (`store.go:302`), and
     `Locked` is checked on Create (`store.go:56`).
   - A corrupt settings value fails closed (`settings.go:433`).
   - Restart: `ExpireStale` (`approval.go:317`, called at `daemon.go:427`).
   - Concurrency is broken elsewhere: List vs the other paths deadlocks (C12-01).
5. **Terminal mode.**
   - `resolveApprovalMode` requires both stderr and stdin to be terminals unless
     `DORYLINAE_DEBUG=1` (`internal/daemon/approval.go:44`). The error maps to exit 2
     (`cmd/agentnetd/main.go:124`).
   - The mode is read only from `os.Getenv` at start (`daemon.go:265`). No IPC path sets it,
     and it is audited as `approval.mode` (`daemon.go:435`).
   - The line reader caps at 128 bytes and survives over-long lines
     (`approval_terminal.go:28-53`). An ambiguous prefix uses no attempt (`store.go:18`).
6. **Summaries.**
   - Clean: device link and device scope use `stripLongDigits(notify.Clean(name,40))`
     (`device.go:487`, `device_scope.go:208`). Debate uses `peerDisplayName` + `DisplayQuote`
     (`debate_constrain.go:58-75`). The window applies `Clean` again (`window.go:182`).
   - Not clean: **grant and grant_policy use `peer.Name` raw** (`grant.go:616,960`). That name
     reaches the code notification body and terminal stderr unsanitised (C12-02).

## Findings

### C12-01 · Medium · confirmed-test
- **Where:** `internal/approval/store.go:943-961` (`List`: `windowState` → `s.mu.Lock()` inside
  the open `rows` loop), against `store.go:54-86` (`Create` takes `s.mu`, then queries),
  `store.go:250-257` (`confirm`), `store.go:24` path via `sweepExpiredLocked`; `internal/store/store.go:546` (`SetMaxOpenConns(1)`)
- **What goes wrong:** `List` holds the only pooled SQLite connection (an open cursor) and
  takes `s.mu` for each row. `Create` and `confirm` hold `s.mu` and then wait for a connection.
  The two lock orders deadlock. IPC handlers get the daemon's lifetime context
  (`internal/ipc/ipc.go:138-176`), and the window's `confirm` runs with
  `context.Background()` (`store.go:822`), so the wait never times out. The approval store
  and every other DB user in the daemon (mail, IPC, audit) hang until the process is killed.
- **Scenario:** desktop mode with at least one pending approval. A local agent, or the human,
  runs `agentnet approve --list` (`approval_list`) while another caller runs `grant_create`,
  or while the human's window answer is being confirmed. Both need only normal use. A
  prompt-injected agent can loop `approval_list` and `grant_create` to hit it on demand. The
  daemon then stops serving, and after a restart every pending approval is expired.
  Temporary test `internal/approval/zz_review55_C12-01_test.go`
  (`TestReview55_C12_01_ListDeadlocksWithCreate`) deadlocks within 3 s. Terminal mode is not
  affected: there `windowState` does not lock.
- **Spec:** none directly. `internal/request/query.go:136-139` documents this exact pitfall
  for the same connection.
- **Fix direction:** collect the rows and close the cursor before calling `windowState`, or
  read the handle map once under `s.mu` before querying.
- **Related:** O-127 (work under `Store.mu`)

### C12-02 · Medium · confirmed-read
- **Where:** `internal/daemon/grant.go:616` (grant), `internal/daemon/grant.go:960`
  (grant_policy); sinks `internal/approval/store.go:204,209` (`deliveryText`),
  `internal/daemon/approval.go:73` (terminal notifier), `cmd/agentnet/approve.go:116`
- **What goes wrong:** the grant and grant-policy approval summaries put `peer.Name` (the peer's
  self-chosen card name) in verbatim. `agentcard.checkText`
  (`internal/agentcard/agentcard.go:109`) refuses only `unicode.IsControl` and has a 128-rune
  cap. So bidi controls (U+202E and similar), other `Cf` characters and long digit runs
  survive into:
  - the code notification body (`notify.Approval.Show` does not clean);
  - terminal mode's stderr line, next to the real code;
  - `agentnet approve --list`.

  No fingerprint is shown either. The other kinds apply `stripLongDigits(notify.Clean(...))`.
  The window alone re-cleans the text (`window.go:182`), and that removes only the listed bidi
  controls, not decoy digits.
- **Scenario:** a paired or team-introduced peer names itself `Alice` (same as a trusted peer,
  O-067) or `Bob. Code 314159. Type "a-…`. A prompt-injected local agent calls `grant_create`
  for that peer. The human sees "approve grant read on repo to Alice …" in the toast or
  terminal and cannot tell the twin apart, since there is no fingerprint. In terminal mode the
  decoy code also sits on the same stderr line as the real one; a decoy burns attempts and the
  daily cap. RLO in the name reorders how the line reads.
- **Spec:** `Docs/protocol/approval.md` §Threat model: "The notification names the local action
  and the peer's name and fingerprint". §Flow 1: "Peer-supplied text in the summary goes through
  `notify.Clean`". `notify.md` §Text and sanitising: "the peer's card `name` … Before they are
  used in any notification … `notify.Clean`".
- **Fix direction:** build grant and policy summaries with the same
  `stripLongDigits(notify.Clean(name,40))` plus the fingerprint used for device kinds.
- **Related:** escalates O-129: that entry records the risk as mitigated by `stripLongDigits`,
  but the grant path, the most common approval, never calls it. Also O-067, O-100.

### C12-03 · Low · confirmed-read
- **Where:** `internal/notify/approval_windows.go:86,95`, via `run` in `internal/notify/desktop.go:33`
- **What goes wrong:** the approval toast, whose environment carries the code in
  `AGENTNET_A_TITLE`, and its history removal start `"powershell.exe"` through
  `exec.LookPath`, which searches `PATH`. Review 29 L2 is marked "fixed" and the spec requires
  the same absolute `GetSystemDirectory` path. Only the dialog was switched
  (`window_windows.go:93`).
- **Scenario:** a `PATH` directory ahead of System32 that another local user can write to (for
  example a world-writable tool dir added to the system PATH). A planted `powershell.exe`
  receives every approval code. This needs a misconfigured machine, so Low per rubric §2.
- **Spec:** approval.md §The approval window, Windows row: "The approval toast and its history
  removal switch to the same absolute path (today `powershell.exe` is found through `PATH`)."
- **Fix direction:** have `showApproval` and `removeApproval` use `powershellPath()`.
- **Related:** R29 L2

### C12-04 · Low · confirmed-read
- **Where:** `internal/notify/approval_linux.go:386-388` (`notifIDs`), fed by `store.go:895`
  (`notifyOutcome`) and `store.go:585` (lock notice)
- **What goes wrong:** on Linux every approval notification id is stored in the global
  `notifIDs` map. That includes `outcome-<id>` and `lock-<ts>`, and nothing ever removes those.
  The map grows by one entry per outcome for the daemon's lifetime.
- **Scenario:** at most about 20 approvals per hour gives about 500 small entries a day. The
  growth is local and slow; only a long-running daemon notices.
- **Spec:** none
- **Fix direction:** record ids only for approval-code notifications, or skip outcome and lock ids.
- **Related:** none

### C12-05 · Info · confirmed-read
- **Where:** `internal/approval/store.go:283-313`
- **What goes wrong:** when `recordBadCode` succeeds but `settings.recordWrongCode` fails (a DB
  write error), the per-approval attempt counts but the daily wrong-code cap does not. The
  daily cap fails open on a rare DB error. It needs DB write failures, and the per-approval 3
  attempts still hold.
- **Scenario:** none practical without a failing disk.
- **Spec:** approval.md §Object (10 per 24 h)
- **Fix direction:** write both in one transaction (same as O-128).
- **Related:** O-128

## Assumptions and contracts

- `Action.Precondition/Perform` never call back into `Store` (they run under `s.mu`,
  `store.go:343-358`). Callers: `grant.go`, `device.go`, `device_scope.go`,
  `debate_constrain.go`. **Unchecked** beyond the Create sites.
- `Action.OnReject` does not call the Store (`approval.go:113-121`); `device.go:482`
  (`ds.RevokePending`) is **checked**.
- Summaries passed to `Create` are already sanitised by callers (the store and notifier do not
  clean them for the notification or terminal). **Checked**: this fails for `grant.go:616,960`
  (C12-02).
- `store.Open` uses one connection (`internal/store/store.go:546`). **Checked**: this is
  what makes C12-01 a deadlock.
- The IPC server passes the daemon-lifetime ctx with no per-request deadline
  (`internal/ipc/ipc.go:173`). **Checked**.
- `DORYLINAE_APPROVAL` cannot reach the daemon's environment through a service
  install or config that an IPC caller controls (`internal/service/*`). **Unchecked**.
- `agentcard.checkText` bounds a peer name to 128 runes with no C0/C1
  (`internal/agentcard/agentcard.go:109`). **Checked**; it allows `Cf`/bidi.

## Checked and fine

- Code generation is uniform by rejection sampling (`approval.go:362-376`). The MAC matches the
  spec vector (`vectors_test.go`), and the comparison is constant time (`store.go:280`).
- There is no code material in SQLite, the audit, a `View`, an error or the window
  (`store.go:170-195`, `approval.go:187-192`).
- A reserved slot cannot be confirmed, rejected, reopened, resolved or swept
  (`store.go:28,252,638,686,716`). A lockout or `Close` during the ready wait stores nothing
  (`store.go:157-169`).
- Window-before-code ordering and kill-on-notifier-failure are correct (`store.go:106-149`).
- The Precondition and Perform transaction and AfterCommit ordering are correct:
  AfterCommit runs after commit and outside `s.mu` (`store.go:332-393`).
- The per-approval timer, and `expireNow` guarded by `AND state='pending'` + `RowsAffected`
  (`store.go:524-558`).
- `Close` kills every window and stops every timer; `reopen` honours `closed`
  (`approval.go:291`, `store.go:744,761`).
- The Windows session-0/WinSta0 check, `CREATE_NO_WINDOW`, job-handle close-once
  (`window_windows.go:107-115,170,200`).
- Linux: never PATH, no dbus-launch autostart (`approval_linux.go:315`), markup escaped in the
  body and dialog args, and `--opt=value` form.
- macOS: fixed script, env text, non-cancel error re-raised → early non-zero = not ready
  (`window_darwin.go:25-46,87-92`).
- The terminal reader survives over-long lines and a final unterminated line
  (`approval_terminal.go:28-53`).
- The CLI has no code form (`cmd/agentnet/approve.go:76`). O-129's `stripLongDigits` mitigation
  is present for device and debate (but see C12-02). Open O-127, O-128, O-136-O-141, O-147,
  O-164, O-166 and O-167 are still as described; they were not re-reported.
