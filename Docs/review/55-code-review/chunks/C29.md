# C29: Spec vectors: generator and independent verifier

Reviewer: CR-C29 · model claude-opus-5-5 · elapsed ~20 min · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 0 · Info 3

Verdict: `tools/verifyvectors` is independent in the way it claims. It imports no `internal/`
package and nothing from `tools/specvectors` (checked with `go list -deps`). It recomputes every
published cryptographic value from primitives: fingerprints, K, T, tags, confirm payloads, HPKE
open, grant hash and signature, audit chain, debate commitment, Decision hash and signatures, and
relay auth v2. The values in `vectors.json` match the protocol documents, and they match a fresh
`go run ./tools/specvectors`. Every published vector is also asserted by a production-package
test, which is what actually ties the specs to the code.

What remains are Info-level gaps in how much the verifier re-derives versus accepts as given.
Some inputs are only checked for being canonical and correctly signed: the Decision object, the
agent cards and the mail plaintext fields. Nothing in the verifier cross-checks one section of
`vectors.json` against another. The generator's cards come from production `internal/agentcard`.
None of these gaps lets a wrong production implementation pass `go test ./...`.

## Questions

1. **Independence.** `tools/verifyvectors/{main,decision,relayauth}.go` import only the
   standard library and `golang.org/x/crypto/argon2` (`main.go:16-39`, `decision.go:3-12`,
   `relayauth.go:3-11`; `go list -deps` shows no `internal/` package). Several things are shared
   with production:
   - (a) The **primitive implementations**: Go's `crypto/hpke`, `crypto/ed25519`, `crypto/ecdh`
     and `x/crypto/argon2`. A bug in one of these would not be caught. That is acceptable: they
     are upstream and RFC-tested.
   - (b) The **generator** `tools/specvectors` imports `internal/agentcard` to build and sign
     `card_I`/`card_R` (`specvectors/main.go:40,146-160`), so the card vectors are
     production output (C29-03).
   - (c) `internal/envelope/authv2_vector_test.go:18` reads `tools/verifyvectors/vectors.json`
     directly. The file is shared data, not shared code, so this is fine.
2. **Coverage: recomputed from primitives versus compared as strings.**
   - **Recomputed from primitives:**
     - identity keys and fingerprints (`main.go:478-484`);
     - K and salt (`:528-532`);
     - T over the canonical card and mbox bytes, and tag_I/tag_R (`:535-544`);
     - the confirm plaintext and payload, built by hand (`:547-552`);
     - the mailbox pub and key_id from the private key, info/aad rebuilt from the plaintext's
       from/to/id, the payload layout, an HPKE open, and the sender signature (`:579-667`);
     - the grant canonical form from hard-coded fields, its hash, the recomputed signature and
       the token (`:699-778`);
     - genesis, `row_c` and each row hash, plus the chain_start counts (`:819-853`);
     - the debate session id and commitment (`:441-458`);
     - the Decision id, hash and both signatures (`decision.go:229-237`);
     - the relay origin (its own parser, not `net/url`), message and signature
       (`relayauth.go:49-65`).
   - **Only checked as canonical and signature-valid, not re-derived:**
     - card_I/card_R content (`main.go:498-512`);
     - the mailbox announcements' fields;
     - the mail plaintext's `created`/`kind`/`body` (signature only);
     - the debate `position` (`:446-451`);
     - the Decision object as a whole: derivation rules 1–12 are not re-applied, and the
       verifier hashes the string from `vectors.json` (`decision.go:223-228`).
     
     The `stale` negative is arithmetic on two JSON fields, not on the plaintext's `created`
     (`main.go:686-689`). See C29-01 and C29-02.
   - **Negatives exercised:** tag byte flips and role swap; secret change; enc/ct bit flips,
     wrong aad and swapped info; widened exp and removed scope; another author, session or
     nonce; six Decision `§Signed file` negatives; origin binding and the v1 domain.
3. **Can the gate pass while production is wrong?** Yes, by construction. `verifyvectors` checks
   the specs' transcribed values against its own re-implementation and never runs production
   code. `TestDetectsMismatch` and similar tests (`main_test.go:21-78`) show it does fail on
   corrupted values, so it does not verify the file against itself trivially.

   Production correctness comes from package tests that assert the same published values
   through the production functions, all run by CI `go test ./...` (`ci.yml:35`):

   | Vector | Production test |
   |---|---|
   | pairing K, T, tags, confirm payloads | `internal/peers/pairv2_test.go:27-90` |
   | mail open of the published payload, key_id, stale | `internal/mail/mail_test.go:57,103-158,292` |
   | grant hash, signature, token round-trip | `internal/capability/token_test.go:21-96` |
   | audit row hashes | `internal/audit/chain_test.go:134` |
   | debate commitment | `internal/debate/flow_test.go:36` |
   | Decision derivation and verify, read from `decision.md` | `internal/decision/decision_test.go:26-205` |
   | relay auth v2, read from `vectors.json` | `internal/envelope/authv2_vector_test.go:17` |
   | fingerprints | `internal/envelope/fingerprint_test.go:8` |

   A script matched every string of length > 12 in `vectors.json` against `internal/**` and
   `cmd/**` tests. Every value is covered, directly or through an equivalent encoding: the
   hex/base64 twins of tested values, the payload that contains enc/ct, and the Decision
   canonical form that `decision_test` reads from the doc.

   What the pipeline cannot catch: a wrong value transcribed identically into the doc,
   `vectors.json` and the production test. The verifier's independent recomputation covers the
   crypto values. The non-re-derived items listed in answer 2 depend on the spec author.

## Findings

### C29-01 · Info · confirmed-read
- **Where:** `tools/verifyvectors/main.go:579-690` (`mail`), also `:686-689`
- **What goes wrong:** the mail section is checked only against itself. Nothing ties
  `mail.priv_hex`/`pub_hex`/`key_id_hex` to the pairing `mbox_R` announcement (seed `60…7f`) or to
  `mail.md`'s stated recipient. Nothing checks that plaintext `from`/`to` equal `key_I`/`key_R`, or
  that `mail.created` equals the plaintext's `created`. The `stale` negative subtracts two JSON
  fields, so it cannot fail for a real implementation bug. `parseRFC3339Z` also ignores `Atoi`
  errors (`:877`).
- **Scenario:** no attacker. A future vector revision regenerates the mail section with a
  different mailbox key, or edits `created` in only one place. The verifier still prints "all
  vectors reproduced" while the published mail vector no longer matches pairing.md's `mbox_R`.
  Today all of these are consistent: a script compared the mbox_R pub and key_id, from, to and
  created, and all were true.
- **Spec:** `Docs/protocol/mail.md` §Test vectors ("using the recipient key above"; negatives
  list)
- **Fix direction:** assert the cross-section equalities, and take `created` from the opened
  plaintext.
- **Related:** none

### C29-02 · Info · confirmed-read
- **Where:** `tools/verifyvectors/decision.go:221-237`; `main.go:446-451`
- **What goes wrong:** the verifier hashes and signs the Decision canonical string from
  `vectors.json`, but does not re-derive it from the debate transcript under `decision.md`
  derivation rules 1–12. The debate `position` is likewise only checked for being canonical. The
  independent check of the Decision therefore stops at "canonical, id, hash and signatures". The
  derivation itself is checked only by production `internal/decision/decision_test.go:123`
  (`TestDecisionVector`).
- **Scenario:** a spec author writes a Decision object that violates a derivation rule, for
  example `final_agreement` copied from the wrong entry, and the production derivation is changed
  to match it. The verifier passes because it only checks the invariants at `decision.go:188-216`.
  Only a human reading rules 1–12 would notice.
- **Spec:** `Docs/protocol/decision.md` §Vector, derivation rules
- **Fix direction:** optionally re-derive the vector Decision from the transcript in the
  verifier, or state in `decision.md` that derivation is covered by package tests only.
- **Related:** none

### C29-03 · Info · confirmed-read
- **Where:** `tools/specvectors/main.go:40,146-160` (`signedCard` calls `agentcard.New/Sign/Canonical`);
  `tools/verifyvectors/main.go:498-512`
- **What goes wrong:** the card vectors are produced by the production package, not
  re-implemented. The verifier checks only that each card is a canonical fixed point and that
  its signature verifies. It does not check the card schema of agent-card.md (field set,
  `version`, `created` format, skill fields).
- **Scenario:** a regression in `agentcard.New` emits a wrong field, such as a `created` with
  sub-second precision. The regenerated vector would pass the verifier and go into pairing.md
  unnoticed, and T and the tags would change to match. Today the cards match agent-card.md
  (`:161` shows the same card_I bytes, and `:14`/`:26` give the field set).
- **Spec:** `Docs/protocol/agent-card.md` §Fields; pairing.md §Test vectors
- **Fix direction:** have the verifier check the card field set and values against the spec text,
  or build the cards in `specvectors` without `agentcard`.
- **Related:** none

## Assumptions and contracts
- `vectors.json` is a faithful transcription of `Docs/protocol/{pairing,mail,grant,audit,debate,decision,envelope}.md`
  (`verifyvectors/main.go:7`). **Checked:** every string value appears in the docs, apart from
  `capability.token` (not published in grant.md), the audit `detail` values (published only
  escaped inside `row_c`) and the relay-auth `message_hex` for cases 1–4 (only case 0's message
  is printed in envelope.md).
- The production code matches the vectors through package tests (table in answer 3).
  **Checked:** each test calls the production functions, e.g. `pairv2_test.go:72-90`,
  `mail_test.go:106`, `token_test.go:74-84`, `decision_test.go:125`, `authv2_vector_test.go:50-62`.
- The merge gate runs the verifier (HANDOFF §2 rule 5). **Checked:** CI has no explicit
  `go run ./tools/verifyvectors`, but `go test ./...` (`ci.yml:35`) runs
  `tools/verifyvectors/main_test.go:9` `TestVectors`, which calls the same `run()`.
- `specvectors` relies on `internal/agentcard.New/Sign/Canonical` to produce spec-conformant cards
  (`specvectors/main.go:146`). **Checked** for the current output against agent-card.md:161.
- Go's `crypto/hpke`, `ed25519`, `ecdh` and `x/crypto/argon2` are correct. **Unchecked**
  (upstream).

## Checked and fine
- `go run ./tools/verifyvectors` prints "all vectors reproduced". `go test ./tools/verifyvectors`
  passes, and its mismatch tests prove that failures are detected and counted (`main_test.go:21-78`).
- A fresh `go run ./tools/specvectors` reproduces every deterministic value in `vectors.json`:
  K, T, tags, cards, mbox, grant canonical/signature/token, Decision canonical/hash/signatures,
  debate position and commitment, audit rows, and all relay-auth messages, signatures and the frame.
- `specvectors -open <published payload>` opens mail.md's payload: "open OK".
- The verifier's canonicaliser rejects duplicate keys, trailing data, invalid UTF-8,
  non-integers and |n| ≥ 2^53, and sorts keys by UTF-16 (`main.go:116-252`).
- The relay re-escaping of `< > &` in card_I is undone by canonicalisation (`main.go:516-525`).
- The relay origin is derived by a parser written from the text, not `net/url` (`relayauth.go:94-137`),
  unlike the generator (`specvectors/main.go:285`). The two implementations agree on all 5 cases.
- The Decision negatives cover signature misplacement, hash, added member, id, free text and
  final_agreement (`decision.go:272-306`).
- The verifier uses `DisallowUnknownFields` on `vectors.json` (`main.go:420`).
- O-021 (origin form of IPv6 and trailing dots) is untouched here. The vector's trailing-dot case
  collapses as documented.

## Leads for other chunks
- `internal/mail/receiver_test.go:334-367` tests a 15 d receive age limit, while the mail.md
  vector negative speaks of 30 d at step 11. They are probably two different limits (open versus
  receive), but worth a glance by the mail chunk.

## Notes
- `specvectors.write` escapes strings with `encoding/json`, so it is correct only for the
  characters in the vectors (the comment at `:52-56` says so).
- `verifyvectors.canonical` inherits `encoding/json`'s silent lone-surrogate → U+FFFD replacement.
  This is harmless for the fixed vectors.
