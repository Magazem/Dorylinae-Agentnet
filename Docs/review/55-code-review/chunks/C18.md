# C18: Requests: lifecycle, mirror, cancel, result

Reviewer: CR-C18 · model claude-opus-5-5 · elapsed 5 min (wall clock from `date`) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 0 | 2 | 1 |

Verdict: the lifecycle core holds up. Every IPC transition resolves the row by
direction: `in` rows for accept/decline/defer/complete, `out` rows for cancel/resend.
Every mirror kind is keyed by `(msg.from, id)` and gated by `seq`. Result payloads are
validated the same way on both sides and capped at 64 KiB. Audit rows carry sizes only.
Outgoing mail is queued in the same transaction as the state change, and audit and
notification run after commit. I found no Critical, High or Medium. Two Lows: a modified
worker can make A's request mirror final while A's work session stays open with live
grants, and a peer can hide one of its `in` rows behind A's `out` row with the same id in
`request_show`. One Info: an audit field is missing. Known open findings O-101, O-102,
O-103, O-106, O-120 and O-148 are all still present as recorded.

## Questions

1. **Only the authoritative side moves state; `seq`; the diagram.**
   - Mirror updates look up the row by `(direction='out', peer = msg.from, id)`
     (`internal/request/mirror.go:289`). A peer can move only its own requests.
   - `seq > state_seq` gates step 4 (`mirror.go:304`). A stale or reordered update changes
     nothing except the step 5 cancel refusal (`mirror.go:333-340`), which is what the spec
     asks for.
   - Following request.md §Sender mirror step 4, the mirror does not check the transition.
     Decline or cancelled after accept therefore applies, and this leaves an open session
     behind (C18-01).
   - On the recipient, `transitionTx` checks the allowed sets (`lifecycle.go:17-20,174`)
     inside one transaction. Cancel is accepted only from `pending`/`deferred`
     (`cancel.go:254`).
2. **Result payload and its visibility.**
   - `DecodeResult` + `ValidateComplete` + `CheckCompleteSize` run at IPC
     (`lifecycle.go:316,349`, `daemon/request_lifecycle.go:32-49`) and on receipt
     (`mirror.go:199-218`). The total is measured on the body actually sent, including
     `seq` and `at`.
   - The quarantine decision is made before anything is stored (`mirror.go:221-242`). A drop
     blanks note and result and sets `op.Withhold`, so D18 holds.
   - `request_show` on A shows only `requests.result`. An honest B writes that column only
     after the session is closed (work-session.md §Closing). The session result itself never
     reaches the request view, which carries only `session {id,state,round}`
     (`request_lifecycle.go:219-227`).
   - So, by session state:
     - `open`, `awaiting_result`, `quarantined`: no result in the view.
     - `closed` + accepted: the D14 result, unless the quarantine rule holds. It then gets
       dropped, which is O-148 and still present (`worksession/hooks.go:108-115`).
     - Discarded: B sends "session cancelled" with no result.
   - `request_list` and `inbox_list` omit `output` (`request_lifecycle.go:482,509`).
3. **Cancel flows.**
   - Sender side: refused after accept/decline/complete (`cancel.go:68`). An in-flight cancel
     is not duplicated (`:71-84`).
   - Tombstones: capped at 1000 per sender (`cancel.go:303`) and pruned after 31 d, but only
     on the early-cancel path (O-102).
   - No reply loops: `request.cancelled` at the sender is mirror-only, and an orphan only
     writes an audit row (`mirror.go:290-292`). The refused/duplicate echo goes through
     `resubmitStale` with a 10-minute throttle (`cancel.go:368-407`), run after commit.
   - O-103 is unchanged: nothing re-drives a sender stuck on `cancel=requested`.
   - O-120 (cancel and accept crossing) is unchanged.
4. **Role checks and ambiguous ids.**
   - accept/decline/defer/complete go through `findInRow`. Several matching `in` rows without
     `from` give `ErrAmbiguousRequest` (`lifecycle.go:43-71`).
   - cancel/resend go through `findOutRow` (`lifecycle.go:75-89`).
   - `request_show` looks up `out` first, as ipc.md:347 specifies. A peer that reuses the id
     of A's own `out` request can shadow its `in` row: C18-01 and C18-02.
   - The `from` param is resolved by `resolveFrom` (`request_lifecycle.go:296-311`). An
     unknown name fails, and a raw key passes.
5. **Transaction discipline.**
   - `transitionTx` updates the row, submits the outbox mail, opens the session and ends the
     debate, all through `tx` (`lifecycle.go:167-218`). Audit runs after commit
     (`:265,285,308,381`).
   - `AcceptInTx` and `CompleteInTx` return after-commit closures instead of auditing inside
     the transaction (`lifecycle.go:251-253`, `session_hooks.go:142-146`).
   - Mirror and cancel Apply read and write only through `tx`. `afterMirror`/`afterCancel`
     do notify, audit and the echo after commit (`mirror.go:348-388`, `cancel.go:329-361`).
   - `resubmitStale` opens its own transaction only after the dedupe transaction has
     committed.
   - No R27 C1 pattern found in scope.

## Findings

### C18-01 · Low · confirmed-read
- **Where:** `internal/request/mirror.go:122-160` (`applyDecline`) and `:267-277` (`applyCancelled`). Contrast `:219-237` (`applyComplete` → `EarlyComplete`). Also `internal/worksession/receive.go:109`.
- **What goes wrong:** a `request.decline` or `request.cancelled` with a higher `seq`, arriving after the accept, moves A's mirror to a final state. Neither kind calls any session hook, so A's work session stays `open` with its grants live. From then on, B's `ws.result` is ignored because the request is declined/cancelled (`receive.go:109`). For a debate, `EndedTx` closes the debate row while its session stays open (`mirror.go:322-326`).
- **Scenario:** a modified paired peer B accepts A's request, which opens sessions on both sides. A grants B read access in the session. B then sends `request.decline {seq: 2}`. A's `request show` says `declined`, and A's human believes the work ended. The session is still `open`, the grant stays usable until it expires, and nothing auto-closes it. The session can end only through a manual `session --cancel`.
- **Spec:** work-session.md §Early complete: "a session can never stay `open` with live grants after the worker considers the work done". The only rule is for `request.complete`. request.md §Sender mirror step 4 says "The sender does not check the transition."
- **Fix direction:** on a mirror move to `declined`/`cancelled`, close an open requester session as cancelled, the same way `EarlyComplete` does.
- **Related:** O-120, O-121 (same "modified B" class), O-148.

### C18-02 · Low · confirmed-read
- **Where:** `internal/request/query.go:12-30` (`Show`), `internal/daemon/request_lifecycle.go:442`. The receive path does not check for a colliding `out` id (`internal/request/receive.go`, C17).
- **What goes wrong:** request ids are unique per sender, so a paired peer B can send A a new request whose id equals A's own `out` request to B, which B knows. `Show` returns the `out` row whenever one exists and ignores `from`. B's `in` row cannot be shown by `request show <id> [--from B]`. At the same time `agentnet accept|decline|complete <id>` acts on B's `in` row (`findInRow`).
- **Scenario:** A sent `r-X` to B. B sends a request with id `r-X` and a title that mimics A's own request. A's human sees `r-X` in the inbox. `request show r-X` displays A's own request with its state and result, while `complete r-X` or `accept r-X` acts on B's request. This confuses the human; it bypasses nothing (the accept still needs the human, and grants still need approval).
- **Spec:** `Docs/protocol/ipc.md:347` ("Looks up `out` rows first, then `in` rows (`from` narrows the `in` lookup)"). The spec did not consider an id shared across directions.
- **Fix direction:** reject an incoming request whose id matches an existing `out` row to the same peer, or make `from` force the `in` lookup.
- **Related:** O-100 (spoofing through display).

### C18-03 · Info · confirmed-read
- **Where:** `internal/request/cancel.go:354-359` (`afterCancel`)
- **What goes wrong:** `request.cancel_in {result: "cancelled"}` leaves out `age_s`, which request.md §Audit and metrics lists for `cancelled`. `cancelOutcome` does not capture `received_at`. This is metric drift, with no content or security impact.
- **Scenario:** none (metrics only).
- **Spec:** request.md §Audit: "For `cancelled`, also `team`, `type`, `urgency`, `seq` and `age_s`".
- **Fix direction:** add `age_s` from the row's `received_at`, or drop it from the spec.
- **Related:** none

Relied on by `mirror.go:240-242` and `cancel.go`. Spec: work-session.md #inbox-copy-d18. I did not re-read `internal/mail/receiver.go`.
- **unchecked.** `op.Msg.From` is the authenticated signer, and `op.Msg.Created` is validated against the window before Apply (`cancel.go:220`, `mirror.go:289`). Relies on `internal/mail`.
- **checked.** `EarlyComplete` touches only `tx` and returns `after` for audits (`worksession/hooks.go:73-146`). It returns no error for an orphan request (`requestType` gives `ok=false`, `worksession/debate.go:86`).

For a `debate`-type `out` row with no debate row, this would fail every redelivery of the accept. Relies on the submit `InTx` always inserting that row.
- **unchecked.** `CompleteShorthand` runs its own transaction and returns `ok=false` only when no session exists (`lifecycle.go:324`, `worksession/submit.go:141`).
- **unchecked.** `Outbox.SubmitTx` writes only through `tx`. Relied on everywhere in scope.
- **unchecked.** The `receive.go` tombstone lookup (`:373-381`) stores a late request as `cancelled` with `state_seq = 1` and a matching `last_reply`. `applyEarlyCancel` replies `seq: 1` on that assumption (`cancel.go:316`). C17 owns it.
- **unchecked.** The daemon wires `s.Notify` to `internal/notify`, which applies the title opt-in and sanitising. `NotifyInfo.Title` carries peer content (`mirror.go:362`, `cancel.go:342`).

## Checked and fine

- Result strictness: unknown members, empty strings, non-integer `exit_code` and non-string artifact members are all rejected (`result.go:104-177`). Output allows no C0 except `\n\t` (`result.go:78`).
- The total cap uses the real `seq`/`at` (`lifecycle.go:345-351`, `session_hooks.go:97-103`), and the receiver re-checks it (`mirror.go:212-218`).
- Audit rows in scope carry no titles, reasons, notes or result fields, only sizes (`lifecycle.go:102-114,375-381`, `mirror.go:372-387`, `cancel.go:350-360`, `session_hooks.go:136-141`).
- Cancel `at ≤ msg.created` is checked (`cancel.go:220`). The `reason` is 1–500 code points with `\n` only (`:234-238`).
- Decline code/reason pairing is enforced (`mirror.go:135-153`). Defer checks `at < until ≤ at+90d` (`mirror.go:175-180`).
- Orphan lifecycle mail: acked and audited, with no reply (`mirror.go:290-292,372-374`).
- Resend is refused unless `pending`, no cancel, mail `expired`/`failed`, and age under 21 d (`cancel.go:136-152`).
- Idempotency race: the unique conflict leads to a re-lookup and a `params_hash` compare (`submit.go:121-133`). O-094 is still present (`submit.go:214`).
- O-101 is still present: the mirror does not check `at ≤ msg.created` (`mirror.go:420-439`). O-106 is still present (`request_lifecycle.go:360`). O-104 is still present (`result.go:230-247`); the input is validated first.
- O-148 is still present: `EarlyComplete` applies the quarantine rule to a `closed` session (`worksession/hooks.go:108-115`).
- Targeted tests pass (see below). I did not systematically audit the tests for ones that cannot fail.

## Leads for other chunks

- `internal/request/validate.go:344`: `hasControl` treats `U+FFFD` as a control character. A valid result output or brief that contains a literal U+FFFD (common in test logs) is rejected with "must not contain control characters". Correctness only (C17).
- `internal/request/submit.go:187-203`: the sender-side urgency budget count runs outside the insert transaction, so concurrent submits can exceed the courtesy budget. The receiver budget still applies (C17 Q3).
- `internal/request/receive.go`: no check that an incoming request id differs from an `out` id to the same peer (see C18-02, C17).
