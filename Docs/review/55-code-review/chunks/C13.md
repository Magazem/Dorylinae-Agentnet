# C13: Device link, helper scope, program ownership

Reviewer: CR-R3 · model claude-opus-5-5 · elapsed 14 min · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 0 | 1 | 2 |

Verdict: the link flow, the hierarchy, the scope validation and the program-ownership walk
match device.md and D13/D22/D24. I found no way to create or activate a link without both
local approvals, no way to get a shell/batch/PATH-resolved program into a scope, and no
fail-open in the ownership walk. A test on this PC showed that a junction is judged by its
own access list (not its target's), which the spec requires and the existing test could not
prove. The one Low is that a Unix script's `#!` interpreter is never checked for ownership.
The two Info items are a design note on the unlink watermark and a small leak on a
failed commit.

## Questions

1. **Link without both approvals (D13); freshness and watermark.** No path found.
   - Only `internal/device` writes `device_links`/`device_offers`/`device_scopes` (a grep
     outside the package finds only the migration, `internal/store/store.go:334`).
     Team, roster, pairing and `peers verify` do not touch them.
   - Activation needs a local `waiting` intent (`internal/device/device.go:563`). The only
     way to get one is `ApproveTx` inside the `device_link` approval's `Perform`
     (`internal/daemon/device.go:428`), after the human typed the peer's fingerprint
     (constant-time compare, `:375`) and the local code.
   - The peer's half is a signed mail. `mail_submit` refuses `device.*`
     (`internal/daemon/outbox.go:25`), so a local agent on the peer cannot send it.
   - `parseOffer` (`internal/daemon/device.go:154`) is strict: exactly five members, a
     valid role and nonce, and the sender/recipient keys must fill the roles.
   - Freshness: `OfferFresh` (`internal/device/device.go:494`) enforces
     `now < at+10m` and `at ≤ now+10m`. It is applied on receipt (`daemon/device.go:229`),
     again in `TryActivateTx` (`device.go:570`) and on the kept-offer path (`daemon/device.go:459`).
     `TryActivateTx` also checks `at ≥ intent.created−10m`, and `OfferGetTx` checks
     `received_at` (`device.go:462`).
   - Watermark: set by `NoteUnlinkTx` on a received unlink and checked by
     `OfferBeforeUnlinkTx` (`device.go:520-554`). Wire times are whole seconds
     (`daemon/grant.go:91`), so the seconds-only RFC 3339 storage loses nothing. Strict
     `Before` lets a same-second offer through, which is the right choice for ties.
     O-158 (a future `at` pins the watermark) is unchanged. C13-02 covers a local unlink,
     which does not set the watermark.
2. **`resolveProgram`.** Sound.
   - A name with a directory part must be absolute (`scope.go:320`). A drive-relative
     `C:x.exe` gets past that check but is refused at `:327`, because `LookPath` returns
     it relative.
   - `LookPath` errors, including Go's `ErrDot` for a current-directory hit, are refused
     (`:323`). A relative PATH entry is refused (`:327`).
   - On Windows only `.exe`/`.com` pass, judged after `TrimRight(". ")` (`:336`).
     `x.bat.`, `x.bat `, `x.bat::$DATA`, `x.exe::$DATA`, `.ps1`, `.vbs`, `.js` and
     extension-less names all land in `.bat/.cmd` or `default` and are refused (fail closed).
   - The stored `argv[0]` is absolute, so no search happens at run time.
   - Residual: on Unix a script's `#!` interpreter (and `/usr/bin/env X`) is neither
     resolved nor ownership-checked (C13-01).
3. **Ownership walk (D24).** Correct for everything I could test or trace.
   - Windows (`perm_windows.go`):
     - Owner must be self, SYSTEM, Administrators or TrustedInstaller. A missing DACL is refused.
     - Inherited ACEs count; inherit-only ACEs are skipped.
     - Deny ACEs are ignored, which is the stricter reading, so ACE order cannot matter.
     - An object or compound ACE with a write bit is refused. The mask sits at the same
       offset in every layout, so reading `ace.Mask` is valid.
     - CREATOR OWNER / OWNER RIGHTS map to the owner. `S-1-15-*` are ignored.
     - The per-role masks match the spec table (`:47`).
     - **Tested:** `GetNamedSecurityInfo` on a junction returns the junction's own DACL,
       not the target's (zz test below), so `roleLink` really judges the link.
     - A path through a junction fails `EvalSymlinks` ("cannot find the path") and is
       refused (O-162).
     - Hard links share one security descriptor, so they cannot bypass the check.
   - Unix (`perm_unix.go`): owner must be root or euid; `o+w` is refused (sticky included);
     `g+w` only for a trusted group. The Linux access ACL is read (`perm_acl_linux.go:215`):
     a named user or untrusted group with write under the mask is refused. A malformed ACL
     or ERANGE (>4096 bytes) is refused.
   - Links: each link is checked with `roleLink` and followed hop by hop at the link's
     depth, up to 40 hops (`perm.go:74-110`).
   - TOCTOU: the start-time re-check is `CheckTarget` (`runner.go:180`, C14). Between that
     check and exec, only someone the check already trusts could swap the file.
4. **Unlink revokes at once.**
   - The local `device_unlink` revokes, deletes the scope and the offer, and submits the
     mail in one tx (`daemon/device.go:531-550`). It then rejects pending link and scope
     approvals and calls `runner.kick()` (`:558-568`).
   - A remote `device.unlink` revokes in `Apply` (`:288`). `After` → `onUnlinked` rejects
     the pending scope approval and kicks (`daemon/daemon.go:504-509`).
   - `peers remove` revokes inside the removal tx and kicks (`daemon/device.go:329-339`).
     It does not close a pending link or scope approval window. Both Preconditions refuse
     later (`daemon/device.go:407`, `device_scope.go:226`), so only a stale window stays.
   - The sweep re-runs `CheckRunTx` and stops the current run (`device_run.go:177`, C14).
     Queued and running work is covered, provided C14's `take`/`stopRunning` hold (see
     contracts).

## Findings

### C13-01 · Low · confirmed-read
- **Where:** `internal/device/perm.go:52` (`CheckProgramOwner`), `internal/device/scope.go:319` (`resolveProgram`)
- **What goes wrong:** on Unix, only the file named in `argv[0]` and its directories are
  checked. When that file is a `#!` script, the kernel runs the interpreter named in its
  first line. That interpreter is neither resolved to a fixed path nor checked for
  ownership. With `#!/usr/bin/env X`, X is found through the helper daemon's `PATH` when
  the run starts.
- **Scenario:** the helper's human scopes `/home/alice/bin/ci.sh`, which starts with
  `#!/opt/tools/node/bin/node`, and `/opt/tools` is owned by another local account (or
  group-writable by `staff`). The scope passes. That other OS user replaces `node`, and
  the next controller request runs their binary as Alice. The same works with
  `#!/usr/bin/env python3` and a PATH directory writable by others. The owner must have
  picked such an interpreter (see rubric §2), so at most Low. Not Windows: `.bat`/`.cmd`
  are refused there.
- **Spec:** `Docs/protocol/device.md` §Program ownership, "a program is accepted only when nobody but this device's user or an administrator can change it"; threat row "Command swapped through PATH".
- **Fix direction:** read the `#!` line at set time and at start. Apply the ownership
  check to the interpreter too, and refuse `env` or relative interpreters. Otherwise
  document the gap in device.md.
- **Related:** O-160 (similar documented Unix gap), O-163

### C13-02 · Info · confirmed-read
- **Where:** `internal/device/device.go:520` (`NoteUnlinkTx`), `internal/daemon/device.go:531` (local `device_unlink`)
- **What goes wrong:** only an unlink *received from* a peer advances the offer watermark. A
  **local** unlink deletes the kept offer, but a peer offer that arrives later and is dated
  before the local unlink is kept again. If the local human re-links within 10 min, that
  old offer completes the link, with no new confirmation on the peer after the unlink.
- **Scenario:** B's human sends two offers within 10 min (for example a retry). The relay
  holds the second. A unlinks locally, then A's human re-links within the window. The
  relay releases B's old offer, and A goes `active` (one-sided) while B, which got A's
  unlink, is revoked. This needs two B confirmations plus a deliberate A re-link, so it is
  a design note. The code matches the spec ("received from that peer").
- **Spec:** `Docs/protocol/device.md` §Link flow step 3, watermark paragraph.
- **Fix direction:** on a local unlink, also record `now` as the watermark for that peer.
- **Related:** O-158, O-150, D22

### C13-03 · Info · confirmed-read
- **Where:** `internal/daemon/device.go:203`, `:242` (`activatedRoles`), `internal/mail/receiver.go:204-229`
- **What goes wrong:** an activation is stored in the global `activatedRoles` map during
  `Apply`. It is removed only by `After`, which runs only after a successful commit. If
  the inbox insert or the commit then fails, the entry for that `*mail.Opened` stays for
  the life of the daemon. A redelivery uses a new pointer.
- **Scenario:** a DB error (disk full, busy) right after a peer's activating `device.link`
  was applied leaks one small entry. The leak is bounded by the number of commit
  failures. The notification is also lost, but the redelivered mail activates and
  notifies again.
- **Spec:** none
- **Fix direction:** pass the role through `op` (like `op.Withhold`), or delete the entry
  on commit failure.
- **Related:** none

## Assumptions and contracts

- The mail receiver only delivers `device.link`/`device.unlink` from a paired peer, with the
  mail signature verified, and `op.Msg.From` is that key (`daemon/device.go:221`, `:288`). **unchecked** (C07/C08).
- `mail_submit` refuses every `device.*` kind (`internal/daemon/outbox.go:25`, `reservedKindPrefixes`). **checked**.
- The approval store runs `Precondition` and `Perform` in one tx and calls `OnReject` on
  reject or expiry (`daemon/device.go:400-485`). **unchecked** (C11/C12).
- `resolvePeer` returns the stored key, and `peer.Fingerprint` is derived from that key
  (`daemon/device.go:370-375`). **unchecked**.
- `helperRunner.kick`/`sweep` → `take` drops queued runs and stops the running one once
  `CheckRunTx` fails (`daemon/device_run.go:171-186`, `:287`). **partly checked**
  (read `sweep`, `stillRunning` and `watch`, not `take`).
- `CheckTarget` re-runs `CheckProgramOwner` at each start (`internal/device/runner.go:180-199`). **checked** (C14 owns the exec path).
- `device_scope.go`'s Precondition re-checks the active helper link by peer key
  (`daemon/device_scope.go:226`). **checked** (glance).
- `peers.SetTrustTx` touches only `peers.trust` (`daemon/device.go:433`). **unchecked**.

## Checked and fine

- Only `internal/device` writes `device_links`/`device_scopes`/`device_offers` (grep; the only other hit is the migration at `store.go:334`).
- The partial unique index allows at most one live row per peer. `CreateIntent` revokes the
  old `pending_approval` before its hierarchy check, and the old approval is rejected as
  `superseded` (`daemon/device.go:386-391`).
- Hierarchy (`device.go:266-301`): reverse link → cycle; opposite role with anyone →
  cycle (depth 1); helper limit 1; controller limit 8. Intents count, and lapsed intents
  are cleared first (`ExpireTx`). Since each device checks its own side, no chain can form.
- The `device_link` Precondition re-checks the row state, that the peer is still paired,
  D5 and the hierarchy inside the approval tx (`daemon/device.go:400-422`).
- `LinkID` matches the spec formula and vector (`device.go:119`). Nonces come from `crypto/rand`.
- `device.unlink` is strict (members `at`/`link`, link-id format). It revokes only rows
  with `msg.from`, so a peer can only end its own links (`daemon/device.go:267-300`).
- `RevokeForPeerTx` deletes the scopes of every revoked row and the kept offer (`device.go:604-635`).
- `CheckRunTx` applies checks 1–5 in the spec order, keyed on the peer's key (`scope.go:487-521`).
- `ValidateScope` bounds match the spec table. `DORYLINAE_*` env names are refused case-insensitively, and duplicate env names are refused with Windows case folding (`scope.go:186-314`).
- `DisplayQuote` escapes non-graphic runes, format characters, Zl/Zp and U+FFFD (`scope.go:360`).
- Windows: `GetNamedSecurityInfo` does not follow a junction, so `roleLink` judges the link's own DACL (confirmed-test, zz file below).
- On Windows, every non-allow ACE type (audit, label, deny object and so on) is ignored, and each of them only takes access away or is not in a DACL (`perm_windows.go:128-134`).
- Linux ACL parser: rejects a bad version or length, honours the mask, and ignores `USER_OBJ`/`GROUP_OBJ`/`OTHER`. Those three are covered by the mode bits, where `g+w` shows the mask and errs only toward refusing (`perm_acl.go:172-198`).
- CLI output passes peer data only through `devicePeerLabel`/tabwriter. The approval summary puts the peer name through `notify.Clean` + `stripLongDigits` (`daemon/device.go:487`).
- O-162: still as recorded (a junction path is refused at `EvalSymlinks`, confirmed-test).

## Leads for other chunks

- `internal/daemon/device.go:329` (`revokeDeviceForRemovedPeer`): `peers remove` does not reject pending `device_link`/`device_scope` approvals (`scopes.take`), unlike `device_unlink`. The windows stay open until the code is refused (UX; related O-122).
- `cmd/agentnet/device.go:191,244`: the peer name is printed raw. Whether card names are sanitized at pairing belongs to the peers/card chunk.
- `internal/daemon/device.go:144`, `:278`: `time.Parse(time.RFC3339, at)` accepts fractions and numeric offsets, which is looser than the wire format (strictness theme).
- Environment: this PC's `C:\` grants Authenticated Users `(M)` on the root itself (not the Windows default `AD`), so every program on `C:` is refused here. `TestOwnerWalkJunction` and `TestValidateScopeResolvesArgv0` fail for that reason only.

## Notes

- A local agent could put a homoglyph path or argv in a scope summary. `DisplayQuote`
  shows confusable letters as they are. The human is the gate, and a hostile repo is an
  accepted risk, so this is not a finding.
- `TestOwnerWalkJunction` sets its ACL with `SetNamedSecurityInfo` and reads it back
  through the same path. It would pass even if the API followed the junction. The zz test
  below closes that gap.
