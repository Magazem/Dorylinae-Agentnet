# C10: Fetch server and client, git serving

Reviewer: CR-R7 · model claude-opus-5-5 · elapsed 8 min · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 2 · Info 1.

The fetch path holds up well. Peer values reach `git` only as a validated path after `--`,
with literal pathspecs. The branch comes from the signed token and is re-checked on every
call. Every inherited `GIT_*` is removed and the hardening `-c` overrides are in place.
Slots are released on every path, before the last response, and a holder can pin only its
own two. Both the client and the CLI validate every response member and bound it. `--out`
writes atomically with mode 0600 and never follows a symlink. The three findings are about
the audit trail and the byte budget, not about access control:
- suppressed `grant.fetch` ops are lost when the server closes (C10-01);
- the 24 h byte budget is a fixed window, so twice the budget can be served across a
  boundary (C10-02);
- audit append errors are ignored (C10-03).

## Questions

1. **Git argument and environment safety.** No peer value becomes an option, a revision or
   magic.
   - The path goes only after `--` (`internal/capability/git.go:292-295`). It has already
     passed `ValidScopePath` (`fetch.go:454`: no `:`, so no `:(magic)`), and
     `GIT_LITERAL_PATHSPECS=1` is set (`git.go:43`).
   - The revision passed to `ls-tree` is the hex OID that `for-each-ref` returned
     (`git.go:267-273`), and `cat-file blob` gets the hex OID from `ls-tree` (`git.go:546`,
     checked by `parseLsTree` `isHexOID`, `git.go:364`).
   - The branch comes from the stored token. `checkBranch` runs again on every call
     (`git.go:223`, `git.go:243`) and refuses a leading `-` and the fnmatch metas `* ? [ \`
     (`token.go:250-277`), so the `for-each-ref` pattern is literal. An exact-name, `commit`,
     non-symref check follows (`git.go:267`).
   - The cursor never reaches git: it is compared in Go only (`git.go:488`).
   - Hooks, fsmonitor and transports are closed by `gitHardening` (`git.go:130-140`), and
     lazy fetch by `GIT_NO_LAZY_FETCH` plus `protocol.*.allow=never`.
   - Every `GIT_*` variable is removed, compared without case (`git.go:52-60`), and
     `GIT_CEILING_DIRECTORIES` is added per command (`git.go:215`).
   - `git` is resolved once with `exec.LookPath` (`git.go:68`). Since Go 1.19 that refuses
     a result from the current directory or a relative PATH entry (`ErrDot`). The result is
     made absolute, and Windows uses the `--exec-path` `git.exe` (`git.go:76-80`).
   - Residuals are unchanged: O-151 (config includes, alternates, UNC) and O-152.
2. **Limits.**
   - `Handle` reserves the peer and daemon slots (`fetch.go:220-233`). They are freed by
     `done` (a `sync.OnceFunc`, `fetch.go:339-340`), which is deferred, so it runs on every
     return.
   - The grant slot is freed by `finish` (`fetch.go:436-437`), also deferred. Both are
     called before the last response (`fetch.go:465`, `476`, `491`), which is the R39
     property.
   - Queue-full releases immediately (`fetch.go:237-238`). Reject jobs decrement
     `rejects` (`fetch.go:247-251`).
   - A holder can hold only its own 2 slots, for at most one op's duration (git 10 s per
     call, `opBudget` 1 min).
   - Byte budget: see C10-02 (fixed window) and O-143 (reads in flight).
3. **Fetch client and CLI.**
   - Stat and list responses are rebuilt from known members only (`fetch_client.go:301-347`).
     Types are an enum, names are 1–1024 bytes of UTF-8, sizes are ≥ 0, at most 1000
     entries, the cursor is at most 1024 bytes, and `commit` must be hex.
   - Fragments are checked before base64 decoding for count ≤ 8, index, size ≥ 0, commit
     and encoded length (`fetch_client.go:361-378`). They must be consistent within an
     attempt, and the total must equal `min(length, size−offset)` (`fetch_client.go:392-398`).
   - The error code is restricted to `^[a-z_]{1,32}$` (`fetch_client.go:280`).
   - A response is accepted only from the Noise peer of the pending op
     (`fetch_client.go:271`).
   - CLI:
     - `size` is capped at 8 MiB, and an empty chunk before `size` fails
       (`cmd/agentnet/fetch.go:209`).
     - The list is capped at 1000 pages (`fetch.go:297`). Each page is at most 64 KiB (the
       Noise limit), so memory stays bounded.
     - No peer-supplied name is ever used as a local path: `--out` is the user's own
       argument.
     - `writeFileAtomic` (`cmd/agentnet/fetch.go:243-263`) writes a `CreateTemp` file
       (mode 0600) in the same directory, runs `Sync`, then renames it over the target. A
       symlink is replaced, not followed, and the temp file is removed on failure. The only
       gap: a kill between create and rename leaves a `.name.*.part` file (not a finding).
     - Human output passes names and types through `termSafe` (`fetch.go:267-272`, 320,
       348).
4. **Audit.**
   - Every op that reaches a worker writes one row before its last response: success rows
     at `fetch.go:466/477/492`, error rows at `fetch.go:361` before `respondErr`.
   - The only fields are ids, the `op` enum (`fetch.go:374-379`), byte counts and codes. No
     path, scope, branch or content.
   - Three gaps:
     - ops over 60 per grant per minute are only summarised, and `Close` drops the pending
       summary (C10-01);
     - an `Append` error is ignored, so the read is served with no row (C10-03);
     - over-limit `rate_limited` answers from `Handle` are not audited. These are not served
       reads.
   - O-189 (a failed last send is audited `ok`) is unchanged.
5. **Shutdown.**
   - The daemon's defers run `fetchClient.Close` and `stopFetch` after `stopRelay`, the
     outbox and presence (`internal/daemon/daemon.go:554-583`, LIFO). They run before
     `sessions.Close` and the audit log close.
   - `FetchServer.Close` (`fetch.go:187-197`) closes `stop` and waits. Running ops do not
     take `s.mu` while blocking, and `SendData` with the relay gone returns without waiting
     on anything `Close` holds.
   - The wait is bounded: git calls take up to 10 s each, sends up to `opBudget`. This is
     a delay, not a deadlock (O-144). `Handle` racing `Close` only leaves counters on a
     dead server.

## Findings

### C10-01 · Low · confirmed-test
- **Where:** `internal/capability/fetch.go:187-197` (`Close`), `fetch.go:277-289` (`flusher`), `fetch.go:701-714`
- **What goes wrong:** ops beyond 60 `grant.fetch` rows per grant per minute are only counted, and written later by the flusher as `grant.fetch_summary`. `Close` stops the flusher without a final `Flush`, so the counts of the current window, up to about 70 s of ops, are never audited.
- **Scenario:** a paired peer holding a grant reads at the allowed 20 ops/s. After 60 rows, the next ops are only counted. The grantor's daemon stops (upgrade, logoff, `agentnetd stop`) within the next minute. Up to about 1,300 served reads (bounded by the 256 MiB budget) leave no audit trace. The holder cannot force the shutdown, so it needs luck or a routine restart.
- **Spec:** `Docs/protocol/grant.md` §Audit, "the rest are counted and summarised once a minute as `grant.fetch_summary`"
- **Fix direction:** call `s.aud.flush` for all windows (not only those older than a minute) in `Close`, after `wg.Wait`.
- **Related:** O-189, O-144

### C10-02 · Low · confirmed-test
- **Where:** `internal/capability/fetch.go:653-662` (`addServed`), `fetch.go:639`, `fetch.go:312-316`
- **What goes wrong:** the "256 MiB served per 24 h" budget is a fixed window that starts at the grant's first served byte. Twice the budget can be served within minutes across the window boundary. The in-memory counter is also reset by a daemon restart.
- **Scenario:** a paired peer holds a 7-day grant. It reads 1 byte at `t0` to open the window, then reads 256 MiB during the last minutes before `t0 + 24 h` and another 256 MiB right after. The grantor serves 512 MiB in a few minutes, twice what "per 24 h" promises. It can repeat this every day of the grant.
- **Spec:** `Docs/protocol/grant.md` §Limits, "256 MiB served per 24 h (`rate_limited`)"
- **Fix direction:** use a sliding window, for example hourly buckets summed over 24 h, or state the fixed-window semantics in grant.md.
- **Related:** O-143, O-009 (same fixed-window pattern in the relay)

### C10-03 · Info · confirmed-read
- **Where:** `internal/daemon/fetch.go:45-49`
- **What goes wrong:** the audit callback discards `log.Append`'s error, so an audit write failure lets the fetch be served without its `grant.fetch` row. Examples: `SQLITE_BUSY` past the 5 s budget, disk full.
- **Scenario:** grantor DB contention or a full disk → the holder's reads succeed and the grantor's audit has no trace of them. The grantor's audit is the stated mitigation for exfiltration by a prompt-injected holder.
- **Spec:** `Docs/protocol/grant.md` §Threat model, "audit on the grantor". §Audit does not say whether serving must fail closed on an audit error. This is a design note for the owner.
- **Fix direction:** decide explicitly. Either fail the op with `io_error` when the row cannot be written (as `request.submit` does, O-095), or log the failure to the daemon log.
- **Related:** O-189, invariant 5

## Assumptions and contracts

- `FetchServer.Handle` is called only for Noise-authenticated **paired** peers, with `peer` = the authenticated key. **Checked:** `internal/session/session.go:534-540` refuses unpaired keys, and handlers are dispatched per session peer.
- `Send` (`session.Manager.SendData`) replies on the peer's current session and never starts a handshake. **Checked:** `internal/session/session.go:258-273`.
- `Verify` (RoleGrantor) runs steps 1–8, including step 5 `aud` = counterparty and the signature. `fetch.go:559`; **unchecked** (C09/token chunk).
- `Store.Get` returns `rec.Scope`, `rec.Path`, `rec.Branch` consistent with `rec.Token`, as written at issuance. `authorize` compares only the token bytes (`fetch.go:582`). **Unchecked** (C11 issuance).
- `rec.Scope` is a valid scope path, and `rec.Path` is absolute and was accepted at issuance (with `--absolute-git-dir` for bare repositories). `joinScope` (`fetch.go:457`) and `GitBackend.check` (`git.go:223`) rely on this. **Unchecked** (C11).
- `FSBackend.Read` always emits at least one fragment, so `serve` always sends a last response and calls `finish`. **Checked:** `internal/capability/fs.go:373-398` (`frags` ≥ 1).
- `worksession.View.SelfOf(self)` returns `(requester, worker)` keys, used for step 7 and the per-fragment recheck (`internal/daemon/fetch.go:34`, `fetch_client.go:485`). The grantor is always the requester (grant.md "Terms"). **Unchecked.**
- The IPC server applies the 1 MiB line limit and the per-call context used by `fetch_start`/`fetch_status` (`fetch_client.go:414-425`). **Unchecked.**
- `callDaemon(..., pairTimeout, ...)` in the CLI is shorter than the daemon's 1.5 s call budget plus the network (`cmd/agentnet/fetch.go:158`). **Unchecked.**

## Checked and fine

- `op` reaches the audit log only as an enum or `unknown` (`fetch.go:374-379`). The R34 M2 fix holds.
- The `req` dedupe store is per peer and filled only after steps 1–9 (`fetch.go:429`, `markSeen` `fetch.go:526-549`). The R34 M1 fix holds.
- Over-limit answers are bounded to 2 per peer; the rest are dropped (`fetch.go:220-228`). The R34 M3 fix holds.
- Slots are freed before the last response on every op kind (`fetch.go:465`, `476`, `491`). The R39 fix holds.
- `recheck` runs before every fragment: row state, token bytes, `exp`, session open (`fetch.go:597-621`). Revocation stops a read in progress.
- `authorize` accepts only `issued`, peer-matched, byte-identical-token, `active` rows. `pending_approval` is refused `unknown_grant` (`fetch.go:582-591`).
- A symbolic or non-commit branch is `not_found`, and DWIM is avoided (`git.go:239-274`). The R37 M1 fix holds.
- On Windows the `--exec-path` `git.exe` is used, and `WaitDelay` bounds pipe waits after a kill (`git.go:76-80`, `git.go:120`). The R37 M2 fix holds.
- `ls-tree` output is capped at 32 MiB and 100,000 records. Oversized records are gathered safely, and an unterminated record is `io_error` (`git.go:307-343`).
- Git reads never hold a whole blob: the blob is streamed through `LimitReader(size)` and git is stopped after the last fragment (`git.go:559-595`). Blobs over 8 MiB are `too_large`, and symlinks (120000) and submodules are not served (`git.go:531-544`).
- `.git` components are `out_of_scope` for git as well, and `list` hides them (`git.go:400-408`, `git.go:478`).
- R38 L1/L2 fixes hold: the stat/list member checks, the read `commit` pattern, and the encoded-length check before base64 decoding (`fetch_client.go:308-363`).
- R38 M1/M2 fixes hold: the call budget of 1.5 s (`fetch_client.go:415`), and only pending ops count towards 64 per peer and 2 per peer (`fetch_client.go:504-522`).
- R38 M3/M4 fixes hold: `termSafe` and `writeFileAtomic` (`cmd/agentnet/fetch.go:243-272`).
- Late fragments of an earlier attempt are dropped, because `reqs` is re-keyed on retry (`fetch_client.go:220-225`, `271`).
- The server audit window map and the rate, served and seen maps are pruned by `Flush` (`fetch.go:292-317`). Their size is bounded by the number of grants and paired peers.
- The IPC `fetch_start` validates the path (`ValidScopePath`), the cursor, the offset and length, and the timeout before any send (`fetch_client.go:431-465`). A local agent cannot inject members into the wire request (`wireLocked` builds it from typed fields).

## Leads for other chunks

- `internal/session/session.go:258-273`: `SendData` and `sendApp` hold the global `sendMu` across the relay write (`m.send`). One slow relay write serialises every peer's session traffic, including all fetch fragments. Worth a look for the session/relayclient chunk.
- `internal/capability/token.go:250` `checkBranch`: allows `{`, `}` and non-ASCII. That is harmless for `for-each-ref` (no fnmatch meta). A check against `git check-ref-format` belongs to the issuance chunk.

## Notes

- `Handle` and `onResp` use `json.Unmarshal` (case-insensitive keys, duplicates accepted) rather than a strict parser. Every member used is validated afterwards, so there is no impact.
- Without `--out`/`--json`, a read writes the peer's raw bytes to the terminal (`cmd/agentnet/fetch.go:235`). The spec (`Docs/cli/fetch.md` §Reading) chose this, like `cat`. It may deserve a help-text warning.
- `grant.fetch_summary` also carries `peer`, which is not in the spec's detail list. It is an id, not content.
