# C21: Work sessions: state machine, receive, results, cancel, IPC

Reviewer: CR-C21 · model claude-opus-5-5 · elapsed 7 min · commit 6cc26a7

(Worktree HEAD is `1da650b`, which only adds review-55 docs; `git diff --stat 6cc26a7 HEAD -- internal/` is empty.)

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 4 | 1 |

The A-side state machine is tight. Every A transition checks the role, the exact source state and the debate kind inside its own transaction. Peer mail is bound to `(msg.from, msg.to, request)` by the derived id and to the peer through `(role, peer, request_id)`. Stale rounds and states are ignored and withheld. `toView` withholds the quarantined result at one choke point, and release and accept-result `--human` are bound to `seq`.

The one real defect (C21-01, confirmed by a test) is on the worker side. B keeps its *last submitted* result for the round and completes its request with that result, not with the result A accepted. A's request record, B's request record and B's experience record then carry a result A never reviewed. The Lows cover:
- the peer-wide Phase 1 fallback, which also fires on a bad-body ack;
- an ambiguous `r-` shorthand;
- B's `cancel` mark never becoming `refused`;
- `mail_id` missing from A-side results.

## Questions

1. **Quarantine visibility.** No byte of a quarantined result reaches A's agent through the paths in scope:
   - `ws_show` and `ws_list` build on `toView`, which drops `Result` when role is requester and state is `quarantined` (`internal/worksession/store.go:235`). `sessionView` then shows only `status`, the sizes and the count (`internal/daemon/session.go:199`).
   - `mail_inbox`: the copy is withheld for a quarantined result, an ignored or orphan result, a debate result, and any `ws.cancel` while the rule holds, including orphan and refused cancels (`receive.go:94,104,112,137,142,162`; `cancel.go:158-170`).
   - Audit: `ws.result_in` and `ws.ignored` carry ids and sizes only (`receive.go:222-234`).
   - Notification: `session.quarantined` carries no title (`internal/daemon/quarantine.go:47`).
   - Experience record: it reads `result` only for outcome `accepted` (`experience.go:108`), which A reaches only from `awaiting_result`.
   - Discard and request-changes NULL `result`/`result_round` in the same transaction (`transitions.go:170,227`).
   - `request_show`: an early or post-close `request.complete` is content-dropped while the rule holds (`hooks.go:110-116`, O-148).

   The C21-01 path does not bypass the quarantine: the post-close `request.complete` is dropped when the rule holds. It does bypass acceptance in non-quarantined sessions.
2. **Approval gates.**
   - Release: the Precondition re-reads role, state and `seq`, and refuses a changed `seq` (`session.go:537-555`). `ReleaseInTx` re-checks the state (`transitions.go:341`).
   - Accept-result `--human`: the same pattern (`session.go:399-416`), with `AcceptResultInTx` re-checking `awaiting_result` (`transitions.go:404`).
   - Pending approvals are rejected on close (`quarantine.go:57-65`). A request-changes from `quarantined` moves `seq`, so an older release approval fails its Precondition.
   - Discard and request-changes need no approval and delete the content, as stated in 1.
   - The approval id closure is O-147 (known).
3. **Transition table.** Covered:
   - A side: accept-result, request-changes, discard, cancel and release each check role, debate kind and the exact state (`transitions.go:95-102,148-157,209-217,280-285,335-343`).
   - `applyResult` accepts only `open` with the equal `round`; everything else is ignored, withheld and audited (`receive.go:136-145`).
   - `applyCancel` applies only in `open` (`cancel.go:175`).
   - B's mirror looks up `(worker, msg.from, request)`, so a third peer's `ws.state` is an orphan (`mirror.go:122`), and `seq <= row.seq` is ignored (`mirror.go:137`).
   - A peer cannot move a session it is not party to: the derived-id check is on every kind (`receive.go:66`, `cancel.go:133`, `mirror.go:73`).

   Gaps: see C21-01 (B can submit more than once per round while its mirror is still `open`, `submit.go:58`) and C21-03.
4. **Mixed-version fallbacks.**
   - A-side early complete: only B's own `request.complete` can close A's session, and only from `open`, which B could already do with `ws.cancel`.
   - B-side Phase 1 fallback: only an ack from A can trigger it. Acks are sealed, signed mail (`internal/mail/outbox.go:493-501`), so the relay cannot forge one, and a stale resend is impossible because the outbox expires at 7 d and receive-age is 14 d (`receiver.go:29-34`).
   - However, the receiver also acks **bad-body** mail as `unsupported` (`receiver.go:88-93`). So a current A that rejects one `ws.result` or `ws.cancel` as bad body makes B close **every** open worker session with A (C21-04). Today only version skew in validation, or a B bug, reaches this. A hostile peer gains nothing it could not already do, so the finding is Low.

## Findings

### C21-01 · Medium · confirmed-test
- **Where:** `internal/worksession/mirror.go:212` (B completes with its own `row.result`), `internal/worksession/submit.go:58,78` (a second `ws_result` in the same round is allowed and overwrites B's copy), `internal/worksession/experience.go:108`
- **What goes wrong:** B stores every result it submits and overwrites the previous one while its mirror is `open`. A applies the first result that arrives and ignores later ones (`state`). On close `accepted`, B completes its request, writes its experience record and sends `request.complete` with B's **last submitted** result, not the one A accepted. A's `requests` row then carries a result that neither A's agent nor A's human ever reviewed.
- **Scenario:** A paired peer, or even an unmodified B whose agent revises its answer:
  1. A is offline for a while.
  2. B's agent runs `agentnet result` (R1), then `agentnet result` again (R2). Both succeed because B's mirror stays `open` until A's `ws.state` arrives.
  3. A comes online and applies R1 (`awaiting_result`). R2 is ignored (`ws.ignored state`).
  4. A's human runs `accept-result --human` on R1.
  5. B's mirror closes and B completes the request with R2, and `request.complete{result: R2}` reaches A. The session is `closed` and the quarantine rule does not hold, so A stores R2 in its request record (`request show` and Phase 1 consumers read it). B's own request and experience record also say R2 was accepted.

  Test output:
  `A's session accepted summary: "reviewed result R1"` / `A's request record summary: "never reviewed R2"` → FAIL.
- **Spec:** work-session.md §Closing the request: "`outcome = accepted`: `result` = the D14 part of the **accepted** result". Also §Result object: "Stored result replaces any earlier one" (on A).
- **Fix direction:** Refuse a second `ws_result` for a round B already submitted (or mark the mirror as submitted). Alternatively, carry the accepted result's hash in the closing `ws.state` and have A compare the incoming `request.complete` against its stored accepted result.
- **Related:** O-148 (the same post-close path when quarantine holds), O-121

### C21-02 · Low · confirmed-read
- **Where:** `internal/worksession/cancel.go:42` (duplicate), `internal/worksession/cancel.go:213-214` and `receive.go:253-256` (10-minute resend), `internal/worksession/mirror.go:137,147`
- **What goes wrong:** B's `cancel = 'refused'` value is never set anywhere. A refused `ws.cancel` gets a `last_state` echo only if more than 10 minutes have passed since the last send, and that echo carries the `seq` B already has, so B treats it as a duplicate and does not clear `cancel`. B's view keeps `cancel: "requested"` until A's next real transition. Further `ws_cancel` calls return `duplicate: true` and send no mail.
- **Scenario:**
  1. B's mirror is `awaiting_result`.
  2. B's agent runs `session --cancel`.
  3. A refuses the cancel and does not resend (the last send was under 10 minutes ago, or the resend is a duplicate).
  4. B's `session <id>` shows `cancel: requested` for as long as A's human takes to act; B can neither re-send nor see the refusal.
- **Spec:** work-session.md §Cancel: "otherwise ignores it (`result: "refused"`) and re-sends its `last_state`, so B learns the real state"; §Persistence `cancel … CHECK (cancel IN ('requested', 'refused'))`.
- **Fix direction:** When a `ws.state` with `seq <= row.seq` arrives while `cancel = 'requested'` and `state != open`, set `cancel = 'refused'`. Or exempt the refusal echo from the 10-minute rule once per cancel.
- **Related:** R27 L6

### C21-03 · Low · confirmed-read
- **Where:** `internal/worksession/store.go:269` (`GetByRequestID`: `WHERE request_id = ? LIMIT 1`, no role, peer or order), used by `internal/daemon/session.go:141` for every `ws_*` method
- **What goes wrong:** Request ids are unique only per `(direction, peer, id)` (`internal/store/store.go`, `PRIMARY KEY (direction, peer, id)`). If A has a requester session and a worker session with the same `r-` id, the `r-` shorthand silently picks whichever row was inserted first.
- **Scenario:**
  1. A (paired peer B's requester) sends B request `r-X`.
  2. B sends A its own request with the same id `r-X` before accepting A's request.
  3. A accepts B's request, then B accepts A's request.
  4. A's agent runs `agentnet wait r-X` or `session r-X --cancel` and gets the worker session. It sends a `ws.cancel` for work it does for B instead of cancelling its own request, and `accept-result` or `release` on `r-X` fail with `not_requester`.

  The workaround is to use the `s-` id. No content leaks.
- **Spec:** work-session.md §IPC, "`ws_show` … an `r-` id resolved through its session"
- **Fix direction:** Return `bad_request` ("ambiguous, use the s- id") when more than one row matches, as the request layer already narrows ambiguous ids (`internal/daemon/consult.go:62`).
- **Related:** none

### C21-04 · Low · confirmed-read
- **Where:** `internal/worksession/phase1.go:117-137,157-161`, `internal/daemon/daemon.go:473-481`, `internal/mail/receiver.go:88-93` (bad body acked `unsupported`)
- **What goes wrong:** The Phase 1 fallback treats any `ws.result` or `ws.cancel` acked `unsupported` as proof that A is Phase 1. The receiver sends the same ack for a **bad body**. The sweep is also peer-wide, so one rejected mail closes every open worker session B has with A, revokes its held grants and completes each request. Meanwhile A, which is Phase 2, keeps its `awaiting_result` and `quarantined` sessions open (early complete leaves them to A).
- **Scenario:** Two Phase 2 daemons with a validation difference, for example a later version adding a result member or tightening a cap:
  1. B's `ws.result` for S1 is `bad_body` at A, which acks it `unsupported`.
  2. B closes S1…Sn with A as `cancelled` and sends a `request.complete` for each.
  3. A closes the `open` ones, and its `awaiting_result`/`quarantined` ones diverge from B for good.

  No hostile actor gains anything, since A could close the sessions itself, so this is a robustness and spec-safety issue.
- **Spec:** work-session.md §Early complete, "When a `ws.*` mail from B to A ends `failed` with `unsupported_kind` … A is a Phase 1 daemon". Unsafe as written, because request.md §Invalid bodies acks bad bodies the same way.
- **Fix direction:** Distinguish an unknown-kind ack from a bad-body ack (a separate ack member), or require the failed kind to be unknown to A (for example its capability or version) before running the peer-wide sweep.
- **Related:** R24 M6, R27 M5 (did not consider the bad-body ack)

### C21-05 · Low · confirmed-read
- **Where:** `internal/daemon/session.go:388,454,477,498`
- **What goes wrong:** `ws_accept_result` (without `--human`), `ws_request_changes`, `ws_discard` and A's `ws_cancel` return `SessionResult` without `MailID`, so `"mail_id": ""`. The `ws.state` id is available from `Outbox.SubmitTx` in `sendState` but is dropped.
- **Scenario:** A local agent that tracks delivery by the returned `mail_id` (as it does for `ws_result`) gets an empty id for every A-side transition.
- **Spec:** work-session.md §IPC table: `ws_accept_result` → `{"session": <view>, "mail_id"}`, and the same for `ws_request_changes`, `ws_discard` and `ws_cancel` (A).
- **Fix direction:** Return the `ws.state` mail id from `sendState` and `closeSessionTx` up to the handlers.
- **Related:** none

### C21-06 · Info · confirmed-read

- **Spec:** work-session.md §Mirror step 2 "audit `ws.orphan {session, peer, kind}`"; §Audit `{session, peer, kind, reason?}`

- **Related:** none

## Assumptions and contracts

- The Receiver runs `Apply` and then inserts `mail_inbox` honouring `op.Withhold` in the same transaction, and stores no inbox row for `ErrBadBody` (`internal/mail/receiver.go:88-93`, `store`). **Checked** (comment and flow at `receiver.go:140-160`); the insert itself is unchecked.
- `op.Msg.To` equals our own key, and `op.Msg.From` is authenticated, before `Apply` (`receive.go:66`, `cancel.go:133`, `mirror.go:73` rely on them for the derived id). **Unchecked** (`internal/mail/open.go`).
- `approval.Store.Confirm` runs `Precondition` and `Perform` in one transaction, then `AfterCommit` after commit (`session.go:398-427,536-573`). **Unchecked** (`internal/approval/store.go`).
- `caps.QuarantineHolds(tx, sid, peer)` implements both clauses ("ever active" in this session, and the peer-wide 7 d clause) and fails closed on error. Callers treat an error as a transaction failure (`receive.go:150-153`, `cancel.go:163-166`). **Unchecked** (`internal/capability/store.go`).
- `Outbox.OnAck` is fed only from verified, sealed ack mail (`internal/mail/outbox.go:493`). **Checked** (`receiver.go` `kind == "ack"` after `Opener.Open`).
- `Requests.CompleteInTx` returns `*request.BadStateError` when the request is not `accepted` (`mirror.go:222-233`). **Unchecked**.
- `EarlyComplete` drops `request.complete` content after `closed` when the rule holds (`hooks.go:110-116`). **Checked**; this is what keeps C21-01 out of quarantined sessions.
- `RevokeGrants`/`RevokeForSessionTx` works inside the caller's transaction without touching `s.DB` (`transitions.go:65`, `mirror.go:176`). **Unchecked** (`internal/capability`).

## Checked and fine

- The derived-id check is on all three kinds, with the correct key order (A→B for `ws.result`/`ws.cancel` from B, `from, to` for `ws.state`) (`receive.go:66`, `cancel.go:133`, `mirror.go:73`).
- `ws.state` body rules: the state enum, outcome iff closed, `changes` only with `open` and `round >= 2` and 1–4000 code points, `verification` only with `accepted`, and `seq >= 1` (`mirror.go:80-120`).
- `ws.result` decoding: unknown members are refused, `human_accepted` from B is refused (`result.go:111-116`), and the 64 KiB cap is checked on the canonical whole body (`receive.go:80-86`).
- Discard deletes `result`, `result_round` and `verification` and revokes grants in one transaction; its experience record never reads the result (`transitions.go:226-241`).
- A-side cancel reasons are validated but never stored, sent or audited (`transitions.go:264-309`). The B-side reason is withheld from `mail_inbox` whenever the rule holds, including orphan and refused cancels (`cancel.go:158-170`).
- The `last_state` echo follows the 10-minute rule and is sent after commit, outside the mail transaction (`receive.go:242-280`).
- Review 35 H1 appears fixed for both release and accept-result `--human`: `seq` is bound in the Precondition (`session.go:412,552`).
- Review 27 L6 is partly fixed: any new `ws.state` clears `cancel` (`mirror.go:147`); see C21-02 for the remaining gap.
- Review 27 M5 appears fixed: only `ws.result`/`ws.cancel` created at or after `opened` count (`phase1.go:157-161`).
- Review 43 M4 appears fixed: debate sessions refuse result, accept, discard, request-changes and release (`transitions.go:98,151,212,338,401`; `submit.go:52`).
- Close audits (`ws.close`, `ws.accept_result`, experience) always run after commit, never inside a transaction (review 27 C1) (`transitions.go:113-121`, `session.go:423`).
- No content in audit: every `Audit.Append` in scope carries ids, enums, counts and sizes only.
