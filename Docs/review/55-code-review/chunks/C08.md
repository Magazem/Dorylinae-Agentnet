# C08: Noise sessions, presence, idle, ping

Reviewer: CR-R8 · model claude-opus-5-5 · elapsed ~5 min (shell clock) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 5 | 1 |

The Noise session layer is sound. Unpaired senders are dropped before any Noise work, every
`session.data` is bound to (from, to, sid, counter) in the AD, and replay and reordering are
rejected. Handshake, session, queue, ref and reject state is bounded per peer. The presence
receive path matches the spec: window, order/replay, strict body, no audit, bounded drop
limiter. The one substantive defect: **the idle-detection package is never wired into the
daemon**, so the "human present" level (presence.md §Levels) always reads unknown in
production (C08-01). The other findings are visibility-mode edge cases (a DB error turns
`only_team` into `invisible`; an audit failure skips the goodbye diff; ping answers while
invisible), log volume, and a small spec deviation in how `human_present` is shown.

## Questions

1. **Session: unpaired, AD, replay, bounds.** `handle` calls `IsPaired` before any Noise
   work and rejects `unpaired` (`internal/session/session.go:534-542`). A lookup error drops
   the frame silently (fail closed, `:535-537`). The AD is `domain‖from‖to‖sid‖counter`
   (`:473-484`). Receive uses `dataAD(from, m.self, s.sid, n)` and requires `s.peer == from`
   (`:674-678`). The prologue binds both identities (`internal/noise/noise.go:124-127`), and
   the binding check requires `identity == from` (`noise.go:86`). Replay: `Open` rejects
   `counter < recvNext` and only advances on success (`noise.go:235-244`), which matches
   session.md §Replay. Bounds per paired peer: ≤4 pending responder handshakes (`:575`,
   `:767-784`), ≤4 open sessions (`:733-748`), 1 dial, a 16-message queue (`:418`), and
   handshakes expire after 10 s (`:859`). Global bounds: refs ≤4096 (`:489`) with a 30 s
   TTL, inbox 256 with drop (`:312-316`), audited rejects ≤30/min (`:896-911`). A relay can
   forge `from` of a paired peer and send message 1 (which carries no authentication). That
   only churns that peer's ≤4 pending slots, which is equivalent to dropping frames. Open
   sessions have no idle TTL, but they are bounded by paired peers × 4. The log line for
   every reject is not rate-limited (C08-05). The per-frame peer lookup is a full table scan
   (C08-06).
2. **Concurrency.** Lock order is `sendMu` then `mu`, and it is respected everywhere:
   `send` takes `mu` only briefly (`:499-513`), and `HandleError`/`pingTimeout`/`sweep` take
   only `mu`. No deadlock found. The worker holds `sendMu` while it runs handlers and sends
   (each send ≤5 s, `:82`, `:506`). A flush after a handshake can hold it for up to 16×5 s
   with a stuck relay, which stalls `Ping`/`SendData` callers. That is bounded, and a relay
   can stall them anyway. The `fetch.req` handler only enqueues, non-blocking
   (`internal/capability/fetch.go:209-238`). The worker and sweeper exit on `stop`, and
   `Close` waits for both (`:290-305`). Removing a peer does not drop its in-memory sessions,
   but inbound frames are re-checked with `IsPaired` on every frame, so this is not a leak
   that grows without bound.
3. **Presence.** Window ±10 min (`internal/presence/receive.go:76`). Cross-boot rule
   (`store.go:57-58`, O-064 still open as recorded). No presence-specific size cap before
   crypto (`internal/mail/open.go:151-165` uses the mail `MaxPayload`): O-083 is still open.
   The drop limiter is bounded at 1024 peers with a once-a-minute sweep
   (`receive.go:104-133`), so R17 M2 is fixed. Rejects are never audited and never answered
   (`receive.go:62-99`, `internal/mail/open.go:151`, "never calls o.Audit"). `interval` is
   parsed to 1–300 (`body.go:205-209`) and used as 2.5× (`store.go:161`). O-075 is still
   open as recorded.
4. **Visibility modes.** `invisible` gives an empty visible set (`sender.go:240-241`), so
   ticks, agent edges and the relay-ready `SendNow` send nothing. `LoadSettings` runs before
   the relay starts (`internal/daemon/daemon.go:373` vs `:559`), so there is no
   visible-before-load race. `SetMode` sends goodbyes to `old − new` through `SyncVisibility`
   (`sender.go:527-553`). Gaps: an audit failure skips that diff (C08-03); a transient DB
   error flips `only_team` to `invisible` for good (C08-02); and session ping still answers
   while invisible (C08-04). With `--human off`, `human` is always 2 (`sender.go:202-204`).
5. **Idle.** The mechanisms are safe: no shell (`internal/idle/idle.go:37-46`), a 1 s
   context plus 100 ms `WaitDelay`, and strict anchored regexes with overflow checks
   (`idle.go:48-91`). `gdbus`/`xprintidle` are resolved through `PATH`
   (`idle_linux.go:23-31`; Go's `exec` refuses `.`-relative results). A hostile `PATH` is
   malware-as-user, which is out of scope. **But the package is never called by the daemon**
   (C08-01). The spec's 5 s result cache also does not exist: `humanFlag` would query once
   per recipient per tick (`sender.go:478`).

## Findings

### C08-01 · Medium · confirmed-read
- **Where:** `cmd/agentnetd/main.go:114` (the `daemon.Options` literal has no `Idle`), `internal/daemon/daemon.go:181,368`, `internal/presence/sender.go:205-207`
- **What goes wrong:** No production code imports `internal/idle` (`git grep` finds no importer; `git log -S"idle.Idle"` finds only the package's own commit 4324c4b). `Options.Idle` is therefore nil, and `humanFlag` always returns 2. Every heartbeat carries `human: 2`, and every peer's `human_present` is always `null`, on every OS. The spec's 5 s cache ("result cached for 5 s") is also missing, so wiring `idle.Idle` as is would run up to 3 execs per recipient per tick on Linux.
- **Scenario:** Two users on Windows, in a shared team, both active at the keyboard. `agentnet status --team x` on either side shows `human_present: null` indefinitely. Their own `status.presence.human_present` is also `null`. `presence --human on|off` has no visible effect. The daemon tests inject a fake `Idle` (`internal/daemon/presence_visibility_test.go:151-165`), so the gap is invisible to CI.
- **Spec:** `Docs/protocol/presence.md` §Levels "Human present | OS input idle time is under 10 min | Per-OS idle query"; §Idle detection "runs once per tick … cached for 5 s"; HANDOFF lists 1.2d idle detection as done.
- **Fix direction:** Set `Options.Idle` in `cmd/agentnetd`, defaulting to `idle.Idle` behind a 5 s cache, and add a test that the default is wired.
- **Related:** none

### C08-02 · Low · confirmed-read
- **Where:** `internal/presence/sender.go:301-306` (`checkTeamGone`)
- **What goes wrong:** Any error from `Team.Get` (for example `SQLITE_BUSY`, a context timeout or an I/O error), not only "not found" or "not active", counts as "team gone". The code then persists `invisible`, audits `presence.mode {invisible, team_gone}`, and never restores `only_team`.
- **Scenario:** A user sets `--only-team x`. During a tick, a concurrent long write holds the single DB connection, and `Team.Get` fails with a busy or timeout error. The daemon switches to invisible for good and sends goodbyes on the next `SyncVisibility`. The user's teammates in `x` see them offline until the user notices and re-runs `presence --only-team x`. This fails closed (more private), so it is not a leak. It is wrong persisted state that the user must repair.
- **Spec:** presence.md §Sending "If `x` is no longer `active`, the mode becomes `invisible`".
- **Fix direction:** Degrade only on `team.ErrNotFound` or a non-active state; on other errors, skip this tick.
- **Related:** none

### C08-03 · Low · confirmed-read
- **Where:** `internal/presence/sender.go:362-382` (`SetMode`)
- **What goes wrong:** The mode is persisted and cached first. If `Audit.Append` then fails, `SetMode` returns the error before `SyncVisibility`. The CLI reports failure although the new mode is in force, and the goodbye/online diff is never sent.
- **Scenario:** Audit append fails (disk full, DB busy) during `presence --invisible`. The CLI prints an error, so the user believes they are still visible, but they are invisible from now on. Peers get no goodbye and keep showing the user online for up to 75 s. The reverse direction (`--visible`) gives newly visible peers no immediate online.
- **Spec:** presence.md §Visibility "On a change, the daemon … sends a goodbye to `old − new` and an immediate `online` to `new − old`, and audits".
- **Fix direction:** Run `SyncVisibility` whether or not the audit succeeds, or audit before applying the mode.
- **Related:** none

### C08-04 · Low · confirmed-read
- **Where:** `internal/session/session.go:692-699` (the `ping` case of `onData`)
- **What goes wrong:** The session layer answers every `ping` with a `pong` whatever the presence visibility mode, so any paired peer can check at any time whether an `invisible` user's daemon is up, with an RTT.
- **Scenario:** B sets `presence --invisible`. A (a paired peer that B hid from) runs `agentnet ping @b` and gets `pong from @b: rtt 40 ms`, which shows B's daemon is online right now, on demand. The CLI help says "Invisible hides you from teammates" (`cmd/agentnet/presence.go:144`).
- **Spec:** presence.md §Visibility "It never shows B online while B stays invisible, because B sends A nothing"; `Docs/cli/presence.md`.
- **Fix direction:** Either document ping as a liveness oracle next to O-069, or ignore pings from peers outside the visible set.
- **Related:** O-069 (same class of leak through mail delivery; ping is a new, direct, on-demand path)

### C08-05 · Low · confirmed-read
- **Where:** `internal/session/session.go:893` (`reject`), `:315` (`HandleEnvelope`)
- **What goes wrong:** Every reject is logged at Info before the 30/min limiter, and every inbox overflow logs a Warn. The spec's "the rest are counted in the daemon log" becomes one line per frame. A relay can inject unlimited `session.*` frames from any key (unpaired frames go straight to `reject`), so it controls the daemon's log volume.
- **Scenario:** A hostile relay streams `session.data` frames with a random `from`. Each one writes an Info line. With `--log-file`, the size-capped log (`logfile.MaxSize`) rotates constantly and pushes out the useful history, such as the audit-failure and relay events an operator needs. Without it, stderr floods.
- **Spec:** session.md §Rejection "At most 30 rejects per minute are audited; the rest are counted in the daemon log (`event=session_reject_suppressed`)".
- **Fix direction:** Log rejects at Debug, or only inside the limiter budget, and count the rest in the `suppressed` line.
- **Related:** O-051 (same pattern in mail)

### C08-06 · Low · confirmed-read
- **Where:** `internal/presence/store.go:116-143` (`View`), `internal/daemon/status.go:114`
- **What goes wrong:** When a peer is not effectively online, `View` leaves `HumanPresent` nil, so `status --team` shows `human_present: null`. The spec gives `false`.
- **Scenario:** B goes invisible or is killed. After 75 s, A's `status --team x` shows B with `daemon_online: false`, `human_present: null`. Acceptance 1.3 expects `human_present: false`. Scripts that read `null` as "unknown" rather than "not present" read the wrong thing. Display only.
- **Spec:** presence.md §Receiving "`human_present = daemon_online ? (row.human == 2 ? null : row.human == 1) : false`"; §Visibility acceptance "`human_present: false`".
- **Fix direction:** Set `HumanPresent` to `&false` when not online, or change the spec.
- **Related:** none

### C08-07 · Info · confirmed-read
- **Where:** `internal/daemon/ping.go:57-68` (the `IsPaired` closure given to `session.Config`)
- **What goes wrong:** Every inbound `session.*` frame, including frames from unpaired or forged keys, runs `peers.Store.List`: a full table scan that decodes the skills JSON and computes a fingerprint per row, on the single-connection DB. It runs on the session worker, before any limiter.
- **Scenario:** A relay flood of junk `session.*` frames turns into one full peers scan per frame. That contends with every other DB user. The cost is bounded by the relay's own send rate, and the relay can deny service anyway.
- **Spec:** none
- **Fix direction:** Use a single-row `IsPaired` query or the cached lookup proposed for O-084.
- **Related:** O-084 (the same issue on the mail/presence `peerDirectory` path; this is the session path)

## Assumptions and contracts

- `session.Manager` assumes envelopes reaching it passed `envelope.Parse`, so `from` is a canonical key and type/id are from a safe charset before they reach the audit and log (`session.go:893,912`). **Checked:** `internal/relayclient/relayclient.go:460`, `internal/envelope/envelope.go:56-76`.
- `noise.Handshake.Read` assumes the caller already checked "identity is a paired peer" (session.md binding step 3); `verifyBinding` checks only `identity == peer` (`internal/noise/noise.go:86`). **Checked:** `session.go:534-542` runs `IsPaired(e.From)` first.
- `DataHandler`s must not block or call `SendData` (`session.go:234-239`). **Checked** for `fetch.req` (`internal/capability/fetch.go:209-238`, non-blocking enqueue). **Unchecked** for `fetch.resp` (`internal/daemon/fetch_client.go:261`, which runs under `c.mu`; body not fully read).
- `presence.Receiver` assumes `mail.Opener.OpenPresence` enforces paired-peer, `to == self`, signature, `p-` id and `msg.from == env.from` (mail.md steps 1–10). **Partly checked:** step 1 at `internal/mail/open.go:159-161`; other steps unchecked (C07's scope).
- `Store.Accept` relies on `peers.Remove` deleting the `presence_peers` row. **Checked:** `internal/peers/store.go:351`.
- `Sender.visibleSet` relies on `team.Store` calling `OnMembersChanged` after every membership or state change, so goodbyes go out. **Partly checked:** calls at `internal/team/store.go:275,327,409,445,505` and `kinds.go:244,515,579`. Whether `peers remove` of a teammate triggers it is unchecked.
- `presence.Sender.Priv` returns a fresh copy that it is safe to `clear` (`sender.go:473`). Unchecked (`identityPriv` in `internal/daemon`).

## Checked and fine

- Counter exhaustion: `Seal` refuses `MaxUint64`, and `Open` rejects `counter == MaxUint64` (`noise.go:224,236`).
- Pong matching requires the same peer key, a pending state and a sent ping (`session.go:701`). A peer cannot complete another peer's ping.
- A peer cannot replace built-in `ping`/`pong` handlers (`session.go:248`). Unknown plaintext types are ignored (`:706-711`).
- Handshake state machine: `onResp` requires initiator with `hs != nil`; `onFin` requires responder (`:605,643`). A duplicate sid is rejected (`:571`). `onResp`/`onFin`/`onData` require `s.peer == from`.
- The reject/open audit carries no ciphertext or plaintext, only the peer, type, reason and a 4-byte sid tag (`:885,912-915`). Invariant 1 holds.
- Presence `Parse` is strict: exactly 8 members, ranges, team-id keys, ≤32 epochs, integer-only `json.Number` (`body.go:163-241`).
- The presence limiter map is bounded (`receive.go:104-133`). R17 M2 is fixed.
- Invisible mode is loaded before the relay can call `SendNow` (`daemon.go:373` before `startRelay` at `:559`).
- Shutdown goodbye runs before the presence loop is stopped, and the relay client outlives `ctx` (`daemon.go:572-576,815-818`).
- Idle parsers: anchored regexes, `ParseUint(…,63)`, overflow guard (`idle.go:48-91`). Windows uses uint32 wrap arithmetic and treats session 0 as unknown (`idle_windows.go:32-40`).
- CLI: `ping`/`presence` validate flags locally. Peer names in output are card names filtered by `checkText` (control characters rejected, `internal/agentcard/agentcard.go:116-119`), and team names match `^[a-z0-9][a-z0-9-]{0,31}$`.
- O-031, O-063, O-064, O-068, O-075, O-083, O-085, O-086 and O-192 are still present as recorded. I found no new evidence that any of them is worse.

## Notes

- `sendOne` computes `interval` from the last `SyncVisibility` set (`sender.go:475`), not from the tick's fresh set. Above 90 peers, a stale set could advertise 30 s while ticks run longer.
- `sendOne` loads the identity key and runs `Team.List` once per recipient per tick. That is O(n) DB reads per tick. It is fine at the current scale.
