# C05: Identity, agent card, keystore, Noise wrapper, mailbox keys

Reviewer: CR-R5 · model claude-opus-5-5 · elapsed 10 min · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 3 · Info 3.

This chunk is in good shape. Card signing and verification follow agent-card.md step for step:
the generic parse comes first, then the canonical form, the signature, and the schema last. The
Noise wrapper checks the binding and prologue exactly as session.md describes, and nonces cannot
be reused. Secrets are restricted to the owner before any byte is written, on both Unix and
Windows. Mailbox keys are stored in the keystore before the row is committed, and the row before
the announcement is returned. They are deleted at `not_after + 7 d`.

The one real weakness is the keystore's error handling. In `auto` mode, a keychain that is
merely *unavailable* (locked, timed out) gets folded into "not found". That brings back the
situation the R09 L5 fix was meant to rule out: the mailbox job silently replaces a key whose
secret still exists (C05-01, confirmed by a test). The same folding makes the identity start
error tell the user to delete their card (C05-02). No secret reaches a log, an error string or
IPC anywhere in this chunk.

## Questions

1. **Canonical JSON / strict parse.** Two byte forms reach the same signature only through
   escapes, which is intended because the signature covers the canonical form. There is one
   non-obvious case: lone-surrogate escapes (`"\ud800"`, `"\udfff"`) are silently turned into
   U+FFFD by `encoding/json`, so they canonicalise the same as `"�"`. RFC 8785 would reject
   them (C05-04, confirmed-test). Other properties hold:
   - Numbers: exponent, fraction and `-0` are rejected, and the range is `|n| < 2^53`
     (`internal/agentcard/canonical.go:95-102`).
   - Duplicate keys are compared after unescaping, so `"a"` and `"a"` count as duplicates
     (`canonical.go:69-71`).
   - Key order is by UTF-16 code units (`canonical.go:139-147`).
   - Nesting depth is bounded at 10 000 by `encoding/json`'s `Decoder.Token`. A test at depth
     10^5–2·10^6 (4 MB) fails fast with "exceeded max depth", using no extra stack.
   - `tools/verifycard` canonicalises identically: same decoder, same escape table, same
     ordering (`tools/verifycard/main.go:164-253`). It differs only in not using strict
     base64 (C05-05).
2. **Keystore.**
   - Unix: `CreateTemp` creates the file 0600 and `chmod 0600` runs before `Write`
     (`internal/keystore/file.go:55-79`).
   - Windows: a protected owner-only DACL is set on the empty temp file before `Write`
     (`perm_windows.go:14-30`). The rename then keeps that DACL.
   - The write is atomic by rename. There is no directory fsync on Unix (C05-06, suspected).
   - Permissions are re-checked on read on Unix only. O-030 is still open on Windows:
     `checkOwnerOnly` there is a bare `Stat` (`perm_windows.go:35-38`).
   - `auto` with the keychain locked or unavailable: `Save` falls back to the file silently.
     For the identity the fallback reason lands in the audit `keychain_error`
     (`identity.go:174-176`). For mailbox keys it is discarded (`mailbox.go:349`, Info in
     Notes).
   - `Load` treats unavailable as not found (`keystore.go:44-54`), which causes C05-01 and
     C05-02.
   - Errors carry backend names, paths and go-keyring text only. No secret material ever goes
     into an error.
3. **Noise.**
   - `verifyBinding` requires `identity == h.peer`. `h.peer` is the envelope `from` on the
     responder (`internal/session/session.go:576`) and the dialled key on the initiator
     (`:433`).
   - The signature is checked over `PeerStatic()` (`internal/noise/noise.go:84-101`), and
     msg 1 must have an empty payload (`noise.go:185-190`).
   - The prologue carries both identities in initiator/responder order (`noise.go:124-127`).
   - I found no path that accepts an unbound static key, and a failed handshake cannot be
     continued (`failed` flag, `MessageIndex() > 2` guard).
   - Nonces: `sendN` only increases and stops at `MaxUint64` (`noise.go:223-230`). Each
     handshake gets fresh cipher states. `Open` accepts `counter ≥ recvNext` (gaps allowed) and
     advances only after authentication succeeds, as session.md §Replay says.
   - `Transport` is not concurrency-safe. Locking is up to the caller (see Assumptions).
4. **Mailbox keys.**
   - Ordering: keystore `Save`, then the tx commit, then the announcement is returned, then
     the hook runs (`mailbox.go:349-386`). A failed tx deletes the secret again.
   - Deletion happens at `not_after + 7 d` (`sweepLocked`, `:401-422`), plus early deletion
     above 3 live keys.
   - A key is never used after `not_after + 7 d`: `MailboxKey` filters on that and on
     `deleted IS NULL` (`:263-283`).
   - **A keystore read failure can still cause a silent rotation:** in `auto` mode a keychain
     outage makes `usable` return `false, nil` (C05-01). The old key is not orphaned, because
     its row stays live and it is deleted on schedule. But an extra key is created and pushed
     to every peer, and repeated outages hit the 3-key cap early.
5. **Identity.**
   - Missing key with the card present: start fails with `ErrKeyLost`, as the spec's
     lifecycle table says. This is O-197, as documented. But the same error also fires when
     the keychain is only unavailable, and it advises deleting the card (C05-02).
   - A corrupt card fails start and nothing is overwritten (`identity.go:110-113`).
   - A corrupt key file or keychain entry, or a wrong seed length, fails start
     (`:135-136`, `:188-193`).
   - The seed never leaves the package. `Identity` holds only the card and the backend name.
     The audit detail holds only the public key, the backend and the keychain error.
     `NewKeystoreSigner` reloads the seed for each signature and clears it afterwards
     (`internal/relayclient/signer.go:42-58`).

## Findings

### C05-01 · Low · confirmed-test
- **Where:** `internal/keystore/keystore.go:44-54` (`Store.Load` returns `ErrNotFound` when the
  keychain is only unavailable) with `internal/keystore/keychain.go:36-43` (every error,
  including the 5 s timeout, is wrapped as `ErrUnavailable`); consumed at
  `internal/mailbox/mailbox.go:224-237` (`usable`) and `:304-311` (`Rotate`)
- **What goes wrong:** in `auto` mode, a mailbox key held in the keychain looks "not found"
  while the keychain is locked or slow. `usable` then returns `false, nil`, and `Rotate` or
  `Announcement` creates, announces and pushes a new key although the old secret still
  exists. The code comment at `mailbox.go:222-223` says this must not happen ("rotating then
  would orphan a key"), and so does the R09 L5 follow-up.
- **Scenario:** no attacker; this is a local fault. The identity key sits in `identity.key`
  because the keychain was unavailable at first run (the spec's normal fallback), and later
  mailbox keys go to the keychain once it works. Later the daemon starts while the Secret
  Service or Keychain is locked, or a keychain call takes more than 5 s. The start-time
  `Rotate` then creates a new current key and pushes a `keys` mail to every peer. While the
  keychain stays unavailable, the retired key cannot decrypt anyway. Each such outage that
  hits a keychain-held current key adds one live key, so a third outage within 21 d deletes
  the oldest key early. Mail still queued at the relay for that key becomes a key miss.
  Test: `internal/mailbox/zz_review55_C05-01_test.go` (the identity key is in a file backend,
  mailbox keys use `auto`, `keyring.MockInitWithError`) → "key rotated because the keychain
  was unavailable (pushes=2)". If both keys are in the keychain, signing fails too and nothing
  rotates, which limits the reach.
- **Spec:** mail.md §Lifecycle, "If there is no live key, or the current key's
  `created ≤ now − 7 d`, it creates a new key". An unavailable key is neither.
- **Fix direction:** have `Store.Load` return an error that wraps `ErrUnavailable` (not
  `ErrNotFound`) when a skipped backend could hold the secret, and have `usable` treat that
  as an error.
- **Related:** O-035, R09 L5, C05-02

### C05-02 · Low · confirmed-read
- **Where:** `internal/identity/identity.go:131-133`, root cause `internal/keystore/keystore.go:50-52`
- **What goes wrong:** when the keychain holding the identity seed is unavailable at start, the
  daemon reports `ErrKeyLost`: "agent card exists but its private key was not found … restore
  it or delete agent-card.json to start a new identity". The key is not lost. Following that
  advice destroys the identity and every pairing.
- **Scenario:** no attacker; this is an owner action based on misleading text. On macOS the
  login keychain is locked (for example a service started over SSH), or on Linux the Secret
  Service is not running yet. `agentnetd` exits with the key-lost message. The appended
  "(skipped keychain: …)" is the only hint. The user deletes the card, and a new identity is
  generated at the next start.
- **Spec:** agent-card.md §Key storage lifecycle table: the "missing | present" row is meant
  for a key that is really missing.
- **Fix direction:** separate "keychain unavailable" from "not found" (same root as C05-01)
  and say "unlock the keychain and retry" in that case.
- **Related:** O-197, C05-01

### C05-03 · Low · confirmed-read
- **Where:** `internal/agentcard/agentcard.go:109-122` (`checkText`)
- **What goes wrong:** card text (`name`, `harness`, skill fields) rejects only `unicode.IsControl`
  (Cc) and U+FFFD. Bidi overrides and isolates (U+202A–202E, U+2066–2069, category Cf),
  zero-width characters, and U+2028/U+2029 are accepted into a signed, stored peer card.
- **Scenario:** a paired peer, or the counterparty during pairing, names itself
  `"bob‮ecila"` or pads its name with zero-width characters to imitate another peer. The
  name is shown in pairing confirmation and peer listings. `termSafe` exists in
  `cmd/agentnet/fetch.go:267`, but no card-name output path uses it (grep). Trust still rests
  on the code or fingerprint, so this is display spoofing only.
- **Spec:** agent-card.md §Card, "no control characters", which is silent on Cf.
- **Fix direction:** also reject Cf/Zl/Zp in `checkText`, or escape card names at every
  display point.
- **Related:** O-100 (same class, request text), O-067 (name collisions)

### C05-04 · Info · confirmed-test
- **Where:** `internal/agentcard/canonical.go:40-57` (relies on `encoding/json` string decoding)
- **What goes wrong:** lone-surrogate escapes `"\ud800"`/`"\udfff"` are accepted and decoded to
  U+FFFD, so three different inputs have the same canonical form and signature. RFC 8785
  (I-JSON) requires rejecting them. agent-card.md rule 6 does not mention them.
- **Scenario:** only the signer can pick the form inside a sealed or MAC'd body, so nothing
  can be forged. The risk is interop: an independent non-Go verifier that keeps lone
  surrogates canonicalises differently, and bodies with U+FFFD can pass validators that do
  not check for it. The card path itself rejects U+FFFD in `checkText`. Test:
  `internal/agentcard/zz_review55_C05-02_test.go` `TestReview55LoneSurrogate` →
  `"\ud800" -> "\"�\""`.
- **Spec:** agent-card.md §Canonical serialisation rules 3 and 6 (silent)
- **Fix direction:** state the rule in the spec (reject escaped lone surrogates) and enforce
  it in `ParseStrict` and `verifycard`.
- **Related:** O-049

### C05-05 · Info · confirmed-read
- **Where:** `tools/verifycard/main.go:38` (`base64.RawURLEncoding`, not `.Strict()`) vs
  `internal/agentcard/agentcard.go:27`
- **What goes wrong:** `verifycard` accepts a `public_key` or `signature` with non-zero
  trailing bits, which the daemon rejects. It also never checks the schema (version, lengths,
  `created`), so it can print `OK` for a card the daemon refuses.
- **Scenario:** a self-signed card whose `public_key` string ends in a non-canonical character
  (for example `…B` instead of `…A`), signed over that string, makes `verifycard` print OK
  while `agentcard.Verify` fails. There is no security impact because the key bytes are the
  same, but the "independent verifier" can disagree with the daemon.
- **Spec:** agent-card.md §Verification steps 2 and 5
- **Fix direction:** use strict base64 in `verifycard` and add the schema step (or document
  that it checks only the signature).
- **Related:** none

### C05-06 · Info · suspected
- **Where:** `internal/keystore/file.go:55-80` (`WriteOwnerOnly`)
- **What goes wrong:** the temp file is fsynced, but the parent directory is not fsynced after
  `os.Rename`. On Unix a power loss can therefore lose the rename after later writes have
  become durable.
- **Scenario:** possible sequences are a mailbox key file whose rename is lost while its
  SQLite row (WAL, fsynced) survives, giving an announced key with no secret, or `identity.key`
  lost while `agent-card.json` survives, giving `ErrKeyLost`. Whether this can happen depends
  on filesystem ordering (ext4 `data=ordered` usually commits both in order), so I did not
  confirm it.
- **Spec:** mail.md §Lifecycle "stored, announced". O-035 asks for the crash ordering.
- **Fix direction:** fsync the directory after the rename on Unix.
- **Related:** O-035

## Assumptions and contracts

- `noise.Transport` is not safe for concurrent use. `internal/session` must hold its lock
  around `Seal`/`Open` (`internal/session/session.go:154`, "Lock order: sendMu, then mu"
  `:190`). **unchecked** in detail.
- session.md binding check 3 (the identity is a paired peer) is enforced by `internal/session`,
  not by `noise` (`noise.go:84`). **unchecked**.
- The responder passes the relay-authenticated `from` as `peer` to `NewHandshake`
  (`session.go:576`). **checked**.
- `agentcard.Verify` proves self-signature only. Callers (`internal/peers/pairing.go:642,690`,
  `internal/team/kinds.go:353`) must compare `card.public_key` with the expected peer key or
  pairing MAC. **unchecked** (C06/C09).
- `mailbox.Keys.sign` is `relayclient.NewKeystoreSigner(ks, idPub).Sign`
  (`internal/daemon/daemon.go:326`), which reloads the seed and refuses a mismatched key
  (`internal/relayclient/signer.go:42-58`). **checked**.
- The mailbox keystore mode equals the identity's (`DORYLINAE_KEYSTORE`) and is forced to
  `file` when a keystore is injected (`daemon.go:322-325`). **checked**.
- Callers of `ParseStrict` bound the input size before parsing (the parse depth is bounded by
  `encoding/json`, but width is not). The mail path is bounded by the envelope limit.
  **unchecked** per caller (T-theme on input bounds).
- `mail.ParseAnnouncement` validates `created`/`not_after` per mail.md §Mailbox keys step 5.
  `mailbox` relies on it for `rowPub` and the import (`mailbox.go:240`, `:483`). **unchecked**
  (C07).

## Checked and fine

- `Verify` canonicalises the generic `card` map, not the struct, so any added or changed
  member fails the signature. Unknown fields are rejected afterwards
  (`agentcard.go:198-213`).
- `Sign` refuses a card whose `public_key` does not match the signing key (`agentcard.go:157`).
- The card `created` round-trip check enforces whole-second UTC `Z` (`agentcard.go:102-105`).
- Strict base64url (no padding, zero trailing bits) for the card key and signature
  (`agentcard.go:27`).
- Domain separators: card `dorylinae-agent-card-v1\n`, Noise static
  `dorylinae-noise-static-v1\n`, prologue `dorylinae-noise-xx-v1\n`. All are distinct.
- JSON depth is bounded (10 000) by `encoding/json`: tested at 10^5–2·10^6, fast error, no
  stack growth.
- `WriteOwnerOnly` restricts before writing on both OSes. The temp file is removed on error.
- The Windows DACL is protected (no inheritance) with one allow ACE for the token user
  (`perm_windows.go:14-30`).
- Unix `Get` refuses any group or other bit (`perm_unix.go:12-21`).
- Keychain calls are bounded to 5 s (`keychain.go:59-68`). A late `Set` after a timeout stores
  the same secret that the file fallback got.
- `Store.Delete` does not swallow keychain delete errors: `Keychain.Delete` does not wrap
  `ErrUnavailable`, so a failed deletion is retried and the row is not marked `deleted`
  (`keystore.go:94-106`, `mailbox.go:426-439`).
- O-035 appears fixed in the code: the key is saved before the row, and the secret is deleted
  again on any tx failure (`mailbox.go:349-375`). The residual is C05-06.
- `retired` is set for every previous live key in the same tx as the insert
  (`mailbox.go:363-371`).
- `MailboxKey` never returns a key past `not_after + 7 d` or with `deleted` set
  (`mailbox.go:263-283`).
- The legacy `current.json` import checks the announcement signature against our identity and
  that the private key matches, and keeps the file on a transient keystore error
  (`mailbox.go:462-511`).
- O-030 is still open (Windows `checkOwnerOnly` = `Stat`). It is not re-reported.
- O-197 behaves as documented (`identity.go:131-133`).

## Notes

- `verifyBinding` uses plain `json.Unmarshal` (case-insensitive keys, last duplicate wins).
  This is harmless because the payload is inside the authenticated handshake.
- Mailbox `ks.Save` discards the `skipped` keychain errors, so a mailbox key's fallback to a
  file is neither logged nor audited, unlike the identity's `keychain_error`.
- `identity.pubString` uses non-strict encoding, which is harmless because encoding is
  deterministic.
