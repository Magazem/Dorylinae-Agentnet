# C26: Audit log, SQLite store, migrations, `agentnet log`

Reviewer: CR-C26 · model claude-opus-5-5 · elapsed ~6 min (wall clock as measured by `date`) · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 1 · Info 2.

The chain, the triggers, `Verify` and the migrations match `audit.md` closely. `Append` and
`store.apply` both use `BEGIN IMMEDIATE` on a dedicated connection, re-read state under the
write lock, and roll back with a background context on every error (INV-5). Migration 18's
trigger refuses unchained rows, gaps and `INSERT OR REPLACE` on old ids. `Verify` is paged. The
migration rebuilds (8, 19) copy every column by name. The one real defect is outside the audit
logic: both SQLite DSNs build a `file:` URI from a raw filesystem path. SQLite then parses `#`
and `%` in that path as URI syntax, so the database is opened at the wrong path, or not at all
(confirmed by test). Nothing in this chunk lets the relay, a peer or a local agent break or fork
the chain, or put content into it.

## Questions

1. **Chain integrity.** No path breaks or forks the chain without `--verify` noticing.
   - Every writer goes through `appendChained` (`internal/audit/audit.go:133`). It reads the
     head, then inserts with an explicit `id = head.id + 1`.
   - The migration-18 trigger (`internal/store/store.go:374-376`) refuses a NULL hash and any
     id other than `MAX(id)+1`. That covers `INSERT OR REPLACE` on an existing id (R44 L1) and
     gaps.
   - `grep` finds no `audit_events` write outside `internal/audit` and `internal/store`.
   - Two processes: `Append` uses `BEGIN IMMEDIATE` (`audit.go:78`). With `AppendTx` in a
     deferred transaction, the loser gets `SQLITE_BUSY_SNAPSHOT` or a PK/trigger failure, never
     a fork. That residual is O-169.
   - `--verify` is paged: the head is read once, then 2000-row pages (`chain.go:196-266`,
     `readPage`), each closed before the next. `TestVerifyPagesReleaseTheConnection` passes.
   - Known limits (tail truncation, whole-chain rewrite) are as documented in `audit.md`
     §What the chain proves.
2. **Migrations.** Each migration is atomic.
   - Each runs in `BEGIN IMMEDIATE` and re-reads `MAX(version)` inside the transaction
     (`store.go:602-611`). It skips if another process applied it and fails if the version
     is not `m.version-1`.
   - Two concurrent openers are safe (`TestConcurrentOpenAppliesMigrationsOnce` passes).
   - No data loss on an old DB:
     - Migration 8 copies every old `peers` column.
     - Migration 19 names all 31 `requests` columns on both sides, `result` included
       (`store.go:420-429`), recreates all three indexes with the partial `WHERE`
       (`:432-435`), and copies every `approvals` column (`:448-449`).
     - No FK or trigger references the rebuilt tables, so the DROP is safe with
       `foreign_keys(1)`.
   - Newer-schema check: see C26-03 (Info).
3. **Transactions.**
   - `Append` (`audit.go:68-77`) and `apply` (`store.go:595-601`) issue `ROLLBACK` on a
     background context after any error, including a failed `BEGIN` (INV-5). Their deferred
     calls run in LIFO order, so the rollback happens before `conn.Close`.
     `TestCancelledAppendLeavesNoOpenTransaction` passes.
   - Nested use under `SetMaxOpenConns(1)`: `Append` takes `db.Conn`, so it would deadlock if
     called while the same goroutine held a `*sql.Tx` or open `Rows`. I sampled the heuristic
     hits in `internal/request/cancel.go`, `session_hooks.go`, `worksession/submit.go`,
     `transitions.go`, `mailbox/mailbox.go:372-377` and `approval/store.go:374-386`. All call
     `Append` after `Commit`, or through `AppendTx`. The sweep was not exhaustive; see Leads.
   - `secure_delete(1)` is in the DSN (`store.go:540`, `TestOpenSetsSecureDelete` passes). The
     WAL-frame gap is documented in `work-session.md` §Deleted bytes, so it is not a finding.
4. **`agentnet log` output.** Printing is safe.
   - `formatEvent` (`cmd/agentnet/log.go:262-285`) passes ts, actor, action, every key and every
     compacted value through `notify.Clean`. `Clean` strips C0/C1 controls, bidi controls and
     U+2028/9 (`internal/notify/notify.go:13-40`).
   - Values are first re-marshalled by `json.Marshal`, which escapes control characters.
   - `--json` relies on `json.Encoder` escaping.
   - `printVerify` and `--head` print `Head.Hash`/`TS` raw (`log.go:175,250`). Via IPC these
     are daemon-written. In the fallback they come from a file only the same user can write,
     which is out of scope (Notes).
5. **Read-only fallback.** It neither migrates nor writes.
   - `OpenReadOnly` (`internal/store/readonly.go:13-27`) stats the file first, opens with
     `mode=ro` and `query_only(1)`, and runs no migrations.
   - It is used only when `ipc.Dial` returns `ErrNotRunning` (`log.go:306-326`).
   - The path comes from `paths.Default()`: `$DORYLINAE_HOME` or `os.UserConfigDir()`
     (`internal/paths/paths.go:31-49`). That is the user's own environment, and the file is
     read with the user's own rights, so it cannot reach another user's DB.
   - The `#`/`%` path defect (C26-01) applies here too. With `#`, the part after it
     (including `mode=ro`) is dropped as a URI fragment; the open still fails safe because
     `os.Stat` checked the real path.

## Findings

### C26-01 · Low · confirmed-test
- **Where:** `internal/store/store.go:540` (`Open`), also `internal/store/readonly.go:17`
  (`OpenReadOnly`)
- **What goes wrong:** the DSN is `"file:" + path + "?..."`. modernc passes it to
  `sqlite3_open_v2` with `SQLITE_OPEN_URI`
  (`modernc.org/sqlite@v1.59.0/conn.go:100-105`), so SQLite parses the path as a URI:
  - a `#` starts a fragment and truncates the path;
  - `%xx` is percent-decoded.
  The database is created at a different path, or cannot be opened.
- **Scenario:** no attacker; the actor is the machine's own configuration.
  - A Windows account name may contain `#`, `%` or `&`. Take `Jo#dev`: the config dir is
    `C:\Users\Jo#dev\AppData\Roaming\…`. SQLite tries to open `C:\Users\Jo`, which a
    non-admin user cannot create, so `agentnetd` fails at start.
  - The same happens when `DORYLINAE_HOME` contains `#`, e.g. `D:\data\ag#1`. Then the DB
    silently lands at `D:\data\ag`: a file outside the private home directory that the
    daemon's ACL/0700 setup protects, holding request bodies, results and Decisions.
  - `%41` in a path gives "unable to open database file (14)".
  - The test shows the `#` case creating a file named `a` next to the directory `a#b`, while
    the intended `a#b/dorylinae.db` does not exist.
  - Rated Low because it needs unusual but legal path characters.
- **Spec:** none (agentnetd-install.md and D24 assume the DB lives inside the private home)
- **Fix direction:** build the URI with `url.URL{Scheme: "file", Path: filepath.ToSlash(...)}`
  (plus a leading `/` for a drive letter on Windows), or percent-escape `?#%`; add a test with
  `#` in the path.
- **Related:** none (the same pattern is in `internal/relay/queue.go:210`, see Leads)

### C26-02 · Info · confirmed-test
- **Where:** `internal/audit/query.go:129-158` (`Query`), comment at `:78-79`
- **What goes wrong:** the comment says `Query` "never holds the daemon's only connection for
  long". With a sparse filter (`--action` that matches little, or `--session`, which runs up to
  a dozen `json_extract`s per row), one `LIMIT 1000` statement scans the whole table before it
  returns. It holds the single connection for the whole scan.
- **Scenario:** the actor is the owner or a local agent calling `audit_list {session: …}` on a
  large log. Measured on 200 000 rows: the session filter takes 162 ms, and a concurrent
  `Head()` waits 140 ms. That extrapolates to about 0.8 s per 10⁶ rows. The delay is bounded
  and small; a local agent can stop the daemon anyway. It is recorded because R43 M8 set the
  bar for the audit walk.
- **Spec:** `audit.md` §agentnet log, "`audit_list` and `audit_head` are quick reads"
- **Fix direction:** none needed now; if logs grow past ~10⁶ rows, bound each statement by id
  range (`id > ? AND id <= ?+N`) as `Verify` does.
- **Related:** R43 M8, O-172

### C26-03 · Info · confirmed-read
- **Where:** `internal/store/store.go:573-576`, `:609-621`
- **What goes wrong:** the "schema is newer than this binary" check runs only once, outside
  the per-migration transaction. Suppose a newer binary's migration commits between that read
  and `apply`. `apply` then sees `current >= m.version`, skips silently, and the old binary
  runs on a newer schema.
- **Scenario:** an old `agentnetd install` (or daemon) races a newer one on the same file
  during an upgrade. This needs two binary versions at once, which is rare.
- **Spec:** `audit.md` §Migrations and the second process (does not cover mixed versions)
- **Fix direction:** in `apply`, also fail if `current > len(migrations)`.
- **Related:** R43 M9, O-173

## Assumptions and contracts

- **checked:** every caller of `audit.Append` holds no open `*sql.Tx` or `*sql.Rows` on the
  same `*sql.DB`, since `Append` takes `db.Conn` under `SetMaxOpenConns(1)`. Sampled sites
  (`internal/worksession/transitions.go:113-118`, `internal/request/cancel.go:99-104`,
  `internal/mailbox/mailbox.go:372-377`, `internal/approval/store.go:374-386`,
  `internal/worksession/submit.go:86-126`) all append after `Commit`. Not exhaustive.
- **unchecked:** callers of `AppendTx` pass a transaction on the store's own DB, not a
  read-only handle. Every `AppendTx` caller then handles its error by failing its own
  transaction (the `audit.md` promise).
- **unchecked:** callers put no content in `detail`. `marshalDetail` (`audit.go:109`) accepts
  any value; the guarantee lives in the call sites and in `TestPhase2/3AuditHasNoContent`.
- **checked:** `notify.Clean` strips C0/C1, bidi and U+2028/9 (`internal/notify/notify.go:13-40`).
  `formatEvent` relies on it.
- **checked:** `ipc.Dial` returns `ipc.ErrNotRunning` only when nothing listens, so the fallback
  does not run while a daemon is up (`cmd/agentnet/log.go:307-314`). I did not read the
  per-OS transport code.
- **unchecked:** the IPC handler `ctx` (`internal/ipc/ipc.go:151-176`) is not cancelled when
  the client disconnects. An abandoned `audit_verify` then runs to completion. This is
  harmless because it is paged.
- **checked:** the `paths.Default()` DB path lives in the private home (`internal/paths/paths.go:31-49`).
  C26-01 breaks this for `#` in the path.

## Checked and fine

- The chain hash matches the spec. `rowCanonical` (`chain.go:45-53`) hashes the stored detail
  text as a string, the id as a `json.Number`, and the label with the raw 32-byte previous
  hash. `TestChainVector` passes.
- `decodeHash` rejects uppercase and non-canonical hex (`chain.go:70-76`). `ParseAnchor`
  rejects `id <= 0` (`:85-98`).
- `Verify` order of checks: legacy → chain_start → gap → unchained → hash → malformed →
  anchors after the walk. A legacy anchor gives `anchor_mismatch` only when the walk is clean
  (D31, R44 M1) (`chain.go:196-331`).
- `isChainStart` uses `DisallowUnknownFields` and checks `legacy_rows` and `legacy_last_id`
  against the walk (`chain.go:334-349`).
- `wellFormed` requires valid UTF-8 in every text field, so canonical JSON cannot fold
  distinct invalid bytes together (`chain.go:368-376`).
- `startChain` refuses to start a second chain after an unchained head (`audit.go:163-170`).
  Its error message names `agentnet log --verify` (`audit.md` §When the daemon will not
  start).
- The migration-1 table has `detail CHECK (json_valid(detail))` and `ts NOT NULL`. The
  migration-18 `hash` CHECK enforces 64 lowercase hex characters.
- `Query` validates limit, `after_id`, since/until (RFC 3339) and the session prefix. Each of
  these is `ErrBadParams` → `bad_request` (`query.go:81-104`, `internal/daemon/audit.go:49-54`).
- The `since`/`until` prefilter truncates to the second; `inWindow` then does the exact
  compare, which handles variable fractional digits.
- `sessionClause` wraps its `json_extract` in `CASE WHEN json_valid`. It uses placeholders
  only, with no string interpolation of input (`query.go:219-309`).
- `rawDetail` keeps a tampered detail from breaking the response (`query.go:207-213`).
- `agentnet log`:
  - rejects combining `--verify`/`--head` with filters, and `--anchor` without `--verify`;
  - exits 5 on a broken chain, 3 with no daemon and no DB, 2 on `bad_request`
    (`log.go:116-129`, `:253-256`, `:374-392`);
  - pages with `next_after_id` and stops at `--limit`.
- O-169, O-172 and O-173 are still as recorded and are not re-reported.
- R44 L2 (unchained head blocks `--verify`) stays fixed through the read-only fallback
  (`TestReadOnlyOpenVerifiesUnchainedHead` passes).

## Leads for other chunks

- `internal/relay/queue.go:210`: the same `"file:" + path` DSN as C26-01. A `--queue-db` path
  with `#` or `%` opens the wrong file. This is operator-controlled (relay chunk).
- Theme reviewers should run an exhaustive check for `audit.Log.Append` called while the same
  goroutine holds a `*sql.Tx`/`Rows` on the store DB, which deadlocks under
  `SetMaxOpenConns(1)`. I sampled the sites; I did not check all 83.
- `internal/notify/notify.go:13-18`: `cleanRunes` lacks U+061C (ALM), U+200B–U+200D and
  U+FEFF. That matters for display spoofing in notifications (C27).

## Notes

- `formatEvent` re-marshals values through `any`, so integers above 2⁵³ print as floats. This
  is display only, and the audit values are small.
- `printVerify` and `--head` print `TS`/`Hash` without `notify.Clean`. That only matters for a
  same-user-tampered DB in the fallback, which is out of scope. Cleaning them would still be
  cheap consistency.
