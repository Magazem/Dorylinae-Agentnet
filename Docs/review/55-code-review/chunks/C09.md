## Summary

| Critical | High | Medium | Low | Info |

Verdict: the token, verification and fs-serving core is sound. Verify runs steps 1–8 in the
spec's order and fails closed, including on a nil `SessionOpen`. The signature covers the
generically parsed grant, and the stored-token comparison uses the canonical re-encoding,
not raw bytes. The path grammar plus `os.Root` plus per-component `Lstat` plus the
open-handle `SameFile` check leaves no peer-reachable escape that I could find. `.git`
exclusion handles case, `ı`, Cf characters and 8.3 aliases. The grantor rechecks the row,
exp and session before every read fragment. The quarantine rule matches work-session.md,
and every current activation path records an approval or a policy. The findings are
robustness defects on the holder's grant-mail apply path, plus two Info notes.

## Questions

1. **Path escape.** None found for a peer. `ValidScopePath` (`internal/capability/token.go:295`) rejects `..`/`.`/empty segments, leading and trailing `/`, `\` and `:`, so no drive letters, UNC, `\\?\` or ADS `file:stream`. It also rejects C0, C1 and bidi characters (`:351`), trailing `.` or space (`:320`), and reserved names including `CONIN$`/`CONOUT$` and superscript `COM¹–³`/`LPT¹–³` (`:326`). The fetch server applies it to the request path (`fetch.go:454`), and `Sign` applies it to the scope (`token.go:218`). The effective path is always scope + path. `walk` (`fs.go:179`) refuses any component that `isGitName` matches (`fs.go:124`: EqualFold, per-rune ToUpper for `ı`, Cf characters stripped for HFS+ ignorables) → `out_of_scope`. On Windows it refuses 8.3 shapes (`fs.go:136`) → `bad_path`. It then `Lstat`s each prefix through the `os.Root`, and a symlink or `ModeIrregular` (junction/reparse point) at any depth → `symlink` (`fs.go:167`). `Read` checks `SameFile` plus regular plus size on the open handle (`fs.go:355-367`). `List` checks `SameFile` on the opened directory (`fs.go:277`) and hides `.git` in any case (`fs.go:285`). The root is reopened from the stored resolved path on every call (`fs.go:231`). A swap of that root is a local-only act. A local-writer race inside the root is noted in C09-04. Hard links are the residual the spec documents.
2. **Verification.** Steps 1–8 run in spec order (`verify.go:107-196`); the first failure is returned. Step 1 is strict: size ≤ 2048, `ParseStrict`, exactly `grant`+`sig`, exact member count and JSON types, scope never empty, `v` has no int wrap (`verify.go:231-319`). Step 4 verifies over `CanonicalValue(gen)`, the generic parse (`:151`), and requires `sigPattern` before decoding (`:144`). A nil `SessionOpen` → `unknown_session` (`:178`); R25 M1 is fixed. For the grantor, `aud` = `Counterparty`, which is the Noise-authenticated peer (`fetch.go:559`, peer from the session). Step 9 compares `Canonical(Token{*g, sig})` with the stored token (`fetch.go:571-582`), not the raw bytes. It also checks `Direction == issued` and `Peer == peer`.
3. **Revoked, expired, closed or pending grants.** `authorize` refuses any state other than `active` (`fetch.go:586-592`). `recheck` runs before each fragment (`fetch.go:484`). It re-reads the row (revoked/state/token), `exp`, and the session's known/open state (`fetch.go:598-620`). `FSBackend.Read` stops on the first `emit` error (`fs.go:394`). Stat and list are single-response. No byte can be served after the commit except fragments already handed off, which the spec allows.
4. **Sensitive grants and quarantine.** `QuarantineHolds` (`store.go:302`) matches work-session.md §Quarantine rules 1 and 2. "Ever active" means `active`, or `revoked` with an approval or a policy. Every current activation writes one: `ActivateTx` refuses an empty approval id (`store.go:283`), and the policy path sets `rec.Policy = match.ID` before `InsertActiveTx` (`internal/daemon/grant.go:496`). So O-146 stays limited to pre-2.4 rows; no migration backfills them (no `UPDATE grants` in `internal/store/store.go`). Still open. Debate edges: `PeerQuarantineHoldsTx` (`store.go:319`) is rule 2 with the same "ever active" filter, wired at `internal/daemon/daemon.go:535`. `CheckSensitiveGrant` (`store.go:346`) includes `invited` (review 43 M5) and is called at create, at the approval precondition and on the policy path inside the tx (`grant.go:446,516,569`). A pending sensitive grant does not count for rule 2 at debate submit, but its later activation is refused by the `debate_open` precondition, so there is no gap.
5. **Error strings.** `VerifyError.Error()` can include parser text (`verify.go:38`), but no in-scope caller emits it. The holder's grant apply emits only `ReasonOf` (`grant_kinds.go:77`). The fetch server maps through `FetchCode` (`fs.go:64`), and `FetchError.Error()` is the code only. `fetch_client.go:490-495` returns only the reason. The audit rows in `grant_kinds.go:113-118` carry ids, enums, key and bool only. R25 N2 holds.

## Findings

### C09-01 · Low · confirmed-test
- **Where:** `internal/daemon/grant_kinds.go:51` (`json.Marshal(tokenGen)`), `internal/capability/verify.go:110`
- **What goes wrong:** the holder re-serialises the received token with `encoding/json`. That escapes `<`, `>`, `&` (and U+2028/9) to 6-byte `\uXXXX` before `Verify`'s 2048-byte check. A valid token whose canonical form is within the limit can therefore be rejected at the holder as `malformed`, and the mail is stored as bad body.
- **Scenario:** a grantor issues a grant whose scope or branch has many `&`/`<`/`>` characters (about 170 or more near a large scope; `Sign` accepts it because the canonical form is ≤ 2048). The holder's apply fails at step 1, and the grant never reaches the holder. The grantor's row is `active`. The holder cannot use it and sees no grant. No security impact: the failure is closed. Test: 250 `a&b` in the scope gives canonical 1209 bytes and marshalled 2464 bytes → "rejected at step 1 (malformed): token is 2464 bytes".
- **Spec:** `Docs/protocol/grant.md` §Token, "The wire form is canonical(token). It is at most 2048 bytes."
- **Fix direction:** build `raw` with `agentcard.CanonicalValue(tokenGen)` (or apply the size limit to the canonical form).
- **Related:** none

### C09-02 · Low · confirmed-read
- **Where:** `internal/daemon/grant_kinds.go:56-60`, `:73-75`
- **What goes wrong:** the holder's `sessionOpen` callback maps **any** `wsStore.GetTx` error (a DB error as well as not-found) to "unknown". The grant is then treated as an orphan: the mail is acked and committed, and the grant is dropped for good.
- **Scenario:** a transient SQLite error (I/O error, corruption detected on the page) during the grant mail's apply transaction → `grant.orphan` is audited, the mail is marked seen and never retried, the holder has no row, and the grantor believes the grant is active. Recovery is manual: the grantor revokes and reissues. It fails closed for access, but durable state is silently lost. The trigger is a rare DB error, not an attacker.
- **Spec:** grant.md §Kinds (orphan = "a session the holder does not know yet"); rubric invariant 5 (a transient error should not ack).
- **Fix direction:** distinguish `worksession` not-found from other errors, and return the other errors from Apply so the mail is not acked.
- **Related:** O-077 (pending maps, same function)

### C09-03 · Low · confirmed-read
- **Where:** `internal/capability/store.go:234` (`List`, no limit), `internal/daemon/grant.go:638` (`grant_list`), `internal/daemon/grant_kinds.go:99`
- **What goes wrong:** held grant rows are never pruned (the only `DELETE FROM grants` is `Store.Delete`, `store.go:191`), and `grant_list` returns every matching row in one IPC line.
- **Scenario:** a paired peer that is the requester of an open session with us sends many valid `grant` mails, each with a fresh id (it signs them itself). After roughly 1,700 rows (about 600 bytes per view), `agentnet grants` exceeds the 1 MiB IPC line and fails, and the table grows for as long as the session is open. The per-peer mail rate limit that bounds the speed was not checked; the impact is bounded by it. Expired held rows also stay forever.
- **Spec:** grant.md §Tables (no retention stated); rubric §1 "make us store unbounded data".
- **Fix direction:** cap held grants per peer or session and/or prune rows past `exp` plus a margin, and page `grant_list`.
- **Related:** O-058 (`mail_inbox` never pruned; the same mails are also inbox rows), O-178 (the same unbounded-list pattern)

### C09-04 · Info · confirmed-read
- **Where:** `internal/capability/fs.go:196-206` then `:348-361`
- **What goes wrong:** `walk` `Lstat`s prefixes one at a time. If a local writer replaces an already-checked intermediate directory with a symlink to `.git` (inside the root) before the final `Lstat`, then `root.Lstat("a/config")` follows the new link. `OpenFile` opens the same file and `SameFile` passes, so `.git/config` is served. `os.Root` still prevents any escape from the root.
- **Scenario:** needs a local process writing inside the granted directory at the right moment. That actor is out of scope, and it could copy the file anyway. Recorded because the spec lists "TOCTOU swap" as controlled.
- **Spec:** grant.md §Threat model, "Path traversal, symlink escape, TOCTOU swap"
- **Fix direction:** open components one by one with no-follow, or re-`Lstat` all prefixes after the open.
- **Related:** O-145 (same local-swap class for `list`)

### C09-05 · Info · suspected
- **Where:** `internal/capability/token.go:257` (`checkBranch` uses `hasControl`, not `hasPathControl`)
- **What goes wrong:** a grant's `resource.branch` may contain C1 and bidi characters, which the spec allows (request.md artifact branch rules). A hostile grantor's branch is stored in the holder's row and shown in the holder's grant view.
- **Scenario:** display spoofing of the branch name in `agentnet grants` on the holder, unless the CLI sanitises output (not checked).
- **Spec:** grant.md §Grant object ("branch follows the request artifact branch rules")
- **Fix direction:** reuse `hasPathControl` for the branch, with a spec change.
- **Related:** O-126

## Assumptions and contracts

- `FSBackend`/`Backend` assume `rel` = scope + path, with each part already validated by `ValidScopePath` (`fs.go:91-93`). **Checked:** `fetch.go:454-457` validates the path; the stored scope comes from a signed token (`Sign` → `checkFormats`), and `rec.Token` equals the presented token.
- `Read` assumes `offset ≥ 0` and `1 ≤ length ≤ MaxReadBytes` (`fs.go:331`). **Checked:** `fetch.go:405-406`, and holder-side `fetch_client.go:455`.
- `emit` must enforce revocation, expiry and session per fragment (`fs.go:100`). **Checked:** `fetch.go:484` → `recheck` `:598`.
- Step 5 relies on `Counterparty` being the Noise-authenticated peer (`verify.go:161`). **Checked** at the call (`fetch.go:559`, `peer` from the job); **unchecked** that `j.peer` is derived from the session's static key (C10 / session layer).
- `QuarantineHolds` relies on every path that sets `active` writing `approval` or `policy` (`store.go:304`). **Checked:** `store.go:283`, `internal/daemon/grant.go:496,526`.
- `InsertPending` relies on the caller calling `Delete` when `approval.Create` fails (`store.go:131`). **Unchecked** (C-daemon grant chunk).
- `ActivateTx` does not re-check the session or debate state; the caller's precondition must (`store.go:275`). **Checked:** `grant.go:569` (`CheckSensitiveGrant`) and `recheckIssuanceTx`.
- The holder's `grant` apply assumes that `op.Msg.From` is the signature-verified mail sender and that `op.Msg.Body` was strict-parsed (`grant_kinds.go:38,70`). **Unchecked** (mail chunk).
- `RevokeForSessionTx` relies on the worksession close transaction calling it, and on `OnClosed` rejecting pending approvals (`store.go:378`). **Unchecked** beyond `internal/daemon/quarantine.go:54`.
- `recheck` skips the session check when `cfg.SessionOpen` is nil (`fetch.go:610`). It is harmless only because `authorize` already fails closed in that case (`fetch.go:554`). **Checked.**

## Checked and fine

- Canonical token equality is checked on both sides with the canonical re-encoding, never raw bytes (`grant_kinds.go:79-86`, `fetch.go:571-582`).
- The grantor's step 9 refuses held rows and rows for another peer (`fetch.go:582`), so a grant we hold cannot be replayed at us.
- `grant.revoke` applies only to a held row whose `peer = msg.from` (`store.go:438-450`, `grant_kinds.go:161`); members are strict (`:193`); the reason is enum-checked (`:156`).
- A holder refuses grants for debate sessions (`grant_kinds.go:67`).
- `Sign` refuses malformed, mismatched-kind, wrong-key and oversize tokens (`token.go:136-173`).
- `sigPattern` closes the `\r\n`-in-base64 second wire form (`token.go:56`, `verify.go:144`).
- `policyCovers` compares scope by segments and path/branch exactly. A sensitive policy never auto-issues a public grant (`store.go:635-684`), and a case difference fails closed.
- Store timestamps are fixed-width, so the string comparisons in `QuarantineHolds`/`PeerQuarantineHoldsTx`/policy pruning are correct (`store.go:34,307,562`). An unparsable stored `exp` yields a zero time → `recheck` returns `expired` (fail closed).
- `RevokeTx` is idempotent and does not touch an already-revoked row's `reason` or `revoked_at` (`store.go:365`).
- **O-126 mostly fixed:** `CONIN$`/`CONOUT$`, superscript `COM¹–³`/`LPT¹–³`, C1 and bidi are now rejected in scope and path (`token.go:334-363`). Only `COM0`/`LPT0` remain, and the spec does not list them.
- R25 M1 (nil `SessionOpen`) is fixed (`verify.go:178`). R34 L1 (list size by the encoded length) is fixed (`fs.go:314-320`). R34 L2 (`ı`) is fixed (`fs.go:131`).
- O-146 is still open (no backfill migration), with no new path; O-145 and O-134 unchanged.
