# C27: Notifications: desktop, webhooks, triggers

Reviewer: CR-C27 · model claude-opus-5-5 · elapsed 5 min · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 1 · Low 1 · Info 3.

The notification code holds up well against notify.md. The SSRF guard checks the address
actually dialled. Redirects are off, and the proxy policy follows the spec. Peer text is
passed as argv or env and never reaches script source. The GVariant, Pango, notify-send,
toast-XML, Slack and Discord escaping all match the spec. Payloads and audit details carry
no content, and the secret and URL are kept out of logs, audit and the human CLI output.

There is one new defect with real impact: each webhook attempt builds a fresh
`http.Transport` and never closes it. So every successful delivery leaves an idle TCP
connection and two goroutines alive for as long as the receiver keeps the connection open.
I confirmed this with a test (C27-01). The other items are small: a CLI/daemon event-list
mismatch (C27-02) and spec drift (Info).

## Questions

1. **SSRF.**
   - `resolvingDialer` (`internal/notify/dial.go:142-184`) resolves the name itself. It
     runs `checkDialAddress` on every candidate and dials `JoinHostPort(c.IP, port)`, so
     there is no rebinding window between the check and the connect.
   - Literal IPs skip resolution but are still checked (`:159`). IPv4-mapped IPv6 is
     covered because `IsPrivate`, `IsLoopback` and `IsLinkLocal*` normalise with `To4`.
     Zoned `fe80::1%x` goes through the resolver and is blocked as link-local.
   - Redirects are off: `CheckRedirect` returns `ErrUseLastResponse` (`:254`), and a 3xx
     becomes `failed "redirect"` (`webhook.go:222`).
   - The environment proxy is used (`dial.go:242`). `proxyTracker` switches to the base
     list for the proxy's host:port (`:155`), which matches the spec. For `http` to
     loopback, Go's `ProxyFromEnvironment` never proxies localhost.
   - `CheckRedirect`/`Timeout` are set per client. HTTP/2 is not negotiated (a custom
     `DialContext` without `ForceAttemptHTTP2`), so there is no other dial path.
   - No new SSRF gap beyond O-118.
   - The resource issue in the same function is C27-01.
2. **Injection.**
   - macOS passes the text as argv to a fixed script (`desktop_darwin.go:9-17`).
   - Linux wraps `gvariantString` in quotes and escapes `\` and `'`
     (`desktop_linux.go:48-64`). The body is Pango-escaped (`:68`), and the notify-send
     body has its backslashes doubled against `g_strcompress` (`:39`).
   - Windows passes the text as UTF-16LE base64 in the env. It is decoded and
     `SecurityElement.Escape`d inside a fixed script, and `-f` does not re-parse its
     arguments (`desktop_windows.go:22-47`). O-109 still stands.
   - Slack escapes `&<>` in `text` (`payload.go:146`).
   - Discord escapes the full spec character list and sets `allowed_mentions.parse=[]`
     (`payload.go:120-123,166-182`).
   - JSON goes through `json.Marshal`.
   - `Clean` matches spec steps 1–3 (`notify.go:25-65`). Bare-URL autolinking is an Info
     note (C27-04).
3. **Content.**
   - `buildPayload` adds `title` and `result_status` only with `title:true`
     (`payload.go:84-90`). `buildWebhookText` adds the title and status only with
     `title:true` (`trigger.go:238-250`).
   - The quarantined event passes no title (`internal/daemon/quarantine.go:46`).
   - `device.linked` is excluded from the webhook (`trigger.go:140`).
   - The debate adapter passes only the name, request title, id and session
     (`internal/daemon/notify.go:133-136`).
   - Result status is enum-validated upstream (`internal/request/result.go:62`).
4. **Secrets.**
   - The secret appears only in the `notify_set` result, when first set or rotated
     (`internal/daemon/notify.go:260-266`). The CLI prints it once (`cmd/agentnet/notify.go:208`).
   - The URL is elided in human output (`:218-228`). `transportError` strips `*url.Error`
     (`webhook.go:275-281`).
   - Neither the `notify.config` detail (`internal/daemon/notify.go:277-305`) nor
     `notify.fail` (`webhook.go:261-270`) holds the URL or secret.
   - The URL is returned in full by `notify_get`/`--json`: that is O-070.
5. **Bounds.**
   - The pending queue is capped at 1000 with overflow (`queue.go:81-89`).
   - Retry delays and the 7-attempt/24 h caps are applied (`queue.go:223-239`,
     `webhook.go:238-257`). A huge `Retry-After` that overflows `Duration` is capped at
     6 h or ignored when negative (`queue.go:232-236`).
   - The payload is capped at 8 KiB (`payload.go:100`).
   - The trigger allows at most 16 goroutines (`trigger.go:106-117`).
   - The response body drain is time-bounded by the 10 s client `Timeout`, but has no byte
     cap (O-119).
   - **Not bounded:** idle connections from per-attempt transports (C27-01).

## Findings

### C27-01 · Medium · confirmed-test
- **Where:** `internal/notify/dial.go:245-257` (`newHTTPClient`), `internal/notify/webhook.go:203-213` (`attempt`)
- **What goes wrong:** every delivery attempt creates a new `http.Transport` with no
  `IdleConnTimeout`, no `DisableKeepAlives` and no `CloseIdleConnections`. After the body
  is drained (`webhook.go:213`), the keep-alive connection sits in the idle pool of a
  transport nobody will reuse. Its readLoop/writeLoop goroutines keep it alive until the
  receiver closes the connection, so connections and goroutines grow by one set per
  delivered event.
- **Scenario:**
  - A paired peer sends a stream of requests within its rate limits. Each
    `request.received` enqueues a delivery, and each successful delivery leaves one
    open socket and two goroutines behind.
  - Against Slack/Discord/Cloudflare-fronted receivers, these last until the server's
    idle timeout (minutes).
  - A receiver that never closes idle connections makes the growth unbounded until the
    daemon runs out of fds/handles. That receiver can be a local custom endpoint, or a URL
    set by a prompt-injected local agent over IPC, which the spec allows. Once fds run out,
    the relay connection and IPC fail too.
  - Test: 40 deliveries → 40 server-side connections still open, +120 goroutines.
- **Spec:** notify.md §Delivery (one POST per attempt, 10 s timeout); rubric §2 Medium,
  "resource leak that grows with peer or relay input"
- **Fix direction:** reuse one transport per scheme/resolver, or `DisableKeepAlives: true`,
  or call `transport.CloseIdleConnections()` after each attempt.
- **Related:** O-117 (serial deliveries), O-119 (uncapped drain)

### C27-02 · Low · confirmed-read
- **Where:** `cmd/agentnet/notify.go:34` (`knownNotifyEvents`), versus
  `internal/notify/settings.go:51-54,76-79`
- **What goes wrong:** the CLI's event allow-list lacks `debate.constraint`,
  `debate.agreed`, `debate.escalated` and `debate.broken`, which the daemon supports and
  turns on by default. `agentnet notify --event debate.agreed=off` fails with a usage
  error. The help text also omits the session, device and debate events.
- **Scenario:** a user who does not want debate notifications on the desktop, or sent to
  their Slack webhook with the title under `title:true`, cannot turn them off through the
  CLI. Only a raw IPC `notify_set` works.
- **Spec:** debate.md §Notifications ("Events for notify.md … all on by default");
  Docs/cli/notify.md `--event`
- **Fix direction:** derive the CLI list from `notify.DefaultEvents`, or let the daemon
  validate the name.
- **Related:** none

### C27-03 · Info · confirmed-read
- **Where:** `internal/notify/trigger.go:181`
- **What goes wrong:** the desktop `notify.fail` audit detail is
  `{"channel":"desktop","code":"desktop_failed"}`, but the spec's shape is
  `{channel, event?, id?, status?, error?}`. The key is `code`, not `error`.
- **Scenario:** audit consumers that follow notify.md §Audit do not find `error`. There is
  no security impact.
- **Spec:** notify.md §Audit
- **Fix direction:** use `error`, or update the spec.
- **Related:** O-112

### C27-04 · Info · suspected
- **Where:** `internal/notify/payload.go:146-182`
- **What goes wrong:** Slack and Discord both auto-link bare URLs. A peer name or title
  such as `https://evil.example` becomes a clickable link in the team channel. The link
  shows its real target, so nothing is disguised: masked links, mentions and headings are
  escaped as the spec requires.
- **Scenario:** a paired peer names itself `https://evil.example`, and the webhook message
  in Slack shows a live link. The spec does not require escaping this. It is a note for
  the owner.
- **Spec:** notify.md §Payload (masked links only)
- **Fix direction:** none required; optionally break `://` in `content`/`text`.
- **Related:** none

### C27-05 · Info · confirmed-read
- **Where:** `internal/notify/settings.go:47-54`, `internal/daemon/notify.go:109-137`,
  `internal/notify/payload.go:33`
- **What goes wrong:** debate events are sent to the webhook with
  `request.session`, an empty `type` and an empty `state`. Neither the notify.md Triggers
  table nor its §Payload schema lists these events or the `session` member. It is doc
  drift only: the fields are content-free.
- **Scenario:** a receiver built from notify.md sees event names and a member it does not
  know about.
- **Spec:** notify.md §Triggers, §Payload; debate.md §Notifications
- **Fix direction:** add the debate events and `session` to notify.md.
- **Related:** none

## Assumptions and contracts

- `request.NotifyInfo.Urgency`/`Type` are validated enums before `capitalize(ev.Urgency)`
  and the `%s` insertion (`trigger.go:203`). They come from stored rows
  (`internal/request/receive.go:201`), and the row went through `request.Validate`
  (`internal/request/validate.go:30`). **Unchecked** in depth.
- `ResultStatus` is one of pass/fail/partial/n/a. It is set from `ra.status`
  (`internal/request/mirror.go:329`), and `result.go:62` validates it. **Checked.**
- `peers.Store.List` names are what the spec calls the "local peer name"
  (`internal/daemon/notify.go:77-83`). They are still passed through `Clean`. **Checked**
  (sanitised either way).
- `keystore.NewFile` writes `webhook.key` owner-only
  (`internal/daemon` wiring → `internal/keystore`). **Unchecked.**
- The trigger's `ctx` outlives the envelope (`trigger.go:99-104`), per the comment. The
  mail receiver owns it. **Unchecked.**
- The IPC server enforces the 1 MiB line limit on `notify_set` params, so `Events` map
  size is bounded (`internal/daemon/notify.go:150`). **Unchecked.**

## Checked and fine

- The dial-time check applies to every candidate, and the connection goes to exactly the
  checked IP (`dial.go:167-178`). The rebinding test passes (`TestDialBlocksDNSRebinding`).
- `http` is limited to loopback both statically (`dial.go:48-52`, literal names only) and
  at dial time (`:85-90`).
- Userinfo is rejected, and URLs are capped at 2048 bytes (`dial.go:32-41`).
- A blocked dial is a permanent failure with `error = "blocked_address"` (`webhook.go:205-208`).
- The signature format and headers match the spec (`sign.go:19-32`, `webhook.go:190-201`).
  The timestamp is per attempt and the id and body are fixed.
- Status handling is correct: 2xx → sent, 408/429/5xx → retry, other 4xx → failed
  (`webhook.go:215-231`).
- The secret is 32 bytes from `crypto/rand` and printed as `whsec_`+base64url
  (`webhook.go:56-69`). It is deleted on `--webhook off`, and pending rows are failed as
  `removed` (`internal/daemon/notify.go:225-236`).
- The `notify.config` detail never holds the URL or secret, and records
  set/removed/rotated correctly (`internal/daemon/notify.go:277-305`).
- The webhook `transportError` drops the URL (`webhook.go:275-281`). R22 L1/L2 still hold.
- The fixed script texts contain no peer data on darwin, linux or windows. `run` never
  uses a shell (`desktop.go:33-39`).
- Of the open findings in this area:
  - O-070, O-109, O-112, O-114, O-117, O-118 and O-119 are still present as recorded.
  - O-110 is unchanged: two spawns on gdbus failure (`desktop_linux.go:28-31`).
  - O-111 is still present: desktop is written before events are validated

## Notes

- By spec, changing the URL does not rotate the secret. An IPC client that redirects the
  URL receives validly signed deliveries it could replay to the real receiver within
  300 s. These are real events only, and the spec accepts this.
- On Linux, when gdbus times out at 3 s, the notify-send fallback runs with the already
  expired context and fails at once.
