# C07: Sealed mail: seal/open, receiver, keys, outbox

Reviewer: CR-R7 · model claude-opus-5-5 · elapsed ~25 min · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 1 | 2 | 1 |

The mail core holds up. The verification order matches mail.md steps 1–12. Dedupe and ack
follow the one-transaction rule. Every outbox transition is conditional on a non-final state,
the R10 M1 fix is intact, and `mail_submit` refuses every daemon-owned kind and reserved
prefix. One new Medium: R10 said "after one re-seal it is a no-op, so there are no loops and
no amplification", but that does not hold against a hostile paired peer. The peer can announce
a fresh key before each `keys` mail. Every time it does, the sender re-seals and re-uploads all
of its open rows to that peer at once, bypassing backoff (C07-01, confirmed by a test). The two
Lows are small: attacker-chosen strings reach the audit log, and `mail_submit` silently rounds
large integers. The known open items in this area are all still present, unchanged, and
listed below.

## Questions

1. **Work that can be done before the signature check.** Anyone who knows a mailbox pub or
   key_id can trigger all of the following. Each item is bounded per frame, not per time:
   - Step 1 runs a `peers` query per frame (`daemon/mail.go:45`, O-084).
   - Step 3 runs `mailbox.Keys.MailboxKey`, which lists the live keys and **loads the private
     key from the keystore** for every frame that carries a live key_id, while holding
     `k.mu` (`internal/mailbox/mailbox.go:263-280`). Then one X25519 decap and an AEAD
     open (`open.go:429`).
   - Each rejection writes one Info log line with a relay-chosen `id` (`audit.go:544`,
     O-051). It also writes a `mail.reject` audit row, capped at 30 per minute **globally**
     (`audit.go:547-558`). A relay can therefore use up the budget, and genuine peer rejects
     then go unaudited (as spec'd; see C07-02 for the content angle).
   - Key-miss (`keys.go:178-204`): at most 256 ids per paired peer, and one reply per 10 min
     per peer once a reply has succeeded. If `sent` is false (no mailbox key for the peer,
     or a send error), `last` is never set. Every later miss then re-runs `Flush`
     (`Announcement()` plus a `MailboxPub` query) with no window. That costs DB reads only
     when there is no key. Bounded by frame rate; the O-056 race is still present.
   - The receive queue holds 256 envelopes, and when full it drops silently
     (`daemon/mail.go:188-192`, O-057).

   Memory is bounded. Nothing is stored before step 12.
2. **Exactly-once.**
   - `Handle` is single-threaded in the daemon (`daemon/mail.go:177-187`). Even if it ran
     concurrently, `INSERT OR IGNORE` + `RowsAffected` decides who stores (`receiver.go:195-201`).
   - Acks go out only after commit (`receiver.go:170-174`). A restart between commit and ack
     is covered: the resend is a duplicate and gets re-acked.
   - `storeBad` re-checks in a second transaction (`receiver.go:255-282`), so the audit and
     the ack match the stored row.
   - Residual: `Kind.After` is at-most-once. A crash after commit loses it, and duplicates
     never run it (`receiver.go:170`). The kinds put audits, notifications and the
     auto-accept hook there (`request/receive.go:411-439`). Lead L1, contract A5.
   - No mail is acked with its effects uncommitted.
3. **Outbox state machine.**
   - Every UPDATE is guarded:
     - `finish`: `state IN ('queued','relayed')` (`outbox.go:396-397`);
     - send: same guard (`:461-462`);
     - `OnReady`/`OnPeerOnline`: `state='queued'` (`:297`, `:316`);
     - `HandleError`: `state='relayed'` (`:520`);
     - `Retry`: key_id plus non-final (`:571`);
     - peer removal: `peers/store.go:346`.
   - No final row can be resurrected.
   - The INV-4 counters are intact. `ready`/`online` are read before `Send` and re-checked
     after the update (`:452-476`). B-4 is intact: `OnPeerOnline` counts per peer.
   - O-054 remains: `HandleError` can run before send's `relayed` update (`:461` vs `:520`).
   - O-061/O-062 remain: `OnReady`/`OnPeerOnline` touch only `queued` rows (`:297`, `:316`),
     while the spec says "all non-final rows to a peer" (mail.md §Sending and backoff).
4. **`mail_submit`.** `daemonOwnedKind` (`daemon/outbox.go:333-343`) refuses:
   - every kind from `daemonKinds` plus `withDeviceKinds` (with zero stores, so every
     conditional branch is included), plus `keys` and `ack`;
   - the prefixes `device.`, `ws.`, `request`, `team.`, `grant`, `presence`, `fetch`,
     `consult`, `approval`, `pair`, `keys`, `ack`, `debate.`, `decision.`.

   No bypass found. The only other receiver kinds come from `Options.MailKinds`
   (`daemon.go:784`), which is O-157. `note` is sendable, and handled only under
   `DORYLINAE_DEBUG`. There is also a body-fidelity issue (C07-03).
5. **Key rotation and key-miss.**
   - There is no downgrade:
     - `mergeMailboxKeys` ignores a known key_id or a `created` that is not newer
       (`peers/store.go:179`);
     - sealing uses `anns[0]` (`daemon/mail.go:72`);
     - `verifyAnnouncement` requires `not_after > now` (`body.go:477-479`).
   - No re-seal of a final row (R10 M1 fix at `outbox.go:568-579`, test present).
   - **Amplification exists:** a peer that keeps announcing newer keys triggers repeated
     re-seals of all open rows (C07-01).

## Findings

### C07-01 · Medium · confirmed-test
- **Where:** `internal/mail/outbox.go:530-582` (`Retry`), triggered from `internal/mail/keys.go:40-52` (`KeysKind.After`) and `internal/peers/store.go:179` (merge accepts any newer `created`)
- **What goes wrong:** every `keys` mail that carries a newer announcement and a `retry` list makes the sender re-seal every listed open row to the peer. It re-uploads each one at once, ignoring `next_attempt`. Nothing limits how often a peer can do this.
- **Scenario:** a hostile paired peer B lets A's mail to B pile up unacked (up to 7 d; results and requests can each be up to ~1 MB). It reads the row ids from the envelopes it receives. It then sends A a stream of `keys` mails. Each one carries a freshly signed announcement with `created` one second newer than the last (allowed up to `now + 10 min`, then one per second), plus `retry` = up to 256 of those ids. For each such mail, A merges the key (`MergeMailboxKeysTx`), and `Retry` sees `keyID != newKey`, re-seals the row and calls `send`. A therefore uploads up to 256 × ~1 MB per small `keys` mail. That burns A's bandwidth and its per-key relay rate budget: A's mail to other peers then gets `rate_limited` and backs off. The test shows 3 rows × 5 new announcements = 15 envelopes sent.
- **Spec:** `Docs/protocol/mail.md` §Key-miss recovery 3, "Normal backoff continues, which prevents loops". This prevents loops only while the peer's key is stable. R10 §Checked states "no amplification", and that claim is wrong for a hostile peer.
- **Fix direction:** re-seal a given row at most once per key-miss window (or per N minutes), or only for ids the peer could plausibly have received under the old key_id, and cap accepted announcements per peer per hour.
- **Related:** R10 M1 (fix intact), O-056, O-055

### C07-02 · Low · confirmed-read
- **Where:** `internal/mail/audit.go:544,565`, `internal/mail/open.go:352`, `internal/mail/receiver.go:165`
- **What goes wrong:** the relay and paired peers can put strings of their own choosing into the audit log.
- **Scenario:**
  1. The relay injects envelopes from an unpaired key, or with a garbage payload. The `mail.reject` row stores `id = env.ID`, which only passed `envelope.Validate`: up to 128 chars of `[A-Za-z0-9._:-]` (`envelope/envelope.go:69`). That is 30 rows per minute, indefinitely, plus unbounded Info log lines.
  2. A paired peer sends mail of an unknown kind. `mail.in` stores `kind` = any 64 chars of `[a-z0-9._-]`, one row per mail.

  The charset rules out control characters and spoofing, so the only impact is chosen text and disk growth in an append-only log.
- **Spec:** mail.md §Audit ("Never plaintext…"); rubric invariant 1 (no peer-controlled content in the audit log).
- **Fix direction:** audit `id` only if `ValidID` (else `""`/`"invalid"`), and log unknown kinds as `"unknown"`.
- **Related:** O-051, O-053

### C07-03 · Low · confirmed-read
- **Where:** `internal/daemon/outbox.go:377-385`
- **What goes wrong:** `mail_submit` unmarshals the body into `any`, so every number becomes a `float64`. Integers above 2^53 are silently rounded before signing (`Seal` re-marshals, `mail.go:150`).
- **Scenario:** a local agent submits `{"n": 9007199254740993}`. The signed mail carries `9007199254740992`, and the IPC reply does not say anything was changed.
- **Spec:** mail.md §Message: "Integers only, per canonical rules".
- **Fix direction:** decode with `UseNumber` or `agentcard.ParseStrict`.
- **Related:** none

### C07-04 · Info · confirmed-read
- **Where:** `internal/mail/receiver.go:170-172`
- **What goes wrong:** `Kind.After` is at-most-once. A crash between commit and `After` loses it, and a duplicate never re-runs it. This is a hazard for kinds that put durable effects there: audit rows, notifications, `acceptAfter` (`request/receive.go:431-435`), and the `keys` re-seal (which self-heals at the next key miss).
- **Scenario:** the daemon is killed right after the commit of a `request` that is auto-accepted in `After`. On restart the resend is a duplicate, so it is acked and `After` does not run. Whether the accept is then lost depends on the request chunk.
- **Spec:** none (mail.md is silent on `After`).
- **Fix direction:** document "After is best effort", and have kinds keep durable effects in `Apply`/outbox rows.
- **Related:** O-077, lead L1

## Assumptions and contracts

- **A1.** `Open` assumes `env` passed `envelope.Parse`/`Validate` and that its type is `mail` (`open.go:349`, O-050). The caller is the relayclient read loop via `daemon.go:744`. **Unchecked** beyond `envelope.go:106-116`.
- **A2.** `Keys.MailboxKey` returns only non-deleted keys (`mailbox.go:273`, `notAfter + DeleteGrace`). **Checked.**
- **A3.** `MergeMailboxKeysTx` refuses a rollback, and `MailboxPub` returns `anns[0]` as the newest (`peers/store.go:179`, `daemon/mail.go:72`). **Checked.**
- **A4.** `peers remove` fails the peer's non-final outbox rows in the same transaction (`peers/store.go:346`). **Checked.** It does not call `Outbox.OnFinal` (lead L2).
- **A5.** Kinds' `Apply` uses only `tx` and returns `ErrBadBody` only for incurable bodies (O-059), and `After` is non-durable (C07-04). **Unchecked**; this is the kind chunks' job.
- **A6.** The receiver runs on a single goroutine (`daemon/mail.go:177`). The `pending*` maps keyed by `op` rely on this. **Checked.**
- **A7.** `relayclient` hands up every `mail` repeat (mail.md §Receiving). **Unchecked** (relayclient chunk).
- **A8.** `relayclient.Send` does not block indefinitely. `ack` and the key-miss reply call it on the receiver goroutine (`receiver.go:314`, `keys.go:138`). **Unchecked.**

## Leads for other chunks

- **L1.** `internal/request/receive.go:431-439`: audit, notifications and `acceptAfter` run in `After`. Check whether a crash after commit loses the auto-accept mail or the `request.received` audit for good (see C07-04).
- **L2.** `internal/peers/store.go:346`: removing a peer fails its outbox rows without calling `Outbox.OnFinal`, so hooks such as `worksession.CheckPhase1FallbackForPeer` are skipped.
- **L3.** `internal/mailbox/mailbox.go:263-280`: `MailboxKey` loads the keystore (the keychain on macOS/Windows) under `k.mu` for every frame with a live key_id, which is relay-driven. Consider caching.
- **L4.** `internal/mail/outbox.go:506-524`: any relay can make any row `failed` at once with a `bad_envelope` error frame, which fires `OnFinal` fallbacks. This is as spec'd, but the worksession fallback owner should confirm that a relay-forced `failed` is safe.
