# C17: Requests: wire, decode, validate, receive, submit

Reviewer: CR-C17 · model claude-opus-5-5 · elapsed ~8 min (system clock 00:48 at first read → 00:52; a few minutes before the first read) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 0 | 0 | 2 | 1 |

The request receive path is in good shape. Decode is strict about members, types and nulls.
Validate runs on both sides. Apply ties `request.from` and `request.to` to the mail envelope,
bounds `created`, and checks the size on canonical bytes. D5, the team checks and the urgency
budget all run inside the mail dedupe transaction, and every read error is returned as
retryable. No request content reaches the audit log or the logs: `bad_body` error text is
dropped by `storeBad`. The only new defects are small strictness gaps:
- optional members given as `""` are accepted as if absent (C17-01, confirmed by a test);
- D5 treats a peer row missing at Apply time as "not relay" (C17-02).

The larger known issues in scope are already open and are cited below, not re-reported:
- O-073: `deadline` has no upper bound;
- O-093: auto-declined rows keep their body;
- O-094: `isUniqueConflict` matches on error text;
- O-100: C1 and bidi characters pass request text validation.

## Questions

1. **Strictness and bounds.**
   - Members: unknown members and nulls are refused (`internal/request/decode.go:27-36`, `:134`).
   - Types and time: every string is type-checked. `created` and `deadline` must round-trip in
     exact wire form (`decode.go:157-168`).
   - UTF-8 and length: checked for title, brief, urgency_reason, note, URL, branch, path,
     resource and the context name and text (`validate.go:290-313`).
   - C0 controls and U+FFFD: refused everywhere (`validate.go:342-351`).
   - C1: refused only in context files and in a debate brief (`validate.go:147,167,174`). Title,
     brief, artifacts and note let C1 and bidi through: this is O-100 and O-142, not re-reported.
   - Arrays: artifacts 0–20 (`:84`), context 1–8 (`:159`). The total cap is checked on canonical
     bytes (`canonical.go:100-108`, called at `receive.go:169`).
   - `deadline`: only "after created" is checked (O-073). `created`: must be ≤ `msg.created`
     (`receive.go:162`) and at most 30 days old (`:197`).
   - Error classes: every decode or validate failure is `ErrBadBody`, and every DB error is
     retryable (`receive.go:183,190,207,219`), which follows the O-059 rule. Gap: an optional
     member given as `""` is accepted as absent, against request.md §Size limits (**C17-01**).
2. **D5.**
   - `UnverifiedPeer` reads trust through the Apply transaction. A read error fails the Apply
     and is retried (`receive.go:305-312`, `daemon/request.go:166-172,454-461`). One hole: a
     missing row (`ErrNoRows`) returns trust `""`, which is treated as verified (**C17-02**).
   - "Non-loopback" is decided from the URL text (`daemon/request.go:480-499`, computed once at
     `daemon.go:457`).
   - This is safe because of R51 M1. Every host that `relayIsNonLoopback` calls loopback
     (`localhost` or a loopback IP literal) is also loopback to `envelope.IsLoopbackHost`
     (`authv2.go:178`). For such hosts the relay client wraps its dial in `loopbackOnly`, which
     refuses any peer that is not loopback, proxies included (`relayclient.go:359-386`).
   - So D5 can only be off when the relay connection really reaches loopback. That relies on
     code outside this chunk: see Assumptions.
3. **Urgency budget.**
   - The receiver counts its own `in` rows per `peer = msg.from`, per urgency, over a rolling 7
     days on `received_at` (`receive.go:270-291`, `urgency.go:196`).
   - Rows auto-declined by the daemon are not counted. Rows the user declined (`decline_code =
     'user'`) and cancelled rows are counted, so a cancel refunds nothing (D12). No production
     code deletes `requests` rows (grep for `DELETE FROM requests`: only a test), so nothing
     refunds by pruning.
   - Duplicates and conflicts return before the budget (`receive.go:179-182`). An idempotency
     key only exists on the sender side. A new request id is a new row and is counted.
   - Apply runs serially on the daemon's single connection, so there is no count race.
   - A peer that sets `urgency_declared` downgrades itself to `normal`, which Validate enforces
     (`validate.go:65-74`).
   - Sybil keys: O-066.
4. **Idempotency.**
   - Concurrent submits with one key: both may miss `lookupIdem`. The loser hits the partial
     unique index `requests_idem (peer, idem_key) WHERE direction='out'` (`store.go:212`). Its
     whole transaction rolls back, including the outbox row, and it then re-reads the winner
     and compares `params_hash` (`submit.go:117-133,141-180`).
   - `params_hash` is the hash of the IPC params "as given" (`daemon/request.go:400-448`; O-098).
   - The conflict check matches on error text (O-094). A submit whose audit write fails after
     the commit returns an error (O-095).
   - Wire replay: an existing `(peer, id)` row is a duplicate or a conflict, with no new row and
     no second budget charge (`receive.go:176-185`).
   - An unknown id older than 30 days is `bad_body` (`:197`). An old mail replayed after
     `mail_seen` pruning is stopped first by the mail layer's own stale check (O-036).
5. **Content leaks.**
   - Audit rows carry only ids, peer, team, type, urgency, code and context counts and sizes
     (`receive.go:443-469`, `daemon/request.go:261-272`).
   - The `bad_body` error text (which can quote a peer-chosen member name) is discarded: it is
     not passed to `storeBad`, and `mail.reject` has no content (`mail/receiver.go:206-207`).
   - Retryable Apply errors name only the failing step.
   - The notification carries `title`, which notify.md §Text allows (`receive.go:425-430`).
   - No log line in scope prints any body.

## Findings

### C17-01 · Low · confirmed-test
- **Where:** `internal/request/decode.go:126-139` (`decodeString` for optional members), `:186-195` (artifact members), `:301-307` (`requested_grant.note`); `internal/request/validate.go:65,79,186-208,280`
- **What goes wrong:** an optional member that is present as `""` passes Decode and Validate as if it were absent. This covers `urgency_reason`, `urgency_declared`, `requested_grant.note` and any artifact member (`url`, `branch`, `commit`, `path`), as long as the artifact has another member. `Canonical` then drops the member, so the stored body is not the one that was sent.
- **Scenario:** a modified paired peer sends `{"urgency":"normal","urgency_declared":"", "artifacts":[{"url":"","commit":"abcdef1"}], …}`. The spec requires `bad_body`, but the receiver stores the request. The receiver's `body_hash` covers a different object from the sender's canonical form. No security effect was found: every value that is stored or shown has been validated.
- **Spec:** `Docs/protocol/request.md` §Request object, "urgency_declared … high or blocking", "urgency_reason 1–280 code points"; §Size limits, the table's Recipient column: `bad_body`; §Artifacts, "url 1–2048 bytes …"
- **Fix direction:** in Decode, treat an optional member that is present as present: reject `""` (and let Validate check the length when it is present).
- **Related:** invariant 4 (strict parsing); O-100

### C17-02 · Low · confirmed-read
- **Where:** `internal/daemon/request.go:454-461` (`trustOfTx`: `ErrNoRows` → `""`, nil), used by `UnverifiedPeer` at `:166-172`; `internal/mail/open.go:160` (the paired check is outside the Apply transaction)
- **What goes wrong:** D5 reads a missing peer row as "not a relay peer", so it passes instead of refusing. That is fail-open on a "not found" result, which rubric invariant 3 forbids.
- **Scenario:** a `trust=relay` peer on the hosted relay sends a request. `Open` passes step 1 (`IsPaired`, pool read). Before the receive transaction starts, the user runs `peers remove` on that peer. Apply then reads trust `""`, and D5 does not decline. The team checks still run. If the removed key is still in `team_members` of an owned active team (O-082), the request is stored `pending` and a "received" notification is shown, from a peer that is both unverified and unpaired. The window is a race with a local user action, so the impact is small.
- **Spec:** `Docs/protocol/request.md` §Receiving step 3 (D5); rubric §1 invariant 3
- **Fix direction:** treat `ErrNoRows` as unverified (or as a retryable error) when `nonLoopbackRelay` is set.
- **Related:** O-082, O-096, D5

### C17-03 · Info · suspected
- **Where:** `internal/request/receive.go:188-196` (`consumeTombstone` runs before `declineCode` and the 30-day check)
- **What goes wrong:** a request that matches an early-cancel tombstone is stored `cancelled` with its full body, without the D5 or team checks. This follows the spec's step order (step 2 comes before step 3). The cost is one bounded row per tombstone, so this is noted for the owner and is not a defect.
- **Scenario:** a `trust=relay` peer sends `request.cancel` for id X, then the request X itself. Its title then appears as a cancelled row in the inbox, even though D5 would have declined the request.
- **Spec:** `Docs/protocol/request.md` §Receiving step 2
- **Fix direction:** optionally run D5 before the tombstone path, or leave as designed.
- **Related:** O-093, O-102

## Assumptions and contracts

- The loopback exemption for D5 (`relayIsNonLoopback`) assumes the relay client only completes a connection for a loopback-text URL when the TCP peer is loopback (`internal/relayclient/relayclient.go:359-386`, `loopbackOnly`). **Checked:** the host sets agree (`envelope.IsLoopbackHost` ⊇ the daemon's set), and the proxied dial fails too.
- `apply` assumes `op.Msg` has been through `envelope.Parse` and `mail.Open`. That means `msg.from` is a paired peer's key and is authenticated, and `msg.created` is inside the mail freshness window (`internal/mail/open.go:160`). **Checked** for step 1. The freshness bound is O-036's domain and **unchecked** here.
- `apply` assumes the mail layer rolls back and acks `unsupported` on `ErrBadBody` without logging the error text (`internal/mail/receiver.go:206-207`). **Checked.**
- `apply` assumes the `request` body map comes from `agentcard.ParseStrict`: numbers as `json.Number`, duplicate keys refused, depth bounded. **Unchecked** in this chunk (the mail/envelope chunk covers it).
- `Debates.ReceivedTx` and `Helper.RouteTx` are assumed to return `ErrBadBody` only for incurable input and plain errors otherwise, per O-059 (`receive.go:244,248`). **Unchecked** (debate and device chunks).
- `TeamHasMembers` assumes `team_members` is pruned when a peer is removed. **Unchecked:** O-082 says it is not for owned teams, and C17-02 depends on this.
- `Submit` assumes the caller already ran D5 and team resolution (`submit.go:15-17`). **Checked:** `daemon/request.go:192-198`.
- `Submit` assumes `Outbox.SubmitTx` writes only through `tx`, so a lost idempotency race rolls back the queued mail. **Unchecked** (mail chunk).

## Checked and fine

- Decode refuses unknown members, missing required members and nulls, and checks the type of every member, nested ones included (`decode.go:27-36,174-309`).
- `v` must be the integer 1. `Canonical` writes `"1"` literally, which is safe only after Validate (`canonical.go:17`).
- `request.from` must equal `msg.from`, and `request.to` must equal `msg.to` (`receive.go:156-161`).
- The wire duplicate check is keyed by (sender, id), so another peer cannot shadow an id (`receive.go:176`).
- The size cap is checked on canonical bytes, using the question cap only for question or debate requests with context (`canonical.go:100-108`).
- An auto-decline row and its reply are written in the same transaction as the mail dedupe (`receive.go:340-364`).
- A D5 read error, and errors from the team-active and member reads, are retryable and never fail open (`receive.go:305-333`), apart from C17-02's "not found" case.
- The receiver budget uses consistent store-time strings (`StoreTimeFmt` has fixed width), so the lexicographic cutoff is correct (`receive.go:278-284`).
- `request_submit` refuses a `trust=relay` peer before team resolution when the relay is not loopback (`daemon/request.go:192-194`).
- The audit rows `request.submit`, `request.in`, `request.auto_decline`, `request.duplicate` and `request.conflict` carry no content.
- The debate `position` in the IPC is parsed with `ParseStrict` and is part of `params_hash` (`daemon/request.go:240-247,431-440`).
- O-174 still stands as written (`receive.go:153-154`, message text).
- Tests: `TestUnverifiedPeerReadsTrustInTx` does assert that a read error is returned. `TestRelayIsNonLoopback` covers `LOCALHOST`, `[::1]` and the userinfo tricks. I found no tautological test in the files I read.

## Leads for other chunks

- `internal/request/decode.go:154`: `int(i64)` truncates `v`, `debate.rounds` and `turn_timeout_s` on 32-bit builds (the same pattern as O-052). This matters only if a 32-bit target is shipped (release chunk).
- `cmd/agentnet`: check whether any command opens or makes clickable an artifact `url`. Peer URLs may use `http`/`ssh`/`git` with C1 or bidi characters (review 50 H3 pattern).
- `internal/daemon/request.go:212-219`: the brief is not CRLF-normalised in the daemon (only context text is). Check whether the CLI does it before IPC, as request.md "after CRLF → LF" requires.
