# C15: Supply chain: release, install, CI, deploy, versioning

Reviewer: CR-R1 · model claude-opus-5-5 · elapsed ~35 min · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 1 | 1 | 2 | 3 |

Verdict: the bytes-level checks hold. `install.sh` verifies before it installs anything,
the embedded key is one Ed25519 key in both encodings, `binversion` is bounded, and no
shipped binary links goldmark or the `testhooks` files. Three things around those checks
are weaker:

1. **(High, C15-01)** Nothing ties the `SHA256SUMS` the owner signs to the one CI built.
   The owner downloads it from the mutable draft release. A leaked `contents: write` token
   (the exact threat D36's offline key is meant to stop) can swap the draft's archives and
   sums before signing, and the owner then signs the attacker's files.
2. **(Medium, C15-02)** The actions that 70e8921 did not pin, plus the Go cache in
   release.yml's `sums` job, give a path from a retargeted action tag to the release files.
3. **(Low, C15-03)** Embedding the real key (447f08e) broke the `placeholder` install
   case. The `install-sh` job in both ci.yml and release.yml must now fail, and release.yml
   cannot create a draft until the test is fixed.

## Questions

1. **install.sh.**
   - **Can any input bypass verification?** No. No env var, mirror, redirect, version
     string or `uname` value makes it install unverified bytes, and no input makes it
     write outside the install dir:
     - `AGENTNET_DOWNLOAD_URL` only changes where files come from. The signature is still
       checked (`scripts/install.sh:198-211`, `:259-272`).
     - http needs `AGENTNET_ALLOW_INSECURE_URL=1`.
     - curl pins `--proto-redir =https` (`:218`).
     - The version is regex-checked, including the `v` strip (`:139-140`).
     - `uname` values go through fixed `case` arms (`:147-156`).
     - The archive is hash-checked against the signed sums (`:299-301`). Only the two
       members are extracted, and each must be a regular file (`:305-308`).
     - Paths are quoted throughout, so a `$HOME` with spaces or quotes is safe
       (`:164`, `:310-321`).
   - **sudo:** never used.
   - **Embedded key:** the PEM (`:48-50`) and minisign (`:51`) lines hold the same 32-byte
     key. The minisign key id `5c34a8b39dc0c5ca` equals releasesign's derived id
     (`tools/releasesign/main.go:114-117`); I recomputed both. Whether the key is the
     owner's can only be taken from 447f08e and HANDOFF §0 line 18.
   - **Placeholder check:** it still refuses a placeholder (`:109-113`). But its test no
     longer runs against a placeholder script (C15-03), and the banner at `:38-43` is stale
     (C15-06).
2. **Workflows.**
   - **Triggers:** no `pull_request_target` anywhere. ci.yml runs PR code under
     `pull_request`, and GitHub gives fork PRs a read-only token and no secrets.
   - **Write tokens:**
     - release.yml has top-level `contents: read`; `contents: write` is only on `draft`,
       which sits behind the `release` environment.
     - sensitive-paths.yml has `pull-requests: write` and runs an action pinned by tag
       only (C15-02).
     - ci.yml sets no `permissions:` and does not use `persist-credentials: false`
       (C15-04).
   - **`${{ }}` injection:** release.yml routes every input through `env` and validates it
     (`release.yml:62-90`). ci.yml interpolates only `runner.os` and `matrix.*`
     (`ci.yml:101,122,141,191`), which are not attacker-controlled.
   - **Pinning:**
     - SHA-pinned: ci.yml and release.yml.
     - Tag-pinned: `phase2-harness.yml:21-22,35`, `phase3-harness.yml:16-17,30`,
       `sensitive-paths.yml:18` (C15-02).
   - **Caches:** a PR's cache is scoped to its merge ref and cannot reach a tag run. A
     cache written on `main` can reach release.yml's `test`, `sums` and `install-sh` jobs
     (O-185). `sums` produces the published files (C15-02).
3. **binversion.**
   - **Crafted input:** a crafted binary cannot make it read out of bounds, loop, or
     allocate much:
     - `readAt` checks the range without overflow (`tools/binversion/main.go:60`);
     - offsets above `MaxInt64` are refused (`:64`);
     - the string is capped at 256 bytes (`:30`, `:93`);
     - header parsing is left to `debug/elf|macho|pe`, which cap their own allocations.
   - **Symbol on all 6 targets:** ELF, Mach-O (with or without the `_` prefix) and PE
     (section-relative plus ImageBase) are each handled (`:118-199`). The 2nd dry run
     (HANDOFF §0 line 13) passed on all 6 targets.
   - **Residual:** it checks `verify/`, a second build with the same flags minus `-s`, not
     the shipped `stage/` binaries. `stage/` gets a runtime check only on linux/amd64
     (`release.yml:162-171`). See Notes.
4. **Release builds.**
   - **Flags:** `-trimpath`, `CGO_ENABLED=0`, and `GOFLAGS: ""` (`release.yml:137-144`).
   - **No tags:** any `-tags=` in `go version -m` fails the build (`:152-160`).
   - **testhooks:** the only files with the tag are `cmd/relay/testhooks_on*.go`.
   - **goldmark:** `go list -deps` of the three commands for linux, windows and darwin
     contains no `github.com/yuin/goldmark`.
   - **ParseRelease** (`internal/version/release.go:22-40`): 3 parts, digits only, no
     leading zeros, ≤ 9 digits, so no `Atoi` overflow. It matches install.sh's `is_version`
     and releasesign's regex.
5. **deploy/early.**
   - **Sandbox:** `ProtectSystem=strict` with `StateDirectory=agentnet-relay` (0700,
     `UMask=0077`). This is the only writable path the relay needs: `--db` is inside it,
     no `--security-journal` is set, and `paths.Default` is not reached because `--db` is
     given (`cmd/relay/main.go:129-140`).
   - **Caddy routes:** Caddy proxies exactly `/v1/connect` and `/healthz` and answers 404
     otherwise (`deploy/early/Caddyfile:28-35`).
   - **Metrics:** `/metrics` is on `127.0.0.1:9787` only (`agentnet-relay.service:26`), and
     ufw allows only 22 and 443 (`setup.sh:61-73`).
   - **Rerunning setup.sh:** it is safe to rerun. It refuses to run without a root SSH
     key, so the key-only switch cannot lock you out (`:30-33`, see C15-07). It downloads
     nothing except through apt. The binary is set to root 0755.
   - **Not verified:** that the unit starts under this exact sandbox (see Assumptions).
6. **go.mod.**
   - **Unneeded network code:** none. What is linked is expected: coder/websocket,
     x/crypto acme/autocert (relay `--acme-domain`), and dbus/keyring for the daemon.
   - **goldmark:** test-only (Q4).
   - **Advisories and maintenance:** not checked, because web access is out of bounds for
     this review.
   - **Dependabot:** covers only `github-actions`, not `gomod` (C15-05).

## Findings

### C15-01 · High · confirmed-read
- **Where:**
  - `Docs/ops/release-signing.md` §Every release step 2 (`gh release download vX.Y.Z -p SHA256SUMS` then `sign`)
  - `.github/workflows/release.yml:288-325` (the draft is the only copy the owner is pointed at)
  - `tools/releasesign/main.go:329-363` (`cmdSign`)
- **What goes wrong:** the owner signs whatever `SHA256SUMS` is attached to the draft
  release when they download it. Draft assets can be replaced by anyone with
  `contents: write`. Nothing compares the downloaded file with the one CI built and
  tested, which exists only in the `sums` job log (`release.yml:217`) and the
  `release-files` artifact.
- **Scenario:**
  1. A supply-chain attacker holds a leaked token or PAT with `contents: write`. This is
     the threat install.sh:20-21 and 49 §install say the signature defends against.
  2. The attacker watches for a `v*` draft.
  3. Before the owner signs, the attacker deletes the six archives and `SHA256SUMS` and
     uploads trojaned archives with a matching well-formed `SHA256SUMS`. The attacker can
     also edit the "Built from $SHA" notes.
  4. The owner follows the runbook: download, `sign` (`checkSums` passes the format),
     `verify -install-sh` (passes), upload, publish.
  5. Every `curl | sh` install and every Homebrew install (rendered from "the SHA256SUMS
     you just signed") now runs the attacker's binaries, with a valid release signature.

  This is not R53 L5 / O-180. Those cover a build that was bad in CI. Here CI is clean,
  and the attacker needs only asset write during the draft window.
- **Spec:**
  - `Docs/review/49-phase4-tickets.md` §install: "The signature protects against a swap of
    the release artefacts on GitHub (a leaked token, …)".
  - install.sh:19-21: "protects against a swap of the release files on GitHub after the
    owner signed them". This is true only after signing, and the runbook leaves a window
    before it.
- **Fix direction:** bind the signed file to the CI run. For example, have the owner fetch
  `SHA256SUMS` from the run's artifact or compare its digest with the digest printed in
  the (immutable) run log or job summary. Better, have `releasesign sign` take the expected
  digest, or re-hash archives the owner rebuilt locally.
- **Related:** O-180, O-181, R53 L5/M1, D36 (OD-P4-19 (a)+(ii)), C15-04.

### C15-02 · Medium · confirmed-read
- **Where:**
  - `.github/workflows/phase2-harness.yml:21-22,35` and `phase3-harness.yml:16-17,30`
    (`actions/checkout@v7`, `actions/setup-go@v7`, `upload-artifact@v7`)
  - `sensitive-paths.yml:18` (`actions/github-script@v9` with `pull-requests: write`)
  - `.github/workflows/release.yml:203-218` (`sums`: setup-go with the default cache, then
    `go run ./tools/releasesign`, then uploads `dist/` as `release-files`)
- **What goes wrong:**
  - 70e8921 (R53 L7) pinned ci.yml and release.yml only. Three workflows still use
    mutable tags, and the two harness workflows run on `main` on a schedule with setup-go's
    cache on.
  - Release.yml's `sums` job restores the main-scoped Go build cache. It then runs a Go
    program compiled from that cache and, after that, uploads the `dist/` directory that
    `draft` publishes.
- **Scenario:**
  1. A retargeted `v7` tag of an action used by a scheduled `main` workflow runs attacker
     code in that job. The harness workflows are the unpinned ones.
  2. That code writes poisoned `GOCACHE` entries for `tools/releasesign` under setup-go's
     key (OS, arch, Go version, `hash(go.sum)`). The save happens on a key miss, for
     example the first run after a `go.sum` change.
  3. The next tag's `sums` job restores the cache. A tag run can read default-branch caches.
  4. `go run ./tools/releasesign check` runs the poisoned code. It rewrites the archives
     and `SHA256SUMS` in `dist/` after `build`'s version and tag checks have passed.
  5. `draft` publishes those files, and the owner signs them (C15-01 flow).

  This escalates O-185: the cache reaches the job that produces the release files, not
  only test jobs.
- **Spec:** the rubric's supply-chain row says "any single PR, action or asset swap is not"
  trusted. R53 L7/L13.
- **Fix direction:** set `cache: false` in every release.yml job (as in `build`), and pin
  the three remaining workflows by SHA.
- **Related:** escalates O-185, residual of R53 L7 (Section D), C15-01.

### C15-03 · Low · confirmed-test
- **Where:** `tests/install/run.sh:86` (`cp "$root/scripts/install.sh" "$work/install-placeholder.sh"`),
  `tests/install/cases.sh:195`, `scripts/install.sh:48-51` (447f08e)
- **What goes wrong:** the `placeholder` case copies the repository's install.sh and
  expects "NO RELEASE SIGNING KEY". Since 447f08e that file holds the real key, so the
  script passes the placeholder check and fails later with "signature check FAILED" (the
  fixtures are signed with a test key). The case therefore FAILs, `cases.sh` exits non-zero,
  and the `install-sh` job fails in ci.yml (`:159-167`) and in release.yml (`:229-244`).
  `draft` needs `install-sh` (`release.yml:278`), so the first real tag cannot produce a
  draft. The refusal branch also loses its only test.
- **Scenario:**
  1. Push to main, or push `v0.1.0`.
  2. The install-sh job fails at case 1 `placeholder`.
  3. No draft is created. This is not a security issue, but it blocks the release.
- **Spec:** `Docs/ops/release-signing.md` §Every release step 1 (release.yml "tests
  install.sh").
- **Fix direction:** have run.sh generate the placeholder copy, for example by rewriting
  both key lines back to `REPLACE_WITH_RELEASE_*`, instead of copying the real script.
- **Related:** none (I did not check CI run history; no web access).

### C15-04 · Low · suspected
- **Where:** `.github/workflows/ci.yml:1-8` (no `permissions:`), every `actions/checkout` in
  ci.yml (no `persist-credentials: false`)
- **What goes wrong:** ci.yml's `push` runs on `main` get the repository's default
  `GITHUB_TOKEN` permissions. That token stays in `.git/config` while `go test ./...` runs
  every test and dependency. If the repository default is "read and write", any code
  executed in those jobs holds `contents: write`. That is enough for the C15-01 draft swap
  and to write releases.
- **Scenario:**
  1. A compromised test dependency, or a PR that is merged, runs in `test` on push to main.
  2. It reads the token from `.git/config` and edits a pending draft.
- **Why suspected:** it depends on the repository's default workflow permission setting,
  which I could not read (no web).
- **Spec:** R53 L6 applied `persist-credentials: false` to release.yml only.
- **Fix direction:** add top-level `permissions: contents: read` to ci.yml (and the harness
  workflows), and `persist-credentials: false` to every checkout.
- **Related:** C15-01, O-186.

### C15-05 · Info · confirmed-read
- **Where:** `.github/dependabot.yml:2-6`
- **What goes wrong:** Dependabot watches only `github-actions`. Go module advisories (for
  example x/net, x/crypto, modernc.org/sqlite, coder/websocket, all linked into the relay
  or the daemon) get no automatic PRs, and no CI job runs `govulncheck`.
- **Scenario:** a security release of a linked module ships, and nothing in the repository
  surfaces it before a manual review.
- **Spec:** none.
- **Fix direction:** add a `gomod` ecosystem entry and/or a `govulncheck` CI job.
- **Related:** Q6.

### C15-06 · Info · confirmed-read
- **Where:** `scripts/install.sh:38-43`
- **What goes wrong:** the banner still says "PLACEHOLDER: THE REAL RELEASE PUBLIC KEY HAS
  NOT BEEN GENERATED YET … this script refuses to install anything". The key is now real.
  A user who reads the script before piping it to `sh` (the recommended habit) is told it
  will not work.
- **Scenario:** doc drift only. The `REPLACE_WITH_RELEASE` check itself is still correct.
- **Spec:** `Docs/ops/release-signing.md` §Once.
- **Fix direction:** reword the banner to describe the embedded key; `embed` could rewrite it.
- **Related:** C15-03.

### C15-07 · Info · suspected
- **Where:** `deploy/early/setup.sh:30-33`
- **What goes wrong:** the anti-lockout check only greps `/root/.ssh/authorized_keys` for a
  key-looking string. It does not notice a key line prefixed with
  `command="echo 'Please login as …'"`/`no-pty` options, which some cloud images write for
  root. On such an image root cannot actually log in, yet passwords are disabled.
- **Scenario:**
  1. The owner runs setup.sh on an image that restricts root's key.
  2. Password SSH is turned off.
  3. Only the provider console is left.

  Hetzner's Debian images write a plain root key, so this is unlikely on the target host.
- **Spec:** `Docs/ops/early-relay-deploy.md` (no lockout).
- **Fix direction:** also refuse when the matching line has a `command=` option.
- **Related:** O-195.

## Assumptions and contracts

- **install.sh's pubkey is not the owner's:** unchecked. install.sh trusts that the key
  lines were written by `releasesign embed` from the owner's offline key. Only the commit
  message of 447f08e and HANDOFF §0 line 18 attest this.
- **Old releases after a security fix:** unchecked. install.sh's rollback protection
  assumes the owner raises `AGENTNET_MIN_VERSION` after every security release (O-181).
- **Build info records `-tags`:** checked. release.yml's tag check assumes `go version -m`
  lists `build -tags=…` whenever tags are set. It does (cmd/go `setBuildInfo`); only
  `-ldflags` is dropped under `-trimpath`.
- **binversion reads the linked value, not the runtime value:** checked.
  `internal/version/version.go:18-27`: `init` only rewrites `Version` when it is still
  `0.0.0-dev`, and binversion reads the linked static value.
- **The relay starts under this sandbox:** unchecked. `agentnet-relay.service` assumes
  the relay needs no writable path outside `StateDirectory` and `PrivateTmp` (SQLite
  temp files), and no socket family beyond `AF_INET/AF_INET6/AF_UNIX`. HANDOFF says the
  unit's flags were tested outside systemd, not under this sandbox.
- **Caddy XFF handling:** unchecked, version-dependent. The Caddyfile assumes Debian's
  Caddy (bookworm 2.6.x) replaces a client-supplied `X-Forwarded-For` when no
  `trusted_proxies` is set (Caddy ≥ 2.5 behaviour), and that the relay's `clientAddr`
  takes the last entry (O-029, C0x relay limits).
- **Homebrew's minisign:** unchecked (O-182). install.sh assumes it still accepts legacy
  `Ed` signatures.

## Checked and fine

- **install.sh:**
  - Everything runs inside `main()` called on the last line, so a truncated pipe runs
    nothing (`:64`, `:326`; case `truncated-script-runs-nothing`).
  - The verifier is chosen before any download, with no unsigned fallback (`:169-194`).
  - The signed-sums line regex is anchored; there is one version; `--version` must match;
    the minimum is enforced (`:276-291`).
  - `awk $2 == f` selects a single sum (`:294`).
  - The temp dir comes from `mktemp -d` and is removed on EXIT (`:247-252`).
  - Replacement is a same-dir `mv -f` (`:311-315`).
- **releasesign:**
  - `keygen` uses `O_EXCL` 0600 and prints only public values (`:187-199`).
  - `sign` validates the format, refuses to overwrite, and self-verifies (`:329-363`).
  - `verify` checks the PEM and minisign keys are equal, plus `.sig`, `.minisig` and the
    format (`:448-504`).
  - `embed` requires exactly one match per key line and uses a literal replace (`:435-440`).
  - The minisign legacy layout is correct (`:271-308`).
- **release.yml:**
  - `meta` validates tag and dispatch inputs through `env`, and dry runs only get `0.0.Z`
    (`:62-92`).
  - The `draft` job refuses an existing release name and asserts `isDraft` (`:298-325`).
  - `build` uses `cache: false` (`:121`).
  - The tar is reproducible (`--sort=name --mtime=@0 --owner=0`, `:185`).
- **render.sh:** it validates the version and each sum (`^[0-9a-f]{64}$`) and refuses
  `|&\"` in BASE_URL before `sed` (`packaging/homebrew/render.sh:19-27`).
- **version.ParseRelease** is bounded and strict (Q4). Makefile's `-X` path matches the
  module path (`Makefile:6`).
- **Dependencies:** goldmark and `testhooks` are absent from the linux, windows and
  darwin builds (`go list -deps`, Q4).
- **setup.sh:**
  - the sshd drop-in is named `10-…`, so it wins over a `50-cloud-init.conf`
    (first value wins);
  - `sshd -t` runs before reload;
  - ufw's default is deny, and the SSH_ALLOW_FROM switch deletes the any-address rule;
  - config files are written through `put`, which strips CRs;
  - it is idempotent.
- **.gitattributes** forces LF for `*.sh` and `deploy/early/*`.
- **O-183 (predictable `.agentnet.new.$$`):** still present (`install.sh:312`), unchanged,
  own dir only.
- **O-185:** still present, escalated in C15-02.
- **O-186:** not rechecked (lint chore).
