# C04: Envelope wire format and relay client

Reviewer: CR-R4 · model claude-opus-5-5 · elapsed 4 min (shell clock) · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 1 · Low 1 · Info 2

The wire format is tight: routing fields are ASCII-only with bounded lengths, keys and
nonces use strict base64url, auth v2 binds the origin computed from the configured URL only
(redirects are refused, the TLS name comes from that URL too), and the R51 M1 loopback dial
check looks at the address the socket actually connected to, so DNS rebinding is covered.
The one real defect is at the display edge. The relay's `error` frame `code`/`message` is
stored unbounded and unsanitised in `State().LastError`, and `agentnet status` and `doctor`
print it raw. A hostile relay can therefore write terminal escape sequences (including OSC 8
links) to the user's terminal, or to an agent reading the CLI output. It can also push the
`status` IPC response past the 1 MiB line limit, which breaks `status` and `doctor`
(C04-01, confirmed by test). A Low covers the backoff reset, which lets a relay drive a
~2 Hz reconnect loop.

## Questions

1. **Parse strictness / relay strings.** `Parse`/`ParseHeader` (`internal/envelope/envelope.go:106`,`:118`)
   use `encoding/json`: unknown members are ignored, duplicate keys are last-wins and field
   names match case-insensitively. The relay (`ParseHeader`) and the daemon (`Parse`) use the
   same decoder, so they cannot disagree about a field. After decoding, `Validate` (`:56`)
   restricts `from`/`to` to strict 32-byte keys (`:130`) and `team`/`type`/`id` to bounded
   ASCII sets, and `ts` must be RFC 3339. `payload` is `[]byte` and so is decoded with
   non-strict std base64: the bytes are unambiguous, only their encoding is not (O-053
   territory, harmless). Error strings are static and never echo frame content (`:109`,
   `frames.go:193`,`:200`). No panics were found: `Classify` probes `op` as `*string`, so
   `{"op":null}` goes to the envelope path and fails `Validate`. Relay-supplied strings:
   `min_client` is dropped unless `version.ParseRelease` accepts it
   (`internal/relayclient/relayclient.go:325`). `features` is stored as-is, bounded only by the
   1 MiB frame. `ready.account` is not read at all (see C04-04). The `error` code and message
   are **not** sanitised or bounded: see **C04-01**. Close reasons and handshake errors from
   `coder/websocket` are `%q`-quoted. The daemon log goes through `slog.TextHandler`, which
   quotes values, into a size-capped `logfile` (`cmd/agentnetd/main.go:101`), so logs are safe.
2. **Auth v2 origin / loopback.** The origin is computed once in `New` from the configured
   URL (`relayclient.go:142`) and is never derived from anything the relay sends. Redirects
   are errors (`:364`). HTTP/2 is off. The TLS server name comes from the same URL. Case,
   IDN (`idna.Lookup`), trailing dot, default port and leading zeros in the port are
   canonicalised (`authv2.go:109-174`). Residual IPv6 forms are O-021, and the same origin
   string on two LANs is O-014. The relay cannot make the client sign a different origin.
   Loopback: `IsLoopbackHost` classifies by text (`authv2.go:178`). `loopbackOnly`
   (`relayclient.go:375`) then checks `RemoteAddr` of the connected socket, so a hosts-file
   or DNS answer to another machine (rebinding) fails closed. v1 is signed only when the URL
   is loopback **and** v2 is not offered (`:338`), so stripping v2 from a remote challenge
   gets no signature (`ErrNoAuthV2`). One caveat, under Assumptions: with `HTTP_PROXY` set, a
   `localhost.` URL (trailing dot) is proxied. `loopbackOnly` then checks the proxy's
   address, which fails closed unless the proxy itself is local.
3. **Reconnect / leaks.** Backoff runs from 500 ms to 30 s with jitter (`:212-236`) and resets
   whenever auth completed (`:220`), as envelope.md:393 specifies. A relay that sends `ready`
   and then closes therefore gets ~2 reconnects/s, each re-running `OnReady`: see **C04-02**
   (Low). Goroutines: one `Run` loop. `OnReady` starts `go psender.SendNow` per ready
   (`internal/daemon/daemon.go:767`), bounded by the 10 s write timeout. No pending-send map
   exists (Send is fire-and-forget). The seen-set is a fixed 8192-slot ring (`seen.go:68`).
   Memory is bounded.
4. **Seen-set.** Mail bypasses it (`relayclient.go:480`, mail.md:208). Presence bypasses it
   and is not acked (`:469`). Everything else (`session.*`, `pair.confirm`) goes through it.
   Nothing relies on it for security: a relay can evict it with 8192 forged-`from` envelopes,
   but `session.data` has Noise counter replay rejection
   (`internal/session/session.go:680-683`). A replayed `session.init` cannot complete a
   handshake. `pair.confirm` is accepted once per attempt (`internal/peers/pairing.go:910`).
   Mail replay is handled by `mail_seen` + `created`. So the seen-set is a convenience.
5. **Probe / signer.** `Probe` (`probe.go:30`) has no Signer, reads only the challenge and
   closes. It cannot authenticate, so it cannot replace the daemon's connection. It uses the
   same no-redirect/loopback-only HTTP client. Its errors are not printed by doctor ("cannot
   reach the relay", `cmd/agentnet/doctor.go:366`). `keystoreSigner.Sign` (`signer.go:139`)
   loads the seed per signature, checks its length, rebuilds the key and refuses when the
   public key differs from the card's, then clears the seed and private key.

## Findings

### C04-01 · Medium · confirmed-test
- **Where:** `internal/relayclient/wire.go:183` (handshake `error` frame → `ErrorFrame`),
  `internal/relayclient/relayclient.go:225` (`lastErr = err.Error()`, no sanitising or cap),
  `internal/envelope/frames.go:338` (`Error()` concatenates relay code and message); printed
  raw at `cmd/agentnet/main.go:257-261` (`status`) and `cmd/agentnet/doctor.go:357-358`,`:137`
  (`doctor`).
- **What goes wrong:** the `code` and `message` of an `error` frame sent in place of
  `challenge` or `ready` become `State().LastError` verbatim, up to ~1 MiB, with any control
  characters. `agentnet status` and `agentnet doctor` then print them to the terminal without
  `termSafe`. `lastErr` is never cleared on a later successful connect, so the text stays.
- **Scenario:** relay (hosted, compromised, or any relay the user points at) → answers one
  upgrade with `{"op":"error","code":"internal","message":"\x1b]8;;https://evil/\x1b\\…\x1b[2K\rrelay: connected …"}`.
  (a) The user or a local agent runs `agentnet status`/`doctor`. The terminal gets
  relay-chosen escape sequences: an OSC 8 link to a relay-chosen URL (review 50 H3
  territory, one click away), erased or rewritten lines that fake a healthy status, or text
  aimed at the agent reading the output. (b) With a ~1 MiB message (control characters
  expand 6× as `\u00XX`), the `status` IPC response exceeds `ipc.maxLine` (1 MiB,
  `internal/ipc/ipc.go:28`,`:218`). `agentnet status` then fails, and `doctor` reports the
  socket as "not reachable" and falls back to the probe. This lasts until another connection
  error overwrites `lastErr`. Test: `LastError length 1000083, contains ESC: true`.
- **Spec:** envelope.md error table, `message`: "Human-readable, never contains payload or
  frame contents" (the relay's duty, not the daemon's). Rubric invariant 4 ("parsed strictly
  and bounded before it is … displayed"). review-49 §CLI contracts: `LastError` is
  "content-free".
- **Fix direction:** in relayclient, bound the relay-supplied code/message (e.g. keep a known
  `code` only, drop or clip `message` and strip non-printables) before storing `lastErr`;
  have the CLI `termSafe` it as well.
- **Related:** O-100 (same class for peer text), review 50 H3, C04-L1 below (session/pairing
  surface the same `ErrorFrame.Message`).

### C04-02 · Low · confirmed-read
- **Where:** `internal/relayclient/relayclient.go:220-221` (backoff reset on `authed`),
  `:278` (`OnReady`), `internal/daemon/daemon.go:761-768`.
- **What goes wrong:** the backoff resets as soon as a `ready` arrives, however short the
  connection. A relay that sends `ready` and closes at once keeps the client reconnecting
  every 375–625 ms indefinitely.
- **Scenario:** hostile relay → accepts auth, sends `ready`, closes; repeats. Each cycle the
  daemon does a TLS handshake and a keystore load plus Ed25519 signature
  (`signer.go:140`). It also runs `outbox.OnReady` (an UPDATE of all queued rows and a wake,
  which re-sends every queued row into the dying connection), spawns `psender.SendNow`, and
  writes two log lines. The CPU, battery and bandwidth cost is bounded but continuous, and
  the relay chooses it. The hosted relay's own 20/min reconnect limit does not help, because
  the relay is the attacker here.
- **Spec:** envelope.md:393-394, "the backoff resets once a connection has authenticated"
  (the code follows it; a spec finding).
- **Fix direction:** reset the backoff only after the connection stayed up for a minimum
  time (e.g. ≥ 30 s), both in the spec and in `Run`.
- **Related:** O-061 (hand-off into a dying connection stays `relayed`).

### C04-03 · Info · confirmed-read
- **Where:** `internal/relayclient/relayclient.go:439-484` (`dispatch`).
- **What goes wrong:** the client does not check `e.To` against its own key before handing an
  envelope up and acking it. That is correct only because every consumer binds the recipient
  inside the crypto (mail `msg.To != o.Self`, `internal/mail/open.go:208`; Noise sessions).
  Recorded as a contract (see Assumptions), not a defect.
- **Scenario:** none today. A future unsealed type that trusts the routing `to` would be
  misrouted by a relay.
- **Spec:** none.
- **Fix direction:** optionally drop envelopes whose `to` is not `c.pub` (cheap defence in
  depth).
- **Related:** none.

### C04-04 · Info · confirmed-read
- **Where:** `internal/relayclient/relayclient.go:257-263`.
- **What goes wrong:** `ready.account` (accounts.md) is decoded into `envelope.Control`
  but discarded. Nothing in the daemon learns the bound/suspended state from `ready`.
  This matches doctor's explicit 4.2c gap (`cmd/agentnet/doctor.go:378-381`); it is noted so
  4.2c does not forget that the relay-supplied `Display` must be sanitised when it is added.
- **Scenario:** none today.
- **Spec:** accounts.md (ready carries `account`).
- **Fix direction:** when 4.2c surfaces it, validate `State` against the three constants and
  `termSafe`/bound `Display`.
- **Related:** O-187.

## Assumptions and contracts

- Receivers bind the recipient cryptographically, so `dispatch` need not check `to`: mail
  `internal/mail/open.go:208` **checked**; `session.*` via the Noise keys **checked** (read
  `session.go:668-683`); presence `internal/presence/receive.go` **unchecked** (C-presence
  chunk).
- `OnEnvelope`, `OnError`, `OnControl` and `OnReady` must not block (they run on the read
  loop). Daemon side (`internal/daemon/daemon.go:740-775`): mail goes to a 256-slot queue
  (`startMail`), sessions to a non-blocking `select` (`session.go:312`); `outbox.OnReady` does
  a synchronous DB UPDATE (**checked**, short); `pairs.HandleControl`/`HandleEnvelope` take
  `m.mu` (**unchecked** for long holds, e.g. O-092 `Completed` ≤ 5 s under the pairing path).
- Consumers of `ErrorFrame.Message` must treat it as untrusted relay text:
  `session.failPeerLocked` stores it in a ping `Failure{Message}` (`session.go:331`,`:805`)
  returned over IPC; `pairs.HandleError` (`internal/peers/pairing.go:558`). **unchecked**
  (see Leads).
- `CheckURL` (ws:// only on loopback) is applied by `cmd/agentnetd` and doctor, not by `New`
  or `Probe` (O-023). **checked** for doctor (`doctor.go:347`, but only in `checkRelay`,
  which runs after `Probe` at `:167`: the probe dials a non-loopback `ws://` URL in the clear
  before the rule is applied; it sends nothing secret, so this is not a finding).
- `loopbackOnly` checks the TCP peer of the dial, which is the proxy when
  `ProxyFromEnvironment` applies. Go's proxy logic skips `localhost` and loopback IPs but
  not `localhost.`. A remote proxy fails closed; a local proxy passes the check. **checked**
  (`http.DefaultTransport` clone, `relayclient.go:353`).
- `version.ParseRelease` bounds and rejects any non-`MAJOR.MINOR.PATCH` text before
  `min_client` is stored or printed. **unchecked** (C-version chunk).
- The keystore returns the identity seed and `keystoreSigner` clears it; the keystore itself
  does not keep a copy. **unchecked** (C05).

## Checked and fine

- Strict base64url (`RawURLEncoding.Strict()`) for keys, nonces and signatures
  (`envelope.go:31`,`:130`, `frames.go:400`, `authv2.go:87`), with exact lengths.
- `AuthMessageV2` framing: domain ‖ 32-byte nonce ‖ u16 length ‖ origin, with length checked
  (`authv2.go:36-48`). v1 and v2 domains differ, so there is no cross-version signature
  reuse.
- `authVersion` downgrade rule (`relayclient.go:338-346`): no v1 signature for a non-loopback
  URL, whatever the challenge offers.
- Redirects refused, HTTP/2 off, TLS ≥ 1.2 with the configured roots (`relayclient.go:352-367`).
- R51 M1 appears fixed: `loopbackOnly` checks the connected address (`:375-387`), covered by
  `WithDialerAs` tests.
- `min_client` sanitised before storage, log and status (`:260`, `:325`).
- Read limit 1 MiB set before the handshake (`:249`, `probe.go:46`); binary frames end the
  connection (`:287`, `wire.go:175`).
- Handshake bounded by a 15 s timeout (`:242`); every write by 10 s (`:202`).
- Seen-set bounded (8192 ring) and not security-relevant (Q4); presence cannot evict it
  (`:469`).
- Invalid envelopes are logged with static validation text only (`:462`), never payload;
  the daemon log is size-capped (`cmd/agentnetd/main.go:101`).
- `keystoreSigner` refuses a seed whose public key differs from the card's and clears seed
  and private key (`signer.go:139-154`).
- `Probe` never signs (`probe.go:30-60`).
- `Fingerprint`: 100 bits taken correctly from SHA-256 with a domain tag (`fingerprint.go:17-35`);
  `NewPairCode` has no modulo bias (`pairing.go:30-40`); normalisers cap length before
  appending.
- `Classify`: `op: null` cannot become a control frame; a control frame is never also treated
  as an envelope (`frames.go:188-203`).
- O-023 still open (as listed); O-021 and O-014 still as listed.

## Notes

- `LastError` is documented as "content-free" (review 49), but relayclient cannot guarantee
  that while it stores relay text verbatim.
- `Probe` rebuilds its own URL parsing instead of sharing `New`'s; the two could drift.
