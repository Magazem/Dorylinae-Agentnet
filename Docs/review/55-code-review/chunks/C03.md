# C03: Relay accounts (4.2a), admin CLI, test hooks

Reviewer: CR-R3 · model claude-opus-5-5 · elapsed 6 min (shell clock, start to finish) · commit 6cc26a7

## Summary

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 0 | 1 | 3 | 2 | 3 |

**Verdict.** The routing and state core of 4.2a is sound. `eligible` guards the direct, queued and ephemeral paths, and `accountAllows` guards every control frame. `register` and `accountsChanged` are ordered correctly, so a connection is never half set up. Bind codes use 40 bits from `crypto/rand`, are stored hashed, expire after 10 minutes, are single use and are scoped to one key. Test hooks cannot reach a release build.

The problems are on the edges of the design:
- **High (C03-01):** any stranger can fill the hosted relay's disk with `bind_start`. Each call writes a `bind_requests` row, and rows are kept 24 h after expiry, including rows a later `bind_start` cancelled. That is about 589 MB per /24 prefix at steady state.
- **Mediums:** revocation is not robust to errors. The watcher can permanently skip one change (C03-02). There is no fail-closed behaviour on a database outage (C03-03). The journal is written after the commit and is lost for good when the append fails (C03-04).

Accounts are off by default (`--accounts`); every finding below assumes they are on.

## Questions

1. **Can an unbound or suspended key send, receive or queue beyond accounts.md?** No, except for the queue-drain case in C03-09. The paths and their guards:
   - **Control frames:** `accountAllows` gates every control frame (`internal/relay/pairing.go:142`, `internal/relay/accounts.go:259-277`). Unbound keys get only `bind_*`. Bound keys without a quota group get only `ack`, `pair_redeem` and `unbind`.
   - **Envelopes:** `accountRoutes` checks both `from` and `to` (`accounts.go:284-303`). It is called on the direct/queue path (`relay.go:777`, before `enqueue`, so nothing is queued for an ineligible recipient) and on the ephemeral path (`ephemeral.go:89`).
   - **Queue drain for an unbound key:** it waits. `register` returns `bound=false` (`relay.go:958-961`), and the drain starts only from `accountsChanged` once the key is bound (`accounts.go:205-219`).
   - **Suspended keys:** they are refused at `register` (`relay.go:946`, `serve` at `relay.go:630-638`: `ready`, then `account_suspended`, then 1008). A live one is closed by `accountsChanged` (`accounts.go:199-201`).
   - **Gap (C03-09):** the drain does not re-check eligibility per row.
2. **Bind flow.** The bind flow holds:
   - **Code:** 8 Crockford characters from `crypto/rand` with no modulo bias (`internal/envelope/accounts.go:17-26`). It is stored as a domain-separated SHA-256 (`accounts_store.go:155-158`, `:255`) under a `UNIQUE` index, with a 10-minute TTL (`:87`, `:238`).
   - **One pending bind per key:** a new `bind_start` cancels the older pending one (`:252`).
   - **After `bind_cancel`:** `confirmBind` requires `state='pending' AND expires > now`, so a code confirmed after a cancel fails (`:351-354`).
   - **Poll scope:** `bindStatus` and `cancelBind` are scoped to `key`, so another key cannot poll or cancel the ref (`:278`, `:299`).
   - **`already_bound`:** checked at `bind_start` (`accounts.go:326`) and again inside the confirm transaction (`:371-376`).
   - **Key cap:** the 4-key limit is inside the same transaction (`:377-382`).
   - **Code guessing:** it can only happen through `PendingBind`, which has no rate limit of its own. The rate limit is 4.2b's job (see Assumptions).
3. **Revocation and suspension.** The in-process `accountOp` path always reconciles, even after a journal error (`accounts.go:519-526`). `relay admin` commits are picked up by the 250 ms `data_version` poll (`accounts.go:154-172`), and affected connections are closed within about 550 ms (250 ms plus the 300 ms flush).
   - **A connection that authenticates during a reload:** it is safe. `register` reads the cache and records `acctSeen` under `s.mu` (`relay.go:940-962`). `accountsChanged` reloads and then scans `s.conns` under `s.mu`, so a new connection sees either the new cache or the scan.
   - **Weaknesses:**
     - One failed reload loses the change permanently (C03-02).
     - A database outage does not fail closed (C03-03).
     - A journal failure on the daemon's own `unbind` skips the reconcile (C03-04).
4. **Is `ConfirmBind` reachable in release without the browser?** No.
   - The only non-test callers of `PendingBind`, `DenyBind`, `EnsureAccount` and `ConfirmBind` are in `cmd/relay/testhooks_on.go:54-76`, under `//go:build testhooks`. In a release build `testhooks_off.go` supplies no-op `registerTestHooks` and `wrap`.
   - `release.yml:133-143` builds with `GOFLAGS: ""` and no `-tags`, and `:145-157` fails the job if `go version -m` shows any `-tags`.
   - `TestReleaseBuildHasNoTestHooks` (`cmd/relay/testhooks_release_test.go`) checks that `--help` has no hook, that `--testhook-bind` exits 2, that `/testhook/bind` returns 404, and that the built binary has no hook strings.
   - The Makefile, `ci.yml` and the harness scripts never pass `-tags`.
   - Two consequences:
     - In a release build, `--accounts` can bind nobody until 4.2b ships (Info in Notes).
     - The `testhooks` code itself is never compiled in CI (C03-07).
5. **`relay admin`:**
   - `display` is printed raw (C03-05).
   - `parseInterspersed` (`cmd/relay/admin.go:173-219`) handles keys that start with `-` through `looksLikeKey`, handles `--`, `-` and `--flag=value`, and rejects a second positional argument (`:60-63`). Base64url has no `=`, so a key is never split as `name=value`.
   - Admin and relay use separate connections on a WAL database with `busy_timeout(5000)` (`queue.go:210`). Each admin operation is one statement or one transaction. `execGroupState` is a read then a write without a transaction (`accounts_store.go:500-511`), which is harmless because the write is idempotent.
   - The mutating commands skip the journal when `--security-journal` is omitted (C03-06).
6. **Journal:**
   - **Events written:** `unbind`, `account_delete`, `suspend` and `unsuspend` (`accounts_store.go:97-102`, `:419`, `:427`, `:436`, `:446`), which covers relay-hosted.md §3 for 4.2a. The `invite_*` and `team_remove` events are 4.3a's.
   - **Contents:** entries carry account or quota-group ids and 8-character key prefixes only. There is no email, no display and no full key.
   - **Order:** the database change commits first and the journal is appended after, so a failed append leaves a change that is not journaled and cannot be recovered (C03-04). The reverse (journaled but not committed) cannot happen.

## Findings

### C03-01 · High · confirmed-test
- **Where:** `internal/relay/accounts_store.go:234-268` (`createBind`), `:458-463` (`prune`, keeps rows 24 h after `expires`), `internal/relay/accounts.go:324-344` (`bindStart`), `:399-410` (`notePoll`)
- **What goes wrong:** every `bind_start` from an unbound key inserts a new `bind_requests` row, and a later `bind_start` only marks the old row `cancelled` without deleting it. `prune` deletes rows only 24 h after they expire. Nothing limits `bind_start` beyond the generic 60 control frames per minute per key, and the queue's free-disk and total-size caps do not count these rows. Each call is also an fsync'd write (`synchronous=FULL`) on the relay's single SQLite connection.
- **Scenario:** a stranger (no account) opens the maximum 16 unbound connections per /24 prefix with fresh keys (`accounts.go:27`), and each sends `bind_start` 60 times a minute. That is 16 rows/s and about 1.4 M rows per 24 h 10 min window. The measured cost is 423 B per row (data plus indexes), so one prefix holds about **589 MB** at steady state. Four or five /24s, or /48s (cheap in IPv6), fill the hosted relay's 2–3 GB volume.
  - The queue then hits its minimum-free-disk check and refuses mail for everyone.
  - The same flood serialises the single database connection with fsyncs, which delays `ack`, drain and enqueue for all users.
  - Secondary effect: `lastPoll` keeps one entry per ref for up to 10 min (`accounts.go:340`, `:402-409`; refs cancelled by a later `bind_start` are never forgotten), about 9.6 k entries per prefix.
- **Spec:** `Docs/protocol/accounts.md` §Frames ("at most one pending bind per key"; no row lifetime); `relay-hosted.md` §2 ("An `unbound` connection is still subject to every per-prefix and per-key limit"). The threat model says an internet stranger must not exhaust relay disk or the single SQLite connection.
- **Fix direction:** reuse or overwrite the key's single `bind_requests` row, or delete cancelled and expired rows at once, and add a per-key and per-prefix `bind_start` rate limit.
- **Related:** O-187 (4.2a must-check list), O-027 (free-disk check), O-024 (sizing)

### C03-02 · Medium · confirmed-read
- **Where:** `internal/relay/accounts.go:165-170` (`watchAccounts`), `:182-185` (`accountsChanged`)
- **What goes wrong:** the watcher stores the new `data_version` (`a.version = v`) **before** `accountsChanged` reloads. If `reload` fails, `accountsChanged` logs one Warn and returns. The next tick sees the same version and does nothing, so the `relay admin` unbind, suspension or deletion is never applied to the cache or to live connections. The cache is stale for new connections too, because `register` reads the cache (`relay.go:946`).
- **Scenario:** the operator runs `relay admin account suspend acc_X` against an abusive account while the relay's single connection is busy. For example, a C03-01 flood or a large drain holds it past `queueOpTimeout` (10 s), or `SQLITE_BUSY` occurs during a WAL checkpoint. `relay admin` prints `done`, but the reload times out and the suspended keys keep sending and receiving, including after reconnects. This lasts until an unrelated account change reloads the cache (another `relay admin` commit, a bind or a daemon's `unbind`). A `bind_poll` right after a `ConfirmBind` whose reload failed also answers `bind_expired` although the key is bound (`accounts.go:369-381`).
- **Spec:** `accounts.md` §Revocation ("Suspend … live connections closed"); Acceptance ("Unbind closes the live connection within 1 s").
- **Fix direction:** advance `a.version` only after a successful reload, or retry on the next tick while the last reload failed.
- **Related:** O-187 ("`data_version` polling watcher … silent on DB outage"), C03-03

### C03-03 · Medium · confirmed-read
- **Where:** `internal/relay/accounts.go:165-167` (a `dataVersion` error is `continue`, not logged), `internal/relay/relay.go:940-962` (`register` admits from the in-memory cache), `relay.go:445-470` (no database check before the upgrade)
- **What goes wrong:** the spec says a relay whose database is unavailable refuses new connections. The code keeps admitting and routing from the last loaded binding cache. The watcher swallows every `PRAGMA data_version` error without a log line, so neither the operator nor the relay reacts. Only `/healthz` reports the outage.
- **Scenario:** the database becomes unreadable, for example after an I/O error or when the file is replaced during a mistaken restore. Keys that were unbound or suspended since the last reload (via `relay admin` on a replica copy or a restored file) keep full access. The operator sees no `accounts_error` log from the watcher.
- **Spec:** `accounts.md` §Web security requirements, **Outages**: "If the relay's database is unavailable, the relay refuses new connections (fails closed) and `/healthz` is 503."
- **Fix direction:** have the watcher record database health (log on the first error) and have `register`/`ServeHTTP` refuse new connections while it is unhealthy.
- **Related:** O-187 (first item), C03-02, C01 (`serveHealth`)

### C03-04 · Medium · confirmed-test
- **Where:** `internal/relay/accounts_store.go:407-447` (commit, then `st.record`), `internal/relay/accounts.go:385-393` (`unbindSelf` returns before `accountsChanged` on that error)
- **What goes wrong:** every security change commits to the database first and appends to the journal afterwards. If the append fails, the operation returns an error although the database already changed. A retry finds nothing to change (`ErrNoAccount`) and writes no journal line, so the event is missing from the journal for good.
  - On the daemon's own `unbind`, the error branch also skips `accountsChanged`. The relay replies `internal` "could not unbind" while its cache still says the key is bound.
- **Scenario:** the journal file cannot be written (disk full, which C03-01 can cause; a rotated or removed sink; an I/O error). A user runs `agentnet logout` for a stolen laptop, or the operator runs `relay admin account unbind`. The row is deleted but no journal line exists. After a later `relay restore --replay-journal`, the stolen key is bound again (relay-hosted.md §3, review 50 M6). Test output:
  ```
  after unbind #1: rows=0 cachedBound=true journalWrites=1 reply={"op":"error","code":"internal","message":"could not unbind"}
  after retry: cachedBound=false journalWrites=1
  ```
- **Spec:** `relay-hosted.md` §3 Restore: "the relay writes every security-relevant change (`unbind`, `account_delete`, `suspend`/`unsuspend`, …) as one content-free line to an append-only security journal".
- **Fix direction:** append the journal line before committing (a journaled-but-uncommitted replay is idempotent), or write it in the same step and fail the operation before committing; always reconcile in `unbindSelf`.
- **Related:** O-187 ("DB change succeeds but journal append fails"), C02 (journal writer)

### C03-05 · Low · confirmed-read
- **Where:** `cmd/relay/admin.go:132-133` (`adminList`), `:143-144` (`adminShow`); source `internal/relay/accounts_store.go:199-230` (`ensureAccount` stores `display` unvalidated)
- **What goes wrong:** `relay admin account list/show` print `accounts.display` raw to the operator's terminal. `display` is an email address or a GitHub login taken from the sign-in, and `ensureAccount` accepts any bytes, including ESC, CR and bidi characters.
- **Scenario:** a person signs up with a crafted email local part, for example a quoted local part containing `\x1b[2K\r` sequences, if 4.2b's normaliser lets it through. When the operator runs `relay admin account list`, the ANSI sequences rewrite or hide lines, such as the STATE column or other accounts. Today the only way to create an account is the `testhooks` hook, so this is reachable only once 4.2b ships. `device` is validated (`envelope/accounts.go:44-48`), and ids and keys are relay-generated.
- **Spec:** none directly; the threat model says a peer must not drive our terminal.
- **Fix direction:** sanitise control and bidi characters when printing, and validate `display` in `ensureAccount`.
- **Related:** O-187 ("`relay admin` prints display/email unescaped")

### C03-06 · Low · confirmed-read
- **Where:** `cmd/relay/admin.go:83-92`, `internal/relay/accounts_store.go:160-163` (`record` is a no-op with a nil journal)
- **What goes wrong:** `relay admin account suspend|unsuspend|delete|unbind` and `group suspend|unsuspend` write no journal line unless `--security-journal` is given. There is no default and no warning, although the running relay may have one configured.
- **Scenario:** the operator suspends an abusive account or unbinds a stolen key with `relay admin` and does not repeat the relay's `--security-journal` path. The change is not journaled, and a restore from the previous night's backup brings it back.
- **Spec:** `relay-hosted.md` §3 ("writes every security-relevant change").
- **Fix direction:** refuse the mutating verbs without `--security-journal` unless an explicit `--no-journal` is given, or print a warning.
- **Related:** C03-04

### C03-07 · Info · confirmed-read
- **Where:** `cmd/relay/testhooks_on.go`, `cmd/relay/testhooks_on_test.go` (`TestBindHook`); `.github/workflows/ci.yml` (no `-tags testhooks` job)
- **What goes wrong:** no CI job compiles or tests with `-tags testhooks`, so the hook and its test never run in CI and can break silently. The release-side check (`TestReleaseBuildHasNoTestHooks` plus `release.yml:145-157`) is sound. Locally, `go vet -tags testhooks ./cmd/relay` and `go test -tags testhooks ./cmd/relay -run 'TestBindHook|TestAdmin'` pass.
- **Scenario:** none; this is missing coverage (4.9b staging relies on the hook).
- **Spec:** `accounts.md` "Test hooks are not in release builds".
- **Fix direction:** add a CI step `go vet -tags testhooks ./cmd/relay && go test -tags testhooks ./cmd/relay -run TestBindHook`.
- **Related:** C15

### C03-08 · Info · suspected
- **Where:** `internal/relay/accounts_store.go:155-158` (`hashBindCode`)
- **What goes wrong:** bind codes are stored as unsalted SHA-256 of 40 bits, so anyone who reads a backup or the live database inverts every pending code in seconds.
- **Scenario:** a code is valid for only 10 minutes, and backups are encrypted and daily, so exploitation needs live database read access on the host. Out of scope as stated; noted for the owner as defence in depth.
- **Spec:** `accounts.md` ("stored hashed").
- **Fix direction:** accept as is, or use an HMAC with a per-relay secret.
- **Related:** none

### C03-09 · Info · confirmed-read
- **Where:** `internal/relay/relay.go:885-921` (`drainStep`), `:651-660`
- **What goes wrong:** the queue drain does not re-check "Who may send to whom" per row. Envelopes queued while both keys were eligible are delivered even if the sender has since been suspended or unbound, or the recipient is now bound without a quota group (for example, re-bound to a new account).
- **Scenario:** an abusive bound key queues 1000 mail envelopes to an offline victim and is then suspended. When the victim reconnects, all of them are delivered. The damage is bounded by the per-pair queue caps, and the envelopes are ciphertext the victim's daemon handles normally.
- **Spec:** `accounts.md` "Who may send to whom" ("routed (directly or through the queue) only if both …"); §Revocation (only the recipient side is addressed: "a re-bind gets them").
- **Fix direction:** owner decision; optionally drop a suspended sender's queued rows on suspension.
- **Related:** O-015

## Assumptions and contracts

- `accounts` reuses the queue's single `*sql.DB` (`accounts.go:80`, `q.db`). `PRAGMA data_version` then sees only other processes' commits (`queue.go:217`, `SetMaxOpenConns(1)`). **Checked**, but it assumes `database/sql` keeps that one connection. If the pool reopens it, the version changes spuriously, which only triggers an extra reload (harmless).
- `ConfirmBind`, `PendingBind` and `DenyBind` assume the 4.2b web layer enforces 5 wrong codes per session, 20 per account per day, 20 sign-ins per prefix per 10 min, CSRF, and a signed-in account `acc`. The Go API itself has no rate limit or authentication (`accounts.go:450-494`). **Unchecked** (4.2b is not built).
- `EnsureAccount` assumes the caller normalises and validates `subject` and `display` (only trim and lower-case for email, `accounts_store.go:203-209`). **Unchecked** (4.2b); see C03-05.
- `bindStart` assumes the per-key control limiter ran first (`relay.go:740-752`); `handleControl` itself does not rate-limit. **Checked.**
- `accountsChanged` holds `s.mu` and takes `a.mu` inside (`accounts.go:192-197`); `ConfirmBind` does the same (`:472-477`). This assumes no code path takes `a.mu` and then `s.mu`. **Checked** in `internal/relay`: `a.mu` is only taken in `reload` and `state`.
- `accountRoutes` relies on `h.From == sender.key` having been checked (`relay.go:760-763`). **Checked** for the direct path. For the ephemeral path, `routeEphemeral` is called after the same check (`relay.go:764-767`). **Checked.**
- The journal replay (`accounts_store.go:558-586`) assumes `ReplayJournal` applies entries in file order and only those after the backup time. **Unchecked** (C02): `cmd/relay/main.go:312` uses the backup file's `ModTime()` as "since", which the copy may change.
- `OpenAdmin` runs `openRelayDB`, which applies pending relay migrations to a database a running (possibly older) relay has open (`admin.go:25`, `queue.go:218`). **Unchecked** (C02: migrations).
- `pairNew` assumes `accountAllows` let only a bound key with a quota group through (`pairing.go:224-226`). **Checked**: `OpPairNew` is not in the no-group allow list (`accounts.go:269`).
- `LoginURLFromOrigin` produces `https://<first origin>/login`. The daemon must validate it (accounts.md, review 50 H3). **Unchecked** (C04/C17).

## Checked and fine

- `eligible` applies the state table correctly, including `pair.confirm` needing only bound keys (`accounts.go:147-150`), and suspension covers a suspended quota group (`accounts_store.go:188`).
- An ineligible recipient means nothing is queued: `accountRoutes` runs before `enqueue` (`relay.go:777` then `:796`), and ephemeral frames are dropped silently for an ineligible recipient while the sender gets `account_required` (`accounts.go:290-296`).
- Unbound connections per prefix: a cap of 16 with oldest-first eviction, bookkeeping kept by `unlistUnbound` on bind and on unregister (`accounts.go:225-254`, `relay.go:963-970`).
- Suspended keys at connect: `ready`, then `account_suspended`, then close 1008, with no registration and no drain (`relay.go:630-638`).
- Re-bound to a different account within one watcher tick: closed as `account_revoked` (`accounts.go:202-204`).
- `bind_poll` is rate-limited per ref (`accounts.go:414-423`); unknown refs are forgotten again (`:380`), so random refs do not grow `lastPoll`.
- `bind_start` from a bound key gets `already_bound`; the device and OS labels are strictly validated (`accounts.go:326-333`, `envelope/accounts.go:44-56`).
- `confirmBind` is transactional: pending and unexpired, account active and not in a suspended group, key not already bound, under 4 keys (`accounts_store.go:341-391`).
- `deleteAccount` removes keys, confirmed bind requests, web sessions and membership, and closes the group when the last member leaves, all in one transaction (`accounts_store.go:514-553`).
- Journal and log lines carry no email or login: `record` uses account or group ids and `short(key)`, and the logs use `short` and `acc` ids (`accounts.go:213`, `:341`, `:391`, `:469`). `TestAccountsLogsHoldNoEmail` has real markers and can fail.
- IDs `acc_`/`bnd_` are 100 bits from `crypto/rand` (`accounts_store.go:143-153`).
- Unbind replay deletes by account plus key prefix, so it cannot hit another account's keys (`accounts_store.go:572`).
- `bind_*` and `unbind` on a relay without accounts are an unexpected control frame (the connection closes), as before 4.2a (`pairing.go:146-149`).
- Test hooks are absent from release builds (Question 4).
- `parseInterspersed` handles keys that start with `-`, and `relay admin` rejects extra positional arguments and unknown verbs (`cmd/relay/admin.go:56-70`).
- Existing tests pass: `go test ./internal/relay -run 'TestAccounts|TestPairNewPerAccount'` and `go test -tags testhooks ./cmd/relay -run 'TestBindHook|TestAdmin'`.

## Leads for other chunks

- `cmd/relay/main.go:312`: journal replay uses `info.ModTime()` of the backup file as "since". A copied or re-downloaded backup gets a later mtime, and entries in between are skipped (C02).
- `internal/relay/admin.go:25` and `queue.go:218`: `relay admin` migrates the live database under a running relay, which may be an older version (C02).
- `internal/relay/journal.go:37-47`: `Append` does not `Sync`, and a partial write leaves a truncated line that makes `ReadJournal` fail the whole replay (C02).
- `internal/relay/relay.go:445-470` (`ServeHTTP`): no database-health gate before upgrade (C01; see C03-03).

## Notes

- In a release build `--accounts github` has no way to bind (no 4.2b page), so turning it on locks every daemon out. The owner should not enable it on the hosted relay before 4.2b.
- `accountsChanged` is called synchronously from `unbindSelf` on the connection's read goroutine; with many connections this is O(conns) under `s.mu` per logout. Not a DoS on its own (control rate).
