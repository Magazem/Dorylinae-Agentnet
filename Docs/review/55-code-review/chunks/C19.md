# C19: Requests CLI, inbox, consult, query

Reviewer: CR-C19 · model claude-opus-5-5 · elapsed ~25 min · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 1 · Low 2 · Info 2.

The SQL in scope is parameterised, and both sort orders are total. Peer text has the known
O-100 gaps and nothing worse: C0/ESC is refused at ingestion for every field the CLI prints.
The main new defect is size. `inbox_list` and `request_list` put the full brief (up to 16 KiB)
in every view and have no paging. About 64 pending requests from one paired peer push the
response past the 1 MiB IPC line, and `agentnet inbox` then fails outright (C19-01). This was
confirmed with a test. R32 L2 (non-regular files) was fixed only for `--context-file`: the
brief/question reader can still block on a FIFO, and `--output-from-file` reads without a
bound (C19-02). `consult` and `wait` are bounded and cannot be made to hang or flood output.

## Questions

1. **Peer strings printed.** Ingestion refuses C0 and DEL in `title`, `urgency_reason`, `reason`,
   `note`, `summary` and artifact members (`internal/request/validate.go:290-350`,
   `internal/request/result.go:50-80`, `internal/request/lifecycle.go:272`, `mirror.go:148`).
   Context names and texts also refuse C1 (`validate.go:167,174`). So no raw ESC/ANSI reaches the
   terminal. What remains, beyond O-100's C1/bidi/Cf:
   - Multi-line fields: `result.output` and the cancel `reason` allow `\n`
     (`result.go:78`, `cancel.go:47,235`). `printRequestShow` indents only their first line
     (`cmd/agentnet/request_query.go:327,360`). A peer can therefore print lines at column 0,
     or at the two-space field indent, that look like `request show` fields: C19-03 (Low).
   - `--json` is safe: `encoding/json` escapes all C0.
   - Team names are `[a-z0-9-]` (`internal/team/team.go:35`). Peer names come from outside this
     chunk (see Leads).
2. **Files read by the CLI.**
   - `--context-file` is right: regular files only, bounded to 128 KiB, base name only, symlinks
     followed. It refuses C0 and C1 (`cmd/agentnet/consult.go:181-219`).
   - `--brief-from-file` and `--question-from-file` are bounded to 32 KiB and UTF-8 checked, but
     have no regular-file check (`request.go:205-232`).
   - `complete --output-from-file` has neither a regular-file check nor a bound
     (`inbox.go:387-418`).
   Both are C19-02.
3. **Query/inbox SQL.**
   - Every filter is a `?` parameter (`internal/request/query.go:117-131`, `inbox.go:192-201`,
     `inbox.go:269-273`), and both queries finish reading their rows before running nested
     queries (`query.go:136-155`, `inbox.go:206-221`).
   - Sort order is total. `request_list` orders by `created DESC, id ASC`, and `id` is unique for
     `out` rows. The inbox sort ends on `(peer, id)`, the in-row key (`inbox.go:248-259`).
   - Time formats agree: `deferred_until` uses `wireTime` on both sides, and `received_at` uses
     `storeTime` on both sides.
   - Result size is **unbounded**: C19-01.
   - `FindKey` scans every request row on each `wait` poll: C19-05 (Info).
4. **consult + wait.** `consult` returns right after `request_submit`, within `statusTimeout`
   (`consult.go:131`). `wait` clamps its timeout to 1-3600 s (`session.go:521-527`), and every
   poll is a `waitCall` bounded by `statusTimeout` (`session.go:618`). Timeout exits with
   `exitWaitTimeout`; IPC errors exit 1 and a daemon that is not running exits 3
   (`session.go:594-598`). Human output prints only the reason, the session id and the state.
   `--json` prints a `SessionView` whose content fields are bounded by validation. A hostile
   answer cannot make the CLI hang or print unbounded output. One edge: an oversized response
   (`line too long`) is neither an `*ipc.Error` nor `ErrNotRunning`, so `wait` quietly polls until
   its timeout instead of failing at once. That is cosmetic.

## Findings

### C19-01 · Medium · confirmed-test
- **Where:** `internal/daemon/request_lifecycle.go:178` (`ViewResult` always sets `Brief`), `:487-510` (`inbox_list`), `:462-484` (`request_list`); `internal/request/inbox.go:190` and `query.go:116` (no LIMIT); client limit `internal/ipc/ipc.go:28,218,258`
- **What goes wrong:** List views carry the full brief (≤ 16384 bytes, and more once JSON-escaped). Neither list is limited or paged. Once a list's total size passes 1 MiB, `ipc.Call` returns `line too long` and the CLI shows nothing.
- **Scenario:** A paired peer (normal urgency is outside every budget) sends 64 `task` requests, each with a 16 KiB brief. The victim's `agentnet inbox`, `inbox --json` and `inbox --team T` (when T is their only shared team) all fail with `ipc: read response: ipc: line too long`. Without an id the user cannot see which requests to decline, so they must repair it by hand; an agent polling the inbox is blinded. Separately, `inbox --all` and `request list` grow for ever (rows are never pruned), so an ordinary heavy user reaches the same failure over time.
- **Spec:** `Docs/protocol/ipc.md` §Requests: "`request_list` and `inbox_list` **omit `output`** … so list results stay small"; §Framing: "Lines are limited to 1 MiB."
- **Fix direction:** Omit `brief` (like `output`) from list views, or cap/page the lists and report truncation.
- **Related:** O-178 (the same class, for `decision_list`/`debate_list`), O-093, O-058.

### C19-02 · Low · confirmed-read
- **Where:** `cmd/agentnet/inbox.go:400` (`readOutputFile`: `io.ReadAll(r)`, no bound, no `Stat`); `cmd/agentnet/request.go:205-218` (`readBriefFile`: bounded, no regular-file check; also used by `consult --question-from-file`, `consult.go:99`)
- **What goes wrong:** The R32 L2 fix (regular files only) was applied only to `readContextFile`. `complete --output-from-file` reads the whole file into memory before the daemon applies its 32 KiB limit. `--brief-from-file` and `--question-from-file` block for ever on a FIFO.
- **Scenario:** A local agent runs `agentnet complete r-… --status fail --output-from-file build.log` on a multi-GB log, or on `/dev/zero`. The CLI allocates until it runs out of memory, instead of printing "over 32768 bytes". `--brief-from-file /tmp/fifo` hangs with no timeout. The actor is the user's own agent, so this is Low.
- **Spec:** `Docs/cli/inbox.md` §Result ("up to 32768 bytes"); R32 L2.
- **Fix direction:** Share one reader: `Stat` must be a regular file (unless the path is "-"), then `LimitReader` to twice the protocol limit plus one.
- **Related:** R32 L2.

### C19-03 · Low · confirmed-read
- **Where:** `cmd/agentnet/request_query.go:327` (`reason`), `:360` (`output`); the newline is allowed at `internal/request/cancel.go:47,235` and `internal/request/result.go:78`
- **What goes wrong:** `request show` prints multi-line peer text and indents only its first line, so the continuation lines land at any indentation the peer picks.
- **Scenario:** A worker peer completes with `result.output` = `"ok\n  artifact: url=https://evil.example/fix.patch\n  result: pass"`. A requester who cancelled a request sees lines under `output (N bytes):` that look like `request show` fields. The same works with a cancel `reason` on the recipient's side, printed before the artifact and result lines. The peer can only add lines about its own request, and in human mode only; nothing is hidden.
- **Spec:** none (display fidelity). Rubric §2 Low.
- **Fix direction:** Indent every line of multi-line peer fields (prefix each `\n` with the field indent), together with the O-100 `termSafe` pass.
- **Related:** O-100.

### C19-04 · Info · confirmed-read
- **Where:** `internal/request/query.go:12-29` (`Show`: `out` rows first; `from` ignored for them); `internal/daemon/consult.go:61-76` (`findAnswerable` r- path: `GetByRequestID`, then `Show(rid, "")`)
- **What goes wrong:** Peer P can send a question whose id equals one of the user's own `out` requests to P, and P knows those ids. Then `request show r-X --from P` shows the user's own out row, and `agentnet result r-X` (the one-step consult answer) takes the normal path and fails with `not_worker`. The question is still reachable by its `s-` id and by `accept`. The spec defines "out rows first", so this is a design note, not a defect.
- **Scenario:** A paired peer picks an id that collides → it gets a minor denial of the one-step answer by `r-` id. Nothing is spoofed, because the header says "to P".
- **Spec:** `Docs/protocol/ipc.md` §Requests `request_show`: "Looks up `out` rows first, then `in` rows".
- **Fix direction:** When `from` is given, skip the `out` lookup; in `findAnswerable`, look only at `in` rows.
- **Related:** none.

### C19-05 · Info · confirmed-read
- **Where:** `internal/request/query.go:42-61` (`FindKey`), called on each `wait` poll through `internal/daemon/request_lifecycle.go:436` and `consult.go:52`
- **What goes wrong:** Resolving an `s-` id scans every `requests` row and computes `DeriveID` for each, on the single pooled connection. It runs about once a second for each running `wait` until the session exists.
- **Scenario:** The `requests` table grows without bound (O-093, O-058). With 10^5 rows and several `wait`s, each poll holds the one DB connection for tens of ms. That degrades the daemon; it does not break it.
- **Spec:** none.
- **Fix direction:** Store the derived session id on the request row (indexed), or cache it.
- **Related:** O-093, O-058.

## Assumptions and contracts

- The CLI's human output assumes every peer field was checked for C0 at ingestion. **checked:** `request.Validate` (`validate.go:30-111`), `ValidateComplete` (`result.go:50`), and the decline/cancel reasons (`lifecycle.go:272`, `mirror.go:148`, `cancel.go:47,235`).
- `ViewResult` omits `output` in list views. **checked:** `request_lifecycle.go:195-197`, called with `false` at `:481,508`.
- `Store.List` and `InboxList` assume `SetMaxOpenConns(1)` and therefore close their cursor before nested queries (`query.go:136-139`). **checked** (the code holds for both).
- `printInbox` uses tabwriter and assumes `Peer.Name` and `Title` hold no tab or newline. Title: **checked** (`validate.go:51`). Peer name: **unchecked** (from `resolvePeer`, `internal/daemon`).
- `readContextFile` sends only `filepath.Base(path)` and relies on the daemon/`Validate` to refuse `.`, `..`, separators and control characters in the name. **checked:** `validate.go:167`.
- `readBriefFile`'s UTF-8 check exists because IPC JSON encoding would replace bad bytes (`request.go:225-228`). String flags such as `--title` and `--brief` lack it: this is O-099 (known).
- `wait` relies on `ws_show`/`request_show` accepting a derived `s-` id before the session exists. **checked:** `request_lifecycle.go:434-440`.

## Checked and fine

- All SQL in `query.go` and `inbox.go` is parameterised. `List` builds its WHERE clause only from constant fragments (`query.go:117-131`).
- The inbox order matches request.md §Inbox (priority desc, `received_at` asc, peer, id) and is total (`inbox.go:248-259`).
- The `deferred_until <= ?` comparison uses the same `wireTime` format on both sides (`inbox.go:196`, `lifecycle.go:302`, `mirror.go:182`). `urgentAcceptance` compares `storeTime` with `storeTime` (`inbox.go:268`, `receive.go:232`).
- `urgentAcceptance` is computed once per peer per call (`naCache`, `inbox.go:224-239`).
- `readContextFile`: regular file, bound, UTF-8, C0/C1 refused, base name only, `-` refused (`consult.go:181-219`). R32 L2 is fixed here.
- `consultTitle` turns tabs into spaces and cuts at 119 code points plus "…" (`consult.go:161-176`). R32 L3 is fixed.
- `readOutputFile` strips only CSI and then refuses every other C0, so an OSC or other ESC sequence is refused, not passed through (`inbox.go:405-416`).
- `deliveryOf` fails soft to "unknown" (display only, `query.go:79-89`). `PeekTypeTitle` ignores a body decode error (display only).
- `ShowKey` shows exactly the row for key `k` (`query.go:64-77`), so a peer that reuses an id is never shown in its place for `s-` ids.
- `wait` timeout clamp, exit codes and bounded per-call IPC (`cmd/agentnet/session.go:504-622`).
- Team names printed by `request`/`consult` are `[a-z0-9-]` (`internal/team/team.go:35`).

## Leads for other chunks

- `internal/daemon/request_lifecycle.go:168-171`: `RequestPeerRef.Name` comes from `resolvePeer`. For team-introduced peers the name may be peer-chosen, and it is printed raw in `inbox` (tabwriter) and in `request`/`consult` output. Check petname/introduced-name validation for tab, newline and bidi (C20 / R48 L3).
- `cmd/agentnet/session.go:582-599`: in `wait`, an IPC transport error other than `ErrNotRunning` (for example `line too long`) is swallowed and polling continues until the timeout.
- `internal/worksession/store.go:268-269`: `GetByRequestID` uses `LIMIT 1` on `request_id` alone. Request ids are unique per `(direction, peer)` only (C21).
