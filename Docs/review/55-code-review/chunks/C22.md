# C22: Work-session store, hooks, Phase 1 fallback, experience, session CLI

Reviewer: CR-C22 · model claude-opus-5-5 · elapsed ~25 min · commit 6cc26a7

## Summary

Critical 0 · High 0 · Medium 0 · Low 4 · Info 2.

The core invariants hold. The experience record is written inside every work-session closing
transaction, it never reads a quarantined, discarded or superseded result, and nothing exposes
it. Quarantined results are withheld from every view at the `toView` choke point. Hooks do no
audit or DB work outside `tx`. The Phase 1 fallback can be triggered only by a signed ack from
the peer of the session, so the relay cannot trigger it. Four things are defects, all Low:
- The experience primary key turns the known O-131 reopen into a mail apply that fails
  permanently. Confirmed by a test.
- The Phase 1 fallback ignores the session kind and closes debate sessions without the debate
  hooks.
- The `r-` shorthand resolves an ambiguous request id arbitrarily.
- `agentnet session`/`sessions` print peer text raw. This is a new code path for O-100.

## Questions

1. **Experience record.** It is written in the closing transaction on every work-session close
   path:
   - `closeSessionTx` (`internal/worksession/transitions.go:54-70`), used by AcceptResult,
     AcceptResultInTx (human), Cancel, applyCancel and EarlyComplete;
   - Discard (`transitions.go:240`);
   - the Phase 1 fallback (`phase1.go:73`);
   - B's mirror close (`mirror.go:187-200`).

   Debate closes are written by `internal/debate/experience.go:76`. `CloseDebateTx`
   (`debate.go:53`) correctly writes nothing itself. Content: `worked` is taken only from an
   accepted result of the current round (`experience.go:105-110`). The builder also refuses
   `worked` for any other outcome (`internal/experience/experience.go:139-150`). Grants carry
   action, sensitive and state only (`experience.go:41-60`). Output, artifacts and notes are
   never copied, and the cancel reason is never stored (`transitions.go:260`). No IPC, CLI or
   mail reads `experience_records` (grep: only `WriteTx` touches it). One gap: the
   one-record-per-(session, role) rule makes a second close fail (C22-01). The debate
   mis-close writes a record of kind `work` (C22-02).
2. **Hook contracts.**
   - `OpenSession`, `EarlyComplete` and `earlyCompleteDebate` touch only `tx`. Every audit is
     returned as an `after` func (`hooks.go:117-146`).
   - `request/mirror.go:229-236` aborts on the hook's error, so the hook fails closed.
   - `RevokeGrants` runs in the same `tx` as every close, so a failed hook rolls back the close
     and the grant revocation together. There is no state where the session is open with live
     grants.
   - `OnClosed` runs after the commit through `auditClose` on all paths, including the Phase 1
     path (`phase1.go:105`). A crash before `OnClosed` leaves pending approvals, but their
     grants are already revoked in `tx`.
3. **CLI.**
   - The human output of `session` prints only status and summary, never output or notes
     (`cmd/agentnet/session.go:268-272`).
   - Quarantined results never print: `View.Result` is nil for requester+quarantined
     (`store.go:235`), and every closing path from quarantined NULLs the result (Discard, and
     RequestChanges at `transitions.go:168`). Cancel, EarlyComplete and ws.cancel never close
     from quarantined.
   - `--json` goes through `encoding/json`, so controls are escaped.
   - Peer title, name and summary are printed raw in human mode (C22-04).
   - Exit codes match the usage texts. `wait` returns 4 on timeout.
4. **`phase1.go`.** The trigger is a signed `mail.ack` from the addressee listing the id as
   `unsupported` (`internal/mail/outbox.go:497-503`; `finish` checks `from`). The relay cannot
   trigger it: its error frames never produce `unsupported_kind` (`outbox.go:506-520`). A
   hostile current peer can close its own sessions with us, which it could already do with
   `ws.state closed`. The result it then receives in `request.complete` is ours, and it would
   have received it anyway. An upgraded peer cannot trigger the fallback retroactively: only
   failures with `created >= opened` count (`phase1.go:160`). The fallback does not filter on
   the session kind, however (C22-02).

## Findings

### C22-01 · Low · confirmed-test
- **Where:** `internal/worksession/mirror.go:187-200` (`applyState`), `internal/experience/experience.go:225`
- **What goes wrong:** After O-131's closed→open reopen, a second `ws.state closed` tries to
  insert the experience record again. The insert hits the `(session, role)` primary key and the
  mail transaction fails. The error is not a bad body, so the mail is never acked. B's mirror
  stays `open` for good and the mail is retried for 14 days. The code's own comment at
  `mirror.go:203-206` says such a later state "must not fail the mail transaction".
- **Scenario:** A paired peer A (misbehaving) sends ws.state seq 1 closed/cancelled, then seq 2
  open, then seq 3 closed/cancelled. Steps 1 and 2 apply. Step 3 fails with `UNIQUE constraint
  failed: experience_records.session, experience_records.role`. B's row stays open with seq 2,
  so B's user sees an open session they cannot close, and B's agent can submit results into it.
  The damage is limited to that peer's own session.
- **Spec:** experience.md §When and where, "Exactly one record per (session, role) (a second
  close is impossible by the state machine)". The mirror does not enforce that state machine.
- **Fix direction:** Refuse a transition out of `closed` in `applyState` (this closes O-131),
  or skip the record when one already exists.
- **Related:** escalates O-131 (new consequence: a permanent apply failure and a stuck open
  mirror). Test: `internal/worksession/zz_review55_C22-01_test.go`.

### C22-02 · Low · confirmed-read
- **Where:** `internal/worksession/phase1.go:117-127` (`CheckPhase1FallbackForPeer`), `phase1.go:29-108`
- **What goes wrong:**
  - The fallback selects every non-closed worker-role session with the peer, debate sessions
    included.
  - It closes them with a raw UPDATE instead of the debate hooks, so the `debates` row stays
    open.
  - It writes an experience record with `kind: "work"` and role `worker` for a debate. A second
    record, role `respondent`, follows when `debate.close` arrives.
  - It completes the debate request with note "session cancelled", although B's daemon is
    supposed to do that at the mirror close (review 43 M4).
- **Scenario:** A hostile paired peer A has a debate open with B, and any B→A `ws.result` or
  `ws.cancel` exists (for example B's abandon of another debate, `internal/debate/apply.go:433`).
  A acks it as `unsupported`. Every open debate and work session B holds with A is then closed
  as cancelled, and B's debate rows no longer match B's session rows. A real Phase 1 peer
  cannot hold debates, so only a hostile peer triggers this, and only for its own sessions.
- **Spec:** work-session.md §Kinds "Phase 1 requester"; debate.md §Model (the debate owns the
  session close); experience.md "kind".
- **Fix direction:** Skip `kind = debate` sessions in the fallback.
- **Related:** none.

### C22-03 · Low · confirmed-read
- **Where:** `internal/worksession/store.go:268-278` (`GetByRequestID`), callers `internal/daemon/session.go:141`, `internal/daemon/consult.go:62`
- **What goes wrong:** An `r-` id is resolved with `WHERE request_id = ? LIMIT 1`, with no
  ORDER BY and no ambiguity check. Request ids are unique per sender only. The comment's
  assumption that "a daemon only ever holds one role" does not hold per request id.
- **Scenario:** We send request `r-X` to paired peer D. D sends us its own request with
  id `r-X`, which it knows because we sent it, and we accept. Two sessions now exist:
  `(requester, D, r-X)` and `(worker, D, r-X)`. Two different peers can also collide the same
  way. Then `agentnet session r-X`, `wait r-X`, `accept-result r-X` and `result r-X` act on
  whichever row SQLite returns. `wait` can report "changed" or "closed" for the wrong session,
  and the other commands fail with not_requester or not_worker. `consult.go:62` can also treat
  a pending question as already having a session.
- **Spec:** request.md §Persistence, "A CLI or IPC reference by id alone that matches `in` rows
  from several peers is `ambiguous_request`".
- **Fix direction:** Return `ambiguous_request` when more than one row matches, and accept
  `from`/role as the request commands do.
- **Related:** none.

### C22-04 · Low · confirmed-read
- **Where:** `cmd/agentnet/session.go:96` (`sessions` table), `session.go:258-272` (`printSessionHuman`)
- **What goes wrong:** Peer-controlled text is printed raw in human mode: the request title
  (for worker rows), the peer card name, and `result.summary`. Validation rejects only C0 and
  DEL (`internal/worksession/wire.go:124`, `internal/request/validate.go:342`), so C1 (U+009B
  CSI) and bidi or `Cf` characters pass.
- **Scenario:** A paired peer B submits `ws.result` with a summary that contains a U+202E bidi
  override or U+009B. A's `agentnet session s-…` shows a reordered summary, or runs an 8-bit
  CSI on terminals that honour it.
- **Spec:** none specific; this is the same defect class as O-100.
- **Fix direction:** Route these fields through the `termSafe` helper proposed in O-100.
- **Related:** O-100 (new code path: `session`/`sessions` were not in its list).

### C22-05 · Info · confirmed-read
- **Where:** `internal/worksession/experience.go:124-133`, `transitions.go:117-121`
- **What goes wrong:** The spec puts the `experience.write` audit "in the closing transaction".
  The code appends it after the commit, as R27 C1 requires. A crash between the commit and the
  append loses the audit row.
- **Scenario:** none attacker-driven.
- **Spec:** experience.md §Audit.
- **Fix direction:** Change the spec wording to "after the commit".
- **Related:** none.

### C22-06 · Info · confirmed-read
- **Where:** `internal/worksession/experience.go:105-109`
- **What goes wrong:** On an accepted close, `rounds_rejected` is written only when a
  `changes` text exists. The spec says it is always round count − 1.
- **Scenario:** none today, because RequestChanges always requires a changes text of 1–4000
  characters, so round > 1 implies non-empty changes.
- **Spec:** experience.md §Record, "what failed".
- **Fix direction:** Set `RoundsRejected` from `row.round - 1` on its own.
- **Related:** none.

## Assumptions and contracts

- `request.Store.CompleteInTx` touches only `tx` and refuses a request that is already
  complete (used at `phase1.go:90`, `mirror.go`). Unchecked.
- `Quarantine`, `RevokeGrants` and `Debate.*` hooks touch only `tx`
  (`store.go:47,54`, `debate.go:20`). The daemon wiring was checked for `OnFinal` only
  (`internal/daemon/daemon.go:473-481`); the rest is unchecked.
- `request/mirror.go:229-236` propagates the `EarlyComplete` error and blanks content when
  `keep` is false. Checked.
- `mail.Outbox.OnAck` sets `unsupported_kind` only for ids addressed to the ack's signer
  (`internal/mail/outbox.go:497-503`). Checked that `finish` receives `op.Msg.From`, but the
  `finish` body was not read.
- The daemon's `sessionView` (`internal/daemon/session.go:186-205`) takes the result only from
  `View.Result` and shows sizes only for quarantined rows. Checked.
- `experience_records` exists as migration 21 and is in both rewind DROP lists. Unchecked.

## Checked and fine

- `toView` withholds a quarantined result on the requester (`store.go:235`). Every path that
  leaves quarantined either NULLs the result (Discard, RequestChanges) or requires a release.
- The experience builder never includes output, artifacts, notes, paths, labels or the cancel
  reason. The truncation order matches the spec (`internal/experience/experience.go:96-160`).
  The 64 KiB cap cannot be exceeded at level 3 with the current field limits (title 120 code
  points, summary 280, claims 280).
- A discarded or replaced result never reaches the record: Discard passes the cancelled
  outcome, and RequestChanges clears the result before any close.
- Phase 1 fallback: the in-tx re-read prevents a double close (`phase1.go:55-61`), grants are
  revoked in the same tx, and `OnClosed` runs through `auditClose`.
- `EarlyComplete`: the debate path always drops content, and a Quarantine error fails closed.
- O-130 (early complete close not audited) appears fixed: `hooks.go:125-146` audits
  `ws.close` and `ws.ignored early_complete`.
- The CLI JSON output uses `encoding/json` throughout. `--reason` is never sent unless
  `--cancel` is set.

## Leads for other chunks

- `internal/worksession/mirror.go:130-140`: nothing stops `closed`→anything (O-131). A fix
  there also removes C22-01.
- `internal/request/validate.go:342`: `hasControl` excludes C1, and `hasC1` is applied only to
  context files and brief (O-100 root).

## Notes

- `phase1.go` uses the stored result even when the failed mail was a `ws.cancel`. The spec says
  a `ws.cancel` failure gets no result. This is reachable only when both mails fail, and the
  content is B's own.
