## Findings

| # | Sev | Location | Issue | Fix |
|---|---|---|---|---|
| M1 | Medium | `peers/pairing.go` `checkConfirm`, `onPeerIssuer` | **A tag that verified could still end as a failed pairing, and a correct tag that arrived in time could be dropped.** (a) The attempt's 60 s confirm timer kept running after its `pair.confirm` was accepted. If K was not ready yet (the issuer's Argon2id started at issue time, but a slow or loaded host can lag), the timer failed the attempt as `confirm_timeout`. `checkConfirm` then saw `att.over` and dropped a correct `tag_R`, which also burned one of the 3 attempts. (b) Between the tag check and `finish(complete)`, the code-TTL timer, an attempt timer or a relay `error` frame could run `finish(failed)`. `checkConfirm` went on to store the peer (`trust=code`) and, on the issuer, send `tag_I`. The pairing was then reported as failed, with a `pair.fail` audit row, although the peer had been stored. The same held for the redeemer's confirm timer. This breaks the spec goal "pairing fails visibly and nothing is stored on the side that detects the failure". No MITM follows from it, because the stored key's tag had verified. | **Applied.** An accepted confirm stops its attempt timer, and the timer ignores an accepted attempt. After `hmac.Equal` succeeds, `checkConfirm` claims the pairing under `m.mu`. If the pairing already ended or the attempt is over, it stores nothing. Otherwise it sets `session.completing`, and from then on `finish` (timers, error frames, `attemptFailed`) is a no-op. Only `checkConfirm` ends the pairing, through `end(..., completer=true)`. Tests `TestReviewTagInTimeWithSlowKCompletes` and `TestReviewCompletingPairingIgnoresFailures`. |
| L1 | Low | `peers/pairing.go` `HandleError` | The issuer sent `pair_new` at most **3** times: `sends < maxLookupRetries` with `sends` starting at 1. The spec says it retries with a new code "at most 3 times", 4 `pair_new` in all, which matches the relay's 10/min budget (08b M1). | **Applied** (`<=`). The test `TestV2LookupTakenReissuesNewCodeThreeTimes` now expects 3 reissues. |
| L2 | Low | `peers/pairing.go` `verifyPeer` → `store` | The v2 path stored the relay's raw `card` bytes in `peers.card`. Extra top-level members are dropped from `card_X` (spec), so they are not covered by T. A hostile relay could therefore add unauthenticated junk to the stored card JSON. Nothing reads the column today. | **Applied.** v2 stores the canonical `{"card","signature"}` that the tags cover. v1 still stores the raw bytes. |
| L3 | Low | `peers/pairing.go` `attemptFailed` | `pair.attempt_fail` audited `peer` = the relay-supplied `public_key` before it was validated. That string is up to about 1 MiB, going into the append-only audit table, 3 rows per pairing. | **Applied.** It is audited only if `envelope.ParseKey` accepts it, otherwise `""`. Test `TestReviewRelayStringsAreBounded`. |
| L4 | Low | `peers/pairing.go` `HandleError` | The relay's `error.code` and `error.message` went unbounded into `Status.error` (IPC) and the `pair.fail` audit `code`. Only `reason` was truncated. | **Applied.** `code` is cut to 64 bytes and `message` to 200. Same test. |
| L5 | Low | `mailbox/mailbox.go` `Announcement` / design | Implementer choice (1) keeps the own key only as keystore secret + `mailbox/current.json`. It adds **no `mailbox_keys_own` table**, which mail.md §Tables assigns to "0.8c (first key) / 1.0b". Any failure in `usable` (announcement not parseable, keychain transiently unavailable, which `keystore.Load` reports as `ErrNotFound`, or expiry within 1 h) creates a new key and overwrites `current.json`. The previous private key then stays in the keychain or on disk **with no record anywhere**. 1.0b's deletion job (t + 21 d) cannot find it, which erodes mail forward secrecy. Keychain entries cannot be enumerated. | Not fixed. It is a design choice and 1.0b owns the table. **Owner/orchestrator decision:** 1.0b must add `mailbox_keys_own`, import `current.json` into it, and record every key *before* it is announced. Consider returning an error instead of rotating when `current.json` is valid but the keystore read failed for a reason other than a definite "not found". |
| L6 | Low | `envelope/envelope.go`, `agentcard`, `mail` strict base64 | Compatibility: strict base64url now rejects non-zero trailing bits in keys, signatures and tags. Honest encoders (`RawURLEncoding.EncodeToString`) never produce these, and all vectors pass. So no valid input from our own code is newly rejected. One edge case remains: a `peers` row whose key string is non-canonical, which only a malicious peer's self-signed card could have created before this change, now makes `Store.List` fail as a whole (`KeyFingerprint` error). That breaks `agentnet peers`. | Not fixed. Make `List` skip or flag such a row instead of failing. |
| L7 | Low | `peers/pairing.go` `onPeerIssuer` | A `pair.confirm` that arrives before the issuer has finished verifying its `pair_peer` is dropped (`waiting` is still false). The redeemer has then already marked the code used, so the pairing can only time out. The redeemer's Argon2id makes this ordering practically impossible on a healthy host, and a hostile relay can drop frames anyway. | Not fixed. Optionally buffer one early confirm per peer key. |
| L8 | Low | `peers/pairing.go` `reissue` | Each `pair_lookup_taken` starts a new 64 MiB Argon2id while the previous one keeps running (it cannot be cancelled). A hostile relay can cause 4 concurrent derivations per issuer pairing, 256 MiB. It is bounded, and each needs a user `pair --new`. | Not fixed. |
| L9 | Low | `peers/pairing.go` | The code lives on in immutable Go strings (`Status.Code`, the `Redeem` argument, `NormalizeCode` output), which the wipe in `finish` cannot overwrite. The `[]byte` secret and K are wiped as the spec asks. | Not fixed (language limit). |

## Checked and found sound

- **No store without a verified tag (v2).** The only v2 store is in `checkConfirm`, after `hmac.Equal` against a tag computed from K and this attempt's own T. `onPeerV1` runs only for sessions created by `Redeem(..., allowV1=true)` with a 10-character code. The issuer never takes the v1 path. A `pair_code` carrying `code` fails with `relay_v1` and the relay's code is not shown.
- **MITM binding.** T covers the canonical card (whose `public_key` must equal the frame's `public_key`, and whose signature is checked over the generically parsed card) and the canonical announcement (`identity` = frame key, exactly two top-level members). The stored key is `sc.Card.PublicKey` from that same card. `envelope.from` is not authenticated end to end. That does not matter, because the MAC binds the key through the card. Reflection is rejected: the role strings differ (`issuer\n` / `redeemer\n`), and `verifyPeer` rejects our own key.
- **D9 order.** The issuer computes no reply before a correct `tag_R`, and sends `tag_I` only after storing. A wrong tag, a timeout or bad material sends nothing (`TestV2ThreeBadTagsAbort` asserts zero envelopes).
- **Constant time**: `hmac.Equal`. `parseConfirm` is strict: UTF-8, exactly 3 members, `v` = the JSON integer 2, strict base64url, 32 bytes, no duplicate keys.
- **Transcript and canonicalisation** match the spec vectors: K, T, both tags and both confirm payloads, including the relay's `<` re-encoding and dropped extra top-level members (`TestPairingVectors`, `tools/verifyvectors`). The issuer uses (own, peer) order and the redeemer (peer, own). Both use their own canonical material as sent.
- **Argon2id**: t = 3, m = 65536 KiB, p = 1, 32 bytes; salt `"dorylinae-pair-v2\n" ‖ lookup`.
- **Attempts**: counted when `pair_peer` arrives, capped at 3 under `m.mu`. A 4th is ignored. Failures (bad card/mbox, bad tag, timeout) are counted once each via `att.over`, and the 3rd fails the pairing and sends `pair_cancel`. A relay cannot reset the counter: it lives in the session, and a new code needs the user. Replayed `pair.confirm`: `accepted` (one per attempt), plus the relayclient `(from,id)` seen-set. A confirm for another pairing does not match: lookup and peer key must both match a waiting attempt. Tag checks are serialised by `checkMu`, so the first success ends the pairing and the others are dropped.
- **Redeemer single use**: `CodeUsed` before sending anything, and an atomic `INSERT OR IGNORE` (`MarkCodeUsed`) right before `tag_R`, so two concurrent redemptions cannot both send. The hash is `SHA-256("dorylinae-pair-used-v2\n" ‖ code)`, persisted and pruned after 24 h (migration 4). It survives a restart (tested). At most one `pair_peer` and one tag per redeemer session.
- **Timers**: code TTL is issuer-local (`issued_at + 10 min`, `expires` shown from local time; choice 3 is fine). Relay reply is 30 s, and the confirm wait is 60 s per attempt (issuer) or after sending `tag_R` (redeemer). The KDF wait on the redeemer is bounded by the relay-wait timer.
- **Secrets**: no log, audit row, error or IPC error carries the code, lookup, secret, K, tags, cards or announcements. The IPC server does not log params. Only the pending issuer's `pair_status` returns the code, as specified. `pair_cancel` on every issuer ending (choice 6) is harmless: the relay ignores foreign or unknown lookups.
- **Domain separation**: `dorylinae-agent-card-v1\n`, `dorylinae-mailbox-key-v1\n`, `dorylinae-mail-v1\n`, `dorylinae-pair-v2\n`, `…-transcript\n`, `…-used-v2\n`. None is a prefix of another. Announcement signing and verification use the same generic canonical form.
- **Mailbox key storage**: the keychain account is `mailbox-<id>-<key_id>`, with file fallback `<cfg>/mailbox/<key_id>.key` through `keystore.WriteOwnerOnly` (0600 on unix, protected single-owner DACL on Windows, applied before the secret is written), in a 0700 dir. The private key is saved and read back before `current.json` is written. It follows `DORYLINAE_KEYSTORE`. Daemon and e2e tests force `file` (choice 2). The expiry math holds: `not_after = created + 14 d`, the key is renewed when less than 1 h is left, and the peer-side window checks follow mail.md step 5.
- **v1 downgrade**: a 15-character code is always v2, and a 10-character code needs `--v1` (otherwise `bad_code` with a hint, choice 4). The relay cannot turn a v2 pairing into v1.
- **Ordering in the daemon**: `pair.confirm` goes to `pairs.HandleEnvelope` first (choice 5). The session layer ignores non-`session.*` types, so a confirm is never audited as `unpaired`.
- **ParseStrict / CanonicalValue export**: a pure rename plus a wrapper, with the same behaviour. The `internal/mail/canonical.go` copy is deleted, as HANDOFF asked.
