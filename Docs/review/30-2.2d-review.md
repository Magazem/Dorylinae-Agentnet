## High (fixed)

**H1. A reserved slot (Create during the window's ready wait) broke other calls, and a
lockout or daemon stop during the wait still stored the approval.** `Create` put
`&live{action}` into `s.pending` before the window was ready (up to 10 s on Windows), but the
SQLite row was written only at the end. During that time:
- `sweepExpiredLocked` (run by every `Create` and every `List`) called `checkExpiryLocked` on
  the reserved id, got `sql: no rows`, and returned an error. **Every `approval_list` and
  every other approval-creating IPC call failed** while any approval window was starting.
- `dropAllLocked` (the 10th wrong code) handed the reserved id to `lockAll`, which audited an
  `approval.reject {reason: locked}` for a row that did not exist. `Create` then continued: it
  showed the code, **inserted a `pending` row after the lockout**, found no entry to put the
  MAC in, did not start a watcher and **did not kill its window**. The row stayed `pending`
  in `approval_list` until the next restart, with an orphan window.
- `Close` during the wait did not stop `Create` from finishing, so an approval could be
  created after shutdown began.

Fix (`internal/approval/{approval,store}.go`): `live.reserved` marks the slot until the row
and MAC are stored. Reserved entries count toward `MaxPending` and are skipped by the sweep,
`ResolveTag`, `confirm`, `Reject`, `OpenWindow` and `lockAll`. `Create` inserts the row and
finishes the slot under `s.mu`, and only if the reservation still exists and the store is
not closed. Otherwise it kills the window, withdraws the notification and returns
`approval_locked` (or `approval_unavailable`), storing nothing. `Store.closed` makes
`Create` and `reopen` refuse after `Close`. Tests: `TestReservedSlotDoesNotBreakListOrSweep`,
`TestLockoutDuringReadyWaitStoresNothing` and `TestCloseDuringReadyWaitStoresNothing`
(`internal/approval/window_review_test.go`). All three fail on the original code.

## Medium (fixed)

**M1. Linux: a dialog closed after it was ready never delivered an answer.** The exit
goroutine delivered only on exit 0/1 (zenity) or exit 0 (kdialog). Cancel, Esc, the window
close button, zenity's timeout (5) and kdialog's cancel only called `markNotReady` (a no-op
after ready). The Store's watcher waited forever, `entry.handle` stayed set, the view said
`window: open`, and **`approval_open` was a no-op for the rest of the approval's life**, so
the human could not get the window back. Fix: `decodeExit` in `window_linux.go`; every exit
now delivers an answer (dismiss unless valid). Test: `TestDecodeExit` (Linux).

**M2. Linux: zenity exit 1 without "Reject" counted as ready.** GTK exits 1 with no output
when it cannot open the display. The code treated any exit 1 as "a valid answer", so the
approval became ready, **the code was shown, and no window existed**. The spec says an
early non-zero exit is failure, except a real answer. Fix: only exit 0, or exit 1 with stdout
`Reject`, is valid (`decodeExit`). Test: `TestDecodeExit`.

**M3. Two concurrent `approval_open` calls opened two windows.** `OpenWindow` checked
`entry.handle == nil` and released the lock before `reopen` started a window, so two calls
both started one. The second overwrote `entry.handle` and `watchCancel`. The first window was
never killed on decide or expiry, and its watcher could still act. That breaks "at most one
window per approval" and the 5-window bound, and any caller can run `--open`. Fix:
`live.opening` is claimed under `s.mu` in `reopen`, which also refuses while a handle exists.
`onWindowAnswer` clears the handle only if it is the one that answered, and it kills the
dialog on an approve/reject answer. `startWatch` watches only the current handle. Test:
`TestConcurrentOpenStartsOneWindow` (fails on the original code: 3 windows).

**M4. Windows: the job handle could be closed twice.** Both `Kill` and the exit goroutine
called `CloseHandle(job)`. The usual sequence (a decision kills the dialog, then it exits)
closed it twice. The second close can close an unrelated handle that has reused the value
(a pipe, an IOCP, another job). Fix: a `sync.Once` around the close.

**M5. Lifetime: no Linux `Pdeathsig`, and a Windows dialog could run outside its job.**
The spec's `Pdeathsig = SIGKILL` was missing on Linux, so a dialog outlived a crashed daemon
until its own timeout. On Windows, a failure in `CreateJobObject`, `SetInformationJobObject`
(its error was ignored) or `OpenProcess` left the dialog running outside any job, but it
still counted as ready. Fix: `SysProcAttr{Pdeathsig: SIGKILL}` in `window_linux.go`. The
daemon never calls `runtime.LockOSThread`, so the starting thread does not exit early (the
repo has no `LockOSThread` call). The new `assignKillOnCloseJob` in `window_windows.go`
treats any job-setup failure like a failed assignment: kill and not ready.

**M6. Windows: the WinSta0 half of the interactive-session check was missing.** The
worker said `x/sys/windows` lacks bindings, which is true, but the check is cheap through
`windows.NewLazySystemDLL("user32.dll")`. `windowStationName()` calls
`GetProcessWindowStation` and `GetUserObjectInformationW(UOI_NAME)`, and
`inInteractiveSession` now also requires `WinSta0`. Test: `TestWindowStationNameResolves`
(it resolves the name and opens no window; the value depends on the runner).

**M7. macOS: the script asked System Events to activate, and turned every dialog error into
a valid `dismiss`.** `tell application "System Events" to activate` needs an Automation (TCC)
grant, and the spec says `activate` (osascript itself). `on error → return "dismiss"` made
osascript exit 0 with a "valid answer" when `display dialog` failed. An early failure (no GUI
session, for example) therefore counted as ready, and the code was shown with no window.
Fix: plain `activate`, and any error other than -128 is re-raised, so osascript exits
non-zero and the ready check fails.

**M8. Terminal mode: one over-long stdin line ended code entry for the daemon's life.**
`bufio.Scanner` with a 128-byte buffer stops at `ErrTooLong`, so the reader goroutine
returned. A 129-byte paste left the human with no way to approve until a restart. The
128-byte limit also counted the newline. Fix: a `bufio.Reader` loop that refuses the
over-long line with a message, skips to its newline and continues. It also handles a final
unterminated line. Test: `TestTerminalReaderSurvivesOverlongLine`
(`internal/daemon/approval_terminal_internal_test.go`).

**M9. macOS: a failed `osascript` start crashed the daemon.** The handle's kill function
was built before `cmd.Start`, and `Create` calls `Kill` on every not-ready handle. After a
failed `Start`, `cmd.Process` is nil, so `Kill` panicked in the IPC handler goroutine, and
`ipc.dispatch` has no `recover`. Fix: build the handle after a successful `Start`, the same
as Windows and Linux.

## Low

**L1 (fixed). Window text was not sanitised at the window layer.** A NUL made `exec` fail
(then `approval_unavailable`, a self-inflicted refusal). Newlines and unbounded length went
straight into Linux argv and the dialogs. Current summaries are local text, but the spec
routes peer text through here. Fix: `windowText` in `window.go` applies `notify.Clean` to
tag, kind and summary, capping the summary at 600 code points. Test:
`TestWindowTextSanitises`.

**L2 (fixed). The dialog did not say where the code is** (approval.md: "The code is in the
AgentNet notification for a-012345. If notifications are silenced …", review 29 L5). It is
now appended in `windowText` for all three OSes.

**L3 (fixed). The 256-byte answer cap was not enforced.** The scanners allowed 64 KiB. Now
`parseAnswerLine` and `decodeExit` treat an answer over 256 bytes as dismiss. Test:
`TestParseAnswerLine` (Windows/macOS) and `TestDecodeExit`.

**L4 (fixed). `Store.Close` read `watchCancel`, `timer` and `handle` after releasing
`s.mu`.** That is a data race with the watcher and the timer. It now collects them under
the lock.

**L5 (fixed). The window's Reject showed no outcome notification.** The spec asks for a
short notification after every answer. It now shows "Rejected".

**L6 (note). An answer that arrives before the notification is shown is not treated as
dismiss** (approval.md, Answer format). The answer is buffered and acted on once `Create`
finishes. The code does not exist yet, so a stray early 6-digit value can only use an
attempt, and an early Reject rejects. Fixing it needs a timestamp or sequence on
`WindowHandle.Answer`. That is left to the owner of 2.2d as a follow-up.

**L7 (note). The Windows form is not cascaded** (spec: "cascaded so that several windows do
not stack exactly"). All windows open at the default position. This is cosmetic, but with
several approvals the top window hides the others' tags.

**L8 (note). The Windows job is assigned after `Start`, not from a suspended process.** A
child started in the first microseconds would escape the job. PowerShell starts no child
here, and the spec says "assigned right after Start". Accepted.

**L9 (note). The hourly limit does not count reserved slots.** At most 4 in-flight
`Create`s can exceed 20/hour. `MaxPending` bounds this.

**L10 (note). Timers.** After a `Perform` error, `confirm` restarts the timer for a full
`TTL` rather than the time left, so the proactive kill fires late. Expiry is still enforced:
`checkExpiryLocked` on every confirm, the sweep on every `Create`/`List`, and the dialog's
own timeout at `expires`. The wall-clock timer next to the injected `now` is deliberate
(comment in `confirm`). A cheap follow-up is `time.AfterFunc(time.Until(expires), …)`.
