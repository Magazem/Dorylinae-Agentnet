# R-3.2+3.1a: security review of the debate schemas and the debate core (tickets 3.2, 3.1a)

Review (Opus) of `p3/debate-core` at 20e843e (3.2 schemas), b91a997 (3.1a core, migration
19) and 3ceb049 (rollback-helper fix), against Docs/protocol/debate.md, owner decision D30
(OD-P3-1 one-sided commit, -2, -4, -7) and review 43. Scope: `internal/debate/*`, the
`debate` request type and member in `internal/request`, the debate session kind in
`internal/worksession`, the debate checks in `internal/capability`, the daemon wiring
(kinds, `reservedKindPrefixes`, `request_submit`, grants), migration 19 and the debate
vectors. Fixes were made in place, with tests.

**Verdict: pass after fixes.** Critical 0, High 1 (fixed), Medium 1 (fixed), Low 6 (1 fixed,
5 noted).

## What holds

- **Commitment.** The nonce is 32 bytes from `crypto/rand`, drawn by the daemon in
  `request.Submit`'s `Prepare` (never by the agent, never for an idempotent duplicate). The
  preimage is a versioned tag, then `sid`, `A` and the nonce, each of fixed length and
  separated by `\n`, then the one variable field. So it parses one way only. `sid` binds the
  pair and the request, and `A` binds the author, so a commitment cannot be moved to
  another debate or claimed by B. B recomputes it from the stored commitment, the derived
  session and `msg.from` (`bodyRow` checks `r.peer == msg.from`). It uses nothing from the
  reveal except `nonce` and `position`. A bad nonce, a non-canonical position, a failed
  schema check or a hash mismatch all lead to `broken`.
- **Hiding before B's position.** Before the reveal, A's position exists only as slot 0
  `committed` on A. `last_state` is empty until the reveal, so the echo cannot leak it.
  `Next` gives slot 1 to B, so A's agent cannot submit anything first. The reveal is built
  in `revealTx` from the stored row, in the transaction that applies slot 1. On B, a reveal
  that arrives before B's own slot 1 is `sent` is ignored, with a blank inbox copy
  (`TestRespondentNeverSeesPositionEarly`). B's one-step accept stores slot 1 `sent` in the
  same transaction as the accept and the mail, so a correct A can never reveal early.
- **Turn engine.** `Next` depends only on the transcript. On A it uses `applied` entries.
  On B it uses `applied` and B's own `sent` ones, never `early`. Rounds come from the row
  (CHECK 1–5), so the loop is bounded and the proposal and answer slots stay within 13.
  Checks on A: the entry must be B's, at exactly the next slot, of the expected kind, with
  targets checked against A's copy of the transcript. Checks on B: the same with A as the
  author. A duplicate is ignored, and an entry for a later slot is held `early` and checked
  again when it is drained. So a peer cannot write into the other side's slot, skip
  converge, add a round or replay an entry. Replays across debates are stopped by
  `bodyRow`: the derived `sid` must match `(from, to, request)` and the role. The kinds sent
  only by A are refused from B.
- **Clocks.** Deadlines are A's own `now` plus `turn_timeout_s`. The peer's `at` is
  format-checked and stored for display only. `SweepOne` re-reads the row inside its own
  transaction. The store has a single connection (`SetMaxOpenConns(1)`), so the sweep and an
  incoming entry are fully serialised, and whichever commits second sees the first one's
  phase.
- **Receipt-side rules.** `DecodeEntry`, which applies the free-text rule, the debate-text
  C1/U+2028/U+2029 refusals, the field caps and then `MaxDebateEntry`, runs in `applyEntry`
  and on the reveal's position, not only at IPC. The topic rule is in `request.Validate`,
  which `Decode` calls on receipt. The body is bounded by `MaxMailPlaintext` before
  parsing, and the decoders only walk values that are already parsed.
- **Migration 19.** It runs in `store.apply`'s `BEGIN IMMEDIATE`, so a failure rolls it
  back completely. Column lists are explicit on both sides for both rebuilds, and the
  columns and CHECKs match migrations 11+12 and 15 exactly (checked line by line). The three
  `requests` indexes, including the partial unique `requests_idem`, and `approvals_state`
  are recreated. There is no `REFERENCES` and no trigger on either table (grep of every
  migration). `TestMigration19RebuildKeepsRows` covers rows, `result` and indexes, and the
  rewind helpers undo 19 (3ceb049).
- **Quarantine edges.** `debate` submit checks the peer-wide clause in the request
  transaction (`InTx`). Every accept path (`request_accept`, the one-step accept, and the
  daemon's auto-accept, which never routes debates) reaches `OpenedTx`, which checks it
  from B's side. `CheckSensitiveGrant` runs at `grant_create` (outside the transaction, but
  re-checked at confirm), in the approval `Precondition` and inside the policy transaction.
  `grantKind` treats a debate session as never open for a grant. `PeerQuarantineHoldsTx`
  uses the same "ever active" rule as `QuarantineHolds`.
- **Audit.** `debate.*` details carry ids, enums, counts, sizes and one boolean.
  `grant.refused` carries `action` (an enum) and ids. No topic, entry, reason text or note
  is audited. `TestDebateHappyPath` checks this for the entry texts.

**The worker's decisions.**
- (1) `request_submit` gains the `debate` member in 3.1a: accepted, because the commitment
  must be computed where the request id is drawn.
- (2) The decided outcome is kept in `last_state` and `reason` while `closing`, with
  `outcome` NULL: accepted, because the table's CHECK requires it. The view reads it back.
- (3) A wrong kind in a slot is `bad_body` on receipt and `not_your_turn`/`bad_state` at IPC:
  accepted, as the spec says. A held entry of the wrong kind is dropped when drained, since
  it can no longer fail its mail.
- (4) Ignored bodies get a blank inbox copy, and early reveals are never stored: accepted,
  since this is stricter than the spec and closes the anchoring leak.
- (5) `request.complete` drops `result` and `note` only while A's session is open:
  accepted. The session closes when the debate reaches `closing`, and from then on the
  normal early-complete path (including its quarantine test) applies.
- (6) New audit action `grant.refused`: accepted. It is now listed in grant.md (L6).
- (7) A held A entry that claims a B slot is dropped: accepted.
- (8) An early complete uses reason `cancelled`: accepted, as the spec says.
- (9) `OpenSession` derives the session kind from the request type: accepted. It is the
  only place every accept path passes through, and the request row is always present by
  then.

## High

### H1: B closed its mirror with any outcome A claimed (fixed)

`internal/debate/apply.go` `applyClose`. B applied `debate.close` with A's `outcome` and
`reason` after checking only that the pair was consistent (`validClose`). A modified A could
send `agreed/accepted` while B's agent had answered `accept: false`, or before any answer at
all. B would then close its session `accepted`, notify its human "Debate with <name> ended
in agreement", complete the request with `note = "debate agreed"`, and show `agreed` to its
agent. This breaks §Security considerations, "One writer": *"A cannot fabricate an `agreed`
outcome: agreement exists only as B's own `answer` entry."* 3.3a will add B's own derivation
and signature, but until then this build is the one that ships a respondent, and nothing
bounded what A could claim.

**Fix.** `closeMatches` checks A's outcome against B's own transcript before anything
changes:
- `agreed` needs B's `sent` answer with `accept: true`;
- `escalated/rejected` needs B's answer with `accept: false`;
- `escalated/timeout` needs B's own position (slot 1 `sent`: a timeout after both
  positions exist);
- `cancelled` is always possible (A's cancel, B's `ws.cancel`, or a timeout before slot 1
  reached A).

A close that does not match is ignored (`debate.ignored {reason: "outcome"}`). B's mirror
stays open, and B keeps its abandon path. Legitimate races still apply: A times out
(`escalated/timeout`) while B's answer is in flight. Test: `TestCloseOutcomeCheckedAgainstAnswer`
(agreed with no answer, agreed after a refusal and then the real escalated close, and
escalated/timeout before B's position versus cancelled/timeout). **For 3.3a:** keep this
check in front of the derivation, or subsume it. The signature alone does not stop B's
notification from firing on a close that 3.3a then refuses to sign.

## Medium

### M1: a request.complete before any accept left A's debate `invited` for ever (fixed)

`internal/request/mirror.go` `applyMirror`. `EndedTx` ran for `declined` and `cancelled` but
not for `completed`. A modified B can send `request.complete` for a debate it never accepted
(Phase 1 allows that on the mirror). The early-complete hook finds no session and drops the
content, and A's request becomes `completed`. A's `debates` row then stayed `invited` with no
deadline, and nothing could end it: `request_cancel` is `bad_state` on a completed request,
and `ws_cancel` has no session. Because `CheckSensitiveGrant` counts `invited` (review 43
M5), A could then **never** issue a sensitive grant to that peer again (`debate_open`). The
debate list also showed a pending invitation for ever. **Fix:** `completed` also calls
`EndedTx`, which acts only on `invited`, so an accepted debate is unaffected. Test:
`TestCompleteBeforeAcceptEndsInvitedDebate` (the debate is closed cancelled, the grant check
passes, nothing is revealed).

## Low

### L1: `r-` ids resolve to the older of two rows (noted, for 3.1b)

`internal/debate/store.go` `resolve`. Request ids are unique per sender, so a peer can send
a debate request that reuses the id of one this daemon sent it. `resolve("r-…")` then
returns the older row (`ORDER BY created LIMIT 1`). The attacker's row is always the newer
one, so it cannot capture the local agent's command. It is still an ambiguity the request
package reports as `ErrAmbiguousRequest`. **3.1b:** when two rows match, return the same
ambiguity error (or accept a `from`), as `request_*` does.

### L2: one bad debate stops the sweep (noted, for 3.1b)

`Sweep` returns at the first `SweepOne` error. `loadTranscript` fails if any stored entry no
longer parses (only possible if a later build tightens a rule), so one such debate would
stop timeouts for every debate after it. **3.1b (which wires the sweep):** log the error
and continue with the next debate.

### L3: early entries at a B slot wait for B's own submit (noted)

`applyEntryOnB` holds any A entry for a later slot, including one that claims a slot that
turns out to be B's. `drainTx` or B's `Submit` drops it, and it is never shown (`buildView`
skips `early`). There are at most 12 such rows per debate. Only a modified A can create one,
and it costs a few KiB.

### L4: the IPC `request_submit` error for a debate without a wired store (noted)

`internal/daemon/request.go`: when `debateStore(rs)` is missing, `type: debate` gets
"debate: is allowed only when type is debate". The message is wrong but the refusal is
correct. It cannot happen in the daemon, which always wires the store.

### L5: migration 19 on a very large `requests` table (noted, from review 44 L6)

The rebuild copies every row under `BEGIN IMMEDIATE`. On a database with around 10⁶
requests, a second opener (`agentnetd install`) can exceed `busy_timeout` (5 s) and exit 1.
Correctness holds: the migration is atomic, and the loser retries on the next start. No
change.

### L6: `grant.refused` was not in the audit table (fixed)

Docs/protocol/grant.md §Audit gains the row: `{session, peer, action, reason, policy?}`,
with actor `cli`, or `daemon` on the policy path.
