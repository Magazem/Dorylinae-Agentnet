## Implementer's choices

| Choice | Judgement |
|---|---|
| **Loopback always allowed**, for both `http` and `https` | **Acceptable, keep it.** (1) No remote protocol path sets the URL or its headers. `Settings.SetWebhook` is called only from the `notify_set` IPC handler, and no mail kind touches `notify.*` settings. The headers are constants plus the id, the timestamp and the signature. Peer text reaches only the JSON body, and it is JSON-encoded and `Clean`ed there. (2) The one indirect path is the one notify.md already names: an agent steered by a hostile request calls `notify_set`. That agent is a local process that can reach loopback directly. The spec explicitly allows `http` to literal loopback, so blocking `https` to loopback would close nothing. (3) An `https` delivery to loopback needs a certificate that verifies for the URL's name, so a plain local service only ever sees a ClientHello. If the owner wants to close the steered-agent path, the fix belongs at the IPC layer (confirm the URL at the terminal), not in the dial policy. |
| `https` also blocks private ranges (beyond notify.md) | **Acceptable as hardening**, and now written into notify.md §Configuration. The cost is that an internal receiver with a corporate-CA certificate on RFC 1918 space cannot be used. It was also wrongly applied to the proxy (M1). |
| Own resolver plus dialling the checked IP, instead of `net.Dialer.Control` | **Correct, and equivalent.** Every address DNS returns is checked, and the connection goes to `JoinHostPort(checkedIP, port)`, so there is no gap between the check and the dial in which DNS could be rebound. TLS SNI and verification still use the URL host, because `http.Transport` takes them from the request, not from the dialled address. notify.md no longer names `net.Dialer.Control`. |
| Team name resolved in the daemon adapter | **Fine.** `notifyAdapter` looks up `team.Store.Get(info.TeamID)` locally. The name comes from the local roster, and it is `Clean`ed in `buildPayload` like the peer name. |

## Adversarial questions: result

| Question | Result |
|---|---|
| IPv4-mapped IPv6, `::ffff:127.0.0.1`, `0.0.0.0`, `[::]` | Handled. Go's `IsLoopback`, `IsPrivate` and `IsLinkLocalUnicast` unwrap `::ffff:a.b.c.d`. `0.0.0.0` and `::` are unspecified, so they are blocked. New matrix cases cover the mapped loopback, metadata and private addresses, plus `::` and `fd00::1`. |
| Decimal and octal hosts (`2130706433`, `0177.0.0.1`) | `http`: rejected by the literal-loopback rule, because `net.ParseIP` does not accept them. `https`: the name goes to the resolver, and whatever address the OS makes of it is checked like any other. |
| DNS rebinding between the check and the dial | None. The dial uses the checked IP (see above). `TestDialBlocksDNSRebinding` covers it. |
| Redirects | Not followed (`ErrUseLastResponse`). A 3xx is `failed` with `error = "redirect"`. |
| `HTTP(S)_PROXY` bypassing the checks | By spec, the proxy address is checked and the target is not. For `https`, CONNECT keeps TLS end to end. `http` URLs are loopback-only, and Go never proxies `localhost` or loopback. **M1**: the proxy was held to the target's private-range rule. |
| HMAC scheme | Matches notify.md: `"v1:" ‖ ts ‖ ":" ‖ id ‖ ":" ‖ body`, HMAC-SHA256, base64url without padding. The timestamp is the time of this attempt, and a retry keeps the id and the body. `Verify` uses `subtle.ConstantTimeCompare`. The reference verifier applies ±300 s and answers a replayed id `2xx` without processing it again. |
| Secret generation, storage and rotation | 32 bytes from `crypto/rand`. `whsec_` + base64url is printed only on first set and on `rotate_secret`. It is stored in the keystore (keychain account `webhook`, or `webhook.key`, owner-only), re-read on every attempt, and deleted by `--webhook off`. It is never logged or audited (a new assertion in `TestNotifyWebhookIPC`). |
| Payload privacy | Holds. `buildPayload` emits only the listed fields. `title` and `result_status` appear only with `title: true`, and the brief, output, summary and artifacts never reach `Event`. Existing tests cover this. |
| Slack and Discord neutralising | Slack `&<>` escaping covers `<!channel>` and `<url\|label>`. Discord `allowed_mentions: {parse: []}` covers `@everyone`. **M2**: Discord masked links and other markdown were not neutralised. |
| Queue bounds, backoff, retry storms, restart | At most 1000 pending rows, and overflow fails the oldest. The delays are 10 s … 6 h with ×U(0.9, 1.1) jitter. A row fails after 7 attempts or 24 h. `Retry-After` is capped at 6 h, and an overflowed or negative value is ignored. Deliveries run serially, at most 20 per tick, so there is no storm. Rows and `next_attempt` persist in SQLite, and the worker resumes after a restart. Final rows are purged after 7 days (hourly). |
| Migration 13 | Identical to the DDL in notify.md, including the `webhook_queue_due` index. |
| Timeouts | `http.Client.Timeout` is 10 s and covers the body read. The dial timeout is 10 s. |
| Content in the audit log | `notify.fail` records `{channel, event, id, status?}` only. **M3**: `notify.config` was never written. |

## Medium (fixed)

- **M1 — A private-address proxy was blocked.** `resolvingDialer` applied the full `https`
  target policy, including the private-range hardening, to the proxy address. Behind a
  typical corporate proxy (`10.x:3128`), every delivery failed `blocked_address`. That
  contradicts notify.md ("the proxy is trusted by the user's configuration"). Fix:
  `proxyTracker` records the host:port that the transport's proxy function returns, and dials
  to it use `checkProxyAddress`, which blocks only link-local, unspecified and multicast.
  Direct dials keep the full policy (`internal/notify/dial.go`). Test: `TestDialProxyPolicy`
  covers a private proxy (explicit and default port), a link-local proxy, and a private
  target without a proxy.
- **M2 — Discord markdown in peer text was live.** `content` was the raw `text`. A peer name
  or title such as `[Reset your key](https://evil)` rendered as a disguised link in the user's
  channel. `# …` and `||…||` also rendered. Fix: `discordEscape` backslash-escapes
  ``\ * _ ~ ` | > # - [ ] ( ) < @`` in `content` (`internal/notify/payload.go`, and
  notify.md §Payload). Test: `TestApplyFormatDiscordEscapesMarkdown`. The existing Discord
  test now expects `\@everyone`.
- **M3 — `notify.config` was never audited.** notify.md §Configuration and §Audit require it.
  Without it, a steered agent could redirect the webhook, the one path M13 of review 12 worries
  about, and leave no trace. Fix: `notify_set` appends `notify.config {desktop?, events?,
  webhook: set|removed|rotated?, format?, title?}` (actor `cli`), without the URL or the secret
  (`internal/daemon/notify.go`, `daemon.go`; notify.md now lists `events?`). Test:
  `TestNotifyWebhookIPC` checks the rows, and checks that neither the URL nor the secret
  appears in them.

## Low (fixed)

- **L1** A transport error was stored in `webhook_queue.error` as `url.Error`, which quotes
  the full URL. A Slack or Discord webhook URL is a bearer secret (review 12, L12). Fix:
  `transportError` stores only the inner error. Test: `TestWebhookNetworkErrorOmitsURL`.
- **L2** `agentnet notify` printed the full URL. Docs/cli/notify.md shows
  `https://hooks.example.com/…`. Fix: `elideWebhookURL` (`cmd/agentnet/notify.go`). `--json`
  is unchanged. Test: `TestElideWebhookURL`.
- **L3** `webhookKeystore` ignored the injected-keystore test mode, so a daemon test with
  `Options.Keystore` that set a webhook would write to the real keychain. It now takes the
  mailbox key's mode (`daemon.go`).
- **L4** `notify_webhook_test.go` used `os.MkdirTemp`. It now uses `testutil.TempDir(t)`.

## Low (not fixed)

- **L5** An overflow drop (`error = "overflow"`) and `--webhook off` (`"removed"`) make rows
  `failed` without a `notify.fail` audit row. Decide whether "a failed delivery is audited"
  covers them.
- **L6** The trigger's 16-event bound (`maxQueued`) also drops webhook enqueues. A webhook
  enqueue also waits behind a desktop `Show` (≤ 3 s each). Under a flood, webhook events are
  lost even though the webhook queue holds 1000.
- **L7** The keychain account `webhook` is shared by every config dir on the machine, as
  spec'd. Two daemons (profiles, dev and test) overwrite or delete each other's secret.
- **L8** `applyWebhookSet` saves the rotated secret before the settings write. If that write
  fails, the call errors, the new secret is never shown, and pending deliveries are signed
  with it.
- **L9** Deliveries are serial. A blackholed receiver costs up to 20 × 10 s per tick and
  delays all other rows. There is one receiver, so this is acceptable.
- **L10** The `https` hardening does not cover NAT64 `64:ff9b::/96`, 6to4 `2002::/16`,
  CGNAT `100.64/10`, `0/8` or `255.255.255.255`. TLS still has to verify, so the practical
  risk is small.
- **L11** The reference verifier in `sign_test.go` does not check that the body `id` equals
  the header id, as notify.md §Signature requires.
- **L12** The response body is drained without a byte cap (it is bounded by the 10 s client
  timeout). `io.LimitReader` would bound it.
- **L13** If the settings row goes missing any way other than `--webhook off`, due rows stay
  `pending` and are polled every second until they are purged. This does not happen in
  practice.
