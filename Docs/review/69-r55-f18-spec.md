## 1. Summary for the owner

**The problems.**

1. **A's request record can hold a result nobody reviewed** (R55-022, Medium). B can submit
   two results in one round while A is offline. A applies and accepts the first. B then
   completes its request with the *second*, and A stores that one in `requests`.
2. **A prompt-injected agent on a helper can forge a run result** (R55-029, Medium). A run
   session looks like any worker session. The helper's local agent can submit `pass` /
   `tests_passed` before the runner does, and the controller accepts it.
3. **A late `decline`/`cancelled` leaves A's session open with live grants** (R55-062).
4. **The Phase 1 fallback fires on a bad body** (R55-059). The mail layer acks a bad body
   exactly like an unknown kind. One rejected mail makes B close every session with a
   Phase 2 peer. The fallback also closes debates the wrong way (R55-060), and a restart can
   lose its trigger (R55-061).
5. Small ones: B never shows `cancel: refused` (R55-114); A-side IPC calls return an empty
   `mail_id` (R55-115); `ws.orphan` audit rows lack `session` (R55-167); `rounds_rejected` is
   tied to the changes text (R55-168).

**The fix, in six rules:**

1. **One result per round on B.** `ws_result` (and the `complete` shorthand) is `bad_state`
   once a result exists for the current round. A request for changes starts a new round and
   allows the next result.
2. **A stores its own view of the close.** When a `request.complete` arrives for a session A
   has closed, A writes the result it accepted (or nothing, for a cancel) into the request
   record, whatever B sent. A mismatch is audited.
3. **Run sessions belong to the runner.** The helper marks them. IPC `ws_result`,
   `request_complete` and worker `ws_cancel` are refused on them, and the store enforces it.
   A new round (changes requested) is answered with an automatic `ws.cancel`.
4. **A late decline or cancelled closes an open session**, exactly like an early complete.
5. **The ack gets a `rejected` member** for a bad body and stale mail. `unsupported` means
   "unknown kind" only, and only it triggers the Phase 1 fallback.
6. **The fallback is restart-safe and debate-free.** Debates are skipped. The check runs at
   start for peers with open worker sessions, and shutdown waits for it.

**Wire change:** yes, one: the ack member `rejected`. A daemon from before F18 refuses such
an ack as malformed, and its outbox row then ends `expired` instead of `failed`. This is
fine before the first release (OD-F18-1). **Migration:** yes, one: `work_sessions.runner`
(an `ALTER TABLE … ADD COLUMN`, no backfill).

## 3. Design notes (why this shape)

- **R55-022 needs both sides.** The B-side rule keeps an honest B's own records right (its
  request row, its experience record, and what it sends). Only the A-side rule protects A
  from a *modified* B. A modified B can always send a `request.complete` with any content.
  A already holds the accepted result in its session row (accept keeps `result`), so A
  needs no new wire member to know the truth. That makes the 99-report's alternative (the
  accepted result's hash in `ws.state`) unnecessary (OD-F18-3).
- **Why not let B replace its result before A applies it?** B cannot know whether A applied
  the first one. Mail can be reordered, and `expired` means "delivery unknown". A revised
  answer goes through cancel, or through A's request for changes.
- **Lost result.** If A stays offline beyond the outbox's 7 days, B's `ws.result` ends
  `expired`. B cannot resubmit in that round. It can `--cancel`, which A applies when it
  returns (A is `open`). OD-F18-2 lists a relaxed alternative.
- **Run marker as a column.** The run queue (`settings` `device.runs`) forgets a job once it
  finishes, while the session stays open until the controller acts. A durable per-session
  flag is the simplest correct marker. `kind` cannot take a new value without a table
  rebuild (a CHECK constraint), and `run` is not a separate experience kind (OD-F18-4).
- **Store-level enforcement.** The report's fix direction says "refuse over IPC". Putting the
  check in `SubmitResult`/`SubmitCancel` with an explicit submitter makes a future IPC
  method safe by default. The runner passes `Runner`, and everything else is an agent.
- **`rejected` for stale mail too.** A stale mail is of a known kind, so `unsupported` was
  wrong for it as well. In practice a stale ack never meets a non-final outbox row (7 d
  expiry < 14 d receive age), so this changes only the meaning.
- **Peer-wide sweep kept.** Once `unsupported` really means "unknown kind", a failed
  `ws.result` does prove the peer is Phase 1, so sweeping all its sessions is correct.

## 6. Open decisions (recommendation first)

- **OD-F18-1 — the ack wire form for "refused, known kind".**
  - (a) **New ack member `rejected` (recommended).** Honest meaning, one line per side. Cost:
    a pre-F18 sender refuses such an ack as `malformed` and its row ends `expired` instead
    of `failed`. And a pre-F18 *receiver* still acks bad bodies `unsupported`, so against
    one the fallback can still misfire until it upgrades. Both are acceptable before the
    first release.
  - (b) Keep the ack. B vetoes the fallback when the peer has shown it is Phase 2 (any
    `ws.state`/`grant`/`debate.*` mail from it in `mail_inbox`). No wire change, but the
    evidence can be missing (a new pair) or pruned (F12 may prune `mail_inbox`), and
    `unsupported` keeps two meanings.
  - (c) Both (a) and (b): the most robust, and the most code.
- **OD-F18-2 — B's second result in a round.**
  - (a) **Always `bad_state` (recommended).** Simple. Recovery after a lost (`expired`)
    result is `--cancel`.
  - (b) Allow a resubmit once the earlier `ws.result` outbox row is final and not
    `delivered`. This needs a `result_mail` column (the same migration) and a lookup.
    Better UX when A is offline for more than 7 days. With the A-side rule (4.4) it is safe
    for A either way.
- **OD-F18-3 — how A protects its request record.**
  - (a) **A derives the record from its own closed session (recommended).** No wire change.
  - (b) The report's alternative: carry the accepted result's hash in the closing `ws.state`
    and compare. B would learn nothing new, but it is a wire change and still needs (a)'s
    fallback when the hashes differ.
- **OD-F18-4 — the run marker.**
  - (a) **`work_sessions.runner` column, one `ALTER` migration (recommended).**
  - (b) No migration: keep a list of runner-owned session ids in the `device.runs` settings
    row and prune it on close. Fragile (a JSON list that must track session closes), and the
    check reads settings on every `ws_result`.
  - (c) A new `kind = 'run'`: needs a table rebuild for the CHECK, and would leak into
    experience records.
- **OD-F18-5 — worker `ws_cancel` on a run session.**
  - (a) **Refused over IPC (recommended, as the report says).** The helper's human stops a
    run by clearing the scope or unlinking, which the runner reports.
  - (b) Allowed. A cancel only denies the run and cannot forge a pass, and it gives a human
    on the helper a direct stop. But a prompt-injected agent could then cancel every run.
- **OD-F18-6 — a new round on a run session.**
  - (a) **Automatic `ws.cancel` from the helper (recommended).** device.md already says a
    re-run needs a new request.
  - (b) Leave it `open`. The controller must cancel by hand, and until then the session sits
    open with its grants usable.
- **OD-F18-7 — a late decline/cancelled in `awaiting_result`/`quarantined`.**
  - (a) **Leave it to A (recommended).** This is the same rule as an early complete. Grants
    are unusable outside `open`, and A's human decides on the result.
  - (b) Close it `cancelled` too. That deletes nothing, but it ends a session A may still
    want to accept.
- **OD-F18-8 — the quarantine and the A-side override.**
  - (a) **Store A's accepted copy in the request record even when the rule holds
    (recommended).** The result was released by a human and accepted. Today such a record
    ends with no result at all (O-148 path).
  - (b) Keep dropping it while the rule holds (the request record stays empty; the result
    lives in the session only).
