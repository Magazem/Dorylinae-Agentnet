# R-3.6a: security review of the hash-chained audit log (ticket 3.6a)

Review (Opus) of commit 6422f2f on `p3/audit-chain`, against Docs/protocol/audit.md (§The
chain, §Migration 18, §Existing rows, §Verification, §Anchors), owner decision D30 and
review 43 M8/M9. The threat model is the spec's: the chain makes tampering by anyone who can
write the database **evident**, not impossible. It must never report tampering as something
else, and code that bypasses `internal/audit` must fail loudly. Fixes were made in place,
with tests.

**Verdict: pass after fixes.** Critical 0, High 0, Medium 1 (fixed), Low 6 (1 fixed,
5 noted).

## What holds

- **Row encoding.** `row_c` is canonical JSON of the **stored** strings, and `detail` enters
  as a string, so there are no separator ambiguities, and the result does not depend on how
  Go marshals a map. The prefix is a fixed label, then exactly 32 raw bytes of the previous
  hash, then JSON. The genesis label and the row label differ, and the row label ends in
  `\n`, so neither can be read as the other. `id` enters as an integer. Canonicalisation
  would fold invalid UTF-8 into U+FFFD, but `wellFormed` rejects it on verify. Writers only
  store `json.Marshal` output and constant actor/action strings. `ts`, `actor`, `action`
  and `detail` are `NOT NULL`, and `detail` is `json_valid`, so a NULL cannot reach the
  encoder. Legacy `ts` values come from the same `RFC3339Nano` writer, so they parse.
- **Trigger coverage.** Migration 1's `UPDATE`/`DELETE` triggers are unconditional, so
  they also cover `hash` and `id`. An UPSERT (`ON CONFLICT DO UPDATE`) fires the update
  trigger. The chained trigger is created in migration 18 itself.
  `TestMigration18RefusesUnchainedRows` runs on the latest schema, so a later migration
  that drops the trigger fails it. The one gap was `INSERT OR REPLACE` (L1, fixed).
- **Two writers.** `Append` takes the write lock before reading the head: `BEGIN IMMEDIATE`
  on a dedicated `sql.Conn`, with `ROLLBACK` on a background context. `AppendTx` in a stale
  deferred transaction fails with `SQLITE_BUSY_SNAPSHOT` instead of forking. The explicit
  `id` is the primary key, so two `head+1` rows cannot both commit. A rolled-back
  `AppendTx`, including one that wrote `audit.chain_start`, leaves nothing behind: the next
  append recomputes `head+1`. In-process appends are serialised by the single connection.
  An `Append` made while the caller holds a `Tx` would deadlock, but that was already true
  before this change.
- **Legacy rows and `audit.chain_start`.** A forged or edited chain start, or a changed,
  added or removed legacy row, changes either the virtual chain or the counts. The strict
  decode (`DisallowUnknownFields`), the check on the first stored row and the stored hash
  catch this. Getting past them means recomputing the chain, which is the documented
  "rewrite" limit.
- **Verify paging.** `lastID` and `prev` carry across pages, and each page is bounded by the
  head read at the start, so rows appended during the walk are neither counted nor
  misreported. The walk stops after a short page. A page of exactly 2000 rows costs one
  extra empty read, which is harmless. Anchors that were never reached are reported as
  `anchor_missing` after the walk, so a truncated tail below an anchor is caught.
- **No content.** `audit.chain_start` carries two counts. The chain adds hashes of rows
  that are already stored.
- **Migration 18 on a large database.** `ADD COLUMN … CHECK` scans the table without
  rewriting it (every value is NULL). No hashing happens inside the migration.
- **Vectors.** `tools/verifyvectors` recomputes genesis, `row_c`, every hash (including the
  virtual one) and the chain-start counts, using only the standard library and its own
  canonicaliser. `TestDetectsAuditMismatch` proves it can fail.
- **M9.** `store.apply` re-reads `MAX(version)` under `BEGIN IMMEDIATE`, skips migrations
  that are already applied, and refuses a version jump. The five-round two-opener test
  covers this.

**The worker's decisions.** (1) `List` hiding `audit.chain_start`: accepted. `List` has no
production caller (only tests), and 3.6b's `audit_list` shows every row. (2) `Append`
refusing an unchained head after the chain has started: accepted, since failing loudly is
correct. Its operational cost is L2. (3) M8 tested at store level only: accepted, because
`audit_verify` does not exist until 3.6b. See L5.

## Medium

### M1: an anchor on a row whose hash had been nulled was reported as a caller error (fixed)

`internal/audit/chain.go` `Verify`. Before walking, `Verify` looked up each anchor's row and
returned `ErrBadAnchor` (IPC `bad_request`, exit 1) if that row's `hash` was NULL. Someone
who dropped the triggers and ran `UPDATE audit_events SET hash = NULL WHERE id = <anchor>`
therefore got "your anchor is wrong" instead of `broken`/`unchained`. Nulling every hash
(which removes the chain start) gave the same result. Scripts that treat exit 5 as tampering
never saw either case, and the anchor, which exists to catch exactly this kind of rewrite,
was defeated by the cheapest tamper there is.

**Fix.** The look-up before the walk is gone. The walk marks an anchored row that has no
stored hash. Any failure found during the walk is reported first, so a NULL after the chain
start is `unchained` at that row. After a clean walk, a legacy anchor is `ErrBadAnchor` only
if `audit.chain_start` exists, which keeps the acceptance criterion "an anchor on a legacy
row is `bad_request`". With no chain start at all the result is `anchor_mismatch`: a user can
only get an anchor's hash from a stored row (`log --head` prints `""` for a legacy head).
audit.md §Anchors now says this. Test: `TestAnchorOnNulledHashIsBroken` (both cases). It
fails against the original code and passes now. `TestLegacyRowsMigrate` still gets
`ErrBadAnchor`.

**Residual (for the Orchestrator).** Someone who nulls every hash and then lets the daemon
append re-seals the whole log under a new `audit.chain_start`. An old anchor then lands on a
row that is now legacy and still gets `bad_request`. Closing that means changing the approved
rule to "an anchor on a legacy row is always `anchor_mismatch`". That is consistent: a wrong
`ID` that points at a chained row is already `anchor_mismatch`. It is recommended, but it
changes D30's acceptance line, so it has not been made here.

## Low

### L1: `INSERT OR REPLACE` could rewrite a row with the triggers in place (fixed)

`internal/store/store.go` migration 18. The chained trigger fired only when the hash was
NULL. `INSERT OR REPLACE` (or `REPLACE INTO`) with an existing `id` and any well-formed hash
passed it, and SQLite deletes the old row without firing delete triggers (with
`recursive_triggers` off). That skipped migration 1's append-only guarantee. `Verify` caught
the result, but "code that bypasses `internal/audit` fails loudly" did not hold. **Fix:**
the trigger now also refuses any `NEW.id` other than `MAX(id)+1`, which covers replace, gaps
and inserts without an id. `MAX` on the rowid is O(1). The audit.md §Migration 18 SQL is
updated. Test: `TestMigration18RefusesUnchainedRows` now checks replace, `REPLACE INTO`, a
gap and an omitted id, and asserts that the CHECK (not the trigger) is what refuses an
uppercase hash.

### L2: an unchained head stops the daemon, and with it `log --verify` (noted)

`appendChained` → `startChain` refuses to append after an unchained row once the chain has
started (decision 2). `daemon.Run` returns when the `daemon.start` append fails, so the
daemon no longer starts, and `agentnet log --verify` (3.6b) reads through IPC. The owner
therefore cannot run the one tool that would explain what happened. Only someone who dropped
the trigger can cause this, and they could corrupt the file anyway, so it gives an attacker
nothing new. It is a diagnosability gap. **Suggestion for 3.6b:** have the error name
`agentnet log --verify` / the row id, and either let `log --verify` fall back to opening the
database read-only when the daemon is down, or let the daemon start with auditing reported
as broken in `status`.

### L3: the first append after migration 18 hashes the whole legacy log under the write lock (noted)

`startChain` runs inside `daemon.start`'s `BEGIN IMMEDIATE` and streams every legacy row
(O(n) memory is fine, O(n) time). At roughly 1 to 2 s per 10⁵ rows (the 10⁵-row test), a
log of about 10⁶ rows holds the lock longer than the 5 s `busy_timeout`. That is exactly when
`agentnetd install` appends right after starting the daemon, so install would print "done,
but the audit event could not be recorded" and exit 1. It happens once and only for very
large logs. If a beta user reports it, give `recordAudit` one retry. No change now.

### L4: `service.install` detail carries paths (pre-existing, noted)

`cmd/agentnetd/install.go` `serviceAuditDetail`: `home` and `executable` are filesystem
paths. audit.md §What exists says detail never carries paths, while
Docs/cli/agentnetd-install.md documents these two. This dates from Phase 1 and is outside
3.6a. The chain now makes such rows permanent (they cannot be pruned). **For 3.6b/3.9:**
decide whether to reduce the fields (for example to a hash or a boolean) or to record the
exception in audit.md, before `TestPhase3AuditHasNoContent` is written.

### L5: M8 is tested at store level (decision 3, noted)

`TestVerifyPagesReleaseTheConnection` runs an `Append` and a `mail_seen` write from the page
hook and requires both to finish before the walk goes on. That proves the connection is
released between pages. It does not test a real IPC call during `audit_verify`, which
cannot exist before 3.6b. **3.6b** must add the IPC-level check from the ticket's acceptance
(an IPC call and a mail apply during a 10⁵-row verify).

### L6: a long migration in the other process can exceed `busy_timeout` (noted)

`store.apply` makes the second opener wait on `BEGIN IMMEDIATE` for up to 5 s. A table
rebuild on a large database (migration 19 rebuilds `requests` and `approvals`) could take
longer, and the loser's `Open` would then fail. In practice this is `agentnetd install`,
which would exit 1 after the service had started. This is rare and far better than the
duplicate-column failure it replaces. It is noted for the 3.1a review.
