# R-2.3b: security review of git serving (ticket 2.3b)

Opus security review of the last commit on `p2/git-serving` (08248b5):
`internal/capability/git.go`, `git_test.go`, `internal/daemon/grant.go`, `internal/daemon/fetch.go`.
It checks the code against Docs/protocol/grant.md (§Serving git, §Paths, OD-P2-14), ticket 2.3b
(23-phase2-tickets.md), and reviews 24 M5, 28 L5 and 34. Fixes were made in place, with tests.
The tests ran against Git 2.54.0.windows.1.

**Verdict: pass after fixes.** Critical 0, High 0, Medium 2 (both fixed), Low 6 (1 fixed,
2 documented in the spec, 3 noted).

## Medium

### M1: a missing branch resolved through DWIM to another ref; a symbolic ref was followed (fixed)

- **Location:** `GitBackend.tip` (`internal/capability/git.go`); `validateGitResource`
  (`internal/daemon/grant.go`).
- **Problem:** `rev-parse --verify refs/heads/<b>^{commit}` applies the DWIM rules to its
  argument. If `refs/heads/<b>` is missing, git also tries `refs/refs/heads/<b>`,
  `refs/tags/refs/heads/<b>` and `refs/remotes/refs/heads/<b>`. This was reproduced: with
  the branch `feature` deleted and a tag named `refs/heads/feature` (a tag an upstream can
  publish and `fetch --tags` brings in), rev-parse printed the tag's commit, so the grant
  would have served it. That breaks "other refs unreachable" in the resource-kinds table. It
  also breaks the worker's own "a missing branch → not_found". The residual it flagged was
  real as well: a symbolic ref `refs/heads/<b>` → any ref (for example `refs/stash`, a
  snapshot of the work tree) was served at serving time and accepted at issuance
  (`show-ref --verify` follows it too). A peer cannot create these refs. They come from the
  grantor's repository or from its upstream.
- **Fix:** `GitBackend.BranchTip` runs `for-each-ref --count=1 --sort=refname
  --format=%(refname)%00%(objecttype)%00%(objectname)%00%(symref) refs/heads/<b>`. It
  accepts only an exact `refs/heads/<b>` that names a `commit` and has no symref target.
  for-each-ref never DWIMs, and its patterns match whole path components. Issuance uses
  the same function, replacing `show-ref`. A branch that points at a tag object is now
  `not_found`; `git branch` cannot create one. Tests: `TestGitBranchResolvesExactly`
  covers the tag, remote and `refs/refs` look-alikes, a symref, a tree-valued ref, a
  tag-valued ref and a prefix, for both serving and `BranchTip`. `TestGrantGitIssuanceExact`
  covers issuance. `TestGitEnvironmentAndArgv` now checks the new argv.

### M2: on Windows the 10 s timeout did not stop git (fixed)

- **Location:** `LookGit` (`internal/capability/git.go`).
- **Problem:** On Windows, `exec.LookPath("git")` usually finds Git for Windows'
  `cmd\git.exe`, a launcher that runs `mingw64\bin\git.exe` as a child.
  `exec.CommandContext` kills only the launcher. It was reproduced: after the launcher was
  killed, the child was still alive. A git call stuck on CPU or I/O therefore kept running
  after the timeout. It no longer counted against the 2-per-holder and 32-per-daemon
  in-flight limits, because those slots are freed when the Go call returns. The spec's
  "10 s timeout" did not hold on Windows. On Unix, `git` is the real binary. The served
  commands spawn no child (lazy fetch and every transport are off), so killing the one
  process is enough.
- **Fix:** On Windows, `LookGit` runs `git --exec-path` once at start and uses
  `<exec-path>\git.exe`, the real git, if it is a regular file. It was checked to run with
  a minimal PATH and to spawn no child. Otherwise it falls back to the LookPath result.
  A Job object was the alternative. It was not chosen: the launcher creates its child
  before Go could assign a job, so the child would escape it. Tests:
  `TestGitExecPathBinary` checks the helper through the fake git. On Windows it also
  checks that `LookGit` does not return the `cmd\` launcher. Spec: §Serving git.

## Low

### L1: issuance accepted a directory inside a bare repository (fixed)

- **Location:** `isGitTopLevel` (`internal/daemon/grant.go`).
- **Problem:** `rev-parse --is-bare-repository` run from `repo.git/objects` or
  `repo.git/refs` discovers `repo.git` and prints `true`, so the grant was issued. Serving
  then failed closed, because `GIT_CEILING_DIRECTORIES` stops discovery. The grant was
  useless and confusing, but it did not leak anything.
- **Fix:** The command is now `rev-parse --is-bare-repository --absolute-git-dir`, and the
  git dir, after resolving symlinks, must equal the resolved path.
  Test: `TestGrantGitIssuanceExact`.

### L2: the minimum Git version was not stated (documented)

`GIT_CONFIG_GLOBAL` needs Git ≥ 2.32. An older git ignores it and reads the grantor's own
`~/.gitconfig`: not hostile, and the `-c` overrides still win. `GIT_NO_LAZY_FETCH` needs
2.44. On older git, the `protocol.*.allow=never` overrides still block a promisor fetch.
`--end-of-options` is no longer used. grant.md now states Git ≥ 2.32. The version is not
enforced at start. That would take one more `git version` call and a parser; left for the
owner to decide.

### L3: repository config can still make git read other local paths (documented residual)

`include.path`, `objects/info/alternates`, a `.git` file (`gitdir:`) and `commondir` point
git at arbitrary paths. On Windows a UNC path opens an SMB connection, which can leak NTLM
credentials. No command-line switch turns these off. None of them runs code. A peer cannot
plant them: `git clone` does not copy config. The exposure is the same as the grantor
running any git command in that repository. It is documented in grant.md §Serving git.

### L4: `GIT_CEILING_DIRECTORIES` splits on `:` on Unix (noted)

If the repository's parent path contains `:`, git splits the ceiling into two entries,
neither of which matches the parent, so discovery could climb. This only matters if the
repository's `.git` has also vanished since issuance. Not fixed: git has no escape for the
separator.

### L5: every `list` page re-runs `ls-tree -l` over the whole directory (noted)

A 100 000-entry directory costs one full `ls-tree -l` per 1000-entry page. The per-grant
limits (2 in flight, 20/s) and the per-daemon limit (32) bound this. Caching per commit
would remove it; it is not a security issue.

### L6: repository metadata can change what the tip serves (noted)

A `commit-graph` stores each commit's root tree. A tampered one could map the tip to
another tree, and `info/grafts` rewrites parents (history is not served). Only someone
who can already write the grantor's `.git` can do this, and such a writer could move the
ref just as well. No peer path.

## Checked, no finding

- **Code execution or network from a hostile config:** `TestGitHostileConfigRunsNothing`
  covers fsmonitor, hooks (`core.hooksPath` and hook files), filters including `process`,
  diff/textconv/merge drivers, the pager, `sshCommand`, `askPass`,
  `alternateRefsCommand`, include/includeIf, `protocol.*.allow=always`, and a partial
  clone with an `ext::` promisor and a missing object. The test has a positive control.
  rev-parse is no longer used. `for-each-ref`, `ls-tree` and `cat-file blob` run no
  filter or textconv, and no pager, because stdout is not a TTY. `core.gitProxy`,
  `uploadpack` and credential helpers are transport-only, and every protocol, including
  unknown `x::` helpers, is `never`. `.gitattributes` in the tree and `info/attributes`
  have no effect on these commands. Replace refs are disabled by `GIT_NO_REPLACE_OBJECTS`.
- **Argument injection:** The branch has passed `checkBranch` (no leading `-`, no `~^:?*[\`,
  `..` or `@{`, and no space or control character), and the pattern starts with `refs/`. The
  commit and blob ids are checked as hex. Peer paths come only after `--`, with
  `GIT_LITERAL_PATHSPECS=1`.
- **Path matching:** Paths are matched as exact bytes. `.git` is refused in any case and
  with Cf characters stripped (`isGitName`), and `list` hides such entries. `..`, `.`,
  NUL, control characters and more than 1024 bytes are refused by `ValidScopePath` before
  the backend runs (`fetch.go` step 10). An intermediate symlink or submodule is not
  traversed.
- **Limits:** `ls-tree` output is capped at 32 MiB + 1 by a LimitReader, and entries at
  100 000. A blob is size-checked before `cat-file` and read through a LimitReader. git is
  killed when the read ends or an error occurs. `Wait` runs on every path, and `WaitDelay`
  (1 s) keeps a grandchild holding a pipe from hanging a worker.
- **Error text:** git's stderr is never captured (`cmd.Stderr` is nil; `Output`'s
  `ExitError.Stderr` is unused). Peers and the audit log get only fixed codes and messages.
- **The worker's resolved ambiguities** are sound and are now in grant.md §Serving git:
  the ceiling at the repository's parent, the `-c` overrides, `ls-tree -l`, a missing
  branch → `not_found` (true only after M1), an intermediate symlink or submodule →
  `not_found`, and `safe.directory` not overridden. The "issuance resolves git per call"
  residual stands. It is harmless, because issuance is human-driven.
