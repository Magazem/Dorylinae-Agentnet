# R-3.4: security review of human constraints (ticket 3.4)

Review (Opus) of `p3/debate-constraints` at 30c62f9 (3.4, on main 841979c), against
Docs/protocol/debate.md §Human constraints (authoritative), owner decision D30 (OD-P3-3:
approval-gated), review 43 H2/H3 and review 26 N1–N5. Scope: `internal/debate/constraint.go`,
the `applyClose`/`applyCloseOnB` split, `view.go` (Constraints), `internal/daemon/debate_constrain.go`
(IPC and approval Action), the `debate.constraint` mail kind, `approval.KindDebateConstraint`,
`cmd/agentnet/debate_constrain.go` (and the placeholder `debate.go`), the audit inventory.
Fixes were made in place, with tests.

**Verdict: pass after fixes.** Critical 0, High 2 (fixed), Medium 0, Low 7 (2 fixed, 5 noted).

## What holds

- **No constraint without a local approval.** `debate_constrain` only validates and returns a
  `debate_constraint` approval. The text and the id live in the Action closure. `Perform` is
  the only writer of a local constraint: row `active`, audit `debate.constraint {session,
  peer, id, approval}` and the outbox mail, all in the approval's transaction. A rejection,
  an expiry or a restart (every pending approval expires at start, the closure is gone) leaves
  nothing in the debate tables. `mail_submit` refuses `debate.constraint` (`debate.` is in
  `reservedKindPrefixes` and the kind is in `ownedKinds`), so an agent cannot send one by
  hand.
- **What makes B's constraint "human" on A's side.** Nothing A can check, and the spec says
  so: `applyConstraint` stores a received constraint with `author = other(r.role)`, which comes
  from `bodyRow` (the derived session must match `(from, to, request)`, and `r.peer ==
  msg.from`). It never comes from the body. A modified peer daemon can therefore add an
  unapproved constraint under **its own** side only, which is what §Human constraints, "What
  the record proves", promises. The Markdown caveat is 3.3a's.
- **Receipt checks before storage.** `strictBody`, `commonBody` (`at` in wire form, request and
  session ids), the `c-<32 hex>` id pattern and `ValidateConstraintText` all run before any
  row is read or written. Invisible text is `bad_body`. After that: unknown debate → ignored;
  `closing`/`closed`/`broken` → ignored `closed`; the same id again (including a peer that
  reuses one of our ids) → ignored `duplicate`, and nothing is overwritten; 20 stored →
  ignored `limit`; on A, 10 active → stored `excess` and ignored `limit`. An honest pair
  never reaches 20: each side's own ids are bounded by its 10-active check, and nothing ever
  leaves `active` before the close.
- **Limits and races.** SQLite serialises the approval transaction and the close, so a
  constraint confirmed after A's close fails its precondition (`closing`), and one confirmed
  before is listed. Both sides adding their 10th: A keeps B's as `excess` and does not list it,
  and B marks its own `late` when the close arrives (`TestConstraintBothTenth`).
- **H2 ordering.** B holds a close that lists an id it does not have (in `close_body`, phase
  unchanged) and re-applies it when a constraint arrives (`retryHeldClose`); B's own active
  constraints that the close does not list become `late`. The hold runs after `closeMatches`,
  so a fabricated outcome is still refused first.
- **Late vs excess.** `late` (B, own, unlisted) is shown to agents; `excess` (A, received over
  10) is never shown and never listed. This matches the spec.
- **No text outside the constraint tables.** The audit details are ids only, the
  `debate.constraint` event is content-free, and nothing is logged. The text does appear in
  the approval summary, as the spec requires. That puts it in `approvals.summary`, the
  approval notification and terminal-mode stderr (see L1).
- **Review 26.** N1: phase and count are checked in `Precondition`; `Perform` touches only
  `tx`, and the outbox wake is after commit. N2: `constrainError` maps to `ipc.Error`. N3: no
  callback into the Store. N4: the peer name is `Clean` plus `stripLongDigits`. N5: nothing is
  stored before `Create`, so there is nothing to undo.

**The worker's decisions.**
- (1) Nothing is stored before approval, and the text is held in the Action closure:
  accepted. approval.md §Object now lists `debate_constraint` and says it has no
  `pending_approval` row. debate.md's schema notes that `pending_approval` is unused.
- (2) The summary is the cleaned peer name, the session and `DisplayQuote(text)`: accepted,
  with H2's bound.
- (3) The receiver rules, and a missing listed id holding the close: accepted. See L2 for
  cancelled closes and L4 for a hold that never releases.

## High

### H1: graphic but invisible characters passed the visible-only check (fixed)

`internal/debate/text.go` `ValidateConstraintText`. The rule was "`unicode.IsGraphic` or
U+0020, and not `Cf`". `IsGraphic` is true for many characters that render as nothing:
- the variation selectors U+FE00–U+FE0F and U+E0100–U+E01EF. There are 256 of them, so each
  can carry one byte after any visible character;
- the other default-ignorable code points (U+034F, the Hangul fillers U+115F, U+1160, U+3164,
  U+FFA0, and more);
- every `Zs` space (U+00A0, U+2000–U+200A, U+3000);
- U+2800.

`DisplayQuote` escapes only runes that are not graphic or are `Cf`, so the approval window
shows none of these. A local agent could run `--constrain "No new dependency"` followed by up
to ~480 variation selectors that encode a hidden instruction. The human sees and approves "No
new dependency". The peer's agent reads the raw bytes, and the record calls them a human
decision. This is exactly what review 43 H3 set out to prevent.

**Fix.** A new `invisibleRune` refuses `Cf`, `unicode.Variation_Selector`,
`unicode.Other_Default_Ignorable_Code_Point`, `Zs` other than U+0020, and U+2800. The check
applies at `debate_constrain` (`bad_request`) and on receipt (`bad_body`). Combining marks
and other scripts are still allowed. debate.md §Human constraints, "Text" is updated.
*Tests:* `TestConstraintText` (the no-break-space case moves from ok to bad, and the new
cases are added) and `TestConstraintVisibleOnly` (the same cases at IPC and on receipt; a
combining mark and CJK pass).

### H2: the approval window cut the summary, so the human did not see the whole text (fixed)

`internal/notify/window.go` `windowText` cut every summary to 600 code points
(`maxWindowSummary`). The constraint summary is about 150 code points of wording, the session
and the peer, plus a text of up to 500 code points. `DisplayQuote` escapes `<`, `>` and `&` as
`<`, and so on, so the text can reach 3000 code points. Separately, the Windows window
drew the summary in a fixed 390×70 px Label, which shows roughly 300 characters and cuts the
rest silently. An agent could pad the first ~300 characters with a benign statement and put
the payload after them. The human approves without seeing it, which breaks the spec's "the
approval window shows … the constraint text in full" and the reason given for H3.

**Fix.**
- `notify.MaxWindowSummary` (exported) is now 4096. This fits the worst case: 500 × 6 plus
  the wording.
- The Windows window shows the summary in a read-only, word-wrapped, vertically scrolling
  multi-line TextBox (490×200, `TabStop` off, so focus stays in the code box). The code box
  and the buttons move down. The script was checked with the PowerShell parser.
- `debate_constrain` refuses (`bad_request`) any summary longer than `MaxWindowSummary`. This
  never happens with the current wording. It guards future changes to the wording or the
  bound.

*Test:* `TestConstraintSummaryFitsWindow` (500 × `<`, 40-code-point name: within the bound and
not changed by `Clean`). **Manual check needed:** the new Windows layout, and long summaries in
zenity/kdialog and macOS `display dialog`. They receive the text uncut now, but I could not
look at them here.

## Medium

## Low

### L1: the text persists in `approvals.summary` and in the approval notification (noted, spec text fixed)

The summary is stored in the approval row until `pruneDecided` removes it, even when the
approval is rejected. It is shown in the OS notification (desktop mode) or on daemon stderr
(terminal mode), and in `approval_list`. This is the approval design (local data), not a debate
table. The design note "nothing is stored before approval" holds for the debate tables only.
debate.md now says this.

### L2: a cancelled close was held for a missing constraint (fixed)

`applyCloseOnB` held any close that listed a missing id. A `cancelled` close has no Decision,
and `applyClose`'s own doc says it "ends B's mirror at once". Now only agreed and escalated
closes are held. *Test:* `TestConstraintCancelledCloseNotHeld`. debate.md "Ordering" is
updated.

### L3: decoy codes inside the constraint text (noted)

The text is local-agent input shown in full in the summary. In terminal mode a text like
`… Code 123456. Type "a-… 123456"` puts a decoy in front of the real code, and wrong codes
burn the 10-per-day budget (review 26 N4). Stripping digits would change what the human sees
against what is stored, which is worse. The quotes from `DisplayQuote` and "the real code is
always last" are the mitigation. Consider showing the code in the title in terminal mode too.

### L4: a close held for an id that never arrives (noted)

B cannot tell an A constraint still in flight from an id A made up, or from one B refused as
`bad_body` (for example after Unicode-table skew between Go versions). It holds until it
arrives, and B's abandon is the way out (decision.md §Signing). The hold is silent: nothing is
audited or shown. 3.1b/3.3a could show "waiting: constraints" in the view.

### L5: `approvalID` is read by Perform through a mutex, set after `Create` returns (noted)

This is the same pattern as `device_scope` and `release`. A confirm that lands between the
row insert and the assignment would store `approval = ""`. In practice a human cannot type the
code that fast. A test harness in terminal mode could.

### L6: display fidelity in the window (noted)

`notify.Clean` collapses runs of U+0020, so `a  b` shows as `a b`. `json.Marshal` shows `<`,
`>` and `&` as `<`, `>` and `&`. Neither can hide content. The second makes
the window harder to read. `DisplayQuote` is shared with review 40, so it is left unchanged.

### L7: the list view carries constraint texts (noted, for 3.1b)

`Store.List` loads full constraints. The spec's list view keeps counts only. No IPC method
exposes `List` in this build.

**Outside 3.4 (for the owner):** `device_scope` allows summaries of up to 16384 bytes
(`maxScopeSummary`, "must fit in the approval window"), but the window cut them to 600 code
points, and now to 4096. A long scope is still not shown in full. This needs its own ticket.
