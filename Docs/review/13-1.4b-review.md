## The `!bad_body` suffix on `mail_seen.received_at`

Accepted, and no migration is needed.

- **Nothing parses it.** The only readers of `mail_seen.received_at` in the codebase are
  `Receiver.store` (suffix check) and `Prune` (string `<`). No status, audit or metrics code
  reads the table. `mail_inbox.received_at` always gets the unmarked value.
- **Prune stays correct.** Both values are fixed-width `StoreTimeFmt`, so any two rows with
  different timestamps compare on the timestamp before the suffix. At an equal timestamp the
  marked row sorts higher, the same way `<` treats the unmarked one. `TestBadBodyRowPruned`
  now also checks that the row is kept 1 h before retention and pruned 1 h after.
- **14-day limit** is checked on `msg.created` before `store`, so it never reads the row.
  A resend older than 14 d is acked `unsupported` as `stale`, which gives the sender the same result.
- A typed column would be cleaner, but it costs a migration, and 8–12 are already assigned.
  I don't recommend one now. If a later ticket reads `received_at` as a time, fold a
  `bad_body INTEGER` column into that ticket's migration (see L2).

## Findings

### M1 (fixed): a concurrent delivery between the two transactions caused a double audit and could send the wrong ack

`storeBad` rolls back, then starts a new transaction with `INSERT OR IGNORE`. With
`SetMaxOpenConns(1)`, a waiting `Handle` for the same `(from, id)` can take the connection
in between. It then inserts its own row and calls `Apply` again. The loser's `INSERT OR
IGNORE` was ignored but still returned `seenBad`. The result was a second `mail.reject`
audit. If the other delivery had *accepted* the mail (an `Apply` that depends on state),
the receiver acked `unsupported` for a row stored as accepted. The daemon currently
calls `Handle` from one goroutine (`internal/daemon/mail.go:157`), so this is latent. It
would surface as soon as delivery is parallelised.

Fix (`receiver.go`): `storeBad` checks `RowsAffected`. If it is 0, the existing row decides
the outcome through the new shared helper `seenAs`, giving `seenDupBad` (no audit, ack
`unsupported`) or `seenDup` (ack `ids`). I added a test hook, `beforeBad`, next to the
existing `commit` hook.
Tests: `TestBadBodyRowRecordedInBetween` (marked and accepted sub-cases) and
`TestBadBodyParallelResends` (8 parallel deliveries → 1 marked row, 1 audit, 8
`unsupported` acks). I reverted the `RowsAffected` check, confirmed that both tests fail,
then restored it.

### Other checks (no finding)

- **Rollback discards partial writes.** `tx.Rollback()` runs before the new transaction,
  and the `Apply` insert is gone (`TestBadBodyPath`).
- **Not an oracle.** The ack body is byte-for-byte the same shape as for an unknown kind
  (`{"unsupported":[id]}`). The only difference is one extra local transaction, and only
  the peer that wrote the body can observe it (as review 12 notes).
- **Outbox.** `Outbox.OnAck` sets `unsupported` ids to `failed` / `unsupported_kind`, as
  request.md step 4 requires.
- **keys / ack.** `ack` returns before dedupe. `keys` goes through the same path, so a
  future `keys` `Apply` returning `ErrBadBody` would be marked and deduped. That is fine,
  because a key-miss reply has a new id each time.

### Lows (not fixed)

- **L1.** Marking is permanent for the id (for 35 d). `Apply` must return `ErrBadBody` only
  for failures that a resend of the *same* mail cannot cure. State-dependent refusals (for
  example team validation that depends on a pending join) should be ignores or plain
  errors. Flag this in the 1.1b / 1.4c reviews.
- **L2.** The suffix convention is documented only in a code comment. Add a sentence to
  mail.md §Schema so that future readers of `mail_seen.received_at` (such as 1.9
  metrics) strip it.
- **L3.** `Handle` returns `reject(11, bad_body)`. Step 11 is the `created` age check, so
  the step number is misleading. It is harmless because the daemon ignores the value.
- **L4.** The rate-limited `mail.reject` also writes an Info log line with the id and
  reason. That is consistent with other rejects and contains no content.
