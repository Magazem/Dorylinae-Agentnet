## 1. Summary

- **The rule (D64), now in [audit.md §When the row cannot be written](../protocol/audit.md#when-the-row-cannot-be-written-r55-f31-d64).**
  Every audit action belongs to one of four classes:
  - **S** grants access or trust. Its row is written with `AppendTx` in the action's
    transaction, so no row means no action.
  - **S-** removes access or trust. Its row is written in the same transaction through a
    savepoint, and the change commits even if the row fails (OD-F31-1).
  - **L** is the existing lifecycle tripwire: the daemon does not start without its row.
  - **N** is everything else: the failure is logged and the action reports success.

  All failures are logged once, centrally, by `internal/audit`.
- **The inventory (§3)** covers 66 `_ = …Append` lines, 14 `auditTx` sites and 21 sites that
  check the error, plus the wrapper callers, on current main. Today:
  - 11 S rows are written outside their action's transaction: 10 after the commit with the
    error ignored or only logged, and `team.invite_issued` returned after the fact;
  - 7 S inventory rows are already in a transaction (no change);
  - 7 sites return an audit error after their action committed (O-095 pattern), and all of
    them change.
- **The gaps:**
  - `ws.open` (R55-121);
  - daemon-caused `approval.reject` reasons (R55-123);
  - `grant.revoke` on session close and peer removal (R55-124);
  - `status.approval_window` and messages that name the fix (R55-125);
  - debate kinds in the inventory test (R55-135);
  - policy audit drift (R55-160);
  - `cancel_in.age_s` (R55-164);
  - `grant.fetch` flush at `Close` (R55-078);
  - no-content asserts over logs and webhook rows (R55-200).
- **The I2 sweep (§5)** covers the struct decodes after verification. One decode is
  converted, and the six that read stored, schema-checked bodies get a comment each.

## 2. Classes (short form; the normative text is audit.md)

| Class | Written | Row fails |
|---|---|---|
| S | `audit.AppendTx` in the change's transaction | The transaction rolls back and the action returns the error (`*audit.WriteError`) |
| S- | `audit.AppendTxSoft`: `SAVEPOINT audit_row`, insert, `ROLLBACK TO`/`RELEASE` on failure | Logged (`event=audit_error`), the change commits |
| L | Before the action, as today | The action does not run (unchanged) |
| N | `Log.Append` after the commit (or `AppendTxSoft` inside an open transaction) | Logged, success returned |

`audit.SetErrorLog(*slog.Logger)` is installed by `daemon.Run` before the first append. Both
`Log.Append` and `AppendTx`/`AppendTxSoft` log a failure there, with the action and the
driver error, never the detail.

## 6. Implementation plan

1. **`internal/audit`.**
   - `WriteError{Action, Err}` wraps every append error.
   - `SetErrorLog`.
   - `AppendTxSoft` (savepoint), and `TxLostError` when the transaction itself is gone; the
     S- callers' one retry without the row (audit.md, "What S- really guarantees").
   - Unit tests: a failing insert through a `TEMP` trigger; the savepoint keeps the outer tx
     usable; `RAISE(ROLLBACK)` gives `TxLostError`; the log line has the action and no detail.
2. **`daemon.Run`** calls `audit.SetErrorLog(logger)` before `daemon.start`.
3. **Approvals (#1–#12).**
   - Confirm's tx gains the row.
   - Expiry, attempts, lock and reject become small txs with `AppendTxSoft`.
   - Add `RejectFor`.
   - Coordinate with F27 on #4: F27 owns the attempts/daily-count transaction, and F31 only
     adds the row to it. Whichever ticket lands second rebases.
4. **Grants (#13–#25).**
   - Move the policy-path rows into their tx.
   - Revoke rows: the hooks return the revoked ids, and these are appended in the tx.
   - `policy_remove` becomes one tx.
   - Fetch `Close` flush, and the daemon's close order.
5. **Trust and teams (#26–#41).**
   - The `peers.Store.Remove` audit hook.
   - The `AddTrusted` `onAddedTx` hook.
   - `team.invite_issued` compensation.
   - `roster_apply` and GC `peer.remove` move into the `Apply` tx.
   - `team_remove` logs.
6. **Sessions, requests, decisions (#42–#52).**
   - `ws.release` moves into `Perform`.
   - `OpenSession` writes `ws.open`.
   - `request.submit` logs.
   - `cancel_in.age_s`.
   - The decision rows move into the debate transactions (`debate.Store` calls
     `audit.AppendTx` directly; its `Audit` sink stays for the N rows).
7. **Presence, mail, mailbox, session, reject summary (#57–#63).** Return nil and drop the
   local log lines.
8. **Status (R55-125).** `Check` per OS, the status fields, the `approvalError` message, and
   the `agentnet status` line.
9. **Sweep (§5).**
10. **Tests (§7).** `TestAuditClassification` goes in first, so every later step makes it pass.

Order: steps 1 and 2 first. Steps 3–8 are independent of each other. Expected size: about
25 files, about +600/−150 lines, plus tests.

## 7. Acceptance tests

- **T1 `TestAuditInventoryIsComplete` (R55-135).**
  - The source scan finds `debate.entry`, `debate.reveal`, `debate.close`,
    `debate.constraint` and `debate.sign`.

- **T2 `TestAuditInventory` updates.**
  - `request_accept` expects `request.accept` **and** `ws.open` on B, and the `request.accept`
    kind expects `ws.open` on A.
  - `ws_accept_result` with an active grant expects `grant.revoke {reason:
    "session_closed"}` on A **and** on B.
  - `peers_remove` of a peer with an active grant expects `grant.revoke {reason:
    "peer_removed"}`.
  - `grant_policy_remove` expects `{policy, peer, action}`.
  - The debate scenario expects the five kinds' rows.
- **T3 `TestAuditClassification` (new, `go/parser` AST scan, not regex; review 84b F10).**
  The test holds the class table (actions by string and by named constant) and a fixed list
  of wrappers (`m.audit`, `r.audit`, `s.audit` in `debate`, `audited`, `auditRemoved`,
  `auditLifecycle`, `createAudit`, `fetchAudit`, the `daemon` `auditTx`). For every call of
  `Append`, `AppendTx`, `AppendTxSoft` or a wrapper, it resolves the action argument (string
  literal or package constant). It fails when:
  - the action is not constant and the call is not inside a listed wrapper;
  - an S action is reached by anything but `AppendTx`;
  - an S- action is reached by anything but `AppendTxSoft`;
  - an N call is the init of an `if` whose body returns the call's error;
  - an action is in no class.

  It proves the call kind, not that the transaction is the change's own; T4 and T5 prove
  that.
- **T4 fault injection: a failing `AppendTx` aborts a security action.** Inject with
  `CREATE TEMP TRIGGER audit_fail BEFORE INSERT ON main.audit_events WHEN NEW.action = '<A>'
  BEGIN SELECT RAISE(ABORT, 'injected'); END` on the daemon's store connection. That needs no
  production hook; if the harness cannot reach the connection, add a `testhooks` equivalent.
  A `TEMP` trigger exists only on the connection that created it. The daemon's store has one
  connection (`SetMaxOpenConns(1)`), and `Log.Append` uses the same pool, so the trigger sees
  every production insert. Each case first asserts the trigger is still there (`SELECT 1 FROM
  sqlite_temp_master WHERE name = 'audit_fail'`), so a recycled connection cannot turn a
  case into a silent pass.
  Cases:
  1. `<A> = grant.issue`: approve a grant. Confirm fails `internal`, the grant stays
     `pending_approval`, there is no `grant` mail in the outbox, the approval is still
     `pending`, and there is no `approval.approve` row. Drop the trigger: the same code now
     approves it.
  2. `<A> = approval.approve` (with `grant.issue` allowed): same outcome as case 1.
  3. `<A> = grant.create`, policy path: `grant_create` fails, no active row, no mail.
  4. `<A> = peer.verify`: trust is unchanged after approval.
  5. `<A> = pair.complete`: the pairing fails `store_error` and no peer row exists on that
     side.
  6. `<A> = ws.release`: the session stays `quarantined` and no `ws.state` mail is queued.
  7. `<A> = decision.create`: the close fails and no `decisions` row exists.
  8. `<A> = team.invite_issued`: `team_invite` returns an error with no code. The pairing
     id is not returned, so the test reads it from the log instead: there is a `pair.fail
     {code: "cancelled"}` row, `pair_status` of that id is `failed`, and no
     `team.invite_issued` row exists. Redeeming is impossible because no code left the
     daemon.
  9. `<A> = team.roster_apply`: the roster is not applied and no introduced peer is stored.
- **T5 fault injection, S- (under OD-F31-1 (b)).**

## Implementation notes (code ticket, branch p4/r55-f31)

Where the code differs from, or adds to, what the spec says:

- **`audit.RunSoft(ctx, db, fn)`** is the S- helper. It runs `fn` in a transaction and, if an
  `AppendTxSoft` inside it returns `*audit.TxLostError`, runs `fn` once more in a new
  transaction in which every `AppendTxSoft` on that transaction is a no-op (so nested hooks,
  such as a peer removal's `OnRemovedTx` hooks, skip their rows too). It is used where the daemon
  owns the transaction: approval expiry, attempts, lock and reject, `ExpireStale`, `grant_revoke`,
  `grant_policy_remove` and `peers.Store.RemoveWith` (`peers_remove`). The S- rows that sit in
  someone else's transaction (the session-close revoke hook, the `grant.revoke` mail kind, the
  device unlink and scope-clear transactions, a team leave, B's `decision.refuse`) call
  `AppendTxSoft` directly: a row that fails by a statement error is skipped as specified, but a
  transaction-killing error there fails that operation instead of retrying it without the row.
- **`AuditSink` interfaces** of `approval`, `debate` and `worksession` gain `AppendTx` and
  `AppendTxSoft` (`*audit.Log` has both), so their fakes keep seeing every row. `team`, `peers`
  and the daemon call the `audit` package functions directly.
- **`approval.WindowRunner.Check`**, the cache and `UnavailableError` are in
  `approval/window_check.go`. `approval_unavailable` for a window reads "the approval window is
  unavailable: <fix>", or "the approval window could not be shown"; the notifier keeps its old text.
  The Windows CLM fact comes from the window process's stderr (`BlockedByPolicy`), never logged.
  That path has no test on a real Constrained Language Mode host.
- **T12:** `capability/fetch.go` still has one `json.Unmarshal`, of the peer's `fetch.req`
  plaintext, which is not data that passed `ParseStrict`. The source test therefore checks that the
  verified *token* is no longer decoded into a struct, not that the file has no decode at all.
- **`audit.SetErrorLog` is process-wide.** `daemon.Run` installs the daemon's logger, so with
  several daemons in one process (tests) the last one started owns it. The fault-injection tests
  install their own buffer after both daemons are up.
