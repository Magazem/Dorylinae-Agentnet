## Adversarial questions: result

| Question | Result |
|---|---|
| Can anyone other than the recipient send accept/decline/defer/complete/cancelled? | **No.** The mirror looks up only `(direction='out', peer = msg.from, id)`, where `msg.from` is the verified mail sender. A third party that sends a lifecycle mail for someone else's id finds no row, so the mail is audited `request.orphan` and changes nothing. |
| Can anyone other than the sender cancel? | **No.** `applyCancel` looks up `(direction='in', peer = msg.from, id)`. Tombstones are keyed by `(peer = msg.from, id)`. A third party's early cancel creates a tombstone only under its own key, so it cannot pre-cancel another sender's request. New test: `TestTombstonePrunedAfter31Days`, second half. |
| Can request ids collide across peers? | **No confusion found.** `in` rows are keyed by (peer, id). Local accept/decline/defer/complete by id alone returns `ambiguous_request` when several peers match. `findOutRow` by id alone is safe because `out` ids are generated locally. |
| Replay, reordering, stale seq | Handled. `mail_seen` dedupes the same mail. A resent copy is deduped by (from, id) plus `body_hash`. The mirror applies only `seq > state_seq`. Step 5 (cancel refused) also runs on an ignored seq, as the spec requires. |
| Tombstones as a DoS | The number of tombstones is bounded at 1000 per sender, and old ones are pruned inside the same transaction before counting. Early cancels send at most one reply each, so there is no amplification. See L3 and L5 for small deviations. |
| The refused-cancel race | Correct for both orders: accept first, then cancel is refused; cancel first, then accept gets `bad_state`. One liveness gap remains (L4). |
| Resend bounds, and resend after cancel | Resend needs `pending`, no `cancel`, the mail `expired` or `failed`, and an age under 21 d. New tests: `TestResendAfterExpiredIdempotent` and `TestResendTooOld`. |
| Result caps before storage and on receive | Enforced on both sides, except for M1, M2 and M3 below (all fixed). Every rejection on receive wraps `mail.ErrBadBody`, and every database failure is a retryable error. |
| Control characters in `request show` | C0 control characters and DEL are rejected everywhere, as the spec defines them. C1 control characters (U+0080–U+009F) are not rejected (L1). |
| Content in the audit | None. `request.complete` and `request.state` carry only `result_bytes`, `output_bytes` and `artifacts`, and no audit entry carries a reason. New test: `TestAuditHasNoResultContent`, which uses marker strings. |
| Database pool use inside a transaction or with a cursor open | None left. Every read inside `Apply` or `transition` goes through the transaction. `resubmitStale`, the audit writes and `ViewResult` run after commit. `List` drains its rows before `deliveryOf`. `findOutRow`/`findInRow` close their rows on return. |
| Migration 12 on an existing database | Correct. It is a plain `ALTER TABLE … ADD COLUMN result TEXT CHECK (…)`. Existing rows get NULL, which passes the CHECK, and the migration runs once in the migration transaction. |

## Medium (fixed)

**M1. The total cap on the complete body was checked with `seq = 1` and a timestamp taken
before the transaction.** Every defer raises `seq`, so a request that was deferred 9 or more
times sends `seq` with two or more digits. A result at exactly 65536 bytes with `seq = 1`
passed the check, and the real body was sent at 65537 bytes. The sender mirror rejects that
body as `bad_body`. It also rejects every echo of it, because the echo re-sends `last_reply`
unchanged. The sender therefore never learns of the completion, while the recipient shows
`completed`.
*Fix* (`internal/request/lifecycle.go`): `Complete` now builds `canonical(complete body)` and
checks the cap inside the transition's build step, using the real `seq` and `at`.
*Test:* `TestCompleteSizeCapUsesRealSeq` defers 10 times, then accepts. It checks that a
body of 65536 bytes with `seq = 1` (65537 on the wire) is `result_too_large` and the row
stays `accepted`. It then checks that a body of exactly 65536 bytes on the wire is accepted,
seals into one mail under `MaxMailPlaintext` (a ticket item that had no test before), and is
accepted by the mirror. This test fails on the original code.

**M2. IPC `request_complete` did not decode `result` strictly.** It was decoded into a Go
struct with `omitempty` string fields, so members the wire rejects were accepted or silently
dropped instead of returning `bad_request`:
- `artifacts: []` was dropped;
- `summary: ""` and `output: ""` were dropped;
- `null` members were accepted;
- unknown members were accepted.

The ticket asks for each of these to be rejected. It also asks for `result: null` to be
rejected, and it was accepted too.
*Fix* (`internal/daemon/request_lifecycle.go`): `result` is now taken as raw JSON and parsed
with `agentcard.ParseStrict` plus `request.DecodeResult`, the same decoder the wire uses. The
old `resultParam` type is removed.
*Test:* `TestLifecycleIPCRoundTrip` now checks five malformed results and `result: null`.
Each returns `bad_request` and no `request.complete` mail is sent.

**M3. On the wire, optional members present as `""` were accepted instead of rejected.**
request.md says optional members are "absent, never null or empty". The following were
accepted:
- `DecodeResult` accepted `summary: ""` and `output: ""`;
- the mirror accepted `note: ""` on `request.complete`, and `reason: ""` on a
  `request.decline` whose code is not `user`;
- `applyCancel` accepted `reason: ""`.

*Fix:*
- `internal/request/result.go`: `DecodeResult` rejects `summary: ""` and `output: ""`.
- `internal/request/mirror.go`: a new `decodeNonEmpty` rejects `note: ""` and `reason: ""`.
- `internal/request/cancel.go`: `applyCancel` also uses `decodeNonEmpty`.

All of these are rejected as `bad_body`.
*Test:* `TestEmptyOptionalMembersRejected`, which fails on the original code.

**M4. The lifecycle IPC result's `mail_id` was the original request's mail, not the
lifecycle mail just sent.** `request_accept`, `request_decline`, `request_defer` and
`request_complete` returned `v.MailID`, which is the id of the mail that carried the request
in, and the view already holds that id. A harness therefore could not follow delivery of its
answer.
*Fix:*
- `internal/request/view.go`: new field `View.ReplyMailID`.
- `internal/request/lifecycle.go`: `transition` sets `ReplyMailID` to the id returned by
  `SubmitTx`.
- `internal/daemon/request_lifecycle.go`: the handlers return `ReplyMailID` as `mail_id`.

*Test:* `TestLifecycleIPCRoundTrip` checks that `mail_id` is the `request.accept` outbox row
for accept, and the `request.complete` outbox row for complete.

**Test coverage of the ticket (part of the Medium fixes).** Several acceptance items had no
test. They are now covered in `internal/request/lifecycle_review_test.go`:

| Test | Covers |
|---|---|
| `TestLifecycleRefusedMatrix` | Every refused transition across all 6 states × 4 actions. It checks `bad_state` names the state and nothing changes. The old test had only 5 pairs. |
| `TestResendAfterExpiredIdempotent` | D10. The recipient re-sends the last answer, and the mirror applies it once. |
| `TestResendTooOld` | 21 d → `bad_state`; 20 d → ok. |
| `TestCancelIdempotency` | A cancel in flight gives a duplicate and only one mail. After the cancel mail expires, a new one is sent. A cancel after `cancelled` is a duplicate. On the recipient, a duplicate cancel changes nothing, and accept of a `cancelled` row is `bad_state`. |
| `TestTombstonePrunedAfter31Days` | Pruning with a fake clock, and the per-sender tombstone key. |
| `TestRefusedCancelEchoKeepsResult` | The echo carries the stored result. The mirror sets `cancel = refused` and keeps its result. |
| `TestAuditHasNoResultContent` | No result content in any audit entry, using marker strings. |

Still covered only at unit level, not end to end: the cancel race across two daemons, and
the budget item. The budget item is ticket 1.7: the urgency budgets do not exist yet.

## Low (not fixed)

- **L1.** C1 control characters (U+0080–U+009F) and bidi controls pass validation of
  `summary`, `output`, `note`, `reason` and `title`. `request show` prints them raw. This
  matches request.md's definition of control characters (U+0000–U+001F and U+007F). However,
  notify.md already strips U+007F–U+009F and the bidi controls, so the two documents
  disagree. Recommendation: sanitize peer strings in the CLI text output (1.6b owns
  `inbox` and `show` printing), or widen the spec's definition.
- **L2.** The mirror does not check that `at ≤ msg.created` for the five lifecycle kinds
  (`applyCancel` does check it). A recipient can therefore set a future `state_at`. This is
  cosmetic, because the recipient is authoritative.
- **L3.** An early cancel for an id that already has a tombstone runs `INSERT OR REPLACE`.
  This refreshes `received_at`, which extends the tombstone's 31 d life, and sends another
  `request.cancelled`. At the 1000 cap, even a repeat cancel of an existing tombstone is
  dropped without a reply. The spec says to insert and reply only "if no tombstone
  exists". Both effects are bounded and harmless.
- **L4.** Liveness gap in the refused-cancel path. Suppose the cancel reaches the recipient
  within 10 min of its accept, so the echo is throttled, and that accept mail later expires.
  The sender then stays `pending` with `cancel = requested`. Because the cancel mail is
  `delivered`, every later `request cancel` returns `duplicate: true`, and `resend` is
  refused. Only a lost 14-day mail causes this. A possible remedy is to always echo on a
  refused cancel (ignore the throttle).
- **L5.** Tombstones are pruned only on the early-cancel path, so stale rows stay until the
  next early cancel. The counts are still right. `consumeTombstone` does not check the
  tombstone's age, but that is unreachable in practice.
- **L6.** Entries in `pendingMirror`, `pendingCancel` and `pendingApply` leak if the commit
  fails after `Apply` has stored them. This pattern predates 1.6a (1.4c). The leak is small.
- **L7.** `itoa64` negates its input, which overflows for MinInt64. It is only reached after
  `ValidateComplete`, so it is safe today. `strconv.FormatInt` would remove the risk.
- **L8.** `request_list` and `request_show` do not include `presence`, although ipc.md says
  "`out` views also carry presence". This is the implementer's stated choice and should be
  recorded as a known deviation or scheduled. `printRequestShow` indents only the first line
  of a multi-line output.
- **L9.** `request_defer` parses `until` against `time.Now()` rather than the store clock.
  This matters only to tests that use a fake clock.

The implementer's other stated choices are acceptable:
- a decline reason allows no control characters, while a cancel reason allows `\n`;
- notification hooks are deferred to 1.8a, with audit only for now;
- the fix for the deadlock with an open cursor is to drain the rows first.
