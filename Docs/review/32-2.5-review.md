# R-2.5: security review of consult (ticket 2.5)

Light review (Opus) of commit 734ff92 on `p2/consult`, against Docs/protocol/consult.md,
request.md and work-session.md. Fixes were made in place, with tests.

**Verdict: pass after fixes.** Critical 0, High 0, Medium 1 (fixed), Low 4 (3 fixed, 1 noted).

## Medium

### M1: `request_show s-…` scans every request and then loses the peer binding (fixed)

- **Location:** `internal/daemon/consult.go` `requestIDForSession`; `request_show` in
  `internal/daemon/request_lifecycle.go`; `findAnswerable`.
- **Problem:** (a) Cost: the lookup called `rs.List` and `rs.InboxList` with no filter. That
  decodes every stored request body, which can be up to 320 KiB for a consult, and runs a
  delivery query for each out row. `agentnet wait s-…` repeats this every second for up to
  an hour until the peer answers. The work grows with every request ever stored, and peers
  can add rows (within the Phase 1 rate limits). (b) Binding: the scan matched one exact row,
  `(direction, peer, id)`, but kept only the id. It then called `rs.Show(id, "")`, which
  prefers any out row with that id and otherwise does an unbound in lookup. A peer that
  reuses an id (ids are chosen by the sender) could make `request_show` / `wait` on a session
  id show another request. It could also make `findAnswerable` pick a different row from
  the one the session id names. The in-tx state checks in `AcceptInTx` still held, so this
  gave no wrong-peer answer. It was a confusion and cost issue, not an authority bypass.
- **Fix:** New `request.Store.FindKey` reads only the `direction, peer, id` columns, and
  `ShowKey` returns exactly that row (`internal/request/query.go`).
  `requestKeyForSession` replaces `requestIDForSession`. `request_show` and `findAnswerable`
  now use the exact key, and `findAnswerable` returns "normal flow" at once for an out key.
  Test: `TestShowKeyExactRow` (internal/request/consult_test.go).

## Low

### L1: C1 control characters allowed in context names and text (fixed)
- **Location:** `internal/request/validate.go` `validateContext`; CLI `readContextFile`.
- **Problem:** `hasControl` covers only C0 and DEL. U+009B (CSI) and the other C1 controls
  passed, although the spec says "no control characters". `agentnet request show` prints
  context names to the terminal, where some emulators treat CSI like `ESC [`.
- **Fix:** New `hasC1` check, for context names and text only (the Phase 1 fields are
  unchanged). The CLI now refuses C1 as "not text". Tests were extended in
  `TestContextFileNames` and `TestReadContextFile`.

### L2: CLI reads non-regular files (fixed)
- **Location:** `cmd/agentnet/consult.go` `readContextFile`.
- **Problem:** A FIFO blocked the CLI forever. The read was already bounded, so a device such
  as `/dev/zero` could not use unbounded memory. Symlinks are followed, which is fine: the
  path comes from the user, and only the base name of the path given is sent.
- **Fix:** After `Open`, refuse anything whose `Stat` is not a regular file. Test: a
  directory is refused.

### L3: The default title keeps a tab (fixed)
- **Location:** `consultTitle`.
- **Problem:** Titles allow no control characters. If the first line of the question
  contained a tab, `consult` failed with `bad_request` unless `--title` was given.
- **Fix:** Tabs become spaces. Test in `TestConsultTitle`.

### L4: Duplicate context file names are accepted (noted, not changed)
The spec does not forbid them, and names are informational only (the receiver never writes
files with them). Bidi or format characters (e.g. U+202E) in names can still spoof what a
name looks like in human output, as they already can in titles. Consider a spec rule for
names in Phase 3.

## Checked, no finding

- **Caps on submit vs receive:** the daemon turns CRLF into LF before `Validate`, the size
  cap and the `params_hash`. The receiver refuses any `\r`, so both sides count the same
  bytes. UTF-8 validity, the 1–8 file count, name and text sizes, `.`/`..`/`/`/`\`/NUL, the
  question-only rule, strict members and the empty array are all checked on both paths.
  `MaxQuestionBody` applies only to a question with context.
- **Leaks:** audit entries (`request.submit`, `request.in`) record only counts and sizes.
  Notifications and webhooks carry title, type, peer, state and ids (`request.NotifyInfo`),
  never the brief or context. `inbox_list` / `request_list` carry counts only. The context
  text appears only in `request_show`. The session view shows only the request's type and
  title.
- **One-step answer:** `AnswerQuestion` runs accept, session open and result in one
  transaction. It re-checks the state inside the transaction (pending/deferred) and the
  type (question only). Double answers and a cancel or decline arriving concurrently
  therefore fail with `bad_state`. Declined or cancelled questions fall through to the
  normal flow (`unknown_session`). Out requests are never answerable. The status defaults
  to `n/a` only for this path.
- **D18/quarantine:** the accept issues no grants, so a consult session starts with none.
  Quarantine applies as usual if a grant is issued later.
- **params_hash** includes the normalised context (name and text), so reusing an
  idempotency key with different context is refused.
