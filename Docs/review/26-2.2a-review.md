## Medium (fixed)

**M1. Expired approvals never left memory, so 5 unanswered approvals locked approvals until
a restart.** `Store.pending` lost an entry only in `Confirm`, `Reject` or the lock. An approval
that simply lapsed:
- stayed counted in `len(s.pending) >= MaxPending`, so after 5 lapsed approvals every `Create`
  returned `approval_limit` until the daemon restarted. A looping agent, or a human who ignores
  5 toasts, blocks all approvals permanently.
- stayed `pending` in SQLite and in `approval_list` after its expiry.
- was never audited `approval.reject {reason: "expired"}`, and its notification was never
  withdrawn, although approval.md requires removal "when the approval is decided or expires".

*Fix* (`internal/approval/store.go`): `sweepExpiredLocked` runs under the lock in `Create`
(before the limit check) and in `List`. It marks lapsed entries expired (audited), withdraws
the notification and forgets them. `Confirm`'s own expiry path now withdraws the notification
too.
*Test:* `TestExpiredPendingFreesSlotAndLeavesList` (fails on the old code).

**M2. A guess could still be tried after the 10th wrong code.** `Confirm` recorded the 10th
wrong code, **released `s.mu`**, and only then called `lockAll`, which took the lock again to
drop the other pending approvals. A `Confirm` already queued on the mutex (from another IPC
connection) could win it in between and test a code against another pending approval, and
succeed. Each extra try is an 11th guess beyond the budget of 10 per 24 h (approval.md
§Object).
*Fix:* every pending entry is dropped (`dropAllLocked`) inside the same critical section
that records the 10th wrong code. The rows are then rejected, audited and a notice is shown
outside the lock (`lockAll(ctx, ids)`).
*Test:* `TestLockoutLeavesNoWindowForAnotherGuess` queues a `Confirm` with the correct code for
a second approval while the 10th wrong code holds the lock, and asserts `unknown_approval`,
no perform and state `rejected`. Go's mutex usually lets the unlocking goroutine win, so on the
old code this test does not fail reliably. It pins the new guarantee. `TestLockoutEndsWhenWindowHasRoom`
covers the end of the 24 h window.

**M3. Linux approval body was not escaped as markup.** The freedesktop body may be rendered
as markup. `showDesktop` escapes `& < >` for this reason, but the new `showApproval` passed the
body raw. The summary carries peer-controlled text (the peer's name). With markup such as
`<span size="1">`, an unclosed tag or a fake `Code 000000` in bold, that text can hide the real
code or show a decoy. The human then types wrong codes, so a **remote peer** can burn the
10-per-day budget and lock approvals for 24 h, or mislead the human about what is being
approved.
*Fix* (`internal/notify/approval_linux.go`): `escapeMarkup(body)`. Windows already used
`SecurityElement.Escape`, and macOS `display notification` is plain text.
*Test:* `TestShowApprovalEscapesMarkup` (Linux; compiled with `GOOS=linux go vet`). A decoy
without markup is still possible; see N4.

**M4. Acceptance gap: no test for code material in every table, the log or the IPC
results.** Ticket 2.2a requires a search of "every table for the code string and for any 64-hex
value computable from it", and checks that the code is in no IPC result and no daemon log
line. The existing test only formatted one `View`.
*Added:* `TestNoCodeMaterialAnywhereInDatabase` covers create, a wrong code, confirm and reject. It
dumps every column of every table and every audit detail, then searches for the code as a
delimited token, for SHA-256 of code, id‖code, id\ncode and both domain-separated forms, and
for the real `code_mac`. `TestApprovalCodeNeverInIPCResultOrLog` runs a real daemon with a
captured debug logger, calls list, a wrong confirm and the right confirm, and searches every
IPC result and log line. Both pass. The code is clean.

## Notes for callers (2.2c, 2.4, 2.D1)

- **N1. Put every state check in `Precondition`, not in `Perform`.** A `Precondition` error
  rejects the approval and drops the waiting action. A `Perform` error rolls back and leaves the
  approval **pending** with the waiting row intact, so the same code can be retried. `Perform`
  must touch only `tx`. Mail goes through outbox rows inserted in `tx`, with no relay sends,
  notifier calls or file writes, because the commit can still fail after it.
- **N2.** Return an `*ipc.Error` (for example `bad_state`) from the hooks. Any other error
  reaches the client as `internal error`. That is safe, but it is not the spec's error code.
- **N3.** The hooks run while holding `approval.Store.mu`. They must be quick and must never
  call back into the Store (that would deadlock).
- **N4. Summaries.** Pass peer-supplied text through `notify.Clean` with a length cap, as
  approval.md §Flow says. Even with markup escaped, a peer name such as `bob? Code 123456` puts
  a decoy code in front of the real one (the real code is always last). Spec suggestion: strip
  digit runs of 6 or more from peer text in summaries, or show the code in the title.
- **N5.** Create the waiting row and the approval in one order and undo on failure. If
  `Create` fails (`approval_limit`, `approval_locked`, `approval_unavailable`) after the row was
  inserted as `pending_approval`, the caller must drop the row.
