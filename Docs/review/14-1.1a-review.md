# Review 14: ticket 1.1a (peers trust `team`, `introduced_by`, migration 8)

Reviewer: R-1.1a (Opus). Worktree `AgentNet-wt/t1-1a`, branch `p1/t1-1a` at `da9b4d3`.
Spec: [11-phase1-tickets.md §1.1a](11-phase1-tickets.md), [team.md §Introduced peers](../protocol/team.md#introduced-peers),
[12-phase1-spec-review.md](12-phase1-spec-review.md), HANDOFF §3.

**Verdict: APPROVE.** 0 Critical, 0 High, 0 Medium, 1 Low fixed, 7 Low listed.

## What was checked

**Migration 8 (`internal/store/store.go`).**
- It runs as one transaction. `apply` runs the whole SQL text and the `migrations` insert in a
  single `BeginTx`/`Commit`, and modernc runs every statement of a multi-statement `Exec`
  (migration 1 already relies on this). A crash or error mid-migration rolls back to version 7
  with the old `peers` intact. `peers_new` cannot survive, and the next start retries.
- Nothing is lost. The column lists are explicit on both sides, so this is not a positional
  `SELECT *` copy. `peers` had no indexes other than the PK autoindex, and no triggers, views
  or FKs (checked against migrations 1–7), so the DROP/RENAME cannot cascade.
  `foreign_keys(1)` is harmless because nothing references `peers`.
- The CHECK accepts exactly `relay|team|code|fingerprint`. The DEFAULTs and `json_valid`
  checks are the same as in migrations 2/3.
- It works on DBs from every earlier version. Migrations are applied in order, so a v2 DB gets
  3 (trust, mailbox_keys) before 8. `TestMigrationAddsPeerTrust` exercises 2→8 and
  `TestMigration8PreservesPeers` exercises 7→8.

**Trust never lowers.**
- `AddTrusted`: the ON CONFLICT rank CASE keeps the higher value.
- `SetTrust`: the rank CASE never lowers.
- `Introduce`: it never writes `trust` on a known key.
- Migration: it copies `trust` verbatim.

An invariant follows: `introduced_by` not NULL ⇒ `trust = team`. Only `Introduce` inserts with
a non-NULL `introduced_by`, and every raise clears it: `AddTrusted` always does, and `SetTrust`
does for code/fingerprint.

**Introductions never overwrite a direct peer.** A known key with NULL `introduced_by` only
gets `mailbox_keys` merged. Name, card and trust stay unchanged
(`TestIntroduceKeepsDirectlyPairedPeer`, and the new `TestIntroduceKeepsDirectRelayPeer`).

**GC.**
- It selects only `introduced_by IS NOT NULL`, so a directly paired peer can never be
  selected.
- Delete and outbox fail run through `removeTx` inside the caller's tx, the same code as
  `peers remove`. An error leaves the caller to roll back, so nothing is half-applied.
- Only `queued`/`relayed` rows become `failed`/`unpaired` (`TestGCIntroducedSemantics`).
- Audit is left to the caller, as documented.

**Mail/session acceptance.** "Paired" means a `peers` row exists (`daemon/mail.go` `isPaired`),
so `team` peers are accepted for mail and sessions. That matches team.md (D5 accepts `team`).
No code branches on trust values yet. D5 lands in 1.4c.

**Output.** The `peers` IPC result and `peers --json` gain `introduced_by`, and the human
table gets an `INTRODUCED BY` column. `pair` results build `Peer` with nil `IntroducedBy`,
which is correct because a direct pairing clears it.

## Fixed

- **L-F1 (hardening, `internal/peers/store.go` GCIntroduced).** The "team tables absent"
  fallback selected **every** introduced peer whenever the count of `teams`/`team_members`
  was not 2. So a schema with only one of the two tables would have mass-deleted introduced
  peers. That state is not reachable today, because migration 9 is atomic. GC now fails with
  exactly one table and removes nothing, and keeps the implementer's behaviour for 0 tables.
  Test: `TestGCIntroducedPartialTeamSchemaFails`.
- Test strengthening: `TestMigration8PreservesPeers` now compares all columns of **every** row
  (k1 relay, k2 code, k3 fingerprint). Before, it compared only k3 and counted the rest.

## Low (not fixed)

1. **Ordering note for 1.1b.** Once migration 9 exists, GC treats an introduced peer without an
   `active` `team_members` row as garbage. Roster apply must write `teams`/`team_members`
   **before** calling `GCIntroduced` in the same tx, or it will delete the peers it just
   introduced. The 0-table fallback cannot cause mass deletion after migration 9, because
   the tables then exist and the real query runs.
2. **v1 re-pair of an introduced peer** clears `introduced_by` (ticket: "a direct pairing
   clears") but keeps `trust = team` (never lower). The result is a permanent `team` peer with
   no introducer that GC never collects. This resolves review 12 L14 in the user's favour, but
   `team` then no longer means "introduced". Consider documenting it in cli/peers.md.
3. **Directly paired `relay` peer listed in a roster** stays `relay`, so D5 will refuse it,
   while an unknown key in the same roster gets `team`. This follows the spec ("trust
   unchanged"). Flag it for 1.4c/UX.
4. **L6 (two introducers).** The implementer chose to keep the first `introduced_by` but
   refresh the card from **any** owner's roster. So owner B can replay an older self-signed
   card of a member first introduced by A. The card is authentic, just stale. Consider
   refreshing only when `introduced_by = owner`, and recording the choice in team.md.
5. **`SetTrust` accepts any string.** `team` would raise a relay peer to `team` with no
   introducer, and an unknown value is a silent no-op that returns nil. The only caller passes
   `fingerprint`. Consider restricting it to `code|fingerprint`.
6. **`Introduce` does not reject `key == self`.** The peers store does not know the local key.
   1.1b must skip self before calling it (team.md "not self").
7. **`introduced_by` can outlive its owner.** After `peers remove` of the introducing owner, a
   member still kept by another active team shows a dangling `introduced_by`. This is display
   only. 1.1b's owner-removal hook (M3) runs GC.
