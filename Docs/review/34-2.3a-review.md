# R-2.3a: security review of the fetch server and `fs` serving (ticket 2.3a)

Opus review of commit 282bc62 on `p2/fetch-fs`, against Docs/protocol/grant.md (§Transport,
§Revocation, §Paths, §Serving fs, §Limits, §Audit, §Threat model), session.md and the 2.3a
acceptance list in 23-phase2-tickets.md (reviews 24 M3/M4/L14 and 25 L9 applied). Fixes were
made in place, with tests. (Number 33 was taken by 33-pairtag-flake.md.)

**Verdict: pass after fixes.** Critical 0, High 0, Medium 3 (fixed), Low 6 (2 fixed, 4 noted).

What holds up: every path goes through `os.Root`. Each component is checked with `Lstat`
(symlink or `ModeIrregular` → `symlink`), and the open handle is checked with `SameFile` +
`IsRegular`, so a swap between the check and the open is caught. The grammar blocks `..`,
`\`, `:` (drive letters, UNC paths, ADS), device names, trailing dots and spaces, and
C0/C1/bidi characters. `.git` is refused in any case and with ignorable characters, 8.3
shapes are refused on Windows, and `O_NONBLOCK` keeps FIFOs from blocking. The token is
verified from scratch on every message, with aud = the Noise identity, the issued-direction
row, a byte comparison of the canonical token, and revoked/expired/session-open checks. The
row is rechecked before every fragment. Error texts are codes only (`FetchCode`,
`mapOSErr`). Handlers run with `m.mu` released, `Handle` only queues, and `SendData` follows
the documented sendMu → mu lock order and never starts a handshake. The worker pool stops
cleanly on Close. The session.md and grant.md doc edits (new codes `io_error`/`unsupported`,
list byte cap, CONIN$/CONOUT$/superscript digits, C1/bidi) are sound.

## Medium

### M1: a peer without a grant could fill the global `req` dedupe store and refuse everyone's fetches (fixed)

- **Location:** `internal/capability/fetch.go` `serve` / `markSeen`.
- **Problem:** `markSeen` ran before `authorize`, over one map for all peers, with a cap of
  8192 entries. When the map was full it refused new requests with `stale`. Any paired peer
  with an open Noise session could send about 13 requests per second, each with a fresh
  `req` and a garbage token. It needed no grant. For the 11-minute window this made every
  other holder's fetches fail `stale`: a cross-peer denial of service.
- **Fix:** Dedupe now runs after steps 1–9 pass, so only a holder of a valid grant adds
  entries. The store is per peer (`map[peer]map[req]`, cap `maxSeenPerPeer` = 16384, pruned
  in `Flush`), so a flood refuses only the flooding peer. A replay still fails `stale` (the
  token is still valid). grant.md §Transport documents this. Test:
  `TestFetchDedupeOnlyAfterAuthAndPerPeer`.

### M2: the peer-supplied `op` string was written into the grantor's audit log (fixed)

- **Location:** `fetch.go` `auditOp`.
- **Problem:** `grant.fetch` rows recorded `j.req.Op` exactly as sent. The value is used even
  when the op is unknown, which yields `malformed` and is still audited under the peer's
  key. A peer could write arbitrary text of up to about 60 KiB into 60 audit rows per minute.
  §Audit allows only ids, enums and sizes. This allows log injection and misleading rows,
  and costs about 5 GB of audit rows per day per peer.
- **Fix:** Only `stat`/`list`/`read` are recorded; anything else is recorded as `"unknown"`.
  Test: `TestFetchAuditOpIsEnum`.

### M3: over-limit requests queued an unbounded number of `rate_limited` answers in the shared queue (fixed)

- **Location:** `fetch.go` `Handle`.
- **Problem:** A peer over its 2 in-flight slots got a reject job queued for every further
  request. The job queue (256) and the 8 workers are shared by all peers. When the queue was
  full, other peers' real requests were dropped without an answer. A single flooding peer
  could keep the queue full and keep the workers busy sending its rejects.
- **Fix:** A peer can have at most `maxRejectsPerPeer` = 2 queued rejects. Further requests
  are dropped without an answer: the client retries after 10 s. The counter is released
  after the answer, or when the queue is full (`release`). Test:
  `TestFetchRejectFloodBounded`.

## Low

### L1: the list byte cap estimated JSON size and ignored escaping (fixed)
- **Location:** `internal/capability/fs.go` `List`.
- **Problem:** The size estimate was `len(name)*2+48`, but JSON escapes `&`, `<`, `>` and
  control characters to 6 bytes each. For a directory whose names are heavy in `&`, the
  response exceeded the 65535-byte Noise plaintext. The send then failed with `io_error`
  every time, and the directory could never be listed.
- **Fix:** Each entry is measured with `json.Marshal`. The test harness now fails any
  `fetch.resp` over 65535 bytes. Test: `TestFetchListEscapedNamesFit`.

### L2: `.git` check relied on Unicode case folding only (fixed, hardening)
- **Location:** `fs.go` `isGitName`.
- **Problem:** `strings.EqualFold` does not fold U+0131 `ı` to `i`, but `unicode.ToUpper('ı')`
  is `I`. NTFS compares names through an upcase table built from upper-case mappings, so
  `.gıt` may reach `.git` there. This was not verified on a live volume; the check is cheap.
- **Fix:** The name is also upper-cased rune by rune and compared with `.GIT`. Test cases were
  added to `TestGitNameAndShortName`.

### L3: the 24 h byte budget can be exceeded by the reads in flight (noted)
- **Location:** `fetch.go` `admit` / `addServed`.
- **Problem:** The budget is checked when a request is admitted and counted per fragment
  sent. Two concurrent reads that start just under the budget can each exceed it by up to
  256 KiB. The overshoot is bounded (≤ 512 KiB against 256 MiB). No change.

### L4: `Close` can wait up to about `opBudget` for sends in flight (noted)
- **Location:** `fetch.go` `Close` / `run`.
- **Problem:** `Close` waits for running jobs, and each job can make up to 8 sends of up to
  `sendBudget` each within its 1-minute context. At daemon shutdown the relay stops later
  than the fetch server (deferred in reverse order), so sends normally fail fast. A stuck
  relay write could delay shutdown by up to a minute. It could be fixed by deriving the job
  context from a context that `Close` cancels. Left for 2.3c, which touches shutdown.

### L5: `list` reads entry types by path, not from the opened directory handle (noted)
- **Location:** `fs.go` `List` (`root.Lstat(segs + name)` per entry).
- **Problem:** The directory handle is checked with `SameFile`, but the per-entry `Lstat`
  resolves the path again. A **local** process that swaps an intermediate directory during
  the listing could make it report the type and size of another entry inside the root. It
  cannot escape the root and never serves content. A remote peer cannot cause this. No
  change.

### L6: newer Microsoft docs also list `COM0`/`LPT0` as reserved (noted)
- **Location:** `internal/capability/token.go` `isWindowsReserved`; grant.md §Paths.
- **Problem:** The grammar accepts `COM0`/`LPT0` (`TestPathGrammar` has `LPT0` as valid).
  Current Windows versions do not map these names to devices, and `os.Root` opens them as
  files, so there is no escape. A grammar change would also change the test vectors. It is
  left for the owner to decide with the next vector revision.

## Files changed

- `internal/capability/fetch.go`: per-peer, post-auth dedupe (M1); audit op enum (M2);
  reject cap and `release` (M3).
- `internal/capability/fs.go`: exact list size (L1); `isGitName` upper-case check (L2).
- `internal/capability/fetch_test.go`: 65535-byte guard in the harness; 4 new tests;
  `ı` cases.

  the `req` pattern.
