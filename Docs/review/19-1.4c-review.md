## Post-rebase failure: `TestRequestOfflineQueued` (decided and fixed)

**Root cause (High, a 1.2c wiring bug, not a test problem).** In `startRelay`
(`internal/daemon/daemon.go`), the relay client's context came from the daemon `ctx`. On a
graceful stop `ctx` is cancelled first, so the relay connection closed **before** the deferred
`presenceSender.Goodbye` ran. The goodbye never reached peers. A then kept showing B online for
the full 2.5 × interval (75 s) window. This breaks presence.md ("Graceful stop … A shows it
offline at once"). A probe test confirmed it: after `b.stop()`, A's `presence_peers` row
stayed `online`. With the fix it turns `offline` at once.

**Decision.** request.md §Offline says `daemon_online: false` "with B stopped". presence.md
defines the behaviour for each kind of stop:
- **Graceful stop:** a goodbye is sent, so the peer shows offline at once.
- **Crash:** the peer shows online for up to 75 s.

The test stops B gracefully, so `false` is correct. The fix is in the wiring. The test is not
weakened.

**Fix:**
- `daemon.go`: the relay client now runs on `context.WithCancel(context.WithoutCancel(ctx))`,
  so only `stopRelay` closes it.
- `request_test.go`: the test now waits for A to hear B online, then for A to store B's goodbye.
  The < 2 s timer still wraps only the `request_submit` call. The test also asserts that
  `last_seen` is non-null and that exactly one undelivered (`queued`/`relayed`) request mail
  exists. Without the daemon fix, this test fails at "A to store B's goodbye".
- The crash path (no goodbye) still shows online for up to 75 s, as specified. It is not tested
  here.

**Second-pass check of the ordering.** Deferred calls in `RunWithOptions` run last-in,
first-out: first the goodbye (1 s bound, on `WithoutCancel`), then the presence sender stops,
then the outbox, then `stopRelay` (cancel, wait, `stopMail`). So the goodbye always runs on a
live connection, and the relay client cannot outlive the daemon. The change touches only
shutdown. `request_submit` still never waits for the relay (`insertOut` is one local
transaction), so the < 2 s `queued` guarantee holds.

## Checked with no finding

- **D5 host decision.** `relayIsNonLoopback` fails closed for unparseable or hostless input,
  `localhost.evil.com`, `127.0.0.1.nip.io`, and userinfo tricks (`ws://127.0.0.1@evil.com`).
  It is decided once at start from `opts.RelayURL`, and the same boolean drives both the submit
  refusal and the receive auto-decline. It is table-tested.
- **Idempotency (D10).** On the wire it is keyed per `(peer, id)` (primary key
  `(direction, peer, id)`). The same id from two senders gives two rows. A different body
  under the same id keeps the first row and audits `request.conflict`. A duplicate at 31 d is
  still recognised, and an unknown request older than 30 d is `bad_body`, so a 14-day mail
  replay of an old request cannot surface as new. The client key is scoped per peer by the
  partial unique index `requests_idem`. A lost race re-reads the winner and answers
  `duplicate` or `idempotency_conflict`. Tested, including concurrency.
- **Tx-scoped lookups.** Inside `apply`, every read goes through `tx`: `GetTx`, `MembersTx`,
  `trustOfTx`, `IsPairedTx`/`MailboxPubTx`. `sealWithPub` loads the identity key from the
  keystore, not the DB. The sending path's pool reads (`lookupIdem`, `duplicateOutcome`) run
  outside its transaction. No pool use happens while a transaction holds the only connection.
- **Auto-decline inside the tx.** The declined row, `last_reply` and the decline outbox row
  commit or roll back together (`TestApplyAutoDeclineAtomic`). The reply goes only to the
  authenticated `msg.from`. One reply goes out per new `(from, id)`.
- **Validation and caps.** They run before any storage on both sides (`Validate`, then
  `CheckSize`, then the insert).
- **Receive binding.** `from`/`to`/`created` are bound to the mail.
- **Team scoping.** Submit requires an active team that holds both self and the peer. Receive
  auto-declines `unknown_team` or `not_team_member` the same way, read through `tx`.
- **Atomicity.** The outbox row and the `out`/`in` row share one tx. `Wake` runs only after
  commit.
- **Audit content.** Audit details carry ids, keys, team, type, urgency and code, but no title
  or brief (asserted for auto-decline).
- **CLI `--brief-from-file` path.** The path is opened by the CLI process, relative to the
  user's working directory, never by the daemon. The read is bounded, CRLF is normalised to
  LF, and `-` reads stdin.
- **`internal/daemon/mail.go` wiring.** `request` is registered only when a request store
  exists. `peerDirectory` implements `TxOutboxPeers`.
- **Exit codes.** They match Docs/cli/request.md after #13.

Not covered: there is no e2e run for a `trust=relay` peer on a non-loopback relay, because
the harness relay is loopback. It is covered at unit and IPC level.
