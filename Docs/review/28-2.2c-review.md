## High (fixed)

**H1. A sensitive policy auto-issued `--public` grants, which skips the result quarantine
without any approval.** `policyCovers` rejected only `p.Public && mp.Sensitive`. A human
approves a policy without `--public` for `git.read repo#main`, meaning results from those
grants are quarantined. A prompt-injected agent then calls `grant_create … --public`, the
policy matches, and an active **non-sensitive** grant is issued with no prompt. grant.md
§Policies says the policy matches on "the grant's `sensitive` value", so it must be equal.
*Fix* (`internal/capability/store.go`): `p.Public != !mp.Sensitive` → no match.
*Tests:* `TestPolicyMatchRules` (new case `publicUnderSensitive`) and
`TestReview28PublicGrantNotCoveredBySensitivePolicy`, which runs the full IPC flow: the
grant goes to `pending_approval` and no mail is sent.

## Medium (fixed)

**M1. Auto-issue checked the session and peer outside its transaction.** `grant_create`
read the session state, and did the D5 check, before `BeginTx`. If the session closed in
between, its `RevokeForSessionTx` had nothing to revoke yet. The policy transaction then
inserted an **active** row and sent a `grant` mail for a closed session, and nothing ever
revokes that row. The same applied to a peer removed in between.
*Fix* (`internal/daemon/grant.go`): `recheckIssuanceTx` re-checks the session (still ours as
requester, same peer, `open`), that the peer is still paired, and D5, all through tx, before
`InsertActiveTx`. *Test:* `TestReview28RecheckIssuanceTx`.

**M2. The approval Precondition re-checked step 1 only.** grant.md §Issuance step 7 says
"re-check steps 1–3 against the current state". The Precondition checked the session but not
whether the peer was still paired, nor D5, nor the resource. A directory that was deleted,
or swapped for a symlink or junction pointing elsewhere (for example into the config dir),
between `grant_create` and the approval was still issued. A grant whose `exp` passed while
it waited was also activated.
*Fix:* the Precondition calls `recheckIssuanceTx`. It then checks `exp`, and runs
`recheckResource`, which re-runs `validateResource` on the stored path and requires that
the path still resolves to itself. For `git.read` it also re-checks the repository and
branch. *Test:* `TestReview28ApprovalRechecksResource`.

**M3. Policy approval had no Precondition.** If `peers remove` ran while a `grant_policy`
approval waited, it deleted that peer's policies. The approval then inserted a policy for
the removed key, and that policy comes back to life if the same key is paired again. The
50-policy cap was also checked only at `grant_policy_add`, so several pending approvals
could exceed it.
*Fix:* a Precondition checks, through tx, that the peer is still paired and that there are
fewer than 50 live policies (`capability.Store.PolicyCountTx`).
*Test:* `TestReview28PolicyApprovalAfterPeerRemoved`.

**M4. Some peer removals left grants and policies alive.** `peers.Store.OnRemoved` ran only
from `Remove`, and only after its commit. Peers removed by `GCIntroduced` (a team left or
dissolved) kept their active grants and their policies, and a re-introduction would revive
those policies. On the `Remove` path, a hook failure left the peer removed but its grants
active.
*Fix* (`internal/peers/store.go`, `internal/daemon/daemon.go`, `grant.go`): the hook is now
`OnRemovedTx`. It is called from `removeTx`, which is shared by `Remove` and `GCIntroduced`,
inside the removing transaction. `revokeForRemovedPeer` runs `RevokeForPeerTx` and
`PolicyDeleteForPeerTx` through that transaction. `RevokeForPeer` (which ran in its own
transaction) is replaced by `RevokeForPeerTx`.
*Tests:* `TestOnRemovedTxRunsInsideRemoval` (a failing hook rolls the removal back),
`TestOnRemovedTxRunsOnGC` and `TestReview28PeerRemovalEndsPolicies`.

**M5. Forbidden-path bypass on macOS through letter case.** `pathsEqual` folded case only on
Windows, and `EvalSymlinks` does not canonicalise case on macOS. On the default
case-insensitive APFS, `/Users/me/.DORYLINAE` (the config dir, holding keys) and
`/users/me` (home) passed the checks.
*Fix:* `foldPath` lowercases on Windows and on darwin. On a case-sensitive macOS volume
this refuses slightly more than needed, which is the safe side.
*Test:* `TestReview28PathContainment`.

## Low

**L1 (fixed).** `isWithin` used `HasPrefix(rel, "..")`, which is a string prefix and not a
path component: `<config>/..x` counted as outside the config dir. It now checks
`rel == ".."` or `rel` starting with `".." + sep`. *Test:* `TestReview28PathContainment`.

**L2 (fixed).** `grant_policy_add` resolved the path only with `EvalSymlinks`, so a human
could be asked to approve a policy for `/` or the config dir, even though such a policy
could never match a grant. It now runs `validateResource`, `validateGitResource`, and
refuses a branch on `fs.read`.

**L3 (fixed).** `grant_revoke` guarded `ob` for nil before `SubmitTx`, but then called
`ob.Wake()` unguarded.

**L4 (fixed).** `auditTx` copied `audit.Log.Append`'s INSERT. Both now use one
implementation in the audit package: `audit.AppendTx` and `Append` share `appendTo`. So the
answer to the review question is yes: `auditTx` is sound and equivalent to `Append`, and it
now uses the same code.

**L5 (fixed).** The issuance git calls (`rev-parse`, `show-ref`) inherited the daemon's
`GIT_*` variables and had no timeout. An inherited `GIT_DIR` could make the repository
check pass for a directory that is not a repository. Since M2, these calls also run inside
the approval Precondition, which holds the approval lock and the transaction, so a hung git
would block every approval. `gitCommand` now applies the §Serving git environment rules
(every `GIT_*` removed; `NOSYSTEM`, `GLOBAL=/dev/null`, no prompt) and a 10 s timeout.
2.3b should reuse or extend this helper.

**L6 (note).** A grant dropped by a failed Precondition stays `pending_approval` in `grants`
forever, and `grant_list` shows it. It is inert: activating it needs the approval, which has
been rejected. The Precondition cannot write the row, because its transaction rolls back.
Suggestion: `grant_list` could show a pending grant whose approval is decided as ended, or
2.4 could sweep such rows.

**L7 (note).** `grant_policies.approval` is always `''`, because `Perform` does not know its
approval id. Either `approval.Action.Perform` receives the id, or the daemon writes it after
`Create` (Create returns before Perform can run, so an `UPDATE … WHERE id = pol.ID` in
Perform using a captured variable set after `Create` works).

**L8 (note, cross-ticket).** grant.md §Session end says a pending grant's approval is
"rejected with `reason: "precondition"`" when the session closes. Today it is rejected only
when someone next tries to confirm it, or it lapses at expiry. The grant row itself is
revoked in the closing transaction, as required. Rejecting at close needs a post-commit
callback from `worksession` into the approval Store, because it must not be called under
the tx (N4). 2.1b is changing `worksession` now, so I did not add it here. Owner: 2.1b or
2.4.

**L9 (note, spec).** `grant.orphan` is audited as `{peer}` only. The spec says
`{grant, peer}`. The id is trustworthy at that point (step 7 comes after the signature at
step 4), but `Verify` returns no grant on failure. Either return the parsed grant together
with the `VerifyError`, or change the spec to `{peer}`.

**L10 (note).** `pendingGrant` and `pendingGrantRevoke` are package-level `sync.Map`s keyed by
`*mail.Opened`. If the receiver's transaction fails to commit after `Apply` succeeded,
`After` is not called and the entry leaks. This is bounded by the failure rate. The same
pattern exists in other kinds.

**L11 (note).** `grant_revoke` on a `pending_approval` grant also sends a `grant.revoke` mail
for a grant the holder never received. The holder ignores it (unknown id). Harmless.

**L12 (note).** The `at` of `grant.revoke` is required to be a non-empty string but is not
parsed as a time. It is informational only.

**L13 (note).** Residual risk on APFS: Unicode normalisation (NFC vs NFD) of the config-dir
path is not folded. Hard links and serve-time junction handling are documented in 2.3a's
scope.
