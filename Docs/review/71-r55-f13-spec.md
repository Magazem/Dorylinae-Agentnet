## 1. Summary

A paired peer, and for some items the relay, can make the daemon store data, burn CPU or pin
memory with nothing bounding the amount. The spec now bounds each one:

| Finding | What a peer or relay could do | Bound in the spec |
|---|---|---|
| R55-018 | Store every request twice (`requests.body` + `mail_inbox.signed`), forever, with no per-peer count for low/normal urgency: ~85 GB/day through the hosted relay | **Open cap** 100 per peer → auto-decline `inbox_full`; **daily cap** 200 new `in` rows per peer per 24 h → mail refused (`rejected`, reason `limit`); auto-declined rows keep no content; `mail_inbox.signed = ''` for every kind; `agentnet prune` |
| R55-064 | Grow held grants without end; `grant_list` breaks past the 1 MiB IPC line | 64 held rows per session (`rejected`, `limit`); `grant_list` pages (`limit`, `cursor`); prune removes expired/revoked grants |
| R55-057 | A 480 KiB card, decoded on every inbound session frame | Card envelope ≤ 16384 bytes, checked before parsing; ≤ 32 skills; `IsPaired` becomes a one-row lookup (code only) |
| R55-052 | Pin ~190 MiB of 1 MiB `session.*` frames plus as much in the mail queue | Drop `session.*` payloads over 65559 bytes before queueing; session queue ≤ 16 MiB, mail queue ≤ 64 MiB |
| R55-051 | One keystore read (a `security` process on macOS) per forged frame naming a live key_id | Mailbox and identity private keys cached in memory |
| R55-020 | Re-upload up to 256 × ~1 MB per small `keys` mail | A row is re-sealed at most once per hour |
| R55-079 | Twice the 256 MiB/24 h fetch budget across the fixed-window boundary | Sliding window (hourly buckets, current + 24 previous) |

The prune command is designed around four constraints: only finished items; the audit log
stays append-only; the F12 dedupe set (`mail_seen` + `mail_inbox`) keeps its invariant; and
nothing pruned can be re-admitted as new. A single floor of **35 days** gives all four (§3.3).

## 3. Design notes

### 3.1 Why two request caps

D50 asks for a cap on stored **open** requests with a clear refusal. On its own that is not
enough:

- **Auto-declines bypass it.** A peer that is not (or no longer) a team member, or whose trust
  is `relay` on a hosted relay, gets every request auto-declined, and each one used to store the
  full body (up to 320 KiB for a `question`). The open cap never fills because nothing is open.
  An `inbox_full` decline is itself a new stored row.
- **Declines cost the recipient mail.** Each auto-decline sends a `request.decline` from the
  recipient, which spends the recipient's own per-key relay budget at the sender's pace, so a
  flood could get the recipient's other mail `rate_limited`.

So the spec has the open cap (clear refusal: `inbox_full`, the sender's mirror ends declined)
plus a daily cap (200 new rows per 24 h) that bounds rows and decline mail, and auto-declined
rows keep no content. With the caps, a hostile peer can make the recipient store at most
100 open bodies at any time, plus per day 200 rows of metadata (about 0.5 KB each without
content), and make it send at most 200 decline mails a day. Before, the bound was only the
relay rate.

**Residual (stated, not fixed here).** Every mail still costs `mail_seen` (35 d), a blank
`mail_inbox` row and a `mail.in` audit row, for any kind, including unknown kinds. That is
~0.5-1 KB per mail at the relay rate, and the audit part is append-only. It is the paired-peer
half of R55-015/T10-01 (D49 covers unpaired keys only). Recorded for R55-F14 or a later
ticket; `peers remove` stops it.

### 3.2 Blanking `mail_inbox.signed`

No production code reads `mail_inbox.signed` (checked: the only readers are tests). The D18
blanking already stores `''` for withheld content, so the receiver now does that for every
kind. The one thing lost is a stored copy of the peer's signature over each mail. D6 accepted
non-repudiation as a property of signed mail, but nothing in the product uses the stored
signatures, and Decisions keep their own two signatures. The mail.md text states this loss.

### 3.3 The prune command

- **Only finished items.** A request in a final state whose session is closed and whose debate
  is closed or broken, all older than the cutoff. The request's session, grants, experience
  records and debate go in the same transaction, so no half-pruned item remains. Orphaned
  closed sessions and debates, and grants past `exp`, are pruned by the same age rule.
- **Audit stays append-only** (D49): prune never touches `audit_events`, and it adds one
  content-free `data.prune` row per batch.
- **Dedupe safety.** After F12, `mail_seen` and `mail_inbox` form one dedupe set. `prune` runs
  the regular `mail_seen` prune (35 d) first, then deletes `mail_inbox` rows older than a cutoff
  of at least 35 d, in one transaction, so an id never leaves `mail_inbox` while `mail_seen`
  still holds it (mail.md's rule).
- **Why 35 days.** A pruned request has `created ≤ updated < now − 35 d`. A resend therefore
  fails Receiving step 2's 30-day bound and is refused, not stored as new. `mail_seen` covers
  35 d and the receive age limit 14 d, so no replay re-applies. Late lifecycle and `ws.*` mails
  for pruned items are orphans, which are already handled. One floor covers every window.
- **Batches.** `data_prune` removes at most 500 requests per call (with dependents) so each
  call meets the 2-second IPC rule and the single-writer connection is not held long; the CLI
  loops while `more`.
- **Dry run by default.** Without `--yes` the command only counts. No approval window
  (OD-F13-8).

after both. It takes "the next free version when it merges".

     reason `limit` instead of `bad_body`. Insert `mail_inbox` with `signed = ''` always. Keep

2. **`internal/mailbox/mailbox.go`** `MailboxKey`: cache `keyID → *ecdh.PrivateKey`; clear the

## 7. Checks done

- The only readers of `mail_inbox.signed` are tests (grep over `internal/`, `cmd/`).
- The views tolerate a body that does not decode (`internal/request/query.go`:
  `decodeStoredBody` errors are skipped).
- P2 and N17 were signed in `%TEMP%\f13\sig` with a stand-alone Go program using only
  `crypto/ed25519`. It first reproduced N4's published signature from the same seed and
  canonicalisation, then signed P2 and N17. N16's length (16727 bytes) was computed from the
  Test vector's canonical card.
- The 35-day argument uses: request.md Receiving step 2 (30-day bound), mail.md `mail_seen`
  35 d and receive age 14 d, and the orphan rules of request.md §Sender mirror and
  work-session.md §Mirror.
