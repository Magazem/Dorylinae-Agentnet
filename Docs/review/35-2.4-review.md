# R-2.4: security review of quarantine (ticket 2.4) and the D18 withhold path

Opus review of commit 51c081b on `p2/quarantine` (`git diff main...HEAD`), and of the D18
content-withhold path merged with 2.1b (543bc2e: `internal/mail/open.go` `Opened.Withhold`,
`internal/mail/receiver.go`, `internal/request/mirror.go` `applyComplete`,
`internal/worksession/receive.go`, `cancel.go`). Checked against
Docs/protocol/work-session.md §Quarantine (2.4) (including the 7-day peer-wide clause, early
complete, OD-P2-6 (c) and `#inbox-copy-d18`), grant.md (sensitive, OD-P2-13), approval.md,
and review 28 L8. Fixes were made in place, with tests.

**Verdict: pass after fixes.** Critical 0, High 2 (fixed), Medium 0, Low 6 (1 fixed, 5 noted).

What holds: the rule (`capability.QuarantineHolds`) is evaluated inside the mail transaction
for every `ws.result`, every early `request.complete` (with or without a session row) and
every applied `ws.cancel`. It covers policy-issued grants, grants that were revoked or expired
before the result, and a second session with the same peer. A `--public` git grant and a
never-approved grant do not count. The 7-day boundary uses A's own clock against A's own
`exp`, stored as fixed-width UTC text, so B cannot shift it. Views (`ws_show`, `ws_list`,
`request_show`, `wait`) are all built on `worksession.View`, which drops the result while it
is quarantined. Discard and request-changes delete the result in the transaction. The
`session.quarantined` notification carries only the local peer name and ids. Audit rows carry
sizes only. `OnClosed` runs after commit on every close path, never under a transaction. It
runs once per close, and running it twice would be harmless because `RejectSubjects` is
idempotent. `RejectSubjects` and `Confirm` are serialised by `approval.Store.mu`. A confirm
that is already running keeps the entry, and its Precondition then fails on the closed
session. A new Phase 2 round re-evaluates the rule.

## High

### H1: A stale release approval releases the next round's result (fixed)

- **Location:** `ws_release` (and `ws_accept_result --human`) in `internal/daemon/session.go`;
  `worksession.PeekTx`.
- **Problem:** The Precondition checked only `state == quarantined`. Sequence: round 1 is
  quarantined and A asks for a release, so an approval is pending. A then uses
  request-changes from quarantined. This needs no approval and does not close the session,
  so `OnClosed` does not reject the pending approval. B's round-2 result arrives and is
  quarantined. When the human now answers the round-1 approval, the state is `quarantined`
  again, the Precondition passes, and **round 2 is released**. The human never saw its
  metadata, and B chose its content after learning that round 1 was not released. The same
  gap exists for `accept_result --human`: an approval for round 1 accepts round 2 and marks
  it `human_accepted`.
- **Fix:** `PeekTx` now also returns `seq`. Both handlers record `v.Seq` before `Create`, and
  the Precondition refuses the approval (`bad_state`, approval rejected `precondition`) once
  `seq` has moved. Every transition bumps `seq`. Test:
  `TestSensitiveQuarantine/stale_release_approval_cannot_release_the_next_round`
  (`internal/daemon/quarantine_e2e_test.go`). It fails without the fix.

### H2: The D18 inbox copy keeps content for a refused or orphan `ws.cancel` and an orphan `ws.result` (fixed)

- **Location:** `applyCancel` in `internal/worksession/cancel.go`; `applyResult` in
  `internal/worksession/receive.go`.
- **Problem:** `op.Withhold` was set for a `ws.cancel` only on the *applied* path (session
  `open`). A cancel that is refused (A in `quarantined` or `awaiting_result`, which is exactly
  when the rule holds) and a cancel with no session row (the peer-wide clause) stored their
  `reason`, up to 500 code points, in plaintext in `mail_inbox.signed`. That breaks
  `#inbox-copy-d18 (4)`: B could park up to 500 code points of read data in A's database on
  every cancel. An orphan `ws.result` (no out request row) was not withheld either, so up to
  64 KiB per mail was stored in plaintext. `#inbox-copy-d18 (2)` covers results that are
  "applied nowhere". Nothing reads `mail_inbox.signed` back, so the exposure is the DB file.
  The D18 rule exists to close that exposure (review 29 H1).
- **Fix:** `applyCancel` evaluates the rule (with the verified derived session id) before the
  orphan and refused branches and withholds whenever it holds. An orphan `ws.result` is always
  withheld. Tests: `TestD18_RefusedCancelReasonWithheld` and `TestD18_OrphanResultWithheld`
  (`internal/daemon/session_quarantine_test.go`). Both fail without the fix.

## Low

### L1: Grants revoked before 2.4 lose "ever active" (noted)
`ActivateTx` only records the approval id from 2.4 on. A row that was activated by the
2.2c-era code and later revoked has `approval` NULL and `policy` NULL, so
`QuarantineHolds` treats it as never approved. This affects only databases that ran pre-2.4
builds with real grants. If any exist, a one-off migration should treat revoked rows that
have `approval IS NULL AND policy IS NULL` and an `approved` `approvals` row for the grant
as ever active, or should simply treat every revoked sensitive row from before the
migration as ever active.

### L2: The grant approval id was passed through an unsynchronised closure variable (fixed)
`grant_create` set `approvalID` after `Create` returned, but `Create` had already started
the window watcher. A confirm that won that race would run `ActivateTx` with `""`. This
failed safe, because the grant stays pending, but the variable was also written and read by
two goroutines. `Perform` now reads the id in its own transaction
(`SELECT id FROM approvals WHERE kind = 'grant' AND subject = ? AND state = 'approved'`),
where `Confirm` has just marked it approved (`internal/daemon/grant.go`). The existing
grant e2e tests cover this path. The same pattern remains in `ws_release`, where the id is
used only for the audit row, so it was left as is.

### L3: Early complete after `closed` drops content whenever the rule holds (noted, spec wording)
`EarlyComplete` evaluates the rule for a closed session too. The spec calls a complete
"early" only while the session is not closed. The code is the safe choice: after a discard,
a misbehaving B could otherwise put the discarded content into `requests.result` through a
late `request.complete`. The price is that, after an accepted close of a sensitive session,
A's request row has no D14 result. The session row still holds the result. Suggest that the
spec states this: "while the rule holds, a `request.complete`'s content is dropped
regardless of the session state; the session row is the record".

### L4: Deleted result bytes can survive in SQLite free pages and the WAL (noted)
Discard and request-changes use `UPDATE … result = NULL`. `secure_delete` is off and the DB
runs in WAL mode, so the old bytes stay in free pages and in `-wal` frames until they are
overwritten. The spec's "never re-derivable" holds at the SQL level only. The effect is
small: while a result is quarantined it is stored in plaintext in the same file anyway. If
wanted, add `_pragma=secure_delete(1)` to the DSN (`internal/store/store.go`) and run a
`wal_checkpoint(TRUNCATE)` after a discard.

### L5: `session.quarantined` text differs from work-session.md §Notify (noted)
work-session.md shows "<name>'s result for <title> is quarantined: run agentnet release".
The code and notify.md show a content-free title with an empty body. The title is A's own
text, so adding it would be safe. Align one of the two documents. In the webhook payload,
`state` is the session state (`quarantined`), not a request state.

### L6: Merge note for 2.5 (noted)
On main, Docs/protocol/consult.md (lines 108–110) says an answer is quarantined "if the
requester did grant sensitive access during the session". The peer-wide 7-day clause also
applies, because a consult answer is a `ws.result` and goes through `applyResult`. The
wording should be fixed when this branch is merged.
