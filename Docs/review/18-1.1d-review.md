## Implementer's interpretation: confirmed

The joiner pairs only with the invite issuer (`trust=code`) and meets the other members
through the roster (`trust=team`). This is team.md §Model ("Each joiner pairs only with the
owner … The owner then introduces the members") and `Docs/cli/team.md` §Invite and join.
`TestTeamInviteJoinTwoTeams` checks that D has `A=code` and `B=team`, and that B has `D=team`.

## What holds (adversarial checks)

- **The pairing tag does not weaken pairing v2.** The tag is stored on the session and read
  only when the session ends. MITM (the transcript binds both cards and announcements), the
  confirm order (the issuer sends `tag_I` only after `tag_R` verified and the peer is stored),
  attempt counting (3 bad tags abort) and the `code_used` record (written before `tag_R` is
  sent) all run through the same code as untagged pairings. The existing v2 and review-09
  tests pass unchanged.
- **`Completed` fires exactly once.** The new `session.notified` flag, set under `m.mu`,
  enforces this. `InviteTag` and `JoinTag` act only on `State == complete` with a `Peer`, and
  that state is reached only through `checkConfirm` after an HMAC tag check. Failures,
  timeouts, relay errors, `failSend` and `code_used` give `State=failed` and no `Peer`, so
  both tags do nothing (`TestInviteTagIgnoresFailedPairing`, `TestJoinTagIgnoresFailedPairing`,
  `TestPairingTagCompletedOnFailureCarriesNoPeer`). A relay cannot forge a completion. A
  `pair.confirm` must come from the attempt's key, match its lookup and carry a valid tag,
  and `pair_peer` alone never completes a pairing.
- **A code for team X cannot join team Y.** The team comes from the owner's own
  `team_invites` row, which the owner's `InviteTag.TeamID` wrote. The joiner sends only the
  lookup (`TestTeamInviteScopedToInvitedTeam`).
- **A plain pair never joins.** `pair_redeem` has no tag, so no pending join is written and no
  `team.join` is sent (`TestTeamInvitePlainPairDoesNotJoin`). `team_join` refuses v1 codes
  (`allowV1=false` → `bad_code`).
- **A third party cannot use someone else's invite or pending join.** On the owner,
  `applyJoin` requires `peer_key = msg.from`. On the joiner, rows are keyed by
  `owner_key = msg.from` (`TestTeamJoinWrongLookupIsIgnored`).
- **The `team_full` check versus a race at 32.** `team_invite` checks the size when it starts,
  and `applyJoin` checks it again inside the receive transaction. `store.Open` sets
  `SetMaxOpenConns(1)`, so two `team.join` Applies are serialised. The second one sees 32
  and is ignored with `team_full`, and its invite is marked used (`TestTeamInviteFullTeam`,
  plus review 12 L18 for the user-facing side).
- **The owner deletes the team, or stops being active, between invite and redeem.** The
  pairing still completes and `team_invites` is written. `applyJoin` finds the team inactive
  (or no longer owned by self), marks the invite used and audits
  `team.join_ignored {reason: "inactive"}`. The joiner stays paired with the owner at
  `trust=code` and its pending join expires within 24 h. This is consistent with the spec.
- **Audit carries no secrets.** `team.invite {team, pairing_id}` and
  `team.join {pairing_id, owner}`. No code, secret or K is recorded, and the lookup is not
  logged either.

## Medium (fixed)

| # | Finding | Fix |
|---|---|---|
| M1 | **A race between the invite row and `team.join` could lose the join.** The issuer sent `pair.confirm{tag_I}` and only then ran `end()`. `end()` sends `pair_cancel` to the relay and then calls `InviteTag.Completed`, which writes the `team_invites` row. As soon as the joiner received `tag_I` it completed, wrote its pending join and submitted `team.join`. If that mail was applied on the owner before `RecordInvite` committed (for example because of relay latency on `pair_cancel`, a busy single DB connection, or a slow audit write), `applyJoin` found no row. It acked `no_invite` for good, the code was spent, and the joiner saw "asked to join" but was never added. The same applied if `RecordInvite` failed | `checkConfirm` now calls the issuer's Completer after the peer is stored and **before** `tag_I` is sent. The redeemer cannot complete without `tag_I`, so the owner's `team_invites` row is committed before any `team.join` can exist. A `notified` flag makes `end()` skip the second call. Doc comments on `Tag` and `Completer` are updated. `TestPairingTagIssuerCompletedBeforeTagI` checks that when the issuer's `Completed` runs, the issuer has sent 0 envelopes and the redeemer has not completed. Without the fix it fails ("issuer had sent 1 envelopes"). |

## Low (not fixed)

- **L1. No prune at start or daily.** team.md §Tables says expired `team_invites` and
  `team_pending_joins` rows are "pruned daily and at start". They are pruned only when a new
  row is written (`RecordInvite`, `RecordPendingJoin`). Expired rows are already ignored by
  every query (`expires > now`), and new rows appear only through the user's own completed
  pairings, so the tables stay small. However, stale rows (lookups, owner keys) stay on disk
  until the next invite or join. Suggest also pruning from `rcv.RunPrune` (`daemon/mail.go`).
- **L2. `JoinTag` has a partial failure.** If `RecordPendingJoin` succeeds but
  `Outbox.Submit` fails, the joiner is told `complete` but no `team.join` is ever sent, and
  nothing is retried. The same happens if `RecordInvite` fails on the owner: the error is only
  logged. Both are rare local DB errors. It would help to surface them in the pairing status
  or to retry.
- **L3. `team_join` with a 10-character code suggests the wrong fix.** The `bad_code` message
  says "redeem it with 'agentnet pair --v1 <code>'", which pairs but never joins. Give
  `team_join` its own message ("team invites are 15-character codes").
- **L4. When `team.invite` is audited.** It is written on `pair.complete` (with actor `cli`),
  not when `team_invite` runs. A code that expires unused leaves only `pair.start` and
  `pair.fail`, with no team id. team.md does not say when this event is written. Either say
  "on pair.complete" in team.md, or audit when the invite starts.
- **L5. Pending joins match on the owner only.** This is review 16 L10, confirmed here: any
  active roster from that owner that lists self consumes the oldest live row, whatever the
  team or lookup. It is spec-intended because the owner is trusted (OD-P1-2). If the owner
  sends an unrelated roster first, the join still succeeds when the intended roster arrives,
  as long as another pending row from that owner is live, but it can use up the wrong row
  when two are pending.
- **L6. An owner's invite code outlives a deleted team.** `team_delete` does not cancel
  pending `team_invite` pairings for the team, so a joiner can still pair (`trust=code`) and
  then gets `inactive`. Cancelling the team's pending invite sessions on delete would be
  cleaner.
- **L7. `Completed` runs synchronously, with a budget of up to 5 s.** For the issuer, M1 now
  delays `tag_I` by the DB write. The redeemer waits up to 60 s (`ConfirmWait`), so this is
  well within budget. It is noted because a slow Completer now delays the peer as well as
  local cleanup.
