## Findings

| # | Sev | Location | Issue | Fix |
|---|---|---|---|---|
| M1 | Medium | `mail/outbox.go` `Retry` | **A key-miss re-seal could send a row that had just become final.** `Retry` reads an open row, re-seals it, then runs `UPDATE … WHERE state IN ('queued','relayed')` and calls `send` whether or not the update matched. If an ack, the expiry sweep or `peers remove` finished the row between the read and the update, the re-sealed frame still went out. For a removed peer this sends mail the owner cancelled after the removal committed. For an expired row the peer may process mail the sender already reports as `expired`. Two concurrent re-seals of one row could also both send. | **Applied.** The update also requires `to_key = peer` and the `key_id` read earlier (`key_id IS ?`), and `send` runs only if exactly one row changed. Test `mail/outbox_review_test.go` `TestRetryDoesNotSendRowThatBecameFinal` finishes the row inside the window (fails on the old code: 1 envelope sent). |
| M2 | Medium | `daemon/outbox_harness_test.go` | **The harness did not assert what it claims ("ciphertext only on the wire, relay queue file, logs").** It searched the relay log, the queue DB and the queued frame for the literal marker only. The frame carries the payload in base64, so a plaintext payload would have passed every check. Daemon logs were not captured, and the queued payload's structure was not checked. | **Applied.** `leaksSecret` also looks for the base64 and base64url forms at all 3 alignments (self-tested by `TestLeaksSecretFindsEncodings`). Both daemons' logs are captured at debug level and checked. `TestRelayQueueHoldsOnlyCiphertext` now decodes the queued payload and checks that it does not hold the marker, that its length is exactly `MinPayload + len(signed)` for the signed plaintext in A's outbox row, and that its `key_id` equals the row's `key_id`. |
| M3 | Medium | spec, `mail.md` §Outbox and §Receiving step 11 | **`expired` does not mean "not delivered".** The sender expires a row at `created + 7 d`. Its last resend may be queued at the relay for 7 more days, and the receiver accepts until `created + 30 d`. A mail can therefore be processed up to about `created + 14 d`, after the sender has shown `expired` and ignores the late ack. The same holds for a mail processed just before expiry whose ack was lost. Phase-1 kinds (`request`, `grant`, …) that resubmit on `expired` would act twice under two different ids. Nothing in 1.0 acts on it yet. | Not fixed (spec is authoritative). **Owner decision:** either (a) define `expired` as "delivery unknown" in mail.md and require Phase-1 resubmits to be idempotent (for example carry the original id in the body), or (b) make the receiver reject outboxed kinds with `created < now − 14 d`, so nothing arrives after the sender could still resend plus the relay TTL. That narrows the gap but does not close it, because of lost acks. (a) is recommended; (b) can be added on top. |
| L1 | Low | `mail/outbox.go` `send` / `HandleError` | A relay `error` frame (`queue_full`/`internal`) can arrive before `send` has run its `state = 'relayed'` update. `HandleError` then matches nothing (`WHERE state = 'relayed'`), and the row ends as `relayed`. The only effects are that `status` counts it as relayed and `OnReady` does not resend it at once. Backoff still resends it. | Not fixed. For example, let `HandleError` also accept `queued` and set a flag that `send` respects, or have `send` write the state before `Send`. |
| L2 | Low | `daemon/outbox.go` `mail_submit` | IPC refuses `ack` but accepts `keys` (and any other kind) from local callers. A hand-made `keys` body is rejected by the peer (`bad_keys`/`malformed`, no ack) and is then resent for 7 d. | Not fixed. Refuse `keys` in `mail_submit`, since only the daemon's own pusher should send it. |
| L3 | Low | `mail/receiver.go` `Handle`, relayclient bypass | Each repeat of a mail is fully opened and re-acked, and each ack loads the identity key from the keystore (the keychain in `auto` mode). The relay can replay a stored envelope without limit to make the daemon do this work: a 1:1 amplification that the relay also pays for. Acks are not batched (the spec allows up to 1 s). | Not fixed. Optionally rate-limit re-acks per `(peer, id)` and batch acks per peer. |
| L4 | Low | `mail/keys.go` `KeyMiss` | `last[peer]` is set only after a successful reply. While a reply cannot be sent (no mailbox key for the peer, or a relay write error), every forged key-miss envelope for that peer costs a keystore load and a seal attempt. Two concurrent `Note` calls before `last` is set can send two replies in one window. The `AfterFunc` timers are not cancelled at shutdown (they fire into a stopped client, which is harmless). | Not fixed. Record the attempt time before sending. |
| L5 | Low | `daemon/mail.go` `startMail` | When the 256-slot receiver queue is full, the envelope is dropped after relayclient has already acked it to the relay. Recovery then waits for the sender's backoff, up to 6 h. This follows the design ("the sender resends"), but consider logging drops (`event=mail_dropped`) so they are visible. | Not fixed. |
| L6 | Low | `mail/outbox.go` `Submit`, `mail_inbox` | There is no cap on non-final outbox rows. Each row can hold about 1.9 MB (`signed` + base64 `frame`). `mail_inbox` is never pruned (it is proof by design). Only local IPC callers and paired peers can grow them. | Not fixed. Consider a per-peer cap on queued rows in Phase 1. |

## Checked and found sound

- **Exactly-once on the receiver.** `mail_seen` insert, kind `Apply` and `mail_inbox` insert run in one transaction, and the ack is sent only after commit (`TestNoAckBeforeCommit`). A crash between commit and ack, or a lost ack, leads to a resend, which is found as a duplicate and re-acked (`TestTripleDeliveryOneRowThreeAcks`, `TestReplayAfterRestartStillDeduped`, harness). relayclient hands up every `mail` repeat (seen-set bypass), so re-acks and re-sealed copies reach dedupe.
- **Dedupe window.** A row inserted at `R` has `created ≥ R − 30 d` and `≤ R + 10 min`. After the 35 d prune, a replay at `T > R + 35 d` has `created ≤ R + 10 min < T − 30 d` and is rejected at step 11. Pruning can never re-admit a replay. Relay TTL (7 d from queueing) and outbox expiry (7 d) together bound arrival to about `created + 14 d`, well inside 30 d (see M3 for what this means for `expired`).
- **Acks are authenticated and scoped.** An ack passes steps 1–12: a paired sender, sealed to our key, `msg.from` equal to envelope `from`, and signed by that peer. `OnAck` finishes only rows with `to_key = ack.from` that are not final. Neither a relay nor another paired peer can mark someone else's mail delivered or failed. The new test `TestOutboxAckFromOtherPeerIgnored` covers both `ids` and `unsupported`. Replayed acks only repeat what that peer genuinely acked.
- **Key-miss recovery.** The trigger is unauthenticated by design, so it only queues ids in the `m-<hex>` format, capped at 256 per peer, with one reply per 10 min per paired peer. The reply is a signed `keys` mail, verified at step 12 with `identity = msg.from`. `Retry` touches only open rows addressed to the replying peer, and re-seals only when the row's `key_id` differs from that peer's newest stored key. After one re-seal it is a no-op, so there are no loops and no amplification. There is no downgrade: sealing always uses the newest stored announcement, and merges never go backwards.
- **`keys` announcements.** Strict parse, exactly 2 top-level and 6 inner members, identity bound to `msg.from`, signature over the generic canonical form, `key_id` = `SHA-256(pub)[0:8]`, and the time window checks. Merge ignores known `key_id`s and anything not newer than the newest stored announcement (no rollback), and keeps at most 2. A peer that is not paired is ignored. Pairing uses the same merge.
- **Rotation.** The key is stored before its row, and the row before the announcement is returned. Deletion happens at `not_after + 7 d` = `created + 21 d`, and `MailboxKey` refuses a key past that time even if the keystore deletion failed. The oldest key is deleted early only when a 4th would be live, which normal hourly rotation never reaches. Mail sealed to a deleted key is recovered through key miss for as long as the sender's row is open. `keystore.Delete` treats "not found" as success, so the sweep cannot wedge.
- **Outbox state machine.** Every transition to a final state is one conditional `UPDATE … WHERE state IN ('queued','relayed')` that clears `signed`, `frame` and `next_attempt`. The resend update is also conditional, so a concurrent ack, expiry or removal cannot resurrect a row. The worker sends the stored frame unchanged (same id and `ts`). Backoff is 1 min / 5 min / 30 min / 6 h with ±10 % jitter. Expiry runs every minute and final rows are purged after 30 d. `peers remove` fails open rows in the same transaction, and the worker also fails rows whose peer is gone. `peer_offline`/`peer_busy`/`queue_full`/`internal` go back to `queued` with the backoff kept, and `bad_envelope`/`bad_sender` go to `failed`. The DB has a single connection (`SetMaxOpenConns(1)`), and no code path holds a transaction while calling back into `*sql.DB`.
- **No plaintext leakage.** Audit details are `{peer,id,kind}` / `{peer,id,reason}` / `{key_id,retired}` only. Log lines carry ids and errors, never bodies, frames or key material (now asserted by the harness, M2). Plaintext stays at rest only in open outbox rows (until final) and in `mail_inbox` (proof), as specified.
- **Seal/open.** HPKE base mode, X25519/HKDF-SHA256/ChaCha20-Poly1305 via `NewSender`/`NewRecipient`. `info` binds from, to and `key_id`, and `aad` binds the id. The verification order matches the spec table, and the recorded vector opens (`verifyvectors`). `Reseal` refuses a stored plaintext whose from/to differ.
