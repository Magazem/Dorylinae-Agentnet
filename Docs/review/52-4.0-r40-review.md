## Verdict

**The whole 4.0 set (a+b+c) is ready for the owner's G-4.0 sign-off, with the fixes below,
under two conditions:**

- **M2:** ticket 4.1b must set the memory and disk flags for the real Fly.io machine and
  volume. The spec defaults do not fit a 256–512 MB machine with a 1–3 GB volume.
- **M3:** the branch must be rebased carefully onto the current `main`.

There is one High finding. The memory bound of review 50 M2 counted only frames waiting in
outbound buffers. Two other holders were outside every cap:

- a frame a peer has started and not finished;
- a queue batch loaded for a peer that stopped reading.

The High is fixed in code, with regression tests that fail on the old behaviour. One Medium
(`/healthz` had no rate limit) and one Low (an IPv6 zone in the proxy header) are also fixed.

## High

### H1: the memory bound misses unfinished inbound frames and loaded queue batches

**Where:** `internal/relay/relay.go` `serve` (`c.ws.Read(ctx)`) and `drainStep`
(`q.next` then `sendWait`).

**Defect (a), inbound.** `coder/websocket` `Conn.Read` is `io.ReadAll` over the message
reader. Its buffer grows as bytes arrive, up to the 1 MiB read limit:

- The authenticated read loop has no idle or per-frame timeout.
- The per-key and per-prefix byte limits run only after a frame is complete.

So each authenticated connection can pin about 1 MiB (more with `append` growth) with a frame
it never finishes. That costs the attacker 1 MiB of upload once.

The per-prefix caps allow 64 keys and 64 connections, so that is **64 MiB per /24**, or per
/48 for IPv6, where a small allocation holds hundreds of /48s. Four to eight prefixes exhaust
the planned 256–512 MB Fly.io machine (OD-P4-1, ticket plan line 448). This is exactly the
"exhaust memory" row of the threat model. Review 50 M2 fixed only the outbound side, and the
load test checks only the outbound counters (`Buffered`, `Inflight`), so it could not see
this.

**Defect (b), queue drains.** `drainStep` read a batch of up to 64 rows from SQLite: it stops
at 1 MiB, plus one more frame, so up to about 2 MiB. Only then did `sendWait` wait for room in
the connection buffer and the `--max-inflight` budget. The loaded rows were not charged
anywhere.

Attack: queue at least 1 MiB for each of N of your own recipient keys. The per-pair cap is
8 MiB and the per-sender cap 64 MiB, so a few sender keys suffice. Then connect the N
recipients and never read. Every blocked drain holds its batch outside the budget: N × ~2 MiB
(500 recipients from 8 prefixes ≈ 1 GiB).

**Fix (applied):**

- **Inbound.** `serve` reads through `readFrame`, which reads the message in growing chunks.
  Before each growth it charges the new capacity to a relay-wide `reading` budget of the
  `--max-inflight` size, counted apart from the outbound budget. Growth doubles but never
  past `MaxFrameBytes+1`. The frame is uncharged after `route` returns. Past the budget, the
  reading connection is closed with 1013 "relay busy; retry later" and `event=limit
  limit=max_inflight_read relay=all` is logged.

  Waiting for budget instead of closing was rejected: every holder could be an attacker that
  never finishes a frame, so waiting could deadlock.
- **Drains.** `drainStep` first calls `conn.reserve`, which waits for per-connection room
  (`ConnBufferBytes`) and reserves `drainReserve` (1 MiB + one maximum frame) from
  `--max-inflight`. Only then does it read the batch. `sendReserved` moves each frame from
  the reservation into the buffer without charging it twice, and a deferred release returns
  whatever the batch did not use.

  The first, inline batch in `serve` does not wait. If it cannot reserve, the drain goroutine
  waits instead, so the read loop always starts. `sendWait` is removed; its unit test became
  `TestReserveHonoursByteCap`, with the same assertions plus budget accounting.
- Memory bound after the fix, at the defaults: ≈ 2 × `--max-inflight` + `--max-conns` ×
  (idle connection cost). See M2.

**Regression tests** (`internal/relay/limits_test.go`):

- `TestLimitUnfinishedFramesShareReadBudget`. Two keys each start a ~0.9 MiB frame against a
  1.5 MiB budget. The second connection must be closed 1013, and the first frame must still
  be routed with its bytes uncounted afterwards. **Before the fix** (bytes counted but never
  refused) it fails with "closed with StatusCode(-1) (… context deadline exceeded), want
  StatusTryAgainLater".
- `TestLimitDrainLoadsNothingWhileBudgetSpent`. Three 400 KB envelopes are queued, the budget
  is filled, and the recipient connects. Nothing may be read from the queue until the budget
  frees; then all three are delivered in order. **Before the fix** it fails with "a drain
  holds 1200569 bytes read from the queue while --max-inflight is spent".

Both pass after the fix, and the whole package passes with `-count=10`.

## Attack list

1. **Token buckets.**
   - Each limit has its own `bucketSet`. The key buckets (`keyEnvs`, `keyBytes`,
     `reconnects`) and the prefix buckets (`prefixEnvs`, `prefixBytes`, `upgrades`, now
     `health`) are different maps, so nothing crosses over.
   - `sendAllowed` checks all four buckets with `has` and charges them with `take` under one
     mutex, so either all are charged or none.
   - Refill is `min(burst, tokens + dt·rate)`, guarded by `now.After(last)`, so a clock step
     back never refills. Tokens never go negative (`take` only when ≥ cost), and float64
     cannot overflow here.
   - Pruning deletes only buckets that are full again, which are the same as new ones. So
     reconnecting cannot reset a bucket, and the reconnect bucket is keyed by key across
     connections.
   - No error path charges twice. A refusal after the `has` checks charges nothing; a frame
     that fails parsing or sender checks is refused before `sendAllowed`.
   - The control-strike run logic is correct: it resets unless the previous window was over.
   - Values ≤ 0 turn a limit off in the library, and `cmd/relay` refuses them. `byteSize`
     bounds the shift overflow.
2. **"Four keys" (the author's deviation #1).** Both statements are true, and the spec is not
   ambiguous:
   - Each sender key is held to 300 per recipient (per-pair cap).
   - Four keys together still fill the victim's 1000: 300 + 300 + 300 + 100, stopped by the
     per-recipient cap.

   relay-hosted.md §2 ("four fresh keys fill a victim's 1000-envelope queue") and review 50 M1
   say the second; the author's sentence only says the first. The implementation matches the
   spec, and the test now asserts exactly 1000 (L7).
3. **Proxy header.**
   - The header is used only when the relay is public, a header is configured, and the TCP
     peer (`r.RemoteAddr`, set by `net/http` from the socket) is unmapped and inside a
     `--trusted-proxy` prefix.
   - Only the last entry of the last header line counts. A zone is now stripped (L1).
     Anything malformed falls back to the TCP peer.
   - `parseProxy` rejects an IPv4-mapped CIDR and unmaps a bare IP, so the peer
     `::ffff:10.x` and the CIDR `10/8` match, while a mapped CIDR cannot silently never match.
   - `--behind-proxy` without `--client-ip-header` is refused in `lf.validate`. That is a CLI
     concept: `relay.Options` has no behind-proxy field, and `cmd/relay` is the only non-test
     caller of `relay.Open`. A library caller that sets `Public` without a header gets
     TCP-peer prefixes, which can over-limit but never trusts a header. `Open` still rejects
     a header without a trusted proxy.
4. **Memory:** see H1 (fixed) and M2 (deployment flags, with concrete values).
5. **Queue caps.**
   - At runtime, `route` → `enqueue` → `q.add` runs the dedupe, pair and recipient queries
     from the **same constants** (`queueCapQueries`) that the `EXPLAIN` test checks. So the
     test covers the SQL that actually runs: `queue_dedupe` for the pair query,
     `queue_by_recipient` for the recipient query.
   - The per-sender and relay-wide totals come from memory, adjusted on add, ack and sweep
     under `q.mu`.
   - The index reads are bounded by the caps, plus rows not yet swept.
   - The disk check cannot be forced to "ok" by a client. Its fail-open cases are the
     operator's (L4). Check and write race only within the 1 s cache, which the 1 GiB margin
     absorbs.
6. **Logging.** `hit` logs only:
   - the limit name, a fixed constant;
   - a subject, one of: `short(key)` (8 characters of a key the relay verified), a
     `clientPrefix` built from the TCP peer or a parsed IP (now zone-free), or `all`;
   - the suppression count.

   No error text, id or frame reaches an `event=limit` line, and the existing
   `TestLogsContainNoPayload` and `e.logged` checks pass. The queue-full drop line logs the
   envelope id, as before 4.0b; the id is validated by `ParseHeader`.
7. **Outbox:** see L3. INV-4 is not reintroduced.
8. **Interplay with 4.0a/4.0c.**
   - Every per-prefix limit, and 4.0c's pairing prefix, uses one prefix computed once in
     `ServeHTTP` from `clientAddr`, before admission. Pairing now sees the real client behind
     a proxy, where before everyone shared the proxy's prefix.
   - Every check keyed by a key (reconnects, keys per prefix, max-conns, control, send)
     runs only after `verifyAuth` succeeds. So there is no oracle for whether a key exists,
     and no way to spend another key's budget.
   - Unauthenticated connections share the per-prefix upgrade and connection limits, as the
     spec says, but have their own relay-wide pool (256, separate from 5000).
   - A valid v1 signature refused by a v2-only relay does not count as a failure (spec).
   - 4.0a's origin binding (`auth.go` `setAuth`/`verifyAuth`) and review 51 M1
     (`relayclient` `loopbackOnly`) are untouched: 4.0b does not modify `auth.go` or
     `relayclient.go`, and `public` still comes only from `cmd/relay`'s transport flags.
   - No limit reads a value from before origin or loopback validation.
