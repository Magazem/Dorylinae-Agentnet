# R-2.3c: security review of the fetch client and CLI (ticket 2.3c)

Review (Opus) of commit 60ac193 on `p2/fetch-client`, against Docs/protocol/grant.md
(§Transport, §Revocation, §IPC, §CLI), ipc.md, ticket 2.3c and review 34 (server side).
Every `fetch.resp` was treated as hostile. Fixes were made in place, with tests.

**Verdict: pass after fixes.** Critical 0, High 0, Medium 4 (all fixed), Low 5 (2 fixed,
1 documented, 2 noted).

## Medium

### M1: `fetch_start` could overrun the IPC budget and orphan a fetch slot (fixed)

- **Location:** `internal/daemon/fetch_client.go` `start`, `status`, `wait`.
- **Problem:** `fetch_start` sends first (`session.Manager.Send`: it waits for `sendMu`,
  which the receive goroutine holds while it handles envelopes, and then up to `sendBudget`,
  5 s, on the relay). After that it always waited another full `fetchWait` (1 s). The CLI
  calls with `pairTimeout` (1.9 s). So a send that took more than 0.9 s made the CLI fail,
  while the daemon kept the pending fetch. That fetch held one of the two per-grantor slots
  until its deadline (up to 300 s). Two such fetches locked the holder out of that grantor
  (`rate_limited`) for minutes.
- **Fix:** `wait` now takes the call's start time. It waits at most `fetchWait` and never
  past start + `fetchCallBudget` (1.5 s), so a slow send shortens the wait. The send itself
  can still exceed the budget in the worst case. `Ping` has the same property, because
  `Manager.send` detaches the context. Test: `TestFetchStartKeepsFinishedBoundedAndReturnsInTime`
  (a 1.2 s send; the call returns within about 1.5 s).

### M2: finished fetches counted towards the 64-fetch limit (fixed)

- **Location:** `fetch_client.go` `start` (`len(c.ops) >= fetchMaxLive`).
- **Problem:** finished fetches are kept for 60 s, and the limit counted them too. A file
  read is one fetch per 256 KiB, so two 8 MiB files (32 reads each) filled the table. After
  that, every fetch to every grantor was refused locally with `rate_limited` for up to a
  minute.
- **Fix:** the limit of 64 now counts pending fetches only. Finished ones are capped
  separately (`fetchMaxKept` = 64), and the oldest is dropped first. Memory stays bounded:
  64 × 256 KiB being reassembled plus 64 × about 350 KB of base64 results, about 40 MB at
  worst. Docs: `Docs/protocol/grant.md` §IPC. Test: same as M1 (64 finished fetches, the
  new fetch is accepted, the oldest is dropped).

### M3: names from the grantor printed raw to the terminal (fixed)

- **Location:** `cmd/agentnet/fetch.go` `fetchList`, `fetchStat`.
- **Problem:** entry names come from the grantor, and the server only filters invalid
  UTF-8. On Linux a real file name can contain control characters, and a hostile grantor
  can send any name. The human-readable table printed names as they came. So `ESC`/OSC
  sequences reached the holder's terminal: clipboard writes (OSC 52), title changes, and
  cursor moves that could fake or hide lines. Bidi overrides (U+202E) could disguise a name.
- **Fix:** `termSafe` quotes any name or type that contains a non-printable rune, using
  `strconv.QuoteToGraphic`. `--json` output is unchanged, since JSON escapes control
  characters. Docs: `Docs/cli/fetch.md` §Output. Test: `TestFetchListQuotesControlCharacters`.

### M4: `--out` followed symlinks, kept wider modes and could leave a partial file (fixed)

- **Location:** `fetch.go` `fetchFile` (`os.WriteFile(outFile, data, 0o600)`).
- **Problem:** `os.WriteFile` applies 0600 only when it creates the file. An existing file
  was truncated in place and kept its mode (for example 0644), so the content of a
  sensitive grant could end up world-readable although the help promises 0600. A symlink at
  the path was followed, and a write that failed part-way left a truncated file. Choosing
  the path is the user's own business; these side effects were not.
- **Fix:** `writeFileAtomic` creates a 0600 temporary file in the same directory
  (`os.CreateTemp`), then writes, syncs and closes it and renames it over the target. On
  any error it removes the temporary file. As a result a symlink is replaced rather than
  followed, and a failure leaves the old file untouched. Docs: `Docs/cli/fetch.md` flag
  table. Test: `TestFetchOutReplacesTheFile` covers the 0644 file becoming 0600, a failed
  fetch leaving the old content, and a directory as `--out` leaving no temporary file.

## Low

### L1: stat and list responses were passed through unchecked (fixed)
- **Location:** `fetch_client.go` `onResp`, for any op other than read.
- **Problem:** every member except `type`/`req`/`ok` was copied into the result. That let
  in unknown members and unchecked `entry`/`entries`/`commit`. Also, `json.Marshal`
  HTML-escapes `RawMessage`, which grows `<` sixfold. A frame of about 780 KB could then
  make the `fetch_status` reply larger than the 1 MiB IPC line limit, and every poll of
  that fetch failed.
- **Fix:** `fetchMetaResult` decodes into typed fields and keeps only `entry`, or `entries`
  (at most 1000) and `cursor` (at most 1024 bytes of UTF-8), plus `commit` (a 40 or 64
  character hex hash). Each entry needs a non-empty name of at most 1024 bytes of UTF-8,
  a known type and a size ≥ 0. Anything else fails with `io_error`. Test:
  `TestFetchChecksListAndStatResponses`.

### L2: the read `commit` was unchecked, and base64 was decoded before its size check (fixed)
- **Location:** `fetch_client.go` `onFragLocked`.
- **Problem:** the `commit` of a read was taken from the first fragment, never checked
  against its format, and never compared with the later fragments. Fragment data was
  decoded before its length was checked. The frame size bounds this at about 768 KB, but
  it is wasted work.
- **Fix:** the commit must match the hash pattern and be the same in every fragment. The
  encoded length is checked first. Tests: three new cases in `TestFetchRefusesBadResponses`.

### L3: `changed` cannot see an `fs.read` file rewritten in place at the same size (documented)
- **Location:** `fetch.go` `fetchFile`.
- **Problem:** a file larger than 256 KiB is read in several reads. For `git.read` the
  client compares `commit` across them, but for `fs.read` it can only compare `size`,
  because the protocol carries no mtime or hash. A same-size rewrite between two reads
  gives a silently mixed file.
- **Fix:** documented in `Docs/cli/fetch.md` §Reading. A real fix would add a version
  (mtime+size or a content hash) to the read response. That is a protocol change and
  needs an owner decision (suggested follow-up).

### L4: fetches in flight are not failed locally on revocation (noted)
- The holder does not cancel its pending fetches when it learns of a `grant.revoke` or the
  closing of the session. They end on the grantor's `revoked` / `session_not_open` answer
  or at their deadline. Per §Revocation the grantor is the enforcer, and new `fetch_start`
  calls already fail locally (the row state, plus Verify step 7 through the local session
  view), so no change was made.

### L5: the janitor sends retries one after another (noted)
- **Location:** `fetch_client.go` `janitor`.
- **Problem:** each resend can block for up to 5 s (`sendBudget`), during which deadlines
  and expiry are not applied. The effect is bounded, since there are at most 2 retries per
  fetch and 2 fetches per grantor. No change was made.

## Checked, no finding

- **Reassembly:** `frags` is 1–8 and `frag` must be in range. `size` must be ≥ 0 and the
  same across fragments. Duplicates are ignored, fragments over 32 KiB are refused, and
  the total must equal `min(length, size − offset)` exactly. A malformed fragment either
  fails the fetch or is ignored until the deadline.
- **Response binding:** each attempt uses a fresh 128-bit `req`, checked with the sending
  peer. Responses to an abandoned attempt, a finished fetch, another peer or an unknown
  `req` are dropped, and a response that arrives after the timeout is ignored. A grantor
  that keeps sending duplicates only delays the retry, never past the deadline.
- **Retries:** at most `fetchMaxRetries` (2) whole re-sends per read, and only after a
  fragment arrived. With nothing received, the fetch simply times out.
- **`Manager.Send`:** its only caller is the fetch client. The peer is `rec.Peer` of a held
  grant, and Verify checks it as the counterparty. No IPC method takes an arbitrary peer.
  It uses the same handshake path as `Ping`, the responder's `IsPaired` check still
  applies, and data on a session is bound to that session's peer (`onData`).
- **Protocol additions** (optional `timeout_s` 1–300, the client-side `changed`, local
  failures as IPC errors carrying the Verify reason, a local `rate_limited` for a third
  fetch per grantor): all are sound and consistent with review 34's server behaviour.
- **Grant/policy CLI:** it passes its parameters to the daemon, which validates them
  (grant_create, grant_policy_*), and adds no local interpretation of paths. Peer
  labels, resource labels and scopes on the held side come from verified tokens (label
  pattern, scope path rules), so no terminal escape is possible there.
