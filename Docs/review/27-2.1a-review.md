## Worker's design choices: result

| Choice | Result |
|---|---|
| (1) `reqStore.Sessions` not wired in the live daemon | Phase 1 behaviour is unchanged: no session opens, `request_complete` is not redirected, and `applyComplete` does not call the early-complete hook. **But ws.\* kinds were registered anyway (M1):** a peer could create requester session rows on A and store up to 64 KiB of result per outgoing request. | (2) `Store.Release` performs the transition without an approval | Not reachable: nothing outside the package calls any A-side transition yet. Guarded anyway (L1): renamed to `ReleaseApproved(ctx, id, approvalID)`, which refuses an empty approval id and audits `approval` as the spec requires. |

| (5) B clears its own result copy on round advance or cancel | Correct. On `open` (new round) and on `closed`/`cancelled` the copy is stale. On `closed`/`accepted` it is read before the update and used for the D14 part. |

## Critical (fixed)

**C1. Every session close on B would deadlock the daemon.** `request.Store.CompleteInTx`
ran inside the caller's transaction (the mail dedupe transaction for B's mirror, and the
fallback transaction for `CheckPhase1Fallback`). It then called `s.Audit.Append`. The
daemon's `audit.Log` uses the same `*sql.DB` as the store, and the store has
`SetMaxOpenConns(1)`, so `Append` waits for the connection the open transaction holds. It
waits forever: the mail context has no deadline. From the first `ws.state closed` after 2.1b
wires sessions, the receiver, and with it every DB user in the daemon, would hang. The tests
did not see this because they use a fake audit sink. Reproduced with the real `audit.Log`:
the call hangs.
*Fix* (`internal/request/session_hooks.go`): `CompleteInTx` no longer writes audit. It
returns a function that appends the `request.complete` row, and the callers run it after
commit (`worksession/mirror.go` through `stateOutcome.auditComplete` in `afterState`, and
`worksession/phase1.go` after `Commit`).
*Tests*: `TestReview27_MirrorCloseWithRealAuditDoesNotDeadlock` and
`TestReview27_Phase1FallbackWithRealAuditDoesNotDeadlock`. Both use the real `audit.Log`
with a 10 s watchdog.
*For 2.1b and later*: never call `Audit.Append` (or anything else on `DB`) while holding a
transaction. The `Quarantine` hook (2.4) receives `tx` for this reason and must query
through it.

## High (not fixed: needs a spec decision)

**H1. A quarantined or dropped result survives in `mail_inbox`.** work-session.md §Kinds
registers every ws.\* kind with `Inbox: true`, and `request.complete` is also `Inbox: true`
(Phase 1). So the verified signed plaintext is stored permanently in `mail_inbox.signed`,
including the full `ws.result` (up to 64 KiB) and an early `request.complete` whose
`result`/`note` were "dropped unread, never stored". That contradicts §Discard ("never
stored beyond the transaction that deletes it"), §Quarantine ("nothing computed from the
content survives the transaction"), and ticket 2.1a's "search every table for a marker".
No IPC reads `mail_inbox` today, so nothing surfaces yet. The rows are still on disk and in
backups, and any future `mail`/debug view would expose them.
*Options for the owner/spec*: (a) register `ws.result` without `Inbox`, and have
`applyComplete` skip the inbox row when it drops content; this needs a receiver hook,
because `Inbox` is a static per-kind flag. (b) Keep `Inbox`, and have discard,
request-changes-from-quarantined and the early-complete drop delete or blank the
`mail_inbox` row in the same transaction. (c) Accept it and reword the spec to "never shown
to IPC or the agent". (b) keeps the non-repudiation proof until the content is rejected; my
recommendation is (b), decided before 2.4. The new early-complete test deliberately
searches only `requests`, `work_sessions` and audit, and says so.

## Medium (fixed)

**M1. ws.\* was received while sessions are off.** `newMailReceiver` registered
`ws.result/state/cancel` whenever the `worksession.Store` existed, but no daemon opens
sessions in the 2.1a state. A peer could send `ws.result` for any of A's `pending`,
`deferred` or `accepted` out requests. A then created a requester row, stored the result
(64 KiB per request) and sent `ws.state` mail back. Those rows would then be live when 2.1b
flips sessions on, and nothing could close them before that.
*Fix* (`internal/daemon/mail.go`, comment in `daemon.go`): ws.\* is registered only when
`rs.Sessions != nil`. *Test*: `TestWSKindsOnlyWithSessions` (daemon).

**M2. A second `closed` `ws.state` failed B's mail transaction forever.** B completes its
request on every applied `closed` state. For a request already `completed` (a second
`closed` with a higher seq from a misbehaving A, a reopen followed by a close, or a close
after the Phase 1 fallback), `CompleteInTx` returned `BadStateError`. That is not
`bad_body`, so the receiver never acks and the sender resends for 14 days.
*Fix* (`worksession/mirror.go`): complete only when entering `closed` from a non-closed
state, and treat `request.BadStateError` as "nothing left to complete".
*Test*: `TestReview27_RepeatedClosedStateIsNotAnError`.

**M3. Discard kept B's claimed `verification`.** `Discard` nulled `result`/`result_round` but
left `verification` (a member of the quarantined result). The spec says nothing computed
from the content survives. `RequestChanges` already cleared it.
*Fix* (`worksession/transitions.go`). *Test*: `TestReview27_DiscardClearsVerification`.

**M4. An early complete with no session row skipped the quarantine rule.** `EarlyComplete`
returned `keep = true` when A had no row. That happens when B never accepted, or its
`request.complete` overtook the accept. Phase 1 mirror rules apply that `request.complete`
by seq, and clause 2 of the rule (a sensitive grant to the same peer in another session
less than 7 d ago) does not need a row. So B could return data read in S1 through a new
request's `request.complete`, which is exactly what clause 2 exists to stop.
*Fix* (`worksession/hooks.go`): with no row, the hook is still called, with the derived sid
and `round = 0` (the contract is documented on `Store.Quarantine`).
*Test*: `TestReview27_EarlyCompleteWithoutSessionHonoursQuarantine`.

**M5. The Phase 1 fallback matched stale failures.** See design choice (4).
*Fix* (`worksession/phase1.go`): only `ws.result`/`ws.cancel`, `created ≥ opened`, and the
row is re-read inside the transaction (it was read outside, so a racing `ws.state` could be
overwritten). *Test*: `TestReview27_Phase1FallbackIgnoresOlderFailures`.

**M6. `View` exposed a quarantined result on A.** `toView` decoded `result` in every state,
and the test asserted it. 2.1b builds IPC on `View`, so the quarantine would have depended
on each view remembering to hide it.
*Fix* (`worksession/store.go`): on a requester row in `quarantined`, `View.Result` is nil.
The new `ResultStatus` and `Artifacts` fields, with the existing `ResultBytes` and
`OutputBytes`, carry what the spec allows.
*Test*: `TestSessionStateMachine_OpenToQuarantined` (now asserts that the result is withheld
and becomes visible after `ReleaseApproved`).

## Low

**L1 (fixed). `Release` was unguarded.** See design choice (2).

**L2 (fixed, partly). `ws.close` was never audited on A.** It is now emitted after commit for
accept-result, A's cancel, discard and an applied `ws.cancel`, with `{session, peer, outcome,
rounds, age_s}`. The fallback's `ws.close` now has `rounds`/`age_s`. *Not done*: the close
caused by an early complete runs inside `request.applyComplete`, which has no after-commit
hook into this package (2.1b: return a callback from `EarlyComplete`, as with C1).
*Test*: `TestReview27_WSCloseAudited`.

**L3 (note for 2.4). The early-complete drop is not audited** as `ws.ignored {reason:
"early_complete"}`. It cannot happen until the hook is wired. Same after-commit constraint
as L2.

**L4 (note for the spec). `EarlyComplete` also applies the drop when the session is already
`closed`.** That is stricter than the spec, which only drops "while not closed". It is the
right behaviour after a **discard**: B's later `request.complete` would otherwise put the
discarded content into A's request mirror. The spec should say that after `closed` +
`cancelled` A keeps only the fixed note. After `closed` + `accepted` the drop costs nothing,
because the result is already visible.

**L5 (fixed). The fallback read the row outside its transaction.** See M5.

**L6 (note for 2.1b). B's `cancel` column is never written, and `ws_cancel` for B is not
implemented.** Both are in 2.1b's scope. When B's mirror receives any new state, it must
clear `cancel = requested`.

**L7 (note). `pendingResult`/`pendingState`/`pendingCancel` leak an entry if the mail
transaction's commit fails after `Apply`.** This is the same pattern as
`internal/request.pendingApply`. The leak is bounded and harmless.

**L8 (note). `hasControl` treats a literal U+FFFD as a control character**, so a valid
string containing it is refused. That errs on the safe side. Keep it consistent with
`internal/request` if that code differs.

**L9 (note for 2.1b). A `closed` → `open` `ws.state` from a misbehaving A reopens B's
mirror** (B does not check transitions, per spec). A new `ws.result` from B is then refused
by A (the request is `completed`), and M2 keeps the mail path healthy. No action.
