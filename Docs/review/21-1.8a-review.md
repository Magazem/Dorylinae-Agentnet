## Adversarial questions: result

| Question | Result |
|---|---|
| Is anything peer-controlled put into AppleScript source (macOS)? | **No.** The three `-e` lines are constants. Title and body go after `--` as `argv` items 1 and 2. Because of the `--`, a title such as `-e do shell script "…"` cannot be read as an option by osascript's getopt. The text is at most about 250 code points, far below any argv limit. `desktop_darwin_test.go` asserts the fixed script and argv. It has not been run on a Mac: the manual check in `tests/phase1-manual.md` covers that. |
| Is the gdbus GVariant escaping complete (Linux)? | **Yes.** GLib's string tokenizer ends a quoted literal only at an unescaped matching quote. Inside it, `\` starts an escape (`\\`, `\'`, `\"`, `\n`…, `\uXXXX`, `\UXXXXXXXX`). Everything else is literal. Every `\` and `'` is escaped, so the only escapes in the output are ours, and each decodes to the original character. So a unicode escape typed by a peer (backslash, `u`, four hex digits) gets its backslash doubled, and decodes back to the same literal text, not to the escaped character. `@s`, `@as`, `b'…'`, `[`, `%` and `"` are special only outside a literal, and every argument starts with `'`. NUL and newlines never get here: `Clean` has already replaced them, and Go's exec rejects NUL in argv anyway. Invalid UTF-8 cannot occur, because the text comes from JSON-decoded Go strings. Length is bounded by `Clean` (80 and 40 code points), plus at most 5× markup growth. New round-trip cases: `@as ['x']`, `b'bytes'`, short and long unicode escapes, `\x41`, `%s`, a lone `\`, a lone `'` and the empty string. |
| notify-send fallback | **M1 (fixed).** Argv only, with `--` before the text, and the body is markup-escaped. However, notify-send passes its body through `g_strcompress`, which runs *after* our escaping. So `\074a href='…'\076click\074/a\076` became live `<a href>` markup. |
| Markup escaping of the body | `&`, `<` and `>` are escaped for both gdbus and notify-send, as the spec requires. The summary (title) is plain text by the freedesktop spec and is not escaped. That is correct. |
| Windows: a fixed script, fixed env var names, no `-Command` string building? | **Yes.** The script is a Go constant, and the only concatenation is the constant AUMID. The env var names are constants, and the values are base64 (UTF-16LE), so they cannot inject `=` or anything else. `SecurityElement.Escape` covers `< > & " '`. `-f` interprets `{0}` only in the constant format string, not in the substituted values. This was verified end-to-end on this Windows 11 machine with the real `powershell.exe` and Go's argv quoting: the title ``t'"<x>&{0}$(calc)` `` and the body `]]></text> \` produced well-formed toast XML with the text escaped, and nothing was evaluated. |
| Privacy | Holds. The desktop shows the title, peer name, type and urgency, and only the result `status`, which is a validated enum (`result.go`). The summary, exit code, output, artifacts, brief and reasons never reach `Event`. The team name is not used. |
| Peer flooding → notification storm, or process and goroutine DoS | **M2 (fixed).** `Fire` started one goroutine per event, with no bound. Each goroutine exec'd a notifier with a 3 s timeout. A peer that could send requests at the relay's rate could therefore run hundreds of `powershell.exe`/`gdbus` processes at once. |
| Exec timeouts | 3 s per `Show` (`context.WithTimeout`), plus `WaitDelay` of 200 ms so orphaned pipes cannot hang `Wait`. The Linux fallback shares the same 3 s budget. |
| No notification for an early cancel or a tombstoned request | Correct. `afterCancel` fires only on `result == "cancelled"`, and `after` skips `out.cancelled`, duplicates and auto-declines. An ignored mirror (`seq` not higher) fires nothing (`out.applied`). |
| 5 s latency | Met for a single event. `Fire` returns at once, and the show starts immediately when idle. With the M2 fix, a burst is shown one at a time, so the Nth event waits for the N−1 before it. |
| Settings persistence | `notify.events` and `notify.desktop` are upserted in `settings`. Unknown stored keys are ignored, and defaults apply to missing events. Covered by `settings_test.go`. |

## Medium (fixed)

**M1 — notify-send decodes backslash escapes after markup escaping.**
`internal/notify/desktop_linux.go`: the notify-send body is now passed through
`notifySendBody`, which doubles every `\` so that `g_strcompress` restores it literally.
Test: `TestShowDesktopLinuxNotifySendBodySurvivesStrcompress` (it emulates `g_strcompress`,
and it fails without the fix).

**M2 — unbounded goroutine and process fan-out per event.**
`internal/notify/trigger.go`: `Fire` now counts accepted events (`queued`, at most
`maxQueued = 16`) and serialises `Show` behind `showMu`. So there is at most one notifier
process, and at most 16 held goroutines. Excess events are dropped with a warning
(`event=notify_desktop_drop`), logged at most once a minute. Test: `TestTriggerFireBoundsFlood`
fires 1000 events and asserts at most one concurrent `Show` and at most 16 calls.

## Low (not fixed)

- **L1 — no daemon-level e2e.** The ticket asks for "a fake `Desktop`, the call arrives
  within 5 s of the receiver commit (e2e)". There are trigger-level tests (`TestTriggerFireShowsWithin5s`)
  and request-hook tests, but none of them goes through `notifyAdapter`, the peer-name lookup
  and the real receiver. There are also no IPC or CLI tests for `notify_get`, `notify_set` and
  `notify_test`.
- **L2 — `notifyAdapter` runs `peers.Store.List` synchronously in the `After` hook** for every
  event, which is a full scan on the receiver goroutine. A lookup by key, or doing it inside
  the trigger goroutine, would keep the receiver path O(1).
- **L3 — Windows: XML-invalid non-control characters.** U+FFFE and U+FFFF, and other
  non-characters, pass `Clean`, so `LoadXml` throws and that notification fails (it is logged
  and audited). This cannot inject anything. The only effect is that one notification is lost.
- **L4 — gdbus without introspection.** If the notification server does not answer
  introspection, gdbus parses `0` and `5000` as `int32`, the call fails, and notify-send runs.
  That is two spawns per notification. `@u 0` and `@i 5000` would remove the dependency on
  introspection.
- **L5 — `notify_set` is not atomic.** `desktop` is written before `events` are validated, so
  `{"desktop": false, "events": {"bogus": true}}` returns `bad_request` but has already
  turned the desktop off. Validate every event first, or use one transaction.
- **L6 — settings read errors are silent.** `fire` returns without a log line when
  `EventEnabled` or `GetDesktopEnabled` fails.
- **L7 — burst drops are not audited.** A legitimate burst larger than 16 (for example, an
  outbox flush after a long time offline) loses the excess notifications, with only a log
  line. This is acceptable for a best-effort channel, but it should be mentioned in notify.md
  §Desktop.
